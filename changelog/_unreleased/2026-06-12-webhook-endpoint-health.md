# Core
* Added a per-webhook four-state circuit breaker (`healthy` → `degraded` → `suspended` → `disabled`) on the internal `webhook_health` table, replacing the shared `error_count` propagation and the permanent `active = 0` disable. Gated behind `WEBHOOKS_REWORK`; flag-off behaviour is unchanged.
* Added transient/non-transient error classification: transient failures (network, DNS, timeout, TLS, `404`, `408`, `429`, `5xx`, unfollowed `3xx`) degrade an endpoint after repeated failures; `401`/`403` suspend after a streak of three with no success in between; `410` suspends immediately; `400`-class payload errors never affect endpoint health.
* Added automatic recovery through one half-open ladder (cooldowns 5 m → 4 h): a degraded or suspended endpoint gets one trial delivery per cooldown, each `2xx` climbs one state toward healthy. A suspended endpoint retires to `disabled` after `shopware.webhook.health.max_suspended_days` (default 7); an app install/update resets the app's webhooks to healthy.
* Added backlog handling: already-queued deliveries are held (`paused`) while an endpoint is degraded or suspended and resume on recovery; held deliveries older than 24 hours are cancelled with their `webhook_event_log` rows kept replayable (`failure_reason`). New events for a suspended endpoint are not recorded — apps reconcile that window by time via `suspendedSince` on the state API.
* Added lifecycle business events (`webhook.health.activated` / `webhook.health.degraded` / `webhook.health.suspended` / `webhook.health.disabled`) — Flow-Builder-consumable and delivered to the owning app as ordinary app webhooks — plus Admin notifications on suspension (one per suspension episode), on disable, and a recovery notice.
* Added the app-facing health API: `GET /api/app-system/webhook/state` and `POST /api/app-system/webhook/reactivate` (rate-limited 10/min per integration, max 50 names; refuses operator-disabled webhooks), and the admin surface `GET /api/_action/webhook/health-status` and `POST /api/_action/webhook/{id}/deactivate` (the operator kill-switch, usable in any state).
* Changed the semantics of `webhook.active` under the flag: from v6.8.0 `active = true` means dispatch is *eligible* — a degraded webhook reports `active = true` while delivery is briefly paused. Read `endpointState` on the health API for real-time status. Admin writes carry intent only when they flip the value: writing the value a webhook already has is a no-op for the health state machine, and automation using the legacy `active` toggle inherits the kill-switch semantics.
* Note on rollback: disabling `WEBHOOKS_REWORK` is an execution-path switch, not a state-restoring rollback — behaviour is byte-for-byte identical to trunk only if the flag was never enabled. Run `bin/console webhook:drain-to-async` after disabling the flag to re-publish held and queued deliveries onto the legacy path.
