00 / VERDICT

Is the facade proposal good? Yes — it is the right architecture. It is not yet the right product.

Solution A wins on architecture; Solution B wins on adoption-day experience. Ship A's skeleton with B's compatibility tier grafted on.

Solution A (generated local facade) gets the two hardest constraints right, and it is the only one of the two that even attempts them: the repository root does not exist in a Composer/Flex install (so the contract must ship inside the Administration package), and a build that transpiles without type-checking is not a gate (so a separate vue-tsc + baseline check is required). Its zero-config default, symlink-free projection, and tested multi-topology story are genuinely better engineering than anything in Solution B.

But A has one strategic flaw and a cluster of operational ones. The strategic flaw: its curated type surface is so far from what real plugins use that the same evidence it presents as success — 19,357 baselined diagnostics across SwagPayPal, SwagCommercial and SwagLanguagePack — is better read as a failed compatibility test. Baselines silence the CLI, not the editor: the day this ships, every developer of an existing plugin opens an IDE full of red squiggles that the check command has quietly agreed to ignore. Solution B proved the alternative: typed against the live installed sources, SwagPayPal converts with zero new TypeScript errors.

Solution B is the wrong end-state. It makes the entire Administration internals public API ("./*": "./*" exports, src/* path mapping, global.types.ts as the types entry), requires per-plugin package.json + postinstall + two configs (so it is not zero-config), has a real module: CommonJS misconfiguration, and ships no semantic gate and no migration mechanism at all — the type-aware lint findings it newly surfaces on Commercial have nowhere to land.

The better solution (§06) keeps A's committed-contract / generated-projection / baseline architecture and adds three things, two of them from B: an explicit, deprecated-from-birth compatibility type tier (live-source types, opt-in) so existing plugins are green in the IDE on day one; a conformance guardrail (compile-time assertion binding the curated declaration to the real Shopware object, plus B's fixture-plugin CI job); and the host-provided-modules decision executed as one source of truth. Plus fixes for A's operational findings (facade pruning, entity-schema bootstrap, merged root program, baseline churn, sequential checks).

A−Solution A as architecture — right constraints, right mechanisms, real tests
C+Solution A as shippable product today — the 19k-diagnostic cliff is unresolved
B−Solution B — excellent pragmatic patch, structurally wrong as an end-state

01 / CANDIDATES

What is actually being compared

Both artifacts answer issue #14040 (“TypeScript and ESLint should work naturally for Administration plugins”), and both reject the issue's original sketch of a repository-root monorepo — for the same correct reason. They diverge on everything after that.

Solution A

Generated local facade

Where: issue-14040-tooling-architecture-research.html + uncommitted PoC in this working tree (extension-tooling/, scripts/extensionTooling/, composer wiring).

Idea: the Administration package commits a curated public type declaration, a strict TS/SFC preset, an ESLint flat-config factory and setup/check commands. A setup step reads var/plugins.json and generates a disposable project projection: a private facade package (node_modules/@shopware-ag/administration-extension-tooling, proxy files — no symlinks), root tsconfig.json / eslint.config.mjs for IDE discovery, and per-extension check projects. Existing debt is fenced by exact, committed per-extension baselines; a vue-tsc-based check command becomes the semantic gate. Default plugins need zero tooling files.

Solution B

Admin package contract

Where: branch temporary-test-branch-new-admin-package-contract (commit abcb46850a4) + issue-14040-proposal.md on that branch.

Idea: rename the admin app to @shopware-ag/administration and make it a real, self-describing package: a types entry aggregating the live source graph (global.types.ts + entity schema + shims), a shared tsconfig.plugin.json with a host-provided-modules paths list, and an ESLint preset whose flat-config objects carry the patched Twig parser along. Each plugin gets one generated relative symlink in its node_modules (healed by a per-plugin postinstall resolver + bulk step in bin/install-extension-npm) and two tiny config files. A fixture plugin in CI guards the contract.

Shared ground (both correct): the root-workspace idea from the issue is rejected because the monorepo root is not a release boundary (split.bash ships src/Administration alone) and because dynamically adopting third-party plugins into one npm workspace changes lock ownership, lifecycle-script trust and npm ci reproducibility. Both solutions resolve Shopware by package name instead of relative path ladders, and both exploit the same key ESLint property: flat config passes parsers/plugins as objects, so the patched Twig stack never needs to be installable by plugins.

02 / REVIEW — SOLUTION A

The facade proposal: strong skeleton, five real gaps

The research document itself is excellent — evidence-first, honest about limitations, and it labels facts vs. inferences. The review below is of the solution, based on the document plus the actual PoC source in this tree.

What it gets right

  • Right constraint The contract ships inside the Administration subtree, so vendor/shopware/administration receives it. This is the single most important architectural fact in the whole problem space, and A is built around it. Three topologies (checkout, Composer vendor, Flex) are explicitly designed for and fixture-tested; the Flex recipe is treated as part of the feature, not an afterthought.
  • Zero-config is real A plugin with only src/main.ts + an SFC + a Twig template gets IDE discovery and CLI checks with no package.json, no tsconfig, no ESLint config. Solution B cannot do this at all.
  • The missing gate exists vue-tsc --noEmit per project plus ESLint with v10 file-relative config lookup (check.ts:405 correctly feature-flags ESLint 9). The fixture proves the gate catches a deliberately injected TS2322 that Vite happily builds — the exact defect behind SwagCommercial #2734.
  • No symlinks The facade is proxy files (re-export shims + extends hops), so Windows junctions, Docker bind-mount realpath drift, and tsserver duplicate-path identity issues are avoided by construction. This quietly retires the riskiest mechanism in Solution B.
  • Correct compiler policy extension-tooling/tsconfig.json uses module: ESNext / moduleResolution: Bundler — the truthful model of the Vite runtime. (B ships CommonJS; see finding B2.)
  • User-owned files are respected writeManagedFile() (setup.ts:233) only overwrites files carrying the generated marker; existing root configs are preserved with a warning.
  • Real engineering hygiene Multi-bundle owner walking to the nearest composer.json, macOS /var → /private/var canonicalization in check.ts:36, stale-baseline reporting, and three Jest suites including a full Flex-style end-to-end fixture. The Storefront build is verified untouched.

Findings

A1 · Strategic Baselines silence the CLI — not the IDE. The 19,357 baselined diagnostics are a compatibility failure being reported as a migration feature.

The curated public-api.d.ts types most of the Shopware namespaces as Record<string, unknown> stubs (Mixin, Filter, Utils, Store, State, ApiService, …). Against that surface, SwagPayPal produces 6,062 diagnostics and SwagCommercial 13,272 — dominated by TS2339 (“property does not exist”) and unsafe-any lint findings, i.e. precisely the gap between the curated contract and what plugins demonstrably use. The baseline makes the check command pass, but tsserver and the ESLint IDE plugin know nothing about baselines: every existing plugin developer gets thousands of red markers on day one, with no way to fix them (the missing types are Shopware's to add, not theirs). Under Solution B, the same SwagPayPal conversion produced zero new TypeScript errors, because live sources are the types.

extension-tooling/public-api.d.ts:100–143 · research doc §09 “Real extension corpus”

Fix: add an opt-in, deprecated-from-birth compatibility tier that types against the live source graph (exactly what B's types/index.d.ts does), so existing plugins are IDE-green immediately while the curated surface is grown using the baseline counts as the prioritization signal. Strict curated stays the default for new plugins. Details in §06.

A2 · Contract integrity Nothing binds public-api.d.ts to the runtime. The curated declaration can silently drift from what window.Shopware actually is.

The declaration is hand-written and structurally independent from src/core/shopware.ts. A rename or signature change in the real object leaves the contract stale with no failing check anywhere. The roadmap mentions “API declaration snapshots” but snapshots only prevent accidental expansion, not drift from the implementation. Related: the public Criteria is borrowed from @shopware-ag/meteor-admin-sdk (public-api.d.ts:10) rather than the class plugins actually receive at runtime — a second, independent drift axis.

extension-tooling/public-api.d.ts · no conformance test exists in scripts/extensionTooling/*.spec.ts

Fix: one line inside the admin's own (full-graph) type-check: const _contract: ShopwareExtensionApi = Shopware; in a dedicated conformance spec. Every internal refactor that breaks the public contract then fails the admin's own CI, at the PR that caused it. Add B's fixture-plugin CI job for the end-to-end variant (setup → check → build on a scaffold-identical plugin).

A3 · Resolution The host-provided-modules list is missing: only vue is typed. Real plugins import pinia, vue-router, vue-i18n, axios.

extension-tooling/tsconfig.json:22 maps only vue and @vue/* into the admin's node_modules. The 423 unresolved modules in the Commercial baseline are largely this gap. Solution B made the deliberate product decision A still defers: enumerate which packages the host platform commits to providing to plugins (types now, runtime externalization where applicable) — and B's list (vue, @vue/runtime-core, vue-router, vue-i18n, pinia, vuex, axios, @vue/test-utils) is the right starting candidate set because it was derived from what real plugins rely on.

extension-tooling/tsconfig.json:22–25 vs. branch tsconfig.plugin.json paths block

Fix: adopt B's curated list, but keep it in one machine-readable source of truth in the Administration (JSON), consumed by (a) the generated tsconfig paths, (b) the Vite externals/aliases in build/plugins.vite.ts, and (c) documentation — so the type-level and runtime-level contracts cannot diverge.

A4 · Operations Any plain npm install at the project root deletes the facade; healing is tied to the wrong lifecycle.

The bridge package lives in the project root's node_modules (setup.ts:249). npm prunes packages it does not know from the tree it manages — and a Flex project may well have its own root package.json for unrelated tooling. Solution A regenerates only via composer scripts (build:js:admin, watch:admin, init:js); between an npm operation and the next composer run, root configs and every plugin-owned extends of the package name resolve to nothing. Solution B healed at exactly the lifecycle point that causes the breakage (npm postinstall) — architecturally uglier, operationally smarter.

scripts/extensionTooling/setup.ts:248–327

Fix: make the generated root configs reference the contract by relative path into var/admin-extension-tooling/ (npm never touches var/), and keep the node_modules facade only as the stable specifier for plugin-owned configs — recreated by setup, by check (already implicit), and by a bulk step in bin/install-extension-npm (B's belt-and-braces move, minus the symlinks).

A5 · Bootstrap A fresh checkout hard-fails with TS2307 in every plugin program, and init:js now requires a working backend.

extension-tooling/types.d.ts:10 unconditionally imports ../src/entity-schema-definition, which is gitignored (administration/.gitignore:18). Setup only warns when it is missing (setup.ts:396), but the missing import is a hard error inside every generated program — the zero-config first-run experience is a cryptic module-not-found, not the warning. Separately, wiring @admin:generate-entity-schema-types into init:js (composer.json) makes plain JS bootstrap depend on framework:schema:dump, i.e. on a bootable kernel/DB — a regression for JS-only CI jobs and first-time contributors.

extension-tooling/types.d.ts:10 · setup.ts:383–398 · composer.json init:js block

Fix: commit a core-only fallback schema declaration (or have setup emit a stub with a @generated marker when the real one is absent) so programs always compile; keep a --strict-schema mode for CI where plugin entities must be present. Drop the schema step from init:js; keep it in build/watch where a backend exists.

A6 · Correctness The IDE checks a different program than the CLI: one merged root tsconfig vs. per-extension check projects.

createRootTsconfig() (setup.ts:329) merges all zero-config extensions into a single include — one TS program. Global augmentations are the intended plugin extension mechanism (CustomShopwareServices, CustomShopwareProperties), so in the merged IDE program plugin A's augmentations leak into plugin B's checking, while the CLI checks each extension in an isolated program (setup.ts:189). Result: the editor and the gate can legitimately disagree in both directions.

scripts/extensionTooling/setup.ts:329–354 vs. 189–231

Fix: generate the root tsconfig as a solution-style file with references to the same per-extension configs the checker uses (vue-tsc and tsserver both support references). One program topology, two consumers.

A7 · Migration mechanics Exact line/column fingerprints make the baseline a churn machine at this scale.

The fingerprint is tool|file|line|column|code|message (check.ts:64). Commercial's baseline would hold ~13k entries — a megabytes-large JSON committed into the plugin repo, invalidated in bulk by any edit that shifts lines above a diagnostic. Every unrelated refactor produces new-plus-stale pairs; teams will learn to run --update-baseline all reflexively, which quietly converts the “no new debt” guarantee into “whatever the last update said”. The research doc names this risk; it underprices it at this entry count.

scripts/extensionTooling/check.ts:64–73, 280–302

Fix: fingerprint on file|code|hash(normalized source line) with a per-file+code count as the coarse fallback (the suppression-file model TypeScript/Dart/Betterer use). Line moves stop churning; genuinely new occurrences still fail. Keep exact mode as an option for small baselines.

A8 · Performance Sequential spawnSync per extension, no incremental state.

runTypeScript() (check.ts:345) runs one cold vue-tsc process per project, serially, and ESLint re-lints everything every time. Fine for the PoC; painful for an agency project with fifteen plugins in a watch loop.

Fix: parallelize project checks (they are independent), write tsBuildInfo/ESLint caches under var/admin-extension-tooling/cache/, and offer a changed-extensions-only mode for local runs.

A9 · IDE hazard The generated root ESLint config force-enables the Twig-as-Vue parser project-wide.

createRootEslintConfig() hardcodes legacyTwig: true and the preset matches **/*.html.twig globally. The CLI only ever lints extension source paths, but the IDE ESLint plugin discovers the root config for any open file — including Storefront's genuine (non-Vue) Twig templates under src/Storefront/Resources/views/, which the Vue parser will report as fatal parse errors. In a source checkout this is a daily-annoyance bug.

setup.ts:356–369 · extension-tooling/eslint.mjs:149

Fix: scope the generated root config's Twig (and ideally all) file patterns to the discovered extension source paths, which setup already knows from the manifest.

A10 · API detail tsconfigRootDir defaults to process.cwd().

shopwareAdminExtension() (eslint.mjs:32) makes typed-lint behavior depend on the invocation directory when a consumer omits the option. The generated root config passes it correctly; a hand-written plugin config that forgets it gets confusing project-service errors.

Fix: require it (throw with a helpful message) or derive it from the config file location convention documented for plugins.

A11 · Scope of rules The factory exposes fewer building blocks than B's preset.

B re-exports swCoreRules and swTestRules alongside the deprecation/plugin rules so complex suites can compose the exact admin rule set; A exports only pluginVue, swDeprecationRules, swPluginRules, tseslint (eslint.mjs:156). Commercial will want the rest.

A12 · Cost of ownership ~1,000 lines of new generator/checker code is a product, and it overlaps three open PRs.

setup + check + manifest + baselines constitute a permanent tooling surface with its own bug classes (several are listed above). The research doc correctly flags coordination with #17578 (config-to-TS migration touching the same ESLint files), #18070 (native setup templates) and #16805 (Volar/SFC) — this needs an explicit owner and landing order before the code lands, or the repo grows a third parallel bridge.

03 / REVIEW — SOLUTION B

The package contract: the best patch you shouldn't make permanent

B's proposal document frames the problem perfectly — “the defect is how plugins address the admin, not where configs live” — and its PoC evidence (SwagPayPal and Commercial converted with parity) is strong. Its problem is what it makes permanent along the way.

What it gets right — and what must survive into any final solution

  • Keep Adoption-day parity. Typing against live installed sources means converted plugins keep exactly the diagnostics they had. SwagPayPal: 43 hack-lines → 2-line config, semantically identical output, equal check time. That is what “out of the box” feels like to an existing plugin team, and A currently has nothing comparable.
  • Keep The fixture-plugin CI guardrail. A scaffold-identical plugin consumed adversarially in CI (link → tsc → eslint → build → jest) turns “types happen to work for plugins” into a tested platform feature. A's roadmap has fixtures for its own machinery but no consumer-shaped contract job.
  • Keep The host-provided-modules curation. Replacing the plugins' wildcard node_modules mapping with a deliberate list of what the host provides is the type-level twin of the runtime externals list — a real API decision B makes and A defers (finding A3).
  • Keep Healing at the breaking lifecycle. The postinstall resolver heals on the exact operation that causes breakage (finding A4 shows A misses this), and the relative-link insight (“relative paths survive Docker bind mounts”) was learned the hard way and documented.
  • Good Defusing the squatted administration npm name (SwagPayPal's optionalDependency silently resolving to a stranger's package) — a genuine supply-chain fix both solutions inherit; deleting the bogus dependency is the actual cure.

Findings

B1 · Boundary Everything reachable becomes public API — by construction, in three redundant ways.

The exports map ends with "./*": "./*" (every internal file importable by specifier), the shared tsconfig maps src/* into the admin source, and types/index.d.ts aggregates global.types.ts — a ~621-line file importing ~131 internal symbols. B's own downsides list admits it (“everything reachable is implicitly API”) and defers the curated surface as “an optimization to earn”. But this is not an optimization question: it is the difference between Shopware being able to refactor its admin internals and not. The contradiction is visible inside the branch itself: the ESLint preset ships plugin-rules/no-src-imports: error while the tsconfig deliberately makes those same imports type-resolve.

branch: package.json exports block · tsconfig.plugin.json paths.src · types/index.d.ts

B2 · Misconfiguration tsconfig.plugin.json sets module: CommonJS with no moduleResolution.

Plugin admin code is ESM bundled by Vite. CommonJS + implied node10 resolution cannot see exports-map-only packages, forbids import.meta and top-level await, and generally models a runtime that does not exist here. A's preset (ESNext/Bundler) is the correct one; this alone would surface as mysterious plugin-side errors the moment a modern dependency is used.

branch: src/Administration/Resources/app/administration/tsconfig.plugin.json:7

B3 · DX ceiling Not zero-config — and the plugins that need help most get none.

Every plugin needs a package.json (for the postinstall hook), the committed resolver script, and two config files. That is a fine deal for SwagPayPal; it does nothing for the SwagLanguagePack class of plugin — TS and Twig files, zero tooling — which simply stays dark unless someone hand-adds four files. A's plugins.json-driven discovery covers those plugins with literally no action from their authors.

B4 · No gate, no landing zone New findings surface with nowhere to go.

B ships no check command, no baseline, no CI story beyond the fixture. Its own validation shows the consequence: type-aware linting “ran for the first time ever” on Commercial and immediately produced hundreds of findings (and thousands of TS errors in the end-to-end run). Without a migration mechanism the predictable outcome is what happened last time: teams disable the rules again. A's baseline machinery is precisely the missing piece.

B5 · Mechanism fragility Whole-package symlinks carry known failure modes.

Pruned by npm in --ignore-scripts flows; Windows junction behavior untested (their own downside #10); and one subtle one the branch does not mention: tsserver sees admin files through two paths (real and linked), which is a classic source of duplicate-identity/“two copies of the same type” diagnostics in mixed plugin+core editing sessions. A's proxy-file projection avoids the whole class.

B6 · Product identity The scoped rename creates a package that looks published but never is.

@shopware-ag/administration in every plugin's config strongly implies an npm artifact; its absence from the registry will generate support noise and invites someone to “helpfully” publish it. The rename also churns the package-lock and any tooling matching the old name. A keeps a facade-only name that is explicitly private: true and never leaves the machine — the better shape.

B7 · Phantom dependencies The symlinked package exposes the admin's entire node_modules for deep imports, and "./*" blesses it.

B8 · Topology coverage The resolver probes three fixed layouts and exits silently otherwise.

Composer path-repositories, non-standard vendor dirs and multi-project monorepos fall through without a message; A's manifest-driven discovery both finds more shapes and reports what it found.

B9 · Twig rules The legacy-twig subpath keeps Vue's indentation and structure rules on virtualized Twig.

A's PoC learned these produce false positives on processor-virtualized templates and disables the specific unreliable rules (legacy-twig.mjs:34–42 in this tree); B applies flat/recommended wholesale to **/*.html.twig.

B10 · Schema staleness Entity types are only as fresh as the checked-in schema; plugin-defined entities are explicitly out of scope (their downside #8) — where A wires the backend dump into the lifecycle and covers plugin entities.

05 / ANALYSIS

The real tension: the two solutions answer different questions

Strip the mechanisms away and the disagreement is about one variable: what are the types?

B answers the addressing question

“Plugins already type-check fine against live admin sources — only the path to them is broken. Fix the addressing (a name instead of seven ../), keep the types as they are.” Consequence: perfect continuity, zero boundary. Shopware can never again refactor internals without breaking someone's type-check, and the no-src-imports rule polices a door the tsconfig holds open.

A answers the contract question

“What plugins may rely on must be a curated, versioned surface — the global Shopware object and the entity schema — and everything else must fail to resolve.” Consequence: a real boundary Shopware can maintain, but measured against reality it is off by 19,357 diagnostics, and the baseline mechanism only hides that from CI, not from humans in editors.

The uncomfortable truth both documents avoid saying plainly: the ecosystem's de-facto API today is the internal source graph. A boundary you declare but that rejects the entire existing ecosystem on day one is not a boundary — it's a fork. A boundary you never declare is not an architecture — it's an accident. The only path that is both adoptable and ownable is to ship both surfaces at once, with an explicit gradient between them: live-graph typing as a deprecated compatibility tier, curated typing as the default and the destination, and the baseline counts as the public measure of every plugin's distance from the destination.

Sunset story: Tier 1 ships with a target major version for removal in its deprecation notice. Every check run prints per-extension tier + baseline size — the number every team watches shrink.

Sequencing (delta to A's roadmap)
