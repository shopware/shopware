Concept proposal · Shopware issue #14040 · 10 July 2026

Config Injection.
The boring solution.

Plugins don't locate Shopware. Shopware configures plugins — by writing two tiny, readable, gitignored config files next to their code, the same way it already writes var/plugins.json and builds assets into their folders. No npm package. No symlink. No facade. No baseline database. Nothing to heal, because nothing can break.

2 concepts to teach ~350 lines of new code 0 files in node_modules 0 committed machine paths Every mechanism already validated by the A/B PoCs

01 / WHY THE OTHER TWO ARE COMPLICATED

Both solutions inherit their complexity from one unexamined premise

Solution A (generated facade) and Solution B (package contract + symlink) look different, but they are the same solution to the same sub-problem — and that sub-problem is self-inflicted.

PPremise: a plugin's tsconfig.json and eslint.config.mjs are source code — written by humans, committed to git.
⇒1A committed file must work in every layout (checkout, vendor, Flex) — so it cannot contain a real path.
⇒2So it needs a stable name that resolves everywhere: @shopware-ag/administration….
⇒3Stable names resolve through node_modules — so something must materialize there: B's symlink, A's facade package.
⇒4node_modules belongs to npm, and npm prunes what it doesn't own — so both need healing machinery: B's postinstall resolver, A's composer-lifecycle regeneration.
⇒5Now there is invisible machine state, so you need manifests, markers, ownership rules — and you are explaining facades and symlink lifecycles to plugin developers.

✂ Cut the premise, and the entire chain disappears.

Tooling config for a Shopware plugin is not source code. It contains zero decisions in the default case — every value in it is derived from facts the platform already knows: where the admin app is installed, where the plugin is, which entities exist. Files whose content is fully derived from the environment have a name: machine state. Shopware already generates machine state for plugins without anyone finding it strange:

Generated artifactWritten byWritten whereAnyone confused?

The path problem, stated honestly: the ugly ../../../../../../src/Administration/… path can never be eliminated — it is a fact of the filesystem. You can only choose who maintains it: a human in committed code (the status quo, and the bug), an npm resolution mechanism plus its healing machinery (Solutions A and B), or the machine that already knows it (this proposal). The generator writes the path; nobody else ever touches it.

02 / THE IDEA

Two inversions, and everything else follows

① Tooling config is machine state, not source code. Shopware generates it — gitignored, regenerated on every build and watch, human-readable when you open it.

② The stable path a plugin may commit against is not a global npm name. It is a folder inside the plugin itself: ./.shopware-admin/. Relative, identical in every layout, by definition.

Inversion ① removes the need for stable names, and with them npm, symlinks, facades and healing. Inversion ② restores everything the stable name was for: a plugin that wants to commit its own customized config extends ./.shopware-admin/tsconfig.json — a relative path that is correct in a platform checkout, in a Flex project, in Docker, on Windows, always — because the generator materializes that folder wherever the plugin is. The indirection through the global namespace was never necessary; the plugin's own directory is a perfectly good namespace.

var/the mental model developers already have — generated, disposable, never committed
./the only “resolution algorithm” left in the design: a relative path
catthe debugging tool. Every file in the chain is plain text you can open and read

03 / THE CONCEPT, COMPLETE

Three committed files, one generator, one wrapper — that is the whole system

What Shopware commits (in the Administration app — so it ships in every layout, including vendor/)

tsconfig.extension.json

The static TypeScript preset: ES2023, moduleResolution: bundler, strict, noEmit. Its paths map the host-provided modules (vue, pinia, vue-router, …) and its typeRoots pull in the Shopware global + entity-schema types — all relative to itself, i.e. to the installed admin. A plain, reviewable JSON file. The whole “what is our API surface” debate lives inside this one file and can evolve without touching the mechanism.

eslint.extension.config.mjs

The static ESLint flat-config preset: JS/TS/Vue rules, type-aware linting via projectService (each file finds its nearest generated tsconfig), the Shopware rules, and the legacy-Twig processor. Because flat config carries parsers and plugins as objects, everything — including the patched Twig parser — resolves from the admin's own node_modules and travels with the import. (This is the one genuinely clever trick in the whole design, and both previous PoCs already proved it.)

The generator (~200 lines)

Reads var/plugins.json — the discovery mechanism the build already trusts — and writes the files below into each extension's admin folder. Runs automatically inside composer build:js:admin, watch:admin and the Flex build/watch recipes; also callable directly. Idempotent, marker-aware, skips anything a human owns.

What the generator writes (gitignored machine state)

custom/plugins/SwagExample/src/Resources/app/administration/ ├── src/ ← the only thing the developer writes │ ├── main.ts │ └── sw-example.vue ├── .shopware-admin/ ← generated; self-gitignoring; delete any time │ ├── .gitignore contains “*” — the folder ignores itself, no repo config needed │ ├── tsconfig.json 1 line: extends → installed admin (the ONE machine path) │ ├── eslint.config.mjs 1 line: re-export ← installed admin │ └── README.md explains itself: what, why, how to regenerate ├── tsconfig.json ← generated only if absent; yours the moment you edit it └── eslint.config.mjs ← same rule

These files are small enough to show in full — which is the point:

// .shopware-admin/tsconfig.json  — generated. The single machine-written path in the system.
{ "extends": "../../../../../../../vendor/shopware/administration/Resources/app/administration/tsconfig.extension.json" }

// .shopware-admin/eslint.config.mjs — generated.
export { default } from '../../../../../../../vendor/shopware/administration/Resources/app/administration/eslint.extension.config.mjs';

// tsconfig.json — generated once, becomes yours when you edit it.
// @generated by Shopware · regenerated by build/watch · commit to take ownership
{
    "extends": "./.shopware-admin/tsconfig.json",
    "include": ["src/**/*"]
}

// eslint.config.mjs — generated once, becomes yours when you edit it.
export { default } from './.shopware-admin/eslint.config.mjs';

A customizing plugin deletes the marker and commits the file — still with zero machine paths, because it only ever references ./.shopware-admin/: 

// tsconfig.json — committed by the plugin. Layout-independent forever.
{
    "extends": "./.shopware-admin/tsconfig.json",
    "include": ["src/**/*"],
    "compilerOptions": { "paths": { "SwagExample/*": ["./src/*"] } }
}

// eslint.config.mjs — committed by the plugin.
import shopware from './.shopware-admin/eslint.config.mjs';
export default [
    ...shopware,
    { rules: { 'no-console': 'error' } },
];

The check wrapper (~80 lines, optional)

composer admin:check-extensions loops the discovered extensions and runs the admin's own vue-tsc --noEmit -p <tsconfig> and eslint --config <config> <src>. No output parsing, no diagnostic normalization, no baseline database — the output is the tools' own output, which every JS developer already knows how to read. It exits non-zero when the tools do. For IDE users the generator also writes a solution-style tsconfig.json (project references — so editor and CLI check identical per-plugin programs) and a path-scoped eslint.config.mjs at the project root, both gitignored: open the project root in VS Code or PhpStorm and everything just works.

That is the entire architecture. Two static preset files (the contract), one generator (the distribution), one wrapper (the gate). No new package names, no node_modules writes, no symlinks, no manifest, no baseline format, no custom diagnostic parser, no healing logic — because there is no state that npm, Windows, Docker or a deleted node_modules can corrupt.

04 / DAY IN THE LIFE

What it feels like in each situation

New plugin, zero knowledge

You scaffold a plugin, run composer watch:admin (which you run anyway), open the folder. IntelliSense for Shopware.*, entity types, Vue — everything works. You never created a config file, and if you look, the two that exist are four lines long and say at the top who wrote them and why.

Production / Flex project

Identical, because the presets live inside vendor/shopware/administration and the recipe's build/watch scripts call the same generator right after they generate entity-schema types today. The repository root of the monorepo is never needed — the constraint that killed the issue's original idea is satisfied by construction.

Existing plugin with hacks (SwagPayPal)

Delete the seven-level paths, keep two files that extend ./.shopware-admin/. Because the preset types against the same live sources the hacks already used, the diff in diagnostics is ~zero — the IDE looks the same as yesterday, minus the fragility.

Update Shopware

git pull or composer update, then the build/watch you were going to run anyway. The generator refreshes machine paths if anything moved; the types are the installed sources, so they are current by definition. There is no version of this story where a stale artifact lies to you.

CI for a plugin repo

The job already installs Shopware to run PHPUnit. Add two lines: composer admin:setup-extension-tooling (or just the build) and composer admin:check-extensions. Type errors fail the build with plain tsc/eslint output.

Something looks broken

Open .shopware-admin/tsconfig.json. It is one line containing one path. Does the path exist? No? Run the build; it regenerates. Yes? Then your problem is an ordinary TypeScript problem with an ordinary TypeScript error message. Debugging never involves inspecting symlinks, npm trees, or facade proxies.

Honest remaining limitations

  • Generated files inside plugin folders will be visible in the developer's git status once, until they notice .shopware-admin/ ignores itself and the two seed configs carry an explanatory header. The build already writes Resources/public/ into plugins; this is the same social contract, and it is the entire price of the simplification.
  • The seed configs are generated only if absent — a plugin that already commits configs keeps them untouched (the generator prints how to adopt: extend ./.shopware-admin/). Migration of the first-party plugins is a deliberate, per-repo two-file diff.
  • TypeScript behavior relied upon: relative extends chains, and paths/typeRoots resolving relative to the config file that declares them (TS ≥ 5.0). Both previous PoCs already lean on exactly this; a five-line fixture test in the admin locks it against TS upgrades.
  • The API-surface question is not solved here — it is contained. Whether the types are the live source graph (adoption-friendly) or a curated public surface (boundary-friendly) is a one-file policy decision inside tsconfig.extension.json, changeable per major version, orthogonal to the mechanism. This concept refuses to entangle distribution with that debate — which is precisely what made A heavy (curated surface ⇒ 19k diagnostics ⇒ baseline machinery) and B leaky (live graph ⇒ everything is API ⇒ forever).

07 / MIGRATION WITHOUT A BASELINE DATABASE

A severity dial instead of 19,357 fingerprints

Solution A needed a baseline system because its strict curated surface instantly condemned every existing plugin. This concept starts from parity and migrates by turning a dial, not by managing a database.

  1. Types: start at parity. The preset types against the live installed sources (what every existing hack already does), so existing plugins keep the diagnostics they had — in the IDE too, which is where baselines fundamentally cannot help. New strictness arrives as an opt-in second preset (tsconfig.extension.strict.json) that new plugins get seeded with by default.
  2. Lint: new rule classes enter as warn. Type-aware “unsafe” rules — the ones that produced thousands of findings on Commercial — ship as warnings for one minor release, then flip to errors preset-side. Teams that want them early set one line in their committed config. Severity levels are a concept ESLint users already own; nobody has to learn a fingerprint lifecycle.
  3. The boundary ratchets, visibly. plugin-rules/no-src-imports stays error from day one: typing against internals is tolerated, importing them is not. Each release, the curated portion of the type surface grows (informed by what real plugins use) and the live-graph portion shrinks — inside one reviewable JSON/d.ts file, with normal code review instead of migration tooling.

10 / CONSIDERED AND REJECTED

Paths not taken, and why

Rejected Root monorepo workspace (the issue's sketch)

The root doesn't exist in vendor installs; dynamic third-party workspaces change lock ownership and lifecycle-script trust. Both prior analyses killed this correctly; nothing new to add.

Rejected Published npm dev-kit (@shopware-ag/admin-extension-kit)

The most conventional answer in the wider ecosystem, and worth naming honestly: it fails the product constraint that trunk and unreleased plugin work must type-check today, and it decouples types from the installed platform. It also makes the hardest problem (curated surface) a prerequisite instead of an evolution. Registry publishing remains the right answer later for the standalone shopware-cli build story — as a consumer of the same preset files, not as the primary mechanism.

Rejected Anything in node_modules (facade or symlink)

Placing state in a directory owned by another tool is the root cause of both solutions' healing machinery. The plugin's own folder is the only location npm, Composer and IDEs all agree to leave alone.

Rejected Doing nothing / docs-only

The folklore hacks are the status quo's answer and they are committed machine paths — the exact bug class. SwagCommercial #2734 proves invalid TypeScript ships today through green checks.

11 / ROLLOUT

Three small PRs and a recipe change

  1. PR 1 — the contract files + generator (shopware/shopware, Administration subtree). tsconfig.extension.json, eslint.extension.config.mjs, the generator script, composer wiring into build/watch, the TS-behavior fixture test, and the entity-schema stub fallback. Reuses the discovery/ownership logic and the Twig-rule learnings already written for Solution A's PoC — most of this PR is deleting the facade/manifest/baseline layers from that code.
  2. PR 2 — the gate + fixture plugin. admin:check-extensions wrapper and a scaffold-identical fixture plugin checked in CI (generate → typecheck → lint → build). The fixture is Solution B's best idea and costs one CI job.
  3. PR 3 — recipes + scaffolding + docs (shopware/recipes, docs). Generator call in the Flex build/watch scripts; plugin:create seeds only src/main.ts (the configs arrive generated); one documentation page whose entire mechanism section fits on one screen — that page's brevity is the acceptance test for this concept.

Success criteria

  • A developer who has read nothing runs composer watch:admin, opens a plugin, and has working IntelliSense — and can explain why after reading the two generated files.
  • SwagPayPal's conversion diff is ≤ 10 lines and produces zero new diagnostics in the IDE.
  • Deleting node_modules anywhere, running any npm command anywhere, or switching OS changes nothing about tooling behavior.
  • The docs page for plugin TypeScript setup contains no diagram — because none is needed.

The best contract is the one you can read. Two preset files, one generator, one folder — and the only path in the system is written by the machine that already knows it.
