Issue #14040 · The minimal version · 14 July 2026

Types you already have. Paths you never write.

You have a Shopware checkout whose Administration source is fully typed. You have a plugin. The missing link — where those types live on this machine — is computed for you: the dev setup generates a bridge package inside node_modules, and the plugin’s tsconfig and ESLint config become two static lines that never change.

No paths by hand · no publish step · no profiles
Pieces: config inside the Admin + generated bridge Types: the real installed Shopware source Plugin side: two static lines — or zero
What changed from the earlier walkthrough

Still the minimal design — full window.Shopware types, the generated entity schema, open interfaces to extend — but the last piece of manual labor is gone. The previous version asked the plugin developer to write a .d.ts with absolute reference paths by hand. Now a setup step detects the paths programmatically and generates a bridge package inside node_modules, so "extends": "@shopware-ag/administration-extension-tooling/tsconfig" simply resolves. The plugin never contains a machine-specific path.

00 · The idea

Two things you have. The setup connects them.

The Administration source already declares the entire window.Shopware object and the generated entity schema — and it ships a shared config right next to them. Your plugin just has to see it. A setup step that runs with the normal dev workflow bridges that config into node_modules, so a bare extends / import specifier resolves from any extension. That is the whole design.

01 · Ships with Shopware

A shared config that lives next to the types.

The Administration ships an extension-tooling/ folder: a tsconfig base, an ESLint flat-config factory, and a types entry — sitting right next to the source they describe. Because it is versioned with the platform, rules and types can never drift from the Shopware you actually run. Nothing is published; there is no second version number to keep in sync.

extension-tooling/package.jsonships with the Admin
{
  "name": "@shopware-ag/administration-extension-tooling",
  "private": true,
  "type": "module",
  "types": "./types.d.ts",
  "exports": {
    ".":          { "types": "./types.d.ts" },
    "./eslint":   "./eslint.mjs",
    "./tsconfig": "./tsconfig.json"
  }
}
extension-tooling/tsconfig.jsonbase preset
{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "target": "ES2023",
    "strict": true,
    "noEmit": true,
    // the installed source graph is not YOUR
    // code to fix — do not check its .d.ts
    "skipLibCheck": true,
    // injects window.Shopware + the entity schema

extension-tooling/eslint.mjsflat config factory
import eslintJs from '@eslint/js';
import tseslint from 'typescript-eslint';
import pluginVue from 'eslint-plugin-vue';
import swDeprecationRules
  from '../eslint-rules/deprecation-rules/index.js';

export function shopwareAdminExtension(options = {}) {
  return [
    eslintJs.configs.recommended,
    ...tseslint.configs.recommendedTypeChecked,
    ...pluginVue.configs['flat/recommended'],
    {
      plugins: { 'sw-deprecation-rules': swDeprecationRules },
      rules: {
        // draws the supported-API line
        'sw-deprecation-rules/no-deprecated-admin-api': 'error',
      },
    },
    ...(options.overrides ?? []),
  ];
}
extension-tooling/types.d.tsthe types entry
// The whole “point at the types” problem, solved by location:
// this file LIVES next to the source, so relative paths always hold.
import './public-api';                    // window.Shopware
import '../src/entity-schema-definition'; // generated entity schema
Entities come for free

The types entry pulls in the generated entity schema, so Entity<'product'> and friends resolve in every extension. The core declares Entity<Name extends keyof EntitySchema.Entities>, so an unknown name is a compile error until you augment the schema — see section 03.

The lint dependencies are not yours either

The factory’s imports — typescript-eslint, eslint-plugin-vue, the Shopware rule packages — resolve from the installed Administration’s own node_modules, because Node resolves imports relative to the file doing the importing. A default extension needs no package.json at all.

The supported-API boundary lives here, not in the types

Because the plugin sees the full Shopware source, every member is typed — including internals. The line between “supported” and “internal” is drawn by the ESLint sw-deprecation-rules/no-deprecated-admin-api rule against @deprecated / @internal markers. You keep full autocomplete; touching an unsupported member is a visible lint error rather than a silent unknown.

02 · Connect

No paths by hand: a generated bridge in node_modules.

Machine-specific paths still exist — the plugin’s TypeScript has to reach the installed Administration somehow. The point is that no human writes them. The platform knows where it lives and where every extension lives (var/plugins.json), so the setup computes the paths once and materializes them as a tiny generated package inside the project’s node_modules. The plugin’s own files stay static and committable.

tsconfig.jsonplugin · committable
{
  "extends":
    "@shopware-ag/administration-extension-tooling/tsconfig",
  "include": ["src/**/*.ts", "src/**/*.vue"]
}
eslint.config.mjsplugin · committable
import { shopwareAdminExtension }
  from '@shopware-ag/administration-extension-tooling/eslint';

export default shopwareAdminExtension();
node_modules/@shopware-ag/administration-extension-tooling/generated — never committed
// package.json — same name and exports as the real package
{ "name": "@shopware-ag/administration-extension-tooling", "exports": { … } }

// tsconfig.json — one computed hop to the real config
{ "extends": "../../../src/Administration/…/administration/extension-tooling/tsconfig.json" }

// eslint.mjs — re-export of the real factory
export * from '../../../src/Administration/…/administration/extension-tooling/eslint.mjs';
export { default } from '../../../src/Administration/…/administration/extension-tooling/eslint.mjs';

// types.d.ts — pulls the real types entry
import '../../../src/Administration/…/administration/extension-tooling/types';

// composer run admin:extension-tooling:setup — or hooked into build/watch
const extensions = discoverExtensions(readJson('var/plugins.json')); // nothing to detect plugin-side
createBridgePackage(projectRoot, administrationRoot);                // computes + writes the relative paths
writeManagedRootConfigs(extensions);                                 // zero-config coverage — see below
Why a bare specifier just resolves

TypeScript and ESLint resolve @shopware-ag/administration-extension-tooling/… with plain Node resolution: walk up from the plugin directory until a node_modules contains the package. The project root’s does — an installed extension always lives inside the project. From there the bridge’s relative paths land in the installed Administration, whose own relative imports (../src/entity-schema-definition) resolve next to the real source. No paths mapping in the plugin, no preserveSymlinks flags, no magic.

Symlink or generated files? Both work

A symlink into node_modules — the npm-link move — gives the same DX. Generated proxy files win on robustness: no symlink privileges on Windows, .. inside them means what it looks like (inside a symlinked directory it escapes to the symlink’s parent, not the real one), and the setup is idempotent — wipe node_modules, rerun, it’s back.

Zero-config is the default

An extension with no tsconfig.json or eslint.config.mjs at all is covered by managed root configs the same setup writes at the project root. The two static lines above are the opt-in for plugins that want their own local config — and they never contain more than what you see here.

03 · Extend

Add your own services, entities, and namespaces.

The core exposes CustomShopwareServices, CustomShopwareProperties, and EntitySchema.Entities as open interfaces and namespaces. A plugin merges into them from one .d.ts in src/ — no wrapper, no registration API, just TypeScript declaration merging.

src/global.d.tsyour plugin
import type MyBonusService from './service/my-bonus.service';

declare global {
  // 1 · type your own services → Shopware.Service('…') knows them
  interface CustomShopwareServices {
    swagBonusService: MyBonusService;
  }

  // 2 · add a custom top-level namespace onto the Shopware object
  interface CustomShopwareProperties {
    swagBonus: { readonly version: string };
  }
}

// 3 · add your DAL entities to the schema (namespace + interface MERGE)
declare namespace EntitySchema {
  interface Entities {
    swag_bonus_point: { id: string; points: number; customerId: string };
  }
}

export {};
anywhere in the pluginusage
const svc = Shopware.Service('swagBonusService');   // MyBonusService — fully typed
Shopware.swagBonus.version;                         // string — your custom namespace
Shopware.Component.register('swag-bonus-card', {}); // host API — real, installed types

const rec = repository.get<Entity<'swag_bonus_point'>>('swag_bonus_point', id);
rec.points;                                         // number — your own entity
Why declaration merging is the whole trick

Because tsconfig.json includes the plugin’s own src/**/*.ts (which covers .d.ts files) alongside the Shopware source injected through the bridge, the compiler sees the host’s declarations and the plugin’s augmentations in one program. Merging is symmetric and order-independent — the host provides the base interfaces, the plugin extends them, neither has to know about the other. It is the same mechanism the core already uses for EntitySchema.Entities and CustomShopwareProperties today.

04 · Lifecycle

What actually happens.

Four steps, and none of them is magic once the reference exists.

1

The dev setup generates the bridge

composer run admin:extension-tooling:setup — or the same step hooked into build/watch — reads var/plugins.json and writes the bridge into node_modules. Nothing to detect or configure plugin-side.

2

Opt in with two static lines — or none

Zero-config extensions are covered by the managed root configs. A plugin that wants local control commits the two-line tsconfig.json and eslint.config.mjs from section 02. Neither ever contains a path.

3

Everything reads the same tsconfig

The IDE (Volar), vue-tsc, and eslint all see the full window.Shopware plus your augmentations — identically. No IDE-versus-CLI drift.

4

Switch the Shopware version

git checkout in the Shopware repo, rerun the setup: the bridge is regenerated and config, rules, and types match the platform again. Wiped node_modules? Same answer — the setup is idempotent.

05 · Honesty

What we dropped — and the one trade-off.

The simplicity is real, and so is its cost. Here is exactly what is gone, what stays, and the single downside you are accepting.

Gone
  • Hand-written reference paths (.shopware/shopware-types.d.ts)
  • A published config package that can drift from the platform
  • Public / internal profiles
  • manifest.json
  • connect / ensure-contract CLI
  • The contract producer & self-contained rollup
  • Released snapshots
Kept
  • A shared config (tsconfig + ESLint) — now shipped inside the Administration
  • The irreducible bit: machine-specific paths — computed by the setup, living only in node_modules
  • Three augmentation seams
  • Zero-config coverage for extensions without their own configs
The trade-off you are accepting

Referencing .ts source (not a bundled .d.ts) means TypeScript parses — and, being source, can type-check — Admin’s graph under your config. That is heavier than checking against one declaration file, and it needs the Admin source to be present. Mitigations: skipLibCheck is on; reference the narrowest entry files; and Admin source is CI-clean, so it should not introduce new errors under the same strict + skipLibCheck settings it already uses.

If that cost ever bites, flip the referenced entry to a generated .d.ts barrel — identical wiring, and skipLibCheck then applies to it fully. That is an optimization, not a redesign — V2 below shows exactly what it looks like.

The one case this does not cover

A standalone plugin checkout with no Shopware project around it has nothing to bridge to. That is exactly the artifact V2 produces: publish the generated declarations per release, and a standalone checkout pins a version instead of bridging to an installation.

06 · The evolution

V2: generated declarations instead of source.

V1 points the plugin at the Administration’s .ts source — always fresh, zero build steps, but the plugin’s tooling parses (and type-checks) Admin’s graph. V2 changes exactly one thing: a build step emits .d.ts files, and the types entry points at those instead. The bridge, the plugin’s two-line configs, and the three augmentation seams stay byte-identical — declaration merging works against emitted .d.ts exactly as against source. That is why V2 is an optimization you can defer, not a fork in the road.

tsconfig.types.jsonadmin build
// package.json: "types:build": "vue-tsc -p tsconfig.types.json"
// runs where the entity schema generation already runs
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "noEmit": false,
    "declaration": true,
    "emitDeclarationOnly": true,
    // @internal members drop out of the contract
    "stripInternal": true,
    "outDir": "extension-tooling/dist"
  },
  "files": ["src/global.types.ts"]
}
extension-tooling/types.d.tsthe only change
// V1 — reads the installed source (live, heavy)
import './public-api';
import '../src/entity-schema-definition';

// V2 — reads the generated declarations (flat, light)
import './dist/global.types';
import './dist/entity-schema-definition';

// Everything downstream — bridge, plugin configs,
// augmentations — does not change by one byte.
Dimension V1 · reads source V2 · reads declarations
Freshness Live with every git checkout As fresh as the last types:build
Build step None Declaration emit — must be CI-gated
Plugin’s program The Admin source graph A flat .d.ts set
skipLibCheck Skips .d.ts, still checks the .ts source it pulls in Covers everything Shopware ships
Standalone plugin Not possible — needs the installation The same dist/ can be published per release
Internal APIs Visible; fenced by the ESLint rule Can physically disappear via stripInternal
What V2 buys

The plugin’s tsserver and vue-tsc load a flat declaration set instead of Admin’s source — cold start and memory shrink accordingly. Admin’s compiler settings stop mattering to the plugin entirely. And the standalone gap from section 05 closes: publish dist/ as @shopware-ag/administration-types@<version>, and a checkout without a Shopware project pins a version — while the bridge still wins whenever a real installation is present.

What V2 costs

The declarations are a maintained artifact. Declaration emit can fail on code tsc cannot name (private types in public positions), so the build must be CI-gated. Against a trunk checkout the types go stale until the next types:build — the same lifecycle the generated entity schema already has. And when you hack on Admin and a plugin simultaneously, V1’s live view is nicer.

A middle step already exists

The current tooling already avoids the worst of V1’s cost without any build step: its types entry is a hand-maintained, dependency-light structural contract (public-api.d.ts) that deliberately imports no Administration implementation types — precisely so extensions do not compile the whole Admin graph. V2 is that same idea with the manual curation automated: the contract becomes an emitted artifact instead of a hand-written one, so it can never lag behind the real source.
