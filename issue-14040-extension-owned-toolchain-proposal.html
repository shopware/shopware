01 · Executive answer

Yes—there is a simpler solution.

The earlier proposals are complicated because they preserve one constraint that is more expensive than it first appears: the tooling contract must not be published as an npm package. Remove that constraint and most of the architecture disappears.

The recommendation

Turn the existing private @shopware-ag/administration-extension-tooling prototype into a real, self-contained, types-only npm package. Every extension installs it locally, extends its TypeScript preset, imports its ESLint preset, and runs the standard tools.

This is not another compatibility layer around the host tree. It changes the boundary: the extension owns its development environment, while Shopware publishes the versioned contract it promises to extensions.

02 · Root cause

The previous ideas solve the wrong boundary.

The actual goal is predictable editing and checking of extension code. “Move configuration to the Shopware root” and “make the installed Administration look like an npm package” were implementation hypotheses—not product requirements.

Proposal A · Root projector

Make one host project understand every extension

  • Discover active bundles from the running kernel.
  • Generate root TypeScript and ESLint state.
  • Copy a facade into root node_modules.
  • Suppress pre-existing diagnostics with a baseline.
  • Reconcile aggregate IDE behavior with isolated CLI checks.
Proposal B · Installed facade

Make extensions borrow the host package

  • Rename the Administration npm package.
  • Expose types, presets, source paths, and a runtime target.
  • Link it into every plugin’s node_modules.
  • Repair links after npm changes the dependency tree.
  • Branch for source, Composer, Flex, and plugin layouts.
Shared failure pattern

Both designs make extension correctness depend on where Shopware happens to be installed. That creates the topology matrix: source checkout versus Composer split, active versus inactive plugin, root versus nested package, symlink versus copied vendor tree, Linux versus Windows, and one bundle versus many.

Hidden state

What developers must remember today

Generated configs, active-plugin discovery, facade repair, root baselines, the difference between IDE and CLI programs, and whether the current installation contains source files.

Explicit state

What developers remember with C

The extension has a package dependency and two conventional config files. The lockfile states exactly which contract and tool versions are in use.

Why “zero config” is the trap

TypeScript and ESLint already have project discovery conventions. Removing the local files does not remove configuration; it moves configuration into generators, discovery heuristics, lifecycle hooks, and filesystem links. The developer sees fewer files but the system acquires more states.

Two tiny, checked-in files are not accidental complexity. They are the visible boundary that tells the IDE, command line, code review, and CI which project is being checked.

No proprietary configuration language

Adoption paths

New extension

The plugin skeleton includes all three files and the compatible package range. The developer runs npm ci.

Existing npm extension

Legacy extension without npm

Create the normal package files once. A migration helper may scaffold them, but it is optional and never runs during install.

05 · Package design

Make the current private package real—and intentionally narrow.

The current work already contains a private package with the right name, a dependency-light public API, a TypeScript preset, an ESLint preset, and Twig support. The new architecture packages those actual files instead of creating re-export facades that point back into an installed Shopware tree.

Ship
  • Curated Shopware global declarations.
  • Versioned core entity declarations.
  • HTML and asset module shims.
  • module: ESNext and moduleResolution: Bundler preset.
  • ESLint flat config for JS, TS, Vue, and legacy Twig.
  • Shopware deprecation and forbidden-internal-import rules.
  • Only the tool dependencies needed by those presets.
Do not ship
  • The full global.types.ts import graph.
  • Administration implementation source.
  • A default runtime export.
  • Wildcard package exports such as ./*.
  • Host-relative paths mappings.
  • Node ambient types not needed by an extension.
  • Install, postinstall, or Composer lifecycle mutation.

Types-only root by construction

The package root exposes only a TypeScript types condition. Application code that tries to import the package at runtime receives a package-export error. Config files import only the explicit /eslint subpath. This is a much safer boundary than making the full Administration package importable.

Dependency policy

One install command

npm 10 installs required peers by default. The extension lists one direct dev dependency; npm keeps host tools such as ESLint and TypeScript at a compatible project level.

No phantom imports

Every plugin, parser, rule package, and processor used by the shareable config is declared. The release fixture uses an isolated install strategy to catch undeclared dependencies.

No runtime contamination

The package contains development tools and declarations only. The Administration build continues to decide which runtime dependencies are externalized or bundled.

Public type contract

Keep the current curated, structural approach, but remove its dependency on the installed source tree. A small internal ShopwareExtensionApi model should be compiled both into the Administration and into the package declarations. An internal conformance test then verifies that the runtime object still satisfies the promised contract.

Use unknown for intentionally unmodelled areas. Never import private implementation types merely to make a declaration more precise; that recreates the full-graph problem from proposal B.

06 · Entity types

Two layers, plus a safe fallback.

Entity typing is where both earlier designs acquire hidden failure modes. The package should make the base case useful without a running Shopware installation, and make plugin-specific precision an explicit enhancement.

Layer 1 · Core
The tooling release contains the generated core Shopware entity schema for its supported minor line. Core entities such as product, order, and customer are precise immediately after npm ci.
Layer 2 · Plugin
A plugin that adds DAL definitions or associations may commit .shopware/entity-schema.generated.d.ts. It augments the package interfaces and is produced only by an explicit command in a clean fixture shop.
Fallback · Unknown
If no plugin schema exists, an unknown entity resolves to UnknownEntity—a stateful record with unknown values. It never collapses to any, and known core entities remain precise.
Conceptual safe fallback
interface UnknownEntity extends ShopwareEntityState {
  [property: string]: unknown;
}

type Entity<Name extends string> =
  Name extends keyof EntitySchema.Entities
    ? EntitySchema.Entities[Name] & ShopwareEntityState
    : UnknownEntity;
Default experience

No live shop required

Core types, public APIs, Vue files, Twig linting, and normal CI work in a standalone plugin checkout. A missing custom schema cannot break module resolution.

Optional precision

One explicit backend command

A future bin/console administration:dump-extension-types AcmePlugin command writes the plugin augmentation. A --check mode verifies that the committed result is current without modifying files.

Clean-fixture rule

Generate plugin schema types in a test shop containing Shopware plus the plugin under test. Otherwise, fields from unrelated active plugins could leak into the committed declaration. The generator should record the tooling version and input hash, and CI should use --check.

Why this is safer than importing the installed generated schema

The current private prototype imports ../src/entity-schema-definition. If that declaration is absent and consumers use skipLibCheck, TypeScript can allow the missing graph to degrade generic entity types to any. A check may look green while useful safety has disappeared.

The package design always includes a base declaration, tests its tarball with library checking enabled, and models unknown plugin entities explicitly. Absence therefore has defined behavior.

07 · Head-to-head comparison

The third option removes concepts instead of relocating them.

Proposal C does accept one operational cost: Shopware must publish and maintain an npm package. That cost is bounded, automatable, and already familiar. In return, the per-install topology and repair machinery disappears.

Large extension suites

Repeated installs are a performance concern, not a correctness concern. A suite may opt into an ordinary npm workspace to hoist shared tools. That optimization stays local to the suite and does not change the contract of an individual extension.

Why no central baseline is intentional

A baseline turns existing errors into durable architecture: it needs fingerprints, path normalization, update rules, merge behavior, and decisions about new versus moved diagnostics. It also hides the actual quality state from developers.

Proposal C migrates per extension. New extensions are clean from day one. Existing extensions adopt the package when they can pass, or use a short-lived migration branch owned by that extension. Shopware does not pretend that thousands of errors are a successful global check.

09 · Versioning and release

Make compatibility explicit in the dependency range.

The package version follows the Shopware product minor. Tooling patch releases remain independent of Shopware’s fourth version segment.

Stable line

~6.7.0

Targets Shopware 6.7. The tilde permits tooling fixes in 6.7.x but never moves the extension to 6.8 behavior.

Next line

@next

Immutable prereleases validate the next Shopware minor and allow trunk fixtures without filesystem links.

Exact install

package-lock.json

CI installs the exact tested tree with npm ci; a changed range cannot silently rewrite the lockfile.

Release pipeline

1
Generate

Build the curated declarations and core entity schema for the target minor.

2
Pack

Run npm pack and reject parent paths, local file: dependencies, or unexpected files.

3
Prove

Install only the tarball in clean Linux and Windows fixtures; run IDE-equivalent TS and ESLint checks.

4
Publish

Use npm provenance, immutable versions, stable/next tags, and an automated compatibility changelog.

Publishing is not a new capability

Shopware already publishes generated entity declarations as @shopware-ag/entity-schema-types and Administration lint rules as @shopware-ag/admin-eslint-rules. Proposal C consolidates the extension-facing pieces behind one supported entry point.

Release rules

  • Never publish directly from source references; consumers are tested against the packed tarball.
  • No lifecycle scripts in the consumer package. Initialization and schema generation are explicit commands only.
  • A declaration tightening that rejects valid extension code is developer-facing and must follow Shopware release documentation policy.
  • Run contract fixtures against the oldest and newest supported Shopware patch in the minor line.
  • Keep previous minor lines available; changing a dist-tag never changes a locked extension build.

Prove one vertical slice, then delete the magic.

Do not merge another broad framework integration first. Prove that the package tarball works for a real extension in all supported layouts, then make the scaffold the default.

Migration scope

This report proposes the architecture, not an immediate flag-day conversion. Existing plugins continue to build. Tooling adoption is per extension, while new scaffolds use the package from the start. A behavior/workflow change of this size requires developer-facing release and upgrade documentation.

Storefront coordination

Keep Storefront untouched in the first release. If Storefront later wants the same model, publish a separate @shopware-ag/storefront-extension-tooling package with its own runtime assumptions and lint processors. A multi-surface plugin may use an explicit npm workspace, but Administration and Storefront must not share one ambient TypeScript or ESLint project.

Residual risks worth accepting

Registry availability

Mitigate with lockfiles, npm cache, mirrors, provenance, and immutable versions. This is standard dependency risk.

Install weight

Set a size/time budget, publish no runtime libraries, and compare against the many packages plugins install today.

Contract maintenance

Make ownership explicit, snapshot the public surface, and treat type breakage as developer-facing release work.

12 · Final decision

This is the solution I would build.

Adopt the extension-owned toolchain.

Publish @shopware-ag/administration-extension-tooling as a narrow, types-only development contract. Let each extension own a normal npm project. Keep Administration implementation code private, keep Storefront separate, and make plugin-specific entity precision optional and explicit.

Stop investing in the root projector and the linked Administration facade after the package tarball pilot proves the acceptance gates. Reuse their good assets—the curated types, lint config, Twig processor, entity converter, and tests—but discard their topology machinery.

One extension. One dependency. One local project. The IDE and CI read the same files.
The surprising part

Publishing one small package looks like adding infrastructure, but it removes an entire category of runtime architecture. Release automation is a bounded problem Shopware solves once. Filesystem discovery and repair are unbounded problems every installation would otherwise solve differently.
