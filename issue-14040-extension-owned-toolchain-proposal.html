01 · Executive answer

Yes—there is a simpler solution.

The key is to stop treating tool implementation and the version-dependent Shopware API contract as one artifact. Publish the stable tools once, but read services, entities, and globals from the exact Shopware installation being developed and tested.

The recommendation

Turn the existing private @shopware-ag/administration-extension-tooling prototype into a real, self-contained tooling package. Every extension installs it locally, extends its TypeScript preset, imports its ESLint preset, and keeps one normal TypeScript project.

The package does not freeze Shopware’s services and entity types. A tiny ignored locator connects the project to public.d.ts or internal.d.ts from the current Shopware checkout. The released snapshot is only a standalone fallback.

02 · Root cause

The previous ideas solve the wrong boundary.

The actual goal is predictable editing and checking of extension code. “Move configuration to the Shopware root” and “make the installed Administration look like an npm package” were implementation hypotheses—not product requirements.

Proposal A · Root projector

Make one host project understand every extension

  • Discover active bundles from the running kernel.
  • Generate root TypeScript and ESLint state.
  • Copy a facade into root node_modules.
  • Suppress pre-existing diagnostics with a baseline.
  • Reconcile aggregate IDE behavior with isolated CLI checks.
Proposal B · Installed facade

Make extensions borrow the host package

  • Rename the Administration npm package.
  • Expose types, presets, source paths, and a runtime target.
  • Link it into every plugin’s node_modules.
  • Repair links after npm changes the dependency tree.
  • Branch for source, Composer, Flex, and plugin layouts.
Shared failure pattern in A and B

Both designs mix tool distribution, project discovery, public types, private Administration types, and installation topology. Exact local types are valuable; making the entire toolchain depend on guessed filesystem topology is not.

Hidden state

What developers must remember today

Generated configs, active-plugin discovery, facade repair, root baselines, the difference between IDE and CLI programs, and whether the current installation contains source files.

Explicit state

What developers remember with C2

The extension has one stable tool dependency, two conventional config files, and a connection to its current Shopware. The lockfile identifies tools; the contract manifest identifies Shopware.

Why “zero config” is the trap

TypeScript and ESLint already have project discovery conventions. Removing the local files does not remove configuration; it moves configuration into generators, discovery heuristics, lifecycle hooks, and filesystem links. The developer sees fewer files but the system acquires more states.

Two tiny, checked-in files are not accidental complexity. They are the visible boundary that tells the IDE, command line, code review, and CI which project is being checked.

One additional ignored locator is the minimal environment-specific state. TypeScript requires a concrete file dependency; without a locator, package link, generated config, or custom language server it cannot dynamically select an unrelated Composer checkout.

No proprietary configuration language

A developer can run vue-tsc or eslint directly, inspect the effective configuration, add a local rule override, or replace the scripts. The package supplies mechanics; the connected Shopware supplies types.

05 · Package design

The package is a stable engine, not a frozen Shopware API.

Publish the mechanics that change slowly and keep release-specific services and entities out of the package’s default type graph. This is what prevents every Shopware release—or every local version switch—from becoming an extension dependency update.

Ship
  • TypeScript and Vue project presets.
  • module: ESNext and moduleResolution: Bundler preset.
  • ESLint flat config for JS, TS, Vue, and legacy Twig.
  • Shopware deprecation and forbidden-internal-import rules.
  • connect and ensure-contract commands.
  • Contract manifest validation and standalone snapshot cache.
  • Stable HTML and asset module shims.
  • Only the tool dependencies needed by those presets.
Do not ship
  • A Shopware-minor service or entity map loaded by default.
  • The full global.types.ts import graph.
  • Administration implementation source.
  • A default runtime export.
  • Wildcard package exports such as ./*.
  • Host-relative paths mappings.
  • Node ambient types not needed by an extension.
  • Lifecycle scripts that mutate consumer configuration.

No application runtime export

The root contains only stable tooling declarations. Application code that tries to import it at runtime receives a package-export error. Version-specific Shopware types arrive through the connected declaration file, not through an import that can leak into the application bundle.

Dependency policy

One install command

The extension lists one broad stable tooling range such as ^1.0.0. Shopware 6.7, 6.8, and trunk do not require changing that range merely because their service contracts differ.

No phantom imports

Every plugin, parser, rule package, and processor used by the shareable config is declared. The release fixture uses an isolated install strategy to catch undeclared dependencies.

No runtime contamination

The package contains development tools and declarations only. The Administration build continues to decide which runtime dependencies are externalized or bundled.

A small contract protocol

The tooling package only needs to understand a versioned manifest and three declaration entry points. It validates the contract format, chooses a profile, and writes the locator. It does not contain a table mapping Shopware product versions to npm package versions.

A future incompatible declaration-file layout increments format in the manifest. That rare protocol change may require a tooling update; ordinary service additions, removals, and Shopware releases do not.

06 · Live Shopware contract

The exact Shopware installation is the type authority.

Administration owns a deterministic compact-contract generator and commits its result at a stable path. CI rejects a stale generated diff; Composer Administration artifacts ship those same verified files. A Shopware-aware setup command obtains the real bundle path, so the extension never guesses src/, vendor/, or a plugin directory convention.

Administration package — stable contract location
Resources/app/administration/extension-contract/
├── manifest.json
├── public.d.ts
├── internal.d.ts

A declaration rollup, not a doorway into Admin source

All entry points must be self-contained or import only files inside extension-contract/. The artifact audit rejects parent paths and implementation-source imports. This preserves exact types without recreating proposal B’s full Administration graph.

Extension-local generated locator — .shopware/admin-contract.d.ts
/* Connected Shopware: 6.8.0-dev @ abc123 · profile: public */
/// <reference path="/absolute/shopware/.../public.d.ts" />
/// <reference path="/absolute/shopware/.../entity-schema.d.ts" />
Selection rule: the connected Shopware always wins

In a source checkout, Composer project, Commercial downstream job, or local plugin development shop, failure to find the connected contract is an error. These modes must never silently fall back to a released snapshot, because that would hide exactly the trunk additions and removals the contract is meant to reveal.

Public profile

Third-party extensions

References public.d.ts and the entity schema. It contains supported extension APIs only. Private services do not become an accidental compatibility promise.

Internal profile

Commercial and first-party code

Adds internal.d.ts. Downstream CI connects it to the exact upstream Shopware commit, so private service additions and removals are checked in the same change window.

The three critical workflows

Change Contract selected Result
A new service lands on trunk and Commercial starts using it internal.d.ts from that exact trunk checkout The type exists immediately—no npm publication and no dependency bump
A private service is removed while Commercial still uses it The same PR’s exact contract, where the service is absent The Commercial downstream typecheck fails before merge
A plugin developer switches the local Shopware version The contract bundled with the newly selected installation Linting and typechecking follow it without editing package.json

Automatic connection lifecycle

Setup

bin/install-extension-npm or the Flex development setup invokes shopware-admin connect --shopware <resolved-bundle-path> once.

Daily use

The locator’s filename is stable. When Shopware changes in place, its referenced declaration contents change automatically; there is normally nothing to regenerate.

Recovery

shopware-admin ensure-contract validates the manifest and path. A Shopware wrapper can pass a new resolved path and rewrite it; a direct call with no host information fails with the exact reconnect command.

The declaration producer needs a conformance gate

Administration must derive service keys from a typed registration map—or test the generated declarations against the runtime registry—in the same CI job. A hand-maintained internal.d.ts would simply move drift to a new file and would not reliably catch service removal.

A service-changing PR runs the generator and commits the result. Core CI runs --check before Commercial connects to that exact tree, and the Composer build packages the already-verified directory. A branch switch therefore changes the declarations through Git itself—there is no local release or dependency step.

What about a standalone plugin checkout with no Shopware nearby?

That is the one mode where an explicit released snapshot is legitimate. The resolver downloads or reuses a cached contract for a declared target such as 6.7, without changing the extension dependency or lockfile. A version range is tested as a CI matrix of concrete contracts; a single snapshot must never pretend to prove a range.

As soon as the extension is connected to a real Shopware installation, the live contract replaces the snapshot. The mode is recorded in the locator header and manifest, so CI cannot accidentally claim an exact-host check while using cached release types.

07 · Entity types

Two layers, plus a safe fallback.

Entity typing follows the same authority rule as services. The selected live contract supplies the exact core schema; plugin-owned declarations add precision without merging unrelated plugins into one global program.

Layer 1 · Core
The connected Shopware contract contains the generated entity schema for that exact installation. A standalone checkout uses the schema from its explicitly selected release snapshot. The tooling package owns neither copy.
Layer 2 · Plugin
A plugin that adds DAL definitions or associations may commit .shopware/entity-schema.generated.d.ts. It augments the package interfaces and is produced only by an explicit command in a clean fixture shop.
Fallback · Unknown
If no plugin schema exists, an unknown entity resolves to UnknownEntity—a stateful record with unknown values. It never collapses to any, and known core entities remain precise.
Conceptual safe fallback
interface UnknownEntity extends ShopwareEntityState {
  [property: string]: unknown;
}

type Entity<Name extends string> =
  Name extends keyof EntitySchema.Entities
    ? EntitySchema.Entities[Name] & ShopwareEntityState
    : UnknownEntity;
Connected experience

The current host is authoritative

Core types, services, Vue files, and Twig linting follow the locally installed Shopware. Switching the Shopware checkout or Composer constraint changes the effective types without changing npm dependencies.

Optional precision

One explicit backend command

A future bin/console administration:dump-extension-types AcmePlugin command writes the plugin augmentation. A --check mode verifies that the committed result is current without modifying files.

Clean-fixture rule

Generate plugin schema types in a test shop containing Shopware plus the plugin under test. Otherwise, fields from unrelated active plugins could leak into the committed declaration. The generator should record the selected contract hash and input hash, and CI should use --check.

Why this is safer than an optional source import

The current private prototype imports ../src/entity-schema-definition. If that declaration is absent and consumers use skipLibCheck, TypeScript can allow the missing graph to degrade generic entity types to any. A check may look green while useful safety has disappeared.

The selected contract always includes a base declaration, and ensure-contract fails when it is absent. Standalone snapshots are content-checked before use. Unknown plugin entities remain explicit UnknownEntity values rather than silently degrading to any.

What disappears entirely

Discovery

Kernel activity, bundle locations, custom plugin conventions, and one-versus-many-bundle heuristics.

Repair

Symlink recreation, facade copying, generated root config freshness, package-version pairing, and lockfile churn.

Suppression

Root-scale baselines, diagnostic fingerprints, aggregate cross-plugin declarations, and debt snapshots.

What intentionally remains

The locator is not disguised as zero configuration. TypeScript needs a static path before it can build a program, so one small ignored declaration records the current environment. Its behavior is inspectable, its validation is deterministic, and deleting it has one repair command. That is the irreducible state—not an architecture framework.

Large extension suites

A suite may use an ordinary npm workspace to hoist the stable tools and may reuse one resolved contract location. Each extension remains a separate TypeScript project and receives its own profile/locator, preventing ambient declarations from leaking between plugins.

Why no central baseline is intentional

A baseline turns existing errors into durable architecture: it needs fingerprints, path normalization, update rules, merge behavior, and decisions about new versus moved diagnostics. It also hides the actual quality state from developers.

Proposal C2 migrates per extension. New extensions are clean from day one. Existing extensions adopt the package when they can pass, or use a short-lived migration branch owned by that extension. Shopware does not pretend that thousands of errors are a successful global check.

10 · Versioning and release

Version tools and contract independently.

A linter or resolver update and a Shopware service change are different events. Giving them one version number creates artificial upgrades; separating them lets each change at its natural cadence.

Tool package

^1.0.0

Changes when presets, rules, supported peers, or resolver behavior change—not for each Shopware release.

Contract protocol

format: 1

Changes only when the manifest or declaration entry-point protocol becomes incompatible.

Shopware identity

6.8-dev @ abc123

Describes the declarations being consumed and makes an accidental released fallback observable.

extension-contract/manifest.json — illustrative
{
  "format": 1,
  "shopwareVersion": "6.8.0-dev",
  "contractHash": "sha256:98f4…",
  "profiles": {
    "public": "./public.d.ts",
    "internal": "./internal.d.ts"
  },
  "entitySchema": "./entity-schema.d.ts"
}

Contract pipeline

1
Produce

Generate the public/internal service surfaces and entity schema from the current Administration source.

2
Conform

Compile fixtures and compare service keys with the runtime registration map; reject stale declarations.

3
Distribute

Include the same contract directory in source and Composer Administration artifacts.

4
Snapshot

Publish content-addressed release contracts for explicit standalone targets; trunk never waits for this step.

Two cadences, no forced consumer churn

Tooling releases are occasional npm events. Contract production is part of each Shopware build and release artifact. Extension authors update the dependency only when they want new tooling behavior—not to make types match the Shopware installation they are already using.

Release rules

  • Do not require a dependency or lockfile edit for an ordinary Shopware release or local version switch.
  • A connected local/source/Composer contract always outranks a released snapshot.
  • Integrated and downstream CI fail closed when the exact local contract or expected revision is unavailable.
  • A standalone version target is concrete; a supported range is proven with a matrix of concrete snapshots.
  • Only a contract format incompatibility may require a tooling upgrade.
  • Public declaration changes follow Shopware release documentation and compatibility policy; internal changes run Commercial downstream checks.

Migration scope

This report proposes the architecture, not an immediate flag-day conversion. Existing plugins continue to build. Tooling adoption is per extension, while new scaffolds use the connected contract from the start. The ignored locator is environment state and must not be committed. A behavior/workflow change of this size requires developer-facing release and upgrade documentation.

Storefront coordination

Keep Storefront untouched in the first release. If Storefront later wants the same model, publish a separate @shopware-ag/storefront-extension-tooling package with its own runtime assumptions and lint processors. A multi-surface plugin may use an explicit npm workspace, but Administration and Storefront must not share one ambient TypeScript or ESLint project.

Residual risks worth accepting

Broken locator

A moved checkout can stale an absolute path. Mitigate with a stable filename, pre-check validation, and one repair command.

Producer drift

Generated types can drift from runtime registration. This is acceptable only with typed registration or a mandatory conformance test.

Standalone ambiguity

A single release cannot represent a version range. Require explicit targets and matrix checks, and display the selected identity.

13 · Final decision

This is the solution I would build.

Adopt the connected extension toolchain.

Publish @shopware-ag/administration-extension-tooling as a stable mechanics package. Let each extension own a normal npm project, then connect it to the public or internal declaration contract shipped by the exact Shopware installation. Keep implementation source private and keep Storefront separate.

Stop investing in the root projector, linked Administration facade, and release-coupled type package after the Commercial vertical slice proves the acceptance gates. Reuse their useful assets—the curated public boundary, lint config, Twig processor, entity converter, and tests—but discard their global projection and link-repair machinery.

Install tools once. Types follow the connected Shopware. IDE and CI read the same contract.
The surprising part

The simplification is not “put everything in npm.” It is recognizing that tools and product types have different lifecycles. Once separated, a plugin keeps one familiar dependency while its declarations follow any checkout—from an old supported release to today’s trunk—through one inspectable locator.
