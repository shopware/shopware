Issue #14040 · Improved connected-toolchain concept · 14 July 2026

One local contract. One project graph. Zero paths.

Shopware owns the public Administration contract and the tooling preset. A setup step exposes both through one generated package at the project root. Zero-config extensions then share the same TypeScript project in the IDE, CLI, and ESLint; custom extensions opt in with two stable imports.

Installed version is authoritative Public API by default No machine paths in plugins No root npm workspace required
VerdictReview · Claude · 14 Jul 2026

The architecture is right — amend it, don't replace it. The triad of bridge (resolution), root program (orchestration), and contract (support) is the minimal set that covers IDE, CLI, and ESLint consistently. Every alternative I weighed loses on at least one axis this design holds: npm workspaces require a root package.json and npm-managed plugins, symlinks fail on Windows, a published-package-only contract reintroduces version skew against the installed Administration, and generated per-plugin paths put machine-specific state back into plugin territory.

Four gaps should be closed before treating this as final: a package-manager policy for the bridge (see 03), a failure policy for the shared root program (see 05), two unstated IDE dependencies (see 05), and entity-schema freshness (see 03). Each is annotated in place below; section 08 gets three additional acceptance criteria.

01 · The decision

Keep the bridge. Tighten the contract. Unify the project.

The smallest robust design is not a monorepo migration and not a published package. It is a version-local contract, exposed through a generated Node package, with a single installation-level project for extensions that have no custom configuration.

Keep

The generated bridge

It converts machine-specific installation paths into stable package specifiers without symlinks or plugin-side paths.

Change

The type and project model

Expose a mechanically checked public contract and make the root project the canonical graph for every zero-config consumer.

Defer

Standalone publishing and build layout

A published declaration rollup and the broader package/build restructuring are separate decisions with different owners.

Design principle: unsupported Administration internals should be absent from the extension contract. That is a simpler and stronger boundary than exposing everything and depending on a custom lint rule to identify unsafe property access.
02 · Developer experience

Zero files for the default case. Two files when a plugin wants control.

The normal Shopware project owns the root configuration. An extension only adds local configuration when it intentionally needs different includes, stricter rules, or standalone-editor behavior.

Default extension

No package.json, tsconfig, or ESLint config

  • Discovered from var/plugins.json
  • Included by the managed root tsconfig.json
  • Linted with the managed root flat config
  • Receives Shopware, entity, Vue, and Twig support
Custom extension

One stable import per tool

The bridge makes these files identical across machines and Shopware installations. Their existence is an explicit opt-out from root ownership.

plugin/tsconfig.jsonoptional
{
  "extends":
    "@shopware-ag/administration-extension-tooling/tsconfig",
  "include": ["src/**/*.ts", "src/**/*.vue"]
}
plugin/eslint.config.mjsoptional
import { shopwareAdminExtension }
  from '@shopware-ag/administration-extension-tooling/eslint';

export default shopwareAdminExtension();
Customized project roots are not silently “zero config.” If setup finds a user-owned root tsconfig or ESLint config, it preserves the file and prints the exact integration snippet. The check command fails with an actionable diagnostic until that integration is complete.
03 · Architecture

The installation supplies the truth; setup supplies the location.

Versioned source files remain inside the Administration package. Only tiny proxies and project-level orchestration are generated in the Shopware project. Nothing is copied into a plugin.

Risk 1 — biggest gapReview · Claude

Writing into node_modules needs an explicit package-manager policy. In the default Composer-only project root nothing else manages node_modules, so injection is safe. But when the root has its own package.json — agencies do this for their own tooling — pnpm and Yarn's node-modules linker treat the directory as fully owned and prune foreign packages on install, and Yarn PnP has no node_modules at all. The concept handles user-owned root configs but is silent on user-owned root package management.

Suggestion: apply the ownership principle one layer down. When setup detects a root package.json, generate the bridge into var/admin-extension-tooling/bridge/ instead and print the one-line integration snippet ("file:var/admin-extension-tooling/bridge"), with the check command failing actionably until the specifier resolves — exactly the treatment user-owned root configs already receive.

Related: the check should detect shadowing. Once the deferred published package exists under the same name, a plugin (or root) that npm-installs it wins Node resolution over the bridge, and the plugin silently type-checks against generic published types instead of the installed version.

Step 1

Step 3

Step 4

Gap — freshnessReview · Claude

Entity-schema freshness is under-specified. The contract types are static, but EntitySchema.Entities is installation-specific and changes when plugins are installed or activated — a PHP-side event this JS lifecycle never sees. "Plugin activated, no JS command run since" leaves the tooling checking against a stale schema without any signal.

Suggestion: setup records a hash of var/plugins.json and the schema dump in var/admin-extension-tooling; admin:check-extensions compares and fails with an explicit "run setup" diagnostic when stale, instead of silently type-checking outdated types.

04 · Public contract

One source describes support and proves the runtime matches it.

The public contract is a small, dependency-light TypeScript source file. The Administration runtime is checked structurally against it, while extensions consume its generated declaration. Co-location prevents version skew; the compile-time check prevents declaration/runtime drift.

extension-tooling/public-api.tssource of truth
export interface ShopwarePublicApi {
  Component: ShopwareComponentApi;
  Module: ShopwareModuleApi;
  Service<Name extends keyof CustomShopwareServices>(
    name: Name,
  ): CustomShopwareServices[Name];
  Data: { Criteria: typeof Criteria };
  Context: { api: ShopwareApiContext };
}

declare global {
  interface CustomShopwareServices {
    repositoryFactory: ShopwareRepositoryFactory;
  }

  interface CustomShopwareProperties {}

  const Shopware:
    ShopwarePublicApi & CustomShopwareProperties;
}
src/core/shopware.tsruntime proof
import type { ShopwarePublicApi }
  from '../../extension-tooling/public-api';

class ShopwareClass {
  // The runtime may have more internal members.
  // It must implement every public member correctly.
}

const ShopwareInstance =
  new ShopwareClass() satisfies ShopwarePublicApi;
Extension-facing

Supported APIs are typed

Internal members are not part of ShopwarePublicApi. Deprecated public members carry normal TypeScript JSDoc markers that editors and typed lint rules understand.

Build-facing

The declaration is generated and checked

CI emits dist/public-api.d.ts from the small contract source and fails when the committed artifact is stale. This is declaration emit, not a claim that the full Admin graph is a flat rollup.

The supported-API boundary lives in the type contract. ESLint still blocks direct Administration source imports and handles Vue/Twig deprecations, but it is not responsible for inventing a public/private boundary after autocomplete has already exposed every internal member.
Agree — strongest partReview · Claude

"Unsupported internals are absent from the contract" is the strongest decision in this concept — it is structurally enforceable, where a lint rule that re-invents the public/private boundary after autocomplete already exposed everything is not. The satisfies runtime proof is cheap and catches drift at the source.

One migration it implies: today's extension-tooling/public-api.d.ts on the PoC branch is a hand-maintained declaration file using declare global — no interface can be imported from it for the satisfies check. Moving to a public-api.ts source with a generated declaration is therefore a prerequisite for this section, not an optimization.

05 · One project graph

The IDE and command line compile the same installation.

Default extensions are intentionally one TypeScript program because they run together in one installed Administration. That means declaration merging behaves the same in Volar and vue-tsc, and the checker starts once instead of once per extension.

  "include": [
    "custom/plugins/*/**/administration/src/**/*",
    "vendor/*/*/**/administration/src/**/*",
    "src/Storefront/Resources/app/administration/src/**/*"

}

// default extensions: exactly the project the IDE sees
vue-tsc --noEmit --project <projectRoot>/tsconfig.json

// custom extensions: explicit opt-out, checked separately
vue-tsc --noEmit --project <plugin>/tsconfig.json

// diagnostics are mapped back through var/plugins.json
Gap — IDE parityReview · Claude

"The IDE sees the same project" has two unstated dependencies. Volar uses the workspace TypeScript — with no root node_modules SDK, VS Code falls back to its bundled TS version, which can diverge from the vue-tsc the check uses. And the VS Code ESLint extension must resolve an eslint library from the workspace, which a Composer-only root doesn't have. Both produce exactly the "works in CI, different in my editor" class of bug this concept exists to kill.

Suggestion: setup optionally writes a marker-owned .vscode/settings.json pinning typescript.tsdk and eslint.nodePath into the installed Administration's node_modules.

Risk 2 — blast radiusReview · Claude

The one-program blast radius needs an explicit failure policy. One sloppy third-party store plugin makes the root vue-tsc run red for everyone, and compilerOptions (strictness, allowJs) are global to the program — a legacy JS-heavy plugin under strict mode drowns the output. The PoC already has the ingredients (per-extension baselines, diagnostics mapped through var/plugins.json), but the exit-code semantics are unspecified.

Suggestion: group diagnostics per extension, let baselines suppress pre-existing errors, and by default fail only on custom/plugins — code the project owns — while reporting vendor/ plugins non-fatally unless opted in. Project references would isolate harder, but they break the shared declaration merging that justifies the single program; one program plus diagnostic scoping is the right trade.

Implementation note: this section is the main delta versus the PoC branch, whose check.ts still generates per-project check tsconfigs. The migration to "root program is canonical for defaults" is where this failure policy and the baseline mapping have to land.

06 · Ownership boundaries

Every generated or maintained artifact has one owner.

Clear ownership is what makes regeneration safe. The platform never overwrites user-owned configuration, and plugins never need to understand the physical Administration installation path.

07 · Limits and scope

Solve the connected-project problem without pretending it is every tooling problem.

This concept is deliberately narrow. It creates predictable TypeScript and ESLint behavior for extensions inside a Shopware installation. The broader repository and build architecture remains a follow-up decision.

In scope
  • Shopware global and entity types in installed extensions
  • Vue, TypeScript, JavaScript, HTML Twig, and Vue Twig linting
  • Consistent IDE and CLI project behavior
  • Custom plugin config composition
  • Safe regeneration after install, branch switch, and node_modules cleanup
Separate follow-up
  • Moving the repository's package.json or build orchestration
  • Storefront package/folder redesign
  • A versioned standalone npm contract
  • A self-contained declaration rollup for plugin-only checkouts
  • Changing Administration runtime or plugin loading behavior
Issue handling: land this as the Administration extension-tooling part of issue #14040, with explicit Storefront build regression coverage. Track repository/package restructuring separately with Administration and Storefront owners together.
Why not expose the complete Administration source?

It enlarges every plugin's TypeScript graph, makes internal implementation types look supported, couples plugin checks to Admin compiler details, and requires a sophisticated typed ESLint rule to rebuild the public boundary after the fact. A curated contract is smaller, faster, and easier to evolve intentionally.

Why not publish a package immediately?

A published package is useful for standalone plugin repositories, but it introduces a second version selection and must contain a real, self-contained declaration rollup. The connected Shopware project already knows the exact installed version and entity schema, so the local bridge is the simpler default. Publishing can reuse the same public contract later.

What about external or symlinked plugin workspaces?

The supported V1 case is a plugin path represented inside the Shopware project and included by the root project. Physical paths outside the project, especially with plugin-local bare imports, need an explicit integration test. If Node resolution cannot reach the root bridge, that checkout uses the later standalone package rather than hidden path flags.

08 · Definition of done

Prove the invariants, not only the happy path.

The concept is ready when the default experience is automatic, custom ownership is respected, and the same errors appear in interactive and automated tooling.

  • A zero-config plugin receives public Shopware and generated entity types in TypeScript and Vue files.
  • HTML Twig and Vue Twig files are linted through the installed Administration parser setup.
  • Two zero-config plugins with global augmentations behave identically in Volar and vue-tsc.
  • The CLI starts one TypeScript check for the managed root project, then checks explicit custom projects.
  • A custom plugin composes the tsconfig and ESLint preset using only stable package specifiers.
  • User-owned root configs are preserved and produce exact, actionable integration diagnostics.
  • The public declaration is regenerated in CI and structurally checked against ShopwareClass.
  • Removing node_modules and rerunning setup recreates the bridge without absolute committed paths.
  • Windows path handling works without symlink privileges or platform-specific config.
  • External/path-repository plugins have a documented supported outcome and a dedicated integration test.
  • Administration build/watch flows remain green after setup regeneration.
  • Storefront build and development flows are verified by their owning specialists.
Suggestion — 3 extra criteriaReview · Claude

Add three acceptance criteria matching the annotated risks:

1. A project root with its own package.json (npm, pnpm, or Yarn) survives setup with a documented outcome — never a silently pruned bridge. 2. A shadowed bridge specifier (the future published package installed plugin-locally or at root) is detected and reported by the check. 3. The check detects a stale entity schema or plugin map and demands regeneration instead of type-checking against outdated types.

Outcome: the default plugin author thinks about Shopware APIs, not filesystem topology. Platform maintainers retain one explicit public contract, one local bridge mechanism, and one canonical project to debug.
