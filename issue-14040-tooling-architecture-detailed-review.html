00 / Executive verdict

The proposal is good research and the right direction—not yet a shippable solution

The root cause is not “the package.json sits too deep.” The root cause is the absence of an explicit, version-aligned extension-development contract that survives the Composer subtree split and that produces the same result in editors, CI, and the Vite runtime. Both candidates see part of that truth. Only the generated-facade proposal preserves the release boundary and creates a semantic gate without making every installed plugin part of one npm trust domain.

Recommended decision

Continue from proposal A; retire branch B as an implementation; salvage B’s compatibility evidence and consumer-fixture idea.

Proposal AApprove the architectural direction. Request changes before productization: governed config modes, an editor-compatible migration lane, API conformance, all-installed-plugin discovery, schema fallback, stable baselines, and real Flex/Storefront acceptance.
Branch BDo not merge as the end-state. Its public package shape, wildcard exports, live private type graph, phantom dependency mappings, CommonJS preset, and actual source-checkout-only linker are structurally unsafe.
Better optionShip a dedicated Administration extension contract with a generated projector and verifier, plus a tightly scoped, time-boxed legacy type adapter. Keep the Admin application package private and keep runtime dependency truth separate from type convenience.

01 / Problem framing

What #14040 actually needs to solve

Root cause

A portable development contract

Extension code needs supported types, compiler policy, ESLint/Twig/SFC behavior, project discovery, and a semantic gate tied to the installed Shopware version. That contract must exist in source checkouts and in vendor/shopware/administration.

Not the root cause

A root npm workspace

The repository root is absent after src/Administration is subtree-split. Dynamically joining arbitrary merchant plugins to a root workspace would also change lock ownership, lifecycle-script trust, hoisting, and reproducibility.

Non-negotiable constraints

ConstraintWhy it is architecturalReview consequence
Composer split is the release boundary.github/bin/split.bash splits src/Administration/; monorepo-root files do not ship with shopware/administration.The durable contract must live in the Administration subtree. Root files may only be generated projection.
Vite is not a type checkerThe plugin build creates one Vite root per extension and transpiles TypeScript. Semantic errors need a separate vue-tsc/tsc gate.A solution without an explicit check command does not meet “type checking works.”
Runtime imports and type resolution differThe current externals plugin aliases only bare vue to window.Shopware.Vue.A tsconfig may not map pinia, axios, router, or test utilities to Admin dependencies and then call them host-provided.
Plugins have several ownership shapesConventional plugins, Composer/vendor packages, inactive plugins, path installs, and multi-bundle suites do not share one package root.Filesystem heuristics and custom/plugins/* loops are insufficient as the source of truth.
Existing ecosystem code is not a clean public-API consumerFirst-party plugins rely on deep paths, private globals, and duplicated tooling.Rollout needs an explicit migration policy; neither “everything is public” nor “baseline 19k errors” is acceptable as the default.

Scope conclusion from the Shopware change-scope lens: the smallest root-cause fix is an Administration-distributed contract plus project-local discovery—not a repository-wide JavaScript reorganization. A Storefront implementation can remain separate, but the protocol and acceptance criteria must be designed jointly because the issue explicitly requires that collaboration.

04 / Five decision blockers

What must change before an implementation PR can be approved

Blocking · compatibility
A’s 19,357-diagnostic baseline is not an adoption plan because editor diagnostics remain visible

The check runner can classify diagnostics as known, but TypeScript Server and the ESLint editor extension do not read .shopware-admin-baseline.json. The document itself says the high counts demonstrate that the curated Shopware surface is incomplete. Calling the corpus “passing” before contract-caused errors are separated from plugin-owned debt would produce green CI and unusable IDEs.

Evidence: research §09 reports 13,272 diagnostics for Commercial and 6,062 for PayPal; public-api.d.ts intentionally leaves many namespaces as Record<string, unknown>. A local AST comparison found 7 of 16 runtime Shopware.Component members intentionally absent from the curated interface. Confidence 0.96.
Required change: define a rollout gate and a migration lane. Contract gaps, unsupported-private usage, and plugin code debt must be different categories. Existing first-party plugins may use a clearly named, removal-versioned legacy-internal-types adapter; new plugins default to strict public types. Do not baseline contract/tooling errors.
Blocking · correctness
A can report a custom project as covered even when its tsconfig or ESLint config does not compose the Shopware contract

Discovery marks a project custom whenever either config exists. TypeScript then runs the existing tsconfig directly, and ESLint 10 intentionally stops at the nearest config. Nothing verifies strictness, facade types, required import boundaries, Twig/SFC coverage, or even that the config matches the source files. Existing root configs are likewise preserved with a warning while the zero-config promise quietly stops working.

Evidence: setup.ts:169–180, 199–201, 386–393; check.ts:331–357, 393–429. ESLint 10’s documented algorithm starts from each linted file and uses its nearest eslint.config.*. Confidence 0.95.
Required change: model TypeScript and ESLint ownership separately as managed-default, managed-custom, or unmanaged. Use --showConfig/compiler sentinels and --print-config to prove the contract is composed. An unmanaged project must be visibly skipped or fail the authoritative check—never count as green coverage.
Blocking · implementation gap
B’s committed linker does not implement the branch proposal’s central “every layout” claim

The branch document describes a cross-layout postinstall resolver, Flex recipe steps, Shopware CLI support, and a fixture plugin. None exists in commit abcb46850a4. The only linker hardcodes src/Administration/Resources/app/administration and loops over custom/plugins/*. In a production project it creates a link toward a path that does not exist; vendor packages and nonstandard layouts are skipped.

Evidence: branch bin/install-extension-npm:60–89, especially ADMIN_APP_PATH at line 66 and the custom-plugin loop at line 78. The branch diff contains 10 files and no test/fixture/recipe change. Confidence 1.00.
Required change: do not repair this branch incrementally. Its best ideas—stable local specifier, lifecycle healing, consumer-shaped CI—fit better inside A’s projector. Use backend-discovered paths, not a second filesystem walker.
Blocking · public contract
B turns the Administration application and its private source graph into an importable runtime/public package

The package is renamed to an official scope but is not marked private. Its root export has a runtime default pointing at src/core/shopware.ts, and "./*": "./*" explicitly exposes every subpath. The type entry imports the 621-line global.types.ts graph. This contradicts the accompanying no-src-imports rule and would make internal refactors ecosystem compatibility events.

Evidence: branch package.json:2–15, types/index.d.ts:12–19, and tsconfig.plugin.json:23–27. Node’s package documentation recommends explicit exports so the public interface is well-defined; wildcard subpaths do the opposite here. Confidence 1.00.
Required change: keep the Admin application package identity unchanged/private. Use a dedicated local tooling facade with explicit type/config-only exports and no runtime default. Any legacy live-type adapter must be opt-in, explicitly unstable, and must not export arbitrary source paths.
Blocking · runtime correctness
B’s “host-provided modules” map can make TypeScript pass imports that Shopware does not provide at runtime

The branch maps Vue Router, Pinia, Vuex, axios, and @vue/test-utils to the Administration’s node_modules. The actual Vite external adapter only replaces bare vue with window.Shopware.Vue. Admin using a dependency in its own bundle does not make that dependency a public module import for plugins; test utilities are especially not a browser runtime contract.

Evidence: branch tsconfig.plugin.json:29–39 versus externals-plugin/index.ts:37–43. The branch also uses module: CommonJS without modern module resolution. Confidence 0.98.
Required change: maintain one typed runtime-contract manifest with categories: platform external, plugin-bundled dependency, public type dependency, and test-only. A module becomes “host-provided” only when the build has a matching runtime adapter and compatibility policy. Today, keep Vue as the only such external.

07 / Recommended architecture C

A governed extension contract: contract + projector + verifier + migration lanes

The better solution retains A’s release-boundary and zero-config architecture, uses B’s evidence only as a migration bridge, and adds explicit ownership so the system can never claim a project is checked when it is not. The Admin application remains an application; the extension contract is a dedicated, private, type/config-only surface.

Design decisions in concrete terms

Do not rename the Administration application package

Keep a dedicated local name such as @shopware-ag/administration-extension-tooling, set private: true, and export only types, tsconfig variants, ESLint factories and future compiler adapters. There is no root runtime export.

Make the public interface executable

Move supported interface definitions out of the disconnected PoC declaration and into a dependency-light internal module. ShopwareClass must structurally satisfy it in the normal Admin typecheck. The facade then re-exports the same type source.

Compatibility is a migration tool, not API expansion

A legacy adapter may re-expose the current global type graph for existing plugins, but it is opt-in, emits a deprecation warning, has an announced removal major, and never adds ./* or a runtime entry. New extensions cannot select it by default.

Do not confuse Admin dependencies with host modules

Only Vue has a runtime external adapter today. Router, Pinia, axios and test utilities remain plugin/test dependencies unless Shopware deliberately adds runtime globals/adapters and a BC policy.

Generate schema outside vendor

Write plugin-aware schema types to project state and have the facade import that generated file. Ship a core-only fallback for offline editor bootstrap; require plugin-aware generation in strict CI. This supports read-only vendor deployments.

Make “checked” a provable state

The manifest records resolved-config evidence and tool versions. If custom configs omit strict types or the required ESLint boundary, status is unmanaged. A warning is not converted into a successful certification.

10 / Public release and operating contract

The proposed change directly affects extension authors, public type/API expectations, generated project files, build/watch/setup lifecycle, supported tool versions, and migration behavior. It is not an implementation-only refactor.
