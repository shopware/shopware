Architecture proposal + executable proof of concept · 10 July 2026

Zero-config for plugin authors. One local contract from the installed Shopware source.

A detailed proposal for Shopware issue #14040 based on the current source tree, Composer subtree releases, the production/Flex recipes, real SwagPayPal, SwagCommercial and SwagLanguagePack configurations, and an executable local proof of concept. The recommendation deliberately avoids publishing npm packages.

Issue: open / evaluation Local snapshot: 1ca37a42e66 PoC: executable and passing npm only · no registry release Storefront build unchanged

00 / Executive view

Recommendation: generate a local facade, do not publish a tooling package

The durable contract should live inside the Composer-distributed Administration source. A normal Shopware setup then generates a tiny project-local package facade at node_modules/@shopware-ag/administration-extension-tooling, plus root TypeScript and ESLint discovery files. Plugins consume the installed Shopware source by a stable package name, while no artifact is released to npm and no plugin needs its own package.json, tsconfig.json or ESLint config for the default case.

Proposed architecture

Committed contract in Administration; disposable projection at the project root.

Shopware owns a curated window.Shopware declaration, generated entity-schema types, a strict SFC-aware TypeScript preset, and an ESLint flat-config factory. Setup discovers every active Administration extension from var/plugins.json and projects that contract into whatever layout is installed: source checkout, custom/plugins, Composer vendor, or a production/Flex project.

Advanced extensions can opt into local configs that extend the same package-name contract and append aliases, includes, scripts, dependencies or custom lint rules. Existing debt is isolated by an exact, committed per-extension baseline; new and migrated code remains fully strict.

Proven

Semantic checking is a separate gate

vue-tsc --noEmit catches errors that Vite transpilation does not. The fixture deliberately introduces TS2322, fails, then passes only after the exact diagnostic is baselined.

Proven

Flex/vendor layouts need no path hacks

A temporary production-style project with Administration below vendor/shopware/administration passed TypeScript, ESLint, legacy Twig processing and an actual Vite plugin build.

Required

The Flex recipe is part of the feature

The production template has a minimal Composer file and receives build scripts through recipes. Updating only the monorepo composer.json cannot make IDE setup automatic for external developers.

Why this fits the requested constraints

It tracks trunk immediately, works from the installed Composer package, uses the backend-generated entity schema including plugin entities, keeps plugin package.json optional, supports config overrides by extension, preserves the existing Storefront build, and avoids both deep relative paths and npm release timing.

What the PoC changed after testing the obvious alternatives
  • Bundling the existing global.types.ts was rejected: it imports a large private implementation graph and declaration bundlers surfaced private/unemittable type failures.
  • Publishing multiple npm packages was rejected by product preference and would make unreleased trunk/plugin compatibility difficult to test.
  • A whole-repository dynamic workspace remains unnecessary and unsafe for arbitrary third-party plugins.
  • A local facade rather than a required symlink keeps the public specifier stable and can be regenerated after Composer/npm operations.
  • The default TS preset deliberately does not resolve src/*; new private Admin imports fail while legacy ones can be baselined during migration.

Decision in one sentence

Implement #14040 as an Administration-owned, generated local tooling facade with strict checks and transparent migration baselines; integrate generation in both source Composer scripts and the production Flex recipe, and treat a plugin-owned package/config as an optional escape hatch rather than the default.

Administration package metadata is not a usable public package
  • The name is the generic administration, unscoped and not marked private.
  • main points to ./src/core/shopware.js, although the implementation is now TypeScript.
  • types points to ./types/index.d.ts, which does not exist.
  • It contains local file: dependencies for the Twig processor and custom rule packages.
  • A package under the same generic name exists on npm and is unrelated; plugin constraints such as administration:^6.x do not establish a Shopware contract.
The current plugin build contract
  1. PHP discovers bundles and writes paths into var/plugins.json.
  2. plugins.vite.ts creates one build or dev server per active Admin extension.
  3. Each extension’s Administration src folder becomes a Vite root and receives Shopware plugins, aliases, output, HMR and external handling.
  4. A plugin-local Vite config may be auto-discovered implicitly because the programmatic config does not disable config-file lookup.
  5. Only Vue is explicitly replaced with window.Shopware.Vue. TypeScript aliases for Pinia, Vue Router, axios, test helpers, or other packages do not make those packages host-provided at runtime.
  6. Vite transpiles but does not type-check. A successful production bundle is therefore not a semantic TypeScript gate.
Extension dependency installation is narrower than discovery

bin/install-extension-npm reads active bundle metadata, checks a few expected package locations, and installs under custom/plugins when node_modules is absent. It does not constitute a general contract for inactive plugins, static plugins, Composer/vendor packages, apps, changed manifests, multi-bundle roots, lint/type-check setup, or links pruned by npm.

The repository root is not a release boundary.

.github/bin/split.bash splits src/Administration and src/Storefront into separate Composer packages. A root-only package, lockfile, tsconfig or ESLint config would not be present when a production project installs shopware/administration. Any design that promises plugin tooling must say how its artifacts cross this boundary.

03 / TypeScript

The current types are an application graph, not an SDK

Core’s tsconfig owns the Admin application. Plugins need a different thing: stable declarations and compiler policy that resolve through ordinary packages, while each plugin owns its source set and runtime dependencies.

Current

Core application config

target: ES2023, module: commonjs, baseUrl, source and nested-node-module aliases, Jest globals, no emit, strict mode.

Includes only core Admin source/build/tests—not extensions.

Boundary leak

Live-source global types

global.types.ts is about 621 lines and imports roughly 131 internal and external symbols. Consumers pull a large private source graph into checking.

Generated

Entity schema types

entity-schema-definition.d.ts is large, generated, and ignored in a fresh checkout. “Out of the box” must define how this artifact exists before generation.

Observed failure chain

1 · Resolution

Plugin aliases jump into core internals

Deep relative paths point at Admin source, Admin node_modules, test helpers and declaration files in one assumed checkout layout.

2 · Type ownership

Internal source becomes de facto public API

Type-only imports still expose private file locations. skipLibCheck does not skip ordinary imported .ts implementation files.

3 · Build

Vite erases syntax, not mistakes

Semantic errors survive the current build unless a separate tsc or vue-tsc command runs.

4 · CI

Green checks communicate false confidence

SwagCommercial #2734 deliberately assigns strings to numbers; existing Admin/Storefront lint and check jobs remain green.

Design rule: Recommendation

Treat paths as compile-time aliases only. They do not rewrite emitted imports and should not map sibling packages or core node_modules. Supported Shopware types should resolve through a real package with types/exports; every runtime dependency that is not explicitly externalized by the platform remains a plugin dependency.

Desired minimal plugin shape

// tsconfig.json — illustrative, not a final package name
{
  "extends": "@shopware-ag/tsconfig-admin-extension",
  "include": ["src/**/*.ts", "src/**/*.vue"],
  "compilerOptions": {
    "types": ["@shopware-ag/administration-extension-types"]
  }
}

// package scripts
{
  "scripts": {
    "typecheck": "vue-tsc --noEmit",
    "lint": "eslint src"
  }
}

Use vue-tsc for a project that can contain Vue SFCs; plain tsc remains suitable for pure TypeScript packages. Build, lint and type-check must be separate observable gates.

04 / ESLint and Twig

Installed tooling is shared by path, but behavior is not portable

Core’s flat ESLint config is a large application config with hardcoded project ownership. Its Twig support depends on unpublished code plus patches to exact third-party internals. Plugins either reproduce that environment, borrow it through deep paths, or receive a materially different lint result.

Core ESLint

Hardcoded project and aliases

  • Type-aware parsing points at core ./tsconfig.json.
  • tsconfigRootDir is the core Admin directory.
  • Import resolvers point at core aliases and project.
  • Twig patterns are rooted below core src.
  • A plugin-rules dependency is installed but not registered/applied in the current flat config, illustrating package/config drift.

Running the config directly against external plugin TypeScript can report that the file is outside the base path.

Twig processor

A patch stack with no contract tests

  • Local CommonJS package version 0.0.0.
  • Wraps Twig text in a synthetic Vue template and shifts ranges.
  • Patches compiled internals of vue-eslint-parser@9.4.3.
  • Patches eslint-plugin-vue@9.32.0 filename checks.
  • Has no meaningful test suite.

Why a root config alone will not fix plugin linting

  1. Flat configs import parser and plugin objects from real packages; moving the entry file does not make local patched dependencies portable.
  2. ESLint 10 looks for the nearest config from each linted file. A plugin-local config becomes authoritative and must import a shared Shopware config explicitly.
  3. Typed linting still needs the plugin’s own tsconfig. Pointing every file at core’s project is incorrect.
  4. Glob roots and ignore behavior change when a config is discovered normally versus supplied with --config.
  5. A deeper plugin dependency may receive an unpatched upstream Vue parser/plugin even when a patched copy exists at repository root.

Twig is a compatibility requirement, not just old debt

Counts are a checkout snapshot and include the relevant source trees; they are architectural scale indicators, not release metrics. Shopware’s current guidance describes TwigJS blocks as the stable supported model today, a transition where Twig and SFC coexist, and native SFCs as the future.

What the parser experiment showed

The current processor compensates for a virtual leading <template> line and relies on modified parser internals to hide Twig expressions. Malformed Twig input can produce a fatal Invalid code point -1 error without a useful source location. Inline ESLint directives inside Twig are not reliable, so core retains file-specific overrides. These are signs that the grammar and diagnostic mapping need owned tests, not only a different install location.

Why upgrading upstream packages does not remove the problem

Current upstream vue-eslint-parser still identifies Vue input primarily by a final .vue suffix or source beginning with <. Shopware templates commonly end in .twig and may start with a Twig directive. Current eslint-plugin-vue also still contains .vue-specific behavior in indentation logic. Upgrading is valuable, but is not the complete Twig solution.

Portable flat-config shape

// eslint.config.mjs — illustrative
import { shopwareAdmin } from "@shopware-ag/eslint-config-admin-extension";

  typed: true,
  legacyTwig: true,

The shared package should directly own parsers, processors, Vue rules, Shopware rules and typescript-eslint, with ESLint as a peer. Typed parsing should use projectService: true so each source file resolves the nearest plugin-owned tsconfig.json. A root CI entry may use the same factory with explicit package scopes; it must not become a separate ruleset.

SwagPayPal: toolchain duplication and a misleading npm dependency
  • Its tsconfig maps plugin aliases, core source, core declarations and a wildcard into core’s deeply nested node_modules.
  • Its ESLint config reconstructs the core path and dynamically imports the unpublished Twig processor.
  • TypeScript, Vue ESLint packages and parser versions differ from core, so patched behavior is not inherited naturally.
  • Its optional dependency administration:^6.x does not resolve to a Shopware package; an unrelated administration@1.0.0 exists on npm. Optional failure makes this easy to miss and creates a package-name/supply-chain concern.

Requirement derived: a conventional plugin must consume a scoped, versioned Shopware contract without locating the checkout.

SwagCommercial: a separate repository and a multi-bundle package
  • Its root package contains file: dependencies into Shopware Admin and private lint packages.
  • Its TS graph deliberately includes a wide Admin source surface and uses symlink-preserving behavior.
  • Some nested modules retain legacy ESLint/config styles and very deep paths.
  • Type-aware linting is not generally enforced, and the dedicated proof issue demonstrates that invalid TypeScript can pass the existing checks.
  • Because Commercial is a separate repository, a config that exists only in the Shopware root cannot solve its CI.

Requirement derived: the contract needs a multi-root mode whose implementation ships with the Composer Administration package and can be projected into a separate plugin checkout without a registry release.

SwagLanguagePack: “out of the box” must include scaffolding and CI

This smaller case has TypeScript and Twig sources but no matching compiler/linter setup. Merely making a root config technically capable of seeing those files will not make standalone CI or contributor editor behavior reliable. Generators, documented scripts and extension CI templates are part of the product.

Scaffolding gap:

The current Administration module generator emits a JavaScript entry, module files and snippets, but no package manifest, tsconfig or ESLint entry. The official dependency guide meanwhile teaches a plugin-local package.json and plugin-local node_modules. A successful redesign should update generation and documentation together, not leave every extension to reverse-engineer core.

06 / Storefront boundary

Storefront is a separate migration, not another workspace folder

Storefront has different engines, dependency versions, build systems, install security choices and release ownership. Protecting it means preserving those boundaries until a Storefront-specific contract is designed.

Stable build

Webpack extension model

Reads var/plugins.json, honors plugin Webpack configuration and explicitly adds core Storefront node_modules for plugin resolution.

Newer path

Vite component model

New components live outside the traditional npm root and use symlinks/custom resolution. Extension dependencies may be installed separately.

Security boundary

Install scripts suppressed

The component orchestrator defaults extension installs to --ignore-scripts unless explicitly allowed. A global workspace install could erase this distinction.

Why an immediate Admin + Storefront root lock is high-risk

  • Admin currently uses Vite 6; Storefront uses Vite 8 for newer paths while retaining Webpack for stable extension builds.
  • Node/npm engine floors differ. A root policy uses the strict intersection and raises requirements for contributors who touch only one surface.
  • Shared direct dependencies already have numerous version mismatches and conflicting overrides.
  • Hoisting can expose undeclared packages and select the wrong binary major from an unexpected working directory.
  • Storefront’s plugin-specific resolution and script-suppression decisions are intentional operational behavior, not incidental folder noise.
  • Vite detects workspace roots and changes filesystem/config discovery behavior; adding workspaces can alter HMR and config lookup even without changing build code.
Boundary recommendation:

Keep Administration and Storefront package/build/release boundaries independent in the first phases. Storefront may later adopt parallel types/config artifacts and a fixed internal workspace, but it should have its own requirements, owner, fixtures and rollout. The current Storefront-owned Admin extension becomes one important Administration-contract fixture.

TypeScript 6/7 implications

  • TypeScript 6 deprecates baseUrl and legacy moduleResolution: node, defaults global types to an empty list, and changes several defaults.
  • A new browser-bundled preset should explicitly set target/lib, module, moduleResolution: bundler, types, strictness and noEmit; it should not ship a permanent ignoreDeprecations escape hatch.
  • TypeScript 7’s Go rewrite does not provide the previous JavaScript programmatic API. Upstream guidance is to keep TypeScript 6 available for tools that require that API.
  • Because the current typescript-eslint line supports TypeScript below 6.1, a practical transition may use TS6 for editor/lint program services and evaluate TS7 tsc separately until the integration ecosystem catches up.
  • Config inheritance remains useful, but paths are resolved relative to the config that declares them; leaf file sets replace base sets; references are not inherited.

ESLint 9 → 10 implications

  • ESLint 9.30 introduced a feature flag for lookup from the linted file; ESLint 10 makes that lookup behavior permanent.
  • Flat config does not cascade like .eslintrc. A nearer plugin config replaces discovery of the root entry, so it must import the shared preset itself.
  • Test both normal discovery and authoritative CI with an explicit --config; both should consume the same exported config factory.
  • Use projectService: true for typed linting and keep a real nearest tsconfig.json in each typed package. Do not use broad allowDefaultProject patterns to paper over ownership.
  • Test JS, TS, Vue, html.twig and vue.twig matching plus global/local ignore behavior under ESLint 9, its v10 flag, and ESLint 10.

Security and reproducibility consequence:

Automatically adding every installed plugin to root workspaces is not merely developer convenience. It changes lock ownership, dependency overrides, package-name uniqueness, lifecycle execution, auditing and the reproducibility of npm ci. That requires an explicit trust model and operating contract.

  • extension-tooling/tsconfig.json — strict browser/Vite/SFC base; no private src/* alias.
  • extension-tooling/eslint.mjs and legacy-twig.mjs — flat-config factory, typed rules, source-import boundary and transitional Twig support.
  • scripts/extensionTooling/setup.ts — discovers owners, generates facade/root configs/check projects and preserves user-owned root configs.
  • scripts/extensionTooling/check.ts — invokes vue-tsc and ESLint, normalizes diagnostics and applies exact baselines.
  • setup.spec.ts, check.spec.ts, poc.spec.ts — focused unit/integration coverage.
Honest limitation:

The local database was unavailable, so a live backend dump containing an installed plugin entity could not be regenerated in this session. The fixture verifies the exact generated declaration consumption path with a plugin-defined entity. The existing Shopware/Flex build recipe already performs the real backend schema dump before conversion; productization must add an integration test with a registered DAL definition.

10 / Decision analysis

Why the generated local facade is the best fit

The original issue suggested a repository-root monorepo. Research shows that root discovery files are useful, but a committed root npm workspace is not the contract: it disappears in subtree Composer releases and cannot safely own arbitrary installed plugins. The chosen model keeps the useful root view as generated state.

Important distinction: package name without package publishing

The scoped name is a local resolution contract, not a registry artifact. Setup writes a private facade into the project root's ignored node_modules. Its exported files are tiny proxies to the Administration version actually installed by source checkout or Composer. Pulling trunk or updating shopware/administration, then running normal setup, immediately updates the contract.

Root files are projection

tsconfig.json and eslint.config.mjs exist for editor discovery, are generated and ignored, and are never the release boundary.

Administration is authority

The implementation ships in the Administration subtree, so vendor/shopware/administration receives the same source.

Plugin remains independent

Dependencies and scripts stay local only when needed; no automatic workspace membership or hoisted phantom dependency.

Public TypeScript boundary

1
Global first. Type Shopware and window.Shopware, because that is the documented runtime object available to plugin code.
2
Schema generics. EntityName, Entity<Name>, EntityCollection<Name> and repositoryFactory.create(Name) derive from the generated backend schema.
3
No private source graph. The initial attempt to import/bundle global.types.ts failed because it transitively exposes private implementation. The contract is structural and curated.
4
Augmentable. Named interfaces allow plugin-specific services/properties to merge locally without editing Shopware source.
5
Runtime truth. ESLint rejects src/* and Administration-internal imports; the TS preset supplies no alias that would make those imports appear supported.

Entity-schema lifecycle

  1. Backend bundle discovery/registering runs first, so installed plugin DAL definitions participate.
  2. framework:schema -s entity-schema writes the current schema; the existing converter generates entity-schema-definition.d.ts.
  3. Setup verifies that declaration exists and the local facade imports it directly from the installed Administration source.
  4. A pull/update therefore needs only the normal setup/build/watch lifecycle—no npm release—and custom plugin entities appear after regeneration.
  5. If schema generation is skipped or the backend is unavailable, setup warns. Productization should define whether core-only tracked declarations are an accepted degraded fallback or whether strict checks must stop.

The current production recipe already generates this file inside vendor/shopware/administration. That mutation is disposable generated state and is compatible with the stated constraints, but it must be documented because read-only vendor deployments need a writable build stage or a future project-local output.

Strict migration baseline

StateBehaviorReason
No baselineEvery TS/ESLint diagnostic fails.Default for new plugins and fully migrated modules.
Exact known fingerprintPasses and is counted as baselined.Transparent existing debt; file is committed beside the extension.
New or changed diagnosticFails with normal file/line/column/code/message.Debt cannot silently grow.
Baseline entry no longer observedCheck passes but warns as stale.Improvement becomes visible and removable.
Explicit update commandRewrites selected extension or all baselines.Tool upgrades/migrations are reviewable diffs, not ambient suppression.

The fingerprint currently includes tool, extension-relative file, line, column, rule/code and normalized message. This is intentionally conservative. The tradeoff is that moving a line can create one new and one stale entry; future productization may add a carefully reviewed content anchor without weakening the “no new debt” guarantee.

ESLint, Twig and SFC strategy

  • Use one flat-config factory that owns its direct parser/plugin objects from the installed Administration; plugin configs only compose the factory.
  • Use typescript-eslint project service so each file resolves its nearest owning TS project rather than a single core tsconfig.
  • Support ESLint 9's v10_config_lookup_from_file flag and omit it on ESLint 10.
  • Keep legacy Admin Twig enabled by default during migration. Disable only rules that cannot map reliably through Twig virtualization; record those gaps rather than pretending full Vue parity.
  • Make native Vue SFCs first-class with vue-tsc, Vue parser and <script setup lang="ts">. The future composition/native-block extension system can add its Volar/compiler plugin behind the same facade.
  • Long term, retire the legacy processor when the support horizon allows it; do not let the transitional parser dictate the SFC contract.
Do not expose “whatever compiles” as public API.

The facade is a resolution mechanism, not permission to import Administration source. Every additional property placed on ShopwareExtensionApi must correspond to a supported runtime global. The real-plugin baseline should be used to prioritize curation, not to copy all private types into the contract.

Land the contract in layers, with the Flex recipe in the same initiative

The PoC proves feasibility. It does not remove the need for API ownership, cross-platform tests, docs, release communication and a deliberate baseline migration.

Residual engineering decisions for the implementation PR

  1. Public API completeness gate.
    Define which additional Shopware services/properties graduate based on real plugin usage, and require API declaration snapshots to prevent accidental expansion.
  2. Schema failure mode.
    Choose between warning with core-only fallback and hard failure when a backend/plugin-aware schema cannot be generated. Build, watch and IDE-only setup may need different policies.
  3. Baseline robustness and size.
    Exact line fingerprints are safe but create large files and churn. Measure reviewed content anchors or compressed representations without allowing fuzzy suppression.
  4. Legacy Twig ownership.
    Decide whether to keep the current patched processor in Administration, extract an internal subtree artifact, or replace it; document which rules cannot be reliable.
  5. Recipe command surface.
    Name and document setup/check scripts, dev-dependency installation and when recipes regenerate after plugin add/remove/update.
  6. Cross-platform projection.
    The PoC uses proxy files rather than requiring package symlinks; still test junction/path resolution, realpath normalization and read-only vendor deployments on Windows/Docker.
No further product clarification is required to continue.

These items can be resolved by measurements and maintainership decisions inside the implementation work. None changes the selected no-publish, zero-config, generated-facade architecture.
