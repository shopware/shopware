Overview

A generated, committed list of everything plugins can use in the Administration, so a PR that breaks it shows up in the diff and fails CI.

In short
  • Idea: a generator writes the complete public API of the Administration into committed files. CI compares base and head and fails on breaks that nobody announced.
  • Decided: what counts as public, the file format, the two flag states, the CI checks and the plugin integration (D1–D22).
  • Done: the format spec, a hand-written example snapshot that compiles, 20 test fixtures and 4 real PRs as backtest.
  • Proposed, not decided: the generator design and the answers to the open questions Q1–Q13.
  • Wanted from you: feedback on readability of the reports, on coverage gaps, and on the open questions, by ID.

The problem

Coding agents now write most Administration PRs, and we cannot review all of them line by line. In the Administration the main review risk is breaking extensions. Plugins hook in through names they only know as strings: components, blocks, methods called via $super, props, services, stores, routes and snippet keys. If a PR renames or moves one of them, neither the build nor the tests fail, and the plugin stops working. Today the only way to see what is public is to read the code and know the conventions.

Real cases:

  • #20959 added a <div> that opens in one block and closes in another, and moved a block. Plugins that replace the inner block broke the page (issue #21108, fixed in #21189).
  • #17339 renamed blocks only with the major feature flag on. The bulk edit lost all custom field checkboxes, and nobody noticed for four weeks (issue #19601).
  • #15271 deleted blocks of sw-admin-menu during the UI shell rework and regenerated blocks-list.json, so the guard test turned green again without anyone looking at the deletion. With the snapshot, every deleted block shows up in the PR diff. The check does not fail, because the shell components are @private; it lists the 217 changes in the private group.

One change, end to end

A PR renames a method that plugins can call. This is what every person involved sees.

The change illustrative

The author renames getLoadSalesChannelCriteria to getSalesChannelCriteria. This example comes from FORMAT.md.

// src/module/sw-sales-channel/page/sw-sales-channel-detail/index.js-        getLoadSalesChannelCriteria() {+        getSalesChannelCriteria() {

The diff in the PR

The author regenerates and commits the snapshot. The method list in the report changes by two lines. The neighbouring lines are real.

module/sw-sales-channel/page/sw-sales-channel-detail.api.md
methods   generateAccessUrl(): any-  getLoadSalesChannelCriteria(): any   getRequiredSalesChannelFieldError(fieldName: any): any   getRequiredSalesChannelFieldErrorExpression(fieldName: any): any   getRequiredSalesChannelFields(): any+  getSalesChannelCriteria(): any   getSalesChannelEntityName(): any

What CI prints illustrative

The break check fails. The text follows the format in FORMAT.md. The source line also gets an annotation.

Public API check failed: 1 unannounced break.

Break (1)
  method_missing  component:sw-sales-channel-detail/method:getLoadSalesChannelCriteria  current, major
    The method is gone, so plugin overrides that call $super('getLoadSalesChannelCriteria') throw at runtime.
    Fix: keep the method and mark it @deprecated tag:v6.8.0, or add an entry to public-api/accepted-breaks.json.
    Possible rename: getSalesChannelCriteria.
    Also affects: sw-sales-channel-create (extends sw-sales-channel-detail).
    At: src/module/sw-sales-channel/page/sw-sales-channel-detail/index.js:303

Addition (1)
  method_added  component:sw-sales-channel-detail/method:getSalesChannelCriteria  current, major
    A new public method that plugins can rely on from now on.
    Fix: mark it @private if it is not meant for plugins.

How the author resolves it

Option A, keep and deprecate. The old name stays and delegates. The check passes with one addition and one info, and the removal is allowed in 6.8.

/** @deprecated tag:v6.8.0 - Use getSalesChannelCriteria instead */
getLoadSalesChannelCriteria() {
    return this.getSalesChannelCriteria();
},

getSalesChannelCriteria() {
    // the code of the old method
},

Option B, break on purpose. The author adds an entry with a justification. Code owners approve it, and the check passes with the break in the accepted group.

{
    "accepted": [
        {
            "finding": "method_missing",
            "element": "component:sw-sales-channel-detail/method:getLoadSalesChannelCriteria",
            "justification": "The criteria builder is renamed for 6.8, see UPGRADE-6.8.md.",
            "issue": "https://github.com/shopware/shopware/issues/22591"
        }
    ]
}

If the new method is not meant for plugins, the author marks it @private, and the addition moves to the private group.

What a plugin developer sees illustrative

A plugin that still calls the old name gets a type error. This needs the core change for D20; the message text is not specified yet.

Shopware.Component.override('sw-sales-channel-detail', {
    methods: {
        getLoadSalesChannelCriteria() {
            const criteria = this.$super('getLoadSalesChannelCriteria');
            //                           ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
            // error: 'getLoadSalesChannelCriteria' is not a method of sw-sales-channel-detail
            return criteria;
        },
    },
});

JS plugins get the same finding from admin:check-extensions, with the plugin file and line.
