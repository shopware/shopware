Open questions

What still needs a decision, with a proposed answer for each question, and the known gaps in the spec.

The proposed answers are suggestions, not decisions. Reply with "agree Q4" or with your own answer.

Before the generator starts

These change the spec, so they need an answer first.

IDQuestionProposed answerRelated
Q1Public children of private bases
A public component that extends a @private one (about 17 cases, for example sw-bulk-edit-* on sw-custom-field-set-renderer): are the blocks it inherits public?		Yes. Plugins override them by the child's name, as in #17339. A change in the private base that removes an inherited block is a break on the public child.A15
Q3Private functions that every built plugin calls
overrideComponentSetup, registerNativeExtensionTargets, registerOverrideComponent, attachOverrides and getExposedProps are marked @private, but compiled plugin bundles call them.		A new tag for these functions: changes to them are breaks, but the name helpers do not offer them to plugin code.A33
Q4Removed trailing parameter
Is removing the last parameter of a method always a break? In #20959 the template stopped passing itemIndex, and overrides that read it got undefined.		Yes, always a break. An override can read the parameter even when core no longer uses it.B12
Q6Finding texts
The fixtures use explanations and fix hints for each element kind that the spec does not define.		One text template per finding id, with one sentence per element kind, kept in a table in FORMAT.md.B6, B18, B26
Q7Missing finding ids
method_optional_param_added, service_member_missing, store_member_missing and setup_missing are used but not defined. A position identifier that moves to another host has no finding.		Add the four ids to the table, and add position_id_moved as a break.A18, B18, B23, B27
Q11Still not covered
CSS classes, directives, filters and ACL privileges are now covered (A47–A50). Should Meteor components or Extension SDK locations follow?		Leave both out for now: Meteor components have their own versioning, and only 11 store plugins use the SDK.N11, N12
Q14Private API that store plugins use
Shopware.Application (601 store plugins, getContainer 520), Component.getComponentRegistry (94), Component.build (16) and Shopware.Utils.EventBus (59) are @private.		Make Application.getContainer, addServiceProvider, addServiceProviderDecorator and the EventBus public, because plugins have no alternative. Keep the component registry private and report its use through the store usage index.A33, A55, B30
Q15Store usage index in CI
Where does the break check get the store usage counts from? The mirror is internal.		A scheduled internal job writes the counts per element id to public-api/store-usage.json; the break check only reads that file.B46
Q12Core overrides of native components
How do swDefineOverride and <sw-block extends> in core appear in the snapshot?		As entries in ComponentOverrides, like Options API overrides, with their setup keys and blocks.A25
Q13Version rule for deprecations
How is tag:v6.8.0 compared with the head version 6.8, and does the rule apply per flag state?		Compare major and minor only. Apply the rule per flag state, so a removal in the major state is allowed when the tag names that major.B28

Can be decided while building

IDQuestionProposed answerRelated
Q2Migration to native SFCs
When a component moves from the Options API to a native SFC, every way a plugin uses it changes: overrides, extends and references see different members. The migration codemod also writes @private on every migrated component without @public, which silently makes public components private.		Report the migration as one info finding that lists the changed members, and keep the break rules for members that disappear. Fix the codemod so it keeps the visibility.A21–A25
Q5Where the HTML page lives
Can the HTML page be attached to the PR, or does it stay a workflow artifact?		Workflow artifact, linked from the step summary.
Q8CI runtime
The break check runs the generator twice per PR. What runtime is acceptable?		Under three minutes for both runs. Cache the base model per commit.
Q9Twig parsing
Extend the parser of the existing block list generator or write a new tokenizer?		Start from the existing parser and extend it with nesting and element tracking.
Q16Scope of classes
Should classes list every static class or only the BEM root and element classes of the component?		Every static class: plugins also style utility and state classes such as has-warning, and removals are only info.A47
Q10Native SFC extraction
Is @vue/compiler-sfc enough, or do we need vue-component-meta?		@vue/compiler-sfc first; add vue-component-meta only if prop types need it.

Known gaps in the spec

  • The type checks do not verify block parents or the block names of crossings, so Block<'sw_bogus'> compiles (A13, A16).
  • The order of findings inside a summary group is only a convention in the fixtures: sorted by element id.
  • The fixtures reference _base, which only exists in public-api/. The fixture test has to provide it.
  • The members key of services is not in the printing rules (A34).
