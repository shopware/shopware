Plugins

The same snapshot is a type contract for plugins and the basis for a compatibility check against the current and the next major version.

Plugin developers get two things: typed overrides in their editor, and a check that lists every core name their plugin uses that no longer exists in the current or the next major.

Loading the snapshot

The snapshot ships in the Administration package. extension-tooling/admin-types.d.ts references it, so plugins that already use that file get the types without a change.

/// <reference types="node" />
/// <reference path="../public-api/current.d.ts" />

import '../src/global.types';

A second file, admin-types.major.d.ts, references major.d.ts to check against the next major.

Typed Component.override (D20)

Plugins keep calling Shopware.Component.override as today, without a cast.

Shopware.Component.override('sw-sales-channel-detail', {
    inject: ['themeService'],
    methods: {
        getLoadSalesChannelCriteria() {
            const criteria = this.$super('getLoadSalesChannelCriteria');
            criteria.addAssociation('themes');
            return criteria;
        },
        async onSave() {
            this.isLoading = true;
            await this.$super('onSave');
        },
    },
});
  • this knows the props, data, computed values, methods and injects of the component, its parents, its mixins and the members core overrides add.
  • $super accepts only method and computed names of the target and checks the number of arguments.
  • An override of a native component sees only its public bindings, props and injects, as at runtime.
  • Names the snapshot does not know, for example components of another plugin, keep today's untyped behaviour.

This needs a core change first. Core has to type Component.override through a global interface, ComponentOverrideFn, so that the snapshot can add its typed signature. The change is small and does not touch the runtime, but it is not done yet. We tested the example snapshot without it, and this.$super('doesNotExist') compiles.

Override files loaded lazily (D21)

Many plugins keep each override in its own file and load it with () => import(). SwagCommercial does this for 152 of its 246 overrides. A new helper gives those files the same types:

// sw-sales-channel-detail.override.ts
export default Shopware.Component.wrapOverrideConfig('sw-sales-channel-detail', {
    methods: {
        getLoadSalesChannelCriteria() {
            const criteria = this.$super('getLoadSalesChannelCriteria');
            criteria.addAssociation('themes');
            return criteria;
        },
    },
});

// index.ts
Shopware.Component.override('sw-sales-channel-detail', () => import('./sw-sales-channel-detail.override'));

The helper returns the config unchanged. If the file was wrapped for another component than the one it overrides, TypeScript reports an error.

Name helpers

  • AdminApi.BlockName<'sw-sales-channel-detail'>, AdminApi.SuperName<N>, AdminApi.Instance<N>
  • AdminApi.RouteName, AdminApi.MiddlewareRouteName, AdminApi.RouteParams<R>
  • AdminApi.SnippetKey, AdminApi.PositionIdentifierName, AdminApi.DataSetId
  • Setting strictPublicApi: true in AdminApi.Options hides private components and mixins from these helpers.

admin:check-extensions

Most plugins are JS and Twig, which TypeScript does not check. The extended command covers them in 9 steps:

  1. Find every core name the plugin uses as a string: override and extend targets, overridden members, $super('…') calls, block names in templates, route names, $t keys, position identifiers and data set ids.
  2. Write each use as a typed constant, with the plugin file and line as a comment.
  3. Type-check those constants against current.d.ts and against major.d.ts, and map each error back to the plugin line.
  4. Warn about uses of @private or @deprecated items.
  5. Warn when an override defines a method the target does not have, which happens after a rename in core.
  6. Report a lazy override whose wrapped target differs from the overridden component.
  7. Check the context of every overridden block: variables the override uses must be scope variables of the block, and an override that starts with v-else-if or v-else needs a block that follows an open v-if chain.
  8. Check filter and directive names, acl.can keys and privilege parents, registry lookups and groups, event bus names, feature flag names, $refs reads, and in plugin SCSS the ~scss/ variables, mixins and .sw-* selectors. A missing class is a warning.
  9. Warn about $parent access and about imports from src/, and accept both {% parent %} and {{ parent() }}.
const _1: AdminApi.BlockName<'sw-sales-channel-detail'> = 'sw_sales_channel_detail_content_tab_theme'; // .../sw-sales-channel-detail.html.twig:1

The Storefront bundle overrides sw_sales_channel_detail_content_tab_theme. That block exists only in the current flag state, so the check against major.d.ts fails. This is a real result from the example snapshot.

Upgrade report

With --target=6.8 the same command answers "how much work is the 6.8 upgrade?" while the shop still runs 6.7 (D34). Every finding names its change pattern and is either actionable now, because the replacement already exists, or at upgrade, because it depends on the new version. The output comes as text, JSON for scripts and coding agents, or SARIF for GitHub code scanning.

MyPlugin · target 6.8 · 14 findings

actionable now (9)
  Rename (7, codemod)                 4 methods, 3 blocks
  New required parameter (2)          2 calls

at upgrade (5)
  Block move (3)                      3 overrides without {% parent %}
  Parameter removal (2)               2 overrides read a removed parameter

MyPlugin  current: ok  6.8: 14 findings (7 with codemod)

Findings are warnings by default. --fail-on=actionable lets plugin CI stop new uses without failing on changes the plugin cannot make yet. administration:upgrade-extensions --target=6.8 applies the codemods on the current version, because each of them produces code that runs on both versions (D35). A plugin is ready for 6.8 when both targets report nothing; the report covers names, not behaviour inside methods.

Limits and migration

  • JS members are typed as any, so TypeScript checks names and argument counts, not value types.
  • A typo in the target name falls back to the untyped signature. admin:check-extensions reports unknown targets.
  • A computed override that returns this.$super(…) may need a return type (TS7023). We have not reproduced this yet.
  • With the snapshot loaded, override('<known name>', () => import('./plain')) becomes a type error until the file uses wrapOverrideConfig. The upgrade notes have to say so.
