# Administration public API snapshot: format

This file defines the format of the generated public API snapshot (issue #22591).
It is the single source of truth for the generator, the break check, the fixtures and the golden files.
The decisions D1 to D24 and the break taxonomy live in `PUBLIC_API_SNAPSHOT_PLAN.md`.

Everything below `public-api/` is generated by `composer admin:generate-public-api`, except these hand-written files:

- `FORMAT.md`, this file.
- `.gitattributes`, which collapses the generated files in PR diffs.
- `_base/admin-api.d.ts`, the base types and plugin helpers.
- `accepted-breaks.json`, the intended breaks (D14).
- `_excerpt/route-component-stubs.d.ts`, which exists only while the committed snapshot is a hand-written excerpt, see "Entry points".
  The generator never writes it, and the first generated snapshot deletes the `_excerpt/` folder.

One hand-written file lives outside `public-api/`:
`scripts/generate-public-api/__fixtures__/.gitattributes` collapses the expected output of the fixtures (`expected/**`) in PR diffs the same way.

The snapshot has two outputs per source unit:

- A `.d.ts` file, the machine contract.
  Plugins compile against it, and the break check reads it.
- An `.api.md` file, the report for reviewers.
  It reads like a declaration outline and merges both flag states.

Both are marked `linguist-generated`, so GitHub collapses them in PR diffs.
Reviewers start with the summary and the annotations of the break check (see "CI"), and open an `.api.md` file when they need the full outline.

## Folder layout and file split

The snapshot mirrors `src/`.
One snapshot unit sits at the path of the source file that declares it, without the leading `src/`.

Paths in this table are relative to `public-api/`.

| Path | Content |
|---|---|
| `FORMAT.md` | This file, hand-written |
| `.gitattributes` | Hand-written |
| `accepted-breaks.json` | Hand-written, intended breaks (D14) |
| `_base/admin-api.d.ts` | Hand-written base types and plugin helpers |
| `current.d.ts` | Entry point, flag state "current" |
| `major.d.ts` | Entry point, flag state "major" |
| `index.json` | Machine index for build and lint tools (D15) |
| `core/shopware.d.ts` and `.api.md` | The `Shopware` global object |
| `core/virtual-modules.d.ts` and `.api.md` | The `shopware:*` modules |
| `core/service/<file>.d.ts` and `.api.md` | Services, one file per registering source file |
| `app/store/<file>.d.ts` and `.api.md` | Pinia stores, one file per store source file |
| `app/mixin/<name>.d.ts` and `.api.md` | One file per `Mixin.register` |
| `app/component/<path>/<name>.d.ts` and `.api.md` | Components registered in `src/app/component/index.ts` |
| `app/snippet.d.ts` and `.api.md` | Keys of `src/app/snippet/en.json` |
| `module/<dir>/module.d.ts` and `.api.md` | `Module.register` and all named routes of the module |
| `module/<dir>/snippet.d.ts` and `.api.md` | Keys of `src/module/<dir>/snippet/en.json` |
| `module/<dir>/<path>/<name>.d.ts` and `.api.md` | One file per `Component.register`, `Component.extend` or native `.vue` |
| `module/<dir>/<path>/<name>.major.d.ts` | Only when the major state of that unit differs |
| `types/<path>.d.ts` and `.api.md` | Referenced source types, one file per source file (D16) |

Path rules:

- A component file is named after the registered component name and sits in the parent directory of its config directory.
  `src/module/sw-sales-channel/page/sw-sales-channel-detail/index.js` becomes `module/sw-sales-channel/page/sw-sales-channel-detail.d.ts`.
- A native base SFC `sw-x.vue` or `sw-x/index.vue` follows the same rule.
- Two names that share one config each get their own file.
- A core-internal `Component.override` gets its own file at the path of the override source, for example `module/sw-sales-channel/component/structure/sw-admin-menu-extension.d.ts`.
- A snippet directory `<dir>/snippet/en.json` becomes `<dir>/snippet.d.ts`.
- A referenced type from `src/<path>.ts` goes to `types/<path>.d.ts`, for example `types/app/store/notification.store.d.ts`.
- Moving a source directory renames the snapshot file.
  The classifier keys on names, never on paths, so a move alone is not a finding.
- Jest mocks (`_mocks_`, `__mocks__`), specs and fixtures are never part of the snapshot.

Every `.d.ts` file has an `.api.md` next to it, except the entry points, `_base` and `_excerpt`.

## Common rules

### Generated header

Every generated `.d.ts` file starts with a header of `//` lines and one blank line.
The header has a fixed line order, and each line has one of the exact texts below.
`<name>` is the file name without `.d.ts`, the flag names are those of "Major-flag snapshot".

1. Always: ``// Generated by `composer admin:generate-public-api`. Do not edit.``
2. The flag state, one of:
   - `// Flag state: current (v6.8.0.0 off).` in `<name>.d.ts` of a unit that has a major copy.
   - ``// Flag state: major (v6.8.0.0 and every flag with `major: v6.8.0.0` on).`` in that major copy, `<name>.major.d.ts`.
   - ``// Flag state: current (v6.8.0.0 off). The major state is identical, so there is no `<name>.major.d.ts`.`` in a unit without a major copy.
   - `// Flag state: both. Snippet files do not depend on feature flags.` in snippet files, which are never split.
3. `// Source: <path>`, the file the registration imports, or the source file of a snippet or type unit.
   For a native component it is the registration shim, see "Native setup SFCs".
4. `// SFC: <path>`, only for native components: the `.vue` file with the script and the template.
5. `// Template: <path>`, only for Options API components with a Twig template.
6. `// Referenced source types (D16): a copy for diffs and the break check. The contract files keep their own references.`, only in `types/` files.

Example, the header of `sw-sales-channel-detail.d.ts`, which has a major copy:

```ts
// Generated by `composer admin:generate-public-api`. Do not edit.
// Flag state: current (v6.8.0.0 off).
// Source: src/module/sw-sales-channel/page/sw-sales-channel-detail/index.js
// Template: src/module/sw-sales-channel/page/sw-sales-channel-detail/sw-sales-channel-detail.html.twig
```

The entry points have their own header, see "Entry points".

Every `.d.ts` file is a global script with no `import` or `export`.
It only adds entries to the open interfaces in `declare namespace AdminApi`, and native components also to `ComponentPublicApiMapping`.
References to source types use type-only `import('src/...')` expressions.

### Determinism

- Map keys and report lines are sorted by codepoint (`a < b`), never by locale.
- Report sections come in a fixed order, see "Report layout".
- Mixins and method parameters keep their declaration order.
- Paths are relative to the Administration root.
- No timestamps, versions, absolute paths or line numbers in committed files.
  Line numbers appear only in the break check output, the annotations and the HTML page.
- `.d.ts` files are indented with four spaces, `.api.md` outlines with two spaces per level.
- Line endings are LF, and every file ends with one newline.
- Two runs on the same commit produce byte-identical output.

### Printing the `.d.ts` files

One fixed printing rule keeps every diff line-based:

- Every member of a registry entry goes on its own line, ending with `;`.
  This covers component, mixin, module, route, override, service and store entries.
- Every key of these objects goes on its own line, ending with `;`:
  `$meta`, `props`, `emits`, `slots`, `inject`, `provide`, `data` (nested object literals included), `computed`, `methods`, `blocks`, `positionIdentifiers`, `dynamicPositionIdentifiers`, `dataSets`, `setup`, `setup.public`, `setup.private`, `navigation`, `state`, `getters` and `actions`.
- The lists `crossings` and the location tuples of `positionIdentifiers`, `dynamicPositionIdentifiers` and `dataSets` put each element on its own line, followed by a comma.
- Leaves stay on one line: the `mixins` tuple, an emit payload tuple, one crossing tuple, one location object, a route's `params` object, and the helper types `Prop<...>`, `Block<...>`, `Slot<...>` and `SetupBinding<...>`.
- An empty object is `{}` and an empty list is `readonly []`, both inline.
- A JSDoc tag stands on its own line directly above its key.
- Types copied from source keep the line breaks of the source declaration, re-indented to four spaces per level.
  This applies to TS annotations and to the declarations in `types/` files.

So a new member, a new block, a moved block and a second location of a position identifier are each one line in the `.d.ts` diff.

### Type rendering

Types are copied from source syntax, never printed by the type checker.

- JS members have no declared types, so they render as `AdminApi.Untyped`, an alias of `any`.
  Nested object literals in `data()` keep their keys, for example `productComparison.templateName`.
- JS method parameters render as `name: AdminApi.Untyped`, a parameter with a default as `name?: AdminApi.Untyped`, a rest parameter as `...name: AdminApi.Untyped[]`.
  A destructured parameter renders as `arg<position>`, for example `arg1?: AdminApi.Untyped`.
  JS returns render as `AdminApi.Untyped`, and as `Promise<AdminApi.Untyped>` for `async` methods.
  Code inside a method never changes the snapshot.
- JS prop constructors map to types:
  `String` to `string`, `Number` to `number`, `Boolean` to `boolean`, `Object` to `AdminApi.JsObject`, `Array` to `AdminApi.JsArray`, `Function` to `AdminApi.JsFunction`.
  Constructors from `Shopware.Data` map through a fixed table, for example `Criteria` to `import('src/core/data/criteria.data').default`.
  Anything else, and a prop without `type`, is `AdminApi.Untyped`.
- TS members keep their annotation text.
  An unannotated TS member is `AdminApi.Untyped`.
  Imported names become `import('src/...').Name`.
  A type that is not exported from its source file is inlined from its declaration text.
- Third-party types stay references, for example `typeof import('vue')`.
  Vue's two-parameter forms are normalised: `Ref<T, T>` renders as `Ref<T>`, `ModelRef<T, ...>` as `ModelRef<T>`.
- `Untyped` to a concrete type is never a break, so a JS to TS migration does not show as an API change in the classifier.

## Components

One entry in `AdminApi.Components` per registered name.
Example: an excerpt of `module/sw-sales-channel/page/sw-sales-channel-detail.d.ts`, without the header.
The `// ...` lines stand for members left out here; the golden file has all of them.

```ts
declare namespace AdminApi {
    interface Components {
        'sw-sales-channel-detail': {
            $meta: {
                kind: 'register';
                lang: 'js';
                visibility: 'public';
                visibilitySource: 'default';
                extends: null;
            };
            props: {};
            emits: {};
            slots: {};
            mixins: readonly ['notification', 'placeholder'];
            inject: {
                acl: 'acl';
                // ...
                repositoryFactory: 'repositoryFactory';
            };
            provide: {
                /** @deprecated tag:v6.8.0 - Will be removed */
                swSalesChannelDetailGetAgenticCommerceExportConfig: AdminApi.Untyped;
            };
            data: {
                isLoading: AdminApi.Untyped;
                productComparison: {
                    // ...
                    templateName: AdminApi.Untyped;
                };
                // ...
            };
            computed: {
                // ...
                isProductComparison: AdminApi.Untyped;
                // ...
            };
            methods: {
                // ...
                getLoadSalesChannelCriteria(): AdminApi.Untyped;
                // ...
                onSave(): Promise<AdminApi.Untyped>;
                // ...
            };
            blocks: {
                // ...
                sw_sales_channel_detail_content_tabs: Block<'sw_sales_channel_detail_content', 'afterIf'>;
                // ...
            };
            crossings: readonly [];
            positionIdentifiers: {
                'sw-sales-channel-detail': readonly [
                    { kind: 'tabs'; host: 'sw-tabs'; block: 'sw_sales_channel_detail_content_tabs' },
                ];
            };
            dynamicPositionIdentifiers: {};
            dataSets: {
                'sw-sales-channel-detail__salesChannel': readonly [
                    { path: 'salesChannel' },
                ];
            };
        };
    }
}
```

Every key of `ComponentShape` is always present, empty ones as `{}` or `readonly []`.

| Surface | Representation |
|---|---|
| Component name | The registry key. `$meta.kind` is `register` or `extend`, `$meta.extends` names the parent. |
| Props | `Prop<Type, Required, Default>`, default is `none`, `literal` or `factory`. |
| Emits | Event name to payload tuple. Array-form `emits` gives `readonly AdminApi.Untyped[]`. |
| Slots | Slot name to `Slot<Scope>`, taken from `<slot>` elements of the template, with the enclosing block. |
| Mixins | Registered mixin names in declaration order. Members live in the mixin file. |
| Inject | Local key to injected key. Types resolve through `AdminApi.Service<Key>`, so typing a service never changes a component file. |
| Provide | Provided key to value type. |
| Data | Keys of the `data()` return literal, nested object keys included. |
| Computed | Computed name to value type. Every computed is a `$super` target. |
| Methods | Method signatures. Every method is a `$super` target. |

Watchers, lifecycle hooks, `shortcuts`, `metaInfo` and route guards are not part of the snapshot.

### Reaching members through `$super`

The snapshot does not copy inherited members.
An extend child lists only its own members, and `$meta.extends` points to the parent.
The helper types in `_base` resolve the extends chain and the listed mixins when a plugin types `this`.
`$super` reaches methods and computed properties of the component and its extends chain, not mixin members.

### Core-internal overrides

A core `Component.override` gets an entry in `AdminApi.ComponentOverrides`, keyed `<target> @ <source directory without src/>`.

```ts
declare namespace AdminApi {
    interface ComponentOverrides {
        'sw-admin-menu @ module/sw-sales-channel/component/structure/sw-admin-menu-extension': {
            target: 'sw-admin-menu';
            source: 'src/module/sw-sales-channel/component/structure/sw-admin-menu-extension/index.js';
            mixins: readonly [];
            inject: {
                acl: 'acl';
            };
            data: {};
            computed: {
                canViewSalesChannels: AdminApi.Untyped;
            };
            methods: {};
            blocks: {
                sw_admin_menu_navigation_main: Block<'sw_admin_menu_body', 'keepsParent'>;
            };
        };
    }
}
```

The helper types add these members and blocks to the target, so `this` and `AdminApi.BlockName<'sw-admin-menu'>` include them.
The target's own file does not change when a core override changes.

## Native setup SFCs (D17)

A native base component is a `.vue` file with `<script setup>` and `swDefinePublic`.
Its entry has `$meta.lang: 'vue'` and the extra key `setup`, checked against `AdminApi.NativeComponentShape`.
The core Administration ships no native SFC yet, so the example comes from the fixture `native-sfc` (see "Test fixtures").

The fixture registers the component in `src/app/component/index.ts` with `Component.register('sw-native-example', () => import('./base/sw-native-example'))`.
The import resolves to the registration shim `src/app/component/base/sw-native-example/index.ts`, the re-export the SFC migration codemod writes:

```ts
/**
 * @sw-package framework
 * @public
 */
export { default } from './sw-native-example.vue';
```

The `.vue` file has no export of its own, so the JSDoc on this re-export is the export tag of the component.
With `@private` instead of `@public`, D13 makes the whole component private, `visibilitySource` becomes `export`, and every outline line gets `[private]`.

Fixture source `src/app/component/base/sw-native-example/sw-native-example.vue`:

```vue
<template>
    <sw-block name="sw_native_example">
        <button type="button" @click="emit('save', count)">
            <sw-block name="sw_native_example_label">{{ displayedLabel }}</sw-block>: {{ count }}
        </button>
    </sw-block>
</template>

<script setup lang="ts">
import { computed, ref } from 'vue';

const props = withDefaults(defineProps<{ label?: string }>(), { label: 'Counter' });
const emit = defineEmits<{ save: [value: number] }>();
const displayedLabel = computed(() => props.label);
const count = ref(1);

function increment(step: number): void {
    count.value += step;
}

swDefinePublic({ count, increment });
</script>
```

Expected outline in `sw-native-example.api.md`:


Rules:

- Props, emits and slots come from `defineProps`, `withDefaults`, `defineEmits`, `defineSlots` and `<slot>` elements.
  `defineModel('x')` adds the prop `x`, the emit `update:x` and a setup binding of kind `model`.
- `setup.public` lists the `swDefinePublic` entries, `setup.private` every other top-level runtime binding.
  The macro bindings `props`, `emit` and `slots` are left out, because their content is already in `props`, `emits` and `slots`.
- Each binding records its kind: `ref`, `model`, `computed`, `writable-computed`, `reactive`, `function` or `value`.
  The kind decides how `createExtendableSetup` merges an override, so a kind change is a break.
- `data`, `computed` and `methods` hold the public entries unwrapped, the way Options API overrides reach them through `this` and `$super`.
  Refs and models go to `data`, computed refs to `computed`, functions to `methods`.
- `ComponentPublicApiMapping` gets one entry per native component, so native overrides (`overrideComponentSetup`, `useSwPreviousState`) see the public bindings at the top level and the private ones under `_private`.
- `<sw-block name>` elements are blocks like Twig blocks and share the `blocks` map.
  A dynamic `:name` cannot be enumerated and is reported as a `note dynamic-block`.
- Visibility follows the registration shim (`index.js` or `index.ts`), because the `.vue` file has no export.
  The shim is the `source` header line, the `.vue` file the `sfc` header line, and `visibility-source export` refers to the shim.
  D13 applies to it like to any other component.
  When the registration imports the `.vue` file directly, without a shim, `source` is the `.vue` file, there is no `sfc` line, and only a registration comment can make the component private.
- An HTML comment `<!-- @deprecated tag:vX ... -->` directly before an `<sw-block>` marks that block.

An HTML element cannot cross `<sw-block>` boundaries in a valid SFC template, so native components always have `crossings: readonly []`.

## Blocks

`blocks` is a flat map from block name to `Block<Parent, Facets>`.
`Parent` is the directly enclosing block, `null` at the root.
A block move is therefore one changed line in the `.d.ts`, and a sibling reorder is no change.

```ts
blocks: {
    sw_sales_channel_detail: Block<null>;
    sw_sales_channel_detail_content_tab_theme: Block<'sw_sales_channel_detail_content_tabs', 'empty' | 'afterIf'>;
    sw_sales_channel_detail_content_tabs: Block<'sw_sales_channel_detail_content', 'afterIf'>;
};
```

Facets:

- `empty`: the block has no content and only exists as a hook.
- `inherited`, `replaced`, `keepsParent`: see "Extend children" below.
- `repeated`: the template declares the block more than once under this parent, for example `sw_button_router_link_content` in `sw-button-deprecated`.
- `afterIf` and `scope:<name>`: see "Block context" below.

Facets are printed in a fixed order: origin, `repeated`, `empty`, `afterIf`, then the `scope:` facets sorted by name.

A name that occurs under several parents gets a union of parents, for example `Block<'sw_review_list' | 'sw_review_list_content'>`.
The classifier compares the sets of parents.

Twig blocks and native `<sw-block name>` share the map.
Top-level blocks in an extend or override template are references, not declarations.
Block names are keyed by component, never by prefix: `sw_sales_channel_detail_base_general_input_type` is a block of `sw-settings-number-range-detail`.

### Extend children

The generator resolves the Twig extend and writes the effective blocks of the child, because Twig extend resolution cannot be expressed in types.
Each block of the child carries one origin facet:

- `inherited`: taken unchanged from the parent.
- `replaced`: redeclared by the child template without `{% parent %}`.
  Its inherited children disappear from the child's map.
- `keepsParent`: redeclared with `{% parent %}`.

A block change in a parent therefore also changes the files of its extend children.
That is intended, because their API changes too.

### Block context

An override replaces the content of a block, but it runs in the place of the block.
Two facts about that place are part of the API, because plugin templates depend on them.

**`afterIf`: the block follows an open `v-if` chain.**
The element directly before the block, in the same parent element, has `v-if` or `v-else-if`, and no `v-else` closes the chain before the block starts.
An override may then start with `v-else-if` or `v-else` and continue the chain.
Blocks are transparent here: the element before the block may sit inside an earlier sibling block.
Only whitespace and comments may stand between them, as in Vue.

```twig
<sw-tabs-item v-if="isStorefront">…</sw-tabs-item>
{% block sw_sales_channel_detail_content_tab_theme %}{% endblock %}
```

```ts
sw_sales_channel_detail_content_tab_theme: Block<'sw_sales_channel_detail_content_tabs', 'empty' | 'afterIf'>;
```

**`scope:<name>`: a template variable the block can use.**
Every variable that an enclosing element of the block introduces: the aliases of `v-for` (`item`, `index`, also destructured names), and the props of `v-slot`, `#name="…"` and `slot-scope`, also destructured names.
Variables of enclosing blocks count, because the override sits inside them.
Component members (props, data, computed, methods) are not scope variables; they are in their own maps.

```twig
<li v-for="(item, index) in items">
    {% block sw_example_list_item_label %}{{ item.label }}{% endblock %}
</li>
```

```ts
sw_example_list_item_label: Block<'sw_example_list_item', 'scope:index' | 'scope:item'>;
```

In the report both appear as markers: `sw_example_list_item_label  [scope: index, item]`, `sw_sales_channel_detail_content_tab_theme  [empty] [after v-if] [until v6.8.0]`.
An extend child takes the context of the place where the block sits in the effective template, so an `[inherited]` block keeps the context of its parent.
Native `<sw-block>` elements follow the same rules.

Findings:

- A scope variable that the block had at base and lacks at head is a break (`block_scope_missing`), because plugin overrides that use it fail at render time.
- A block that had `afterIf` at base and lacks it at head is a break (`block_if_context_lost`), because overrides that start with `v-else-if` or `v-else` no longer compile.
- A new scope variable or a new `afterIf` is not a finding; it shows in the snapshot diff.

### Elements that cross block boundaries (D18)

`crossings` lists every HTML element opened in one block and closed in another (#20959).

```ts
crossings: readonly [
    readonly ['div', 'sw_order_detail_header', 'sw_order_detail_header_label_manual_order'],
];
```

- `(root)` stands for "outside any block".
- One crossing is one entry, named by the block that opens the element and the block that closes it.
  Blocks in between that become unbalanced are not listed separately.
- Void and self-closing elements never cross.
  Nested elements with the same tag name are matched by depth, not by name.
- Crossings that exist on trunk are part of the snapshot from its first commit, for example in `sw-sales-channel-detail-domains`:

  ```text
  crossings
    <template>  sw_sales_channel_detail_domains -> sw_sales_channel_detail_domains_grid
  ```

- The break check reports only crossings that are new at head.
  A baseline crossing that disappears is `info` (`crossing_resolved`).

#### `v-if` chains that cross block boundaries

A `v-if` chain whose members sit in different blocks is a crossing too, with `v-if` in place of the element name.
Overriding the block with the `v-if` member without `{% parent %}` leaves the `v-else-if` or `v-else` in the other block without its partner, and the template no longer compiles.
Trunk has one in `sw-order-detail`:

```twig
{% block sw_order_detail_header_title %}
<div v-if="orderIdentifier" class="sw-order-detail__header">…</div>
{% endblock %}

{% block sw_order_detail_header_title_new %}
<h2 v-else>…</h2>
{% endblock %}
```

```ts
crossings: readonly [
    readonly ['v-if', 'sw_order_detail_header_title', 'sw_order_detail_header_title_new'],
];
```

```text
crossings
  v-if  sw_order_detail_header_title -> sw_order_detail_header_title_new
```

- Each member counts in the block where its element opens.
  One crossing is one pair of neighbouring members in different blocks.
- A pair is no crossing when the block of the earlier member contains the block of the later one.
  Overriding the outer block replaces both, and overriding the inner block only ends the chain early.
- The same baseline rule applies: only new chain crossings are findings (`if_chain_crosses_block`), and a disappearing one is `crossing_resolved`.
- The location of the finding is the head line of the continuing element.

## Position identifiers and data sets

Both live in the component entry of the template or config that declares them.
A key maps to a tuple of locations, so an id used twice in one component has two locations.

```ts
positionIdentifiers: {
    'sw-sales-channel-detail': readonly [{ kind: 'tabs'; host: 'sw-tabs'; block: 'sw_sales_channel_detail_content_tabs' }];
};
dataSets: {
    'sw-sales-channel-detail__salesChannel': readonly [
        { path: 'salesChannel' },
    ];
};
```

- `kind` is `componentSection`, `card`, `tabs`, `teaserPopover` or `attribute` (a host without a `positionIdentifier` prop).
- `card` hosts also provide `<id>__before` and `<id>__after`.
  `AdminApi.PositionIdentifierName` derives them.
- A bound id that is not a string literal goes into `dynamicPositionIdentifiers`, keyed by its source expression, for example `` `sw-generic-custom-entity-detail-tab-${card.name}` ``.
- A data set id built at runtime is keyed by its source expression as well.
- An extend child lists the position identifiers of its effective template, like its blocks.

The global unions `AdminApi.PositionIdentifierName` and `AdminApi.DataSetId` are derived from all components, so no global list file is needed.

## Mixins

One entry in `AdminApi.Mixins` per `Mixin.register`, at `app/mixin/<name>.d.ts` or in the module that registers it.
The entry has `$meta`, `props`, `data`, `computed` and `methods`.
A factory mixin such as `discard-detail-page-changes` gets `methods: {}` and a `@factory` JSDoc tag.

## Modules and routes

`module/<dir>/module.d.ts` holds one `AdminApi.Modules` entry and every named route of the module in `AdminApi.Routes`.

```ts
'sw.sales.channel.detail.agenticFile': {
    module: 'sw-sales-channel';
    path: '/sw/sales/channel/detail/:id/agentic-files/:fileName(.*)';
    params: { id: string; fileName: string };
    component: 'sw-sales-channel-detail-agentic-file';
    parent: 'sw.sales.channel.detail';
    redirect: null;
    alias: null;
    coreRoute: false;
    hasPropsMapper: false;
    privilege: 'sales_channel.viewer';
    parentPath: 'sw.sales.channel.list';
    appSystemView: null;
};
```

- Route names follow `module.factory.ts`: the route prefix plus the route key, children appended with a dot.
- `path` is the full path vue-router sees, custom regexes verbatim.
- Only routes with `parent: null` reach a `routeMiddleware`.
  `AdminApi.MiddlewareRouteName` is that union.
- `props` functions are code, so only `hasPropsMapper` is recorded.
- Routes from `src/app/route` live in `app/route.d.ts`.
- Routes created at runtime by the Extension SDK tabs are not part of the snapshot.

## Snippet keys (D19)

`<dir>/snippet.d.ts` lists every key of `<dir>/snippet/en.json`, flattened with dots, with its signature.
Texts are never part of the snapshot.

```ts
'sw-sales-channel.detail.messageSaveSuccess': Snippet<'name'>;
'sw-sales-channel.detail.products.buttonAddProducts': Snippet<'productCount', 3>;
'sw-sales-channel.list.title': Snippet;
```

- `Snippet<Params, Forms>` records the named placeholders and the number of `|` separated plural forms.
  Positional placeholders such as `{0}` count as names, literal interpolations such as `{'@'}` are ignored, arrays use `'array'`.
- The signature is taken from the English text only.
  A translation that uses other placeholders is a translation bug, not an API change.
- A key belongs to the file that defines it, also when it is in a foreign namespace such as `global` or `sw-privileges`.
- A key defined in two files appears in both with the same signature.
  Different signatures for one key fail the generator.
- Only directories the server-side `SnippetFinder` loads are included.

## Shopware object, services, stores and shopware:* modules

These follow the same rules: one entry per runtime name, the declared type copied from source, visibility from tags.

- `core/shopware.d.ts` declares `AdminApi.ShopwareObject`, the tree of `Shopware.*` members down to depth 3.
  Members are plain properties, so `@private`, the source of the tag (`@visibilitySource export`), getters and frozen members (`InAppPurchase`) are JSDoc tags on the member.
- `AdminApi.Services` has one entry per registered service name, including the API services registered by `this.name`.
  `declared` is `typed`, `any` (`$TSFixMe`) or `untyped` (registered, but missing from `ServiceContainer`).
  `registration` is `eager`, `module`, `initializer` or `api-service`.
  The file is the source file that registers the service.
- `AdminApi.Stores` has one entry per store id, with `style` (`options` or `setup`) and separate `state`, `getters` and `actions`.
  Stores registered without a `PiniaRootState` entry are `declared: 'untyped'`.
- `core/virtual-modules.d.ts` keeps the `declare module 'shopware:*'` blocks, sorted by specifier.
  The same registry is in `index.json`, see below.
- Open global interfaces that plugins augment (`ServiceContainer`, `PiniaRootState`, `MixinContainer`, `CustomShopwareProperties`) are never redeclared.
  The snapshot only references them.
  `ComponentPublicApiMapping` is the one exception: native components add their own entry, see "Native setup SFCs".

## Referenced types (D16)

A snapshot entry that references a type from `src/`, directly or through another referenced type, makes that type part of the snapshot.
Examples are `NotificationType` in the `notification` mixin, the service classes behind `ServiceContainer` entries and the global `Entity` alias.
A change to such a type is then a diff and a finding, even though no component file changes.

- `types/<path>.d.ts` holds a copy of every referenced declaration of `src/<path>.ts`, and only those.
  Unreferenced exports of the same file are not copied.
- The copy lives in `declare namespace AdminApi.Src.<path>`.
  The path is taken relative to `src/` without its extension, each segment becomes an identifier with `.` replaced by `$` and `-` replaced by `_`.
  `src/app/store/notification.store.ts` becomes `AdminApi.Src.app.store.notification$store`, `src/global.types.ts` becomes `AdminApi.Src.global$types`.
  Two paths that map to the same namespace fail the generator.
- Interfaces and type aliases are copied with their type parameters.
  A class is copied as an interface of its public instance members; `private`, `protected` and `#` members are left out.
  A default export is copied under its local name.
- Members are sorted by name, with index signatures first.
  A reference to a declaration of the same file keeps its name, a reference to another source file becomes `AdminApi.Src.<path>.<Name>`.
- Types of the installation-specific entity schema (`EntitySchema.*`) and third-party types stay references and are never copied.
- The contract files keep their `import('src/...')` references and global names.
  The copy only exists so that the diff and the break check see the change, and plugin values keep the identity of the real source type.
- A referenced type follows D1 by its own tags: it is public unless it or its file export carries `@private`.

Example: an excerpt of `types/app/store/notification.store.d.ts`, without the header.
The `// ...` lines stand for members left out here.

```ts
declare namespace AdminApi.Src.app.store.notification$store {
    /** @private */
    interface NotificationType {
        [key: string]: string | boolean | object | number | undefined;
        // ...
        autoClose?: boolean;
        // ...
        variant?: NotificationVariant;
        // ...
    }

    /** @private */
    type NotificationVariant = 'neutral' | 'info' | 'attention' | 'critical' | 'positive';
}
```

## Visibility, deprecation and experimental markers

### `@private` (D1, D2, D13)

Everything without `@private` is public (D1).
Private parts stay in the same file (D2).

- Component, mixin, module, service and store entries carry `$meta.visibility` and `$meta.visibilitySource`.
  The `.d.ts` also puts a `/** @private */` tag on the registry key.
- `@private` on a component export, a mixin export or a whole component makes everything of it private, including the registered name, all members and all blocks (D13).
  This also covers a component whose export is the native registration shim.
- `visibilitySource` is `default` (no tag), `export` (JSDoc on `export default`), `registration` (comment directly above the register call), `member` (tag on the member) or `structural` (native SFC binding missing from `swDefinePublic`).
- Only a comment directly attached to the statement counts, as in the `private-feature-declarations` ESLint rule.
  File-header comments of registration functions, for example in `src/app/component/index.ts`, do not count.
- When export and registration disagree, the stricter tag wins, and the report adds a `visibility-conflict` note.
- A member with its own `@private` gets a `/** @private */` JSDoc tag.
- A private entry covers all its members and blocks.
  The break check reports every change inside it in the `private` group and never blocks on it.

Consequences for the historical cases: `sw-custom-field-set-renderer` (#17339) and the UI shell components of #15271 are `@private` on their export, so their block changes are `private` findings.

### `@deprecated tag:vX` and `@experimental`

- JSDoc tags are copied verbatim, including the message, so plugin IDEs show them.
- A `// @deprecated` line comment on a member is normalised to JSDoc.
- A Twig comment `{# @deprecated ... #}` directly before `{% block %}` belongs to that block.
  Otherwise a comment that is the first child of a block belongs to that enclosing block.
  In `sw-sales-channel-detail` the comment inside `..._tab_export_template` marks `..._tab_product_comparison`, and the comment inside `..._agentic_commerce_deprecation_banner` marks the banner block.
- An HTML comment `<!-- @deprecated ... -->` in a native template follows the same rules.
- `@experimental stableVersion:vX feature:FLAG` is copied the same way.
- Only source markers announce a removal (A2).
  An entry in `UPGRADE-*.md` or `RELEASE_INFO-*.md` does not.

## Major-flag snapshot

There are two flag states (D6):

- `current`: `v6.8.0.0` off.
- `major`: `v6.8.0.0` on, plus every flag with `major: v6.8.0.0` in `src/Core/Framework/Resources/config/packages/feature.yaml`.

The generator evaluates feature checks three-valued and prunes dead branches per state:

- `feature.isActive('<flag>')` in `v-if`, `v-else-if` and `v-else` chains, combined with `!`, `&&` and `||`.
- A computed property whose body is only `return this.feature.isActive('<flag>')`.
- `Feature.isActive(...)` around `Component.register` and in module manifests.
- Flag names are normalised, so `V6_8_0_0` equals `v6.8.0.0`.
- Any other condition counts as live in both states.
- The same block name in mutually exclusive branches is kept per branch.

Deprecated items stay in both states, because the flag does not delete code.
The exception is a deprecated item inside a flag-off branch (`v-else` of `feature.isActive('v6.8.0.0')`): it exists only in the current state, like every other item in that branch.

Storage:

- `<name>.d.ts` always holds the current state.
- `<name>.major.d.ts` exists only when the major state of that unit differs.
  The comparison renders both states and ignores the whole `// Flag state:` line, including the sentence about the major copy.
  It is a full copy, so `major.d.ts` loads one coherent program.
- `current.d.ts` references every `<name>.d.ts`.
  `major.d.ts` references `<name>.major.d.ts` where it exists and `<name>.d.ts` otherwise.
- The `.api.md` merges both states, see below.

### Entry points

`current.d.ts` and `major.d.ts` reference `_base/admin-api.d.ts` first, then every snapshot file of their state, sorted by path.
They end with the consistency checks of the drift check (`_CheckComponents` to `_CheckReferences`), see "CI".
Their headers:

```ts
// Generated by `composer admin:generate-public-api`. Do not edit.
// Entry point of the current flag state (v6.8.0.0 off). Every snapshot file, sorted by path.
```

```ts
// Generated by `composer admin:generate-public-api`. Do not edit.
// Entry point of the major flag state (v6.8.0.0 and every flag with `major: v6.8.0.0` on).
// Takes `<name>.major.d.ts` where it exists and `<name>.d.ts` otherwise.
```

The committed golden snapshot is still a hand-written excerpt.
Its entry points carry one more header line, `// Example excerpt: the generated file references every snapshot file of the Administration.`, and reference `_excerpt/route-component-stubs.d.ts` after `_base`.
That file holds minimal entries for the components that the excerpt's routes name but whose snapshot files are not written yet.
Each stub has the real `$meta` of the component and empty members, so the reference checks pass.
The generator writes neither the extra header line nor the stub reference.

## Report layout

Every `.api.md` has a heading, a generated note, three intro lines and one `text` code fence with the outline.
Example: an excerpt of `sw-sales-channel-detail.api.md`.
The indented `...` lines stand for lines left out here; the golden file has all of them.

````text
# Component sw-sales-channel-detail

<!-- Generated by `composer admin:generate-public-api`. Do not edit. -->

API report of component `sw-sales-channel-detail` in both flag states.
Contract: `sw-sales-channel-detail.d.ts` (current) and `sw-sales-channel-detail.major.d.ts` (major).
Line format and markers: `public-api/FORMAT.md`.

```text
component sw-sales-channel-detail  public  js
  registered src/module/sw-sales-channel/index.js
  source src/module/sw-sales-channel/page/sw-sales-channel-detail/index.js
  template src/module/sw-sales-channel/page/sw-sales-channel-detail/sw-sales-channel-detail.html.twig

mixins
  notification, placeholder

inject
  acl
  customFieldDataProviderService
  ...

blocks
  sw_sales_channel_detail
    sw_sales_channel_detail_actions
      sw_sales_channel_detail_actions_save
    ...
```
````

The heading and the first intro line depend on the unit kind:

| Unit | Heading | First intro line |
|---|---|---|
| Component | `# Component <name>` | ``API report of component `<name>` in both flag states.`` |
| Mixin | `# Mixin <name>` | ``API report of mixin `<name>` in both flag states.`` |
| Module | `# Module <id>` | ``API report of module `<id>` and its routes in both flag states.`` |
| Core override | `# Override of <target> in <source directory>` | ``API report of the core override of `<target>` in both flag states.`` |
| Module snippets | `# Snippet keys of module <dir>` | ``API report of the snippet keys defined in `<source path>`.`` |
| App snippets | `# Snippet keys of app` | ``API report of the snippet keys defined in `<source path>`.`` |
| Referenced types | `# Types of <source path>` | ``API report of the source types in `<source path>` that the snapshot references, in both flag states.`` |
| Shopware object | `# Shopware object` | ``API report of the `Shopware` global object in both flag states.`` |
| Services, stores | `# Services of <source path>`, `# Stores of <source path>` | ``API report of the services registered in `<source path>` in both flag states.``, the same for stores |
| Virtual modules | `# Virtual modules` | ``API report of the `shopware:*` modules in both flag states.`` |

The second intro line names the contract: ``Contract: `<name>.d.ts` (both flag states).`` for a unit without a major copy, ``Contract: `<name>.d.ts` (current) and `<name>.major.d.ts` (major).`` for a unit with one.
The third is always ``Line format and markers: `public-api/FORMAT.md`.``

### Outline rules

- The first line names the unit: `component <name>  <visibility>  <lang>`.
  `<lang>` is `js`, `ts` or `vue`.
- The header lines below it are indented two spaces, in this order: `extends <parent>` when the component is an extend child, then the paths `registered`, `source`, `sfc` (native only) and `template` (Twig only), then `visibility-source <source>` when the unit is private.
- Sections follow, separated by one blank line, each a header word on its own line and its items indented two spaces.
- Empty sections are left out.
- Every item is on its own line, except `mixins`: the mixin names stay on one line, comma-separated, in declared order, because their order changes the merge result.
- Items are sorted by name, and an item that differs between the states is listed once per state, current before major.
- There is no column alignment anywhere.
- Types render as in the `.d.ts`, with `AdminApi.Untyped` shown as `any`, `AdminApi.JsObject` as `object` and `import('...').Name` as `Name`.
  A type that spans several lines in the `.d.ts` is joined to one line: each line break with its indentation becomes one space, and a `;` directly before a closing `}` is dropped.

### Separators

Two separators make every line parseable:

- One space joins a keyword and its value.
  The keywords are the unit words (`component`, `mixin`, `module`, `override`, `interface`, `type`, `snippets`, `types`, `service`, `store`, `member`), the header words (`extends`, `registered`, `source`, `sfc`, `template`, `visibility-source`, `entity`, `title`, `routes`), `->`, `from` and the kind of a note.
  Examples: `registered src/module/sw-sales-channel/index.js`, `<local> from <serviceKey>`, `-> sw-sales-channel-detail`, `flag-removal-undeprecated block sw_sales_channel_detail_content_tab_theme`.
- Two spaces separate independent fields, and the group of markers from the field before it.
  Markers inside the group are separated by one space, see "Markers".
  Examples: `component sw-sales-channel-detail  public  js`, `sw-sales-channel-detail  tabs  host=sw-tabs  block=sw_sales_channel_detail_content_tabs`, `count: Ref<number>  ref`.
- A field never contains two spaces in a row.
  A field may contain single spaces, for example in a type, a signature, a comma-separated list or a `<keyword> <value>` pair.
- A `key=value` field has no space around `=`, and a marker has no space after `[` or before `]`.

### Component sections

Component sections, in this order:

| Section | Item format |
|---|---|
| `mixins` | `notification, placeholder` |
| `inject` | `acl`, or `<local> from <serviceKey>` when the local name differs |
| `provide` | `key: type` |
| `props` | `name: type` when required, `name?: type` when optional, then `default=literal` or `default=factory` |
| `emits` | `name(payload)`, for example `save(value: number)`; array-form emits give `change(...args: any[])` |
| `slots` | `name  { scope }  block=<enclosing block>` |
| `data` | `name: type`; the parent of a nested object literal renders as `name: object`, and its keys follow indented two more spaces |
| `computed` | `name: type` |
| `methods` | `name(params): returnType` |
| `public` | native only: `name: type  <binding kind>`, functions as `name(params): returnType  function` |
| `private` | native only: like `public`, with `[private]` |
| `blocks` | the block tree, see below |
| `crossings` | the tag in angle brackets, two spaces, then `<opening block> -> <closing block>`, for example `<div>  sw_order_detail_header -> sw_order_detail_header_label_manual_order` |
| `position-ids` | `id  kind  host=<host>  block=<block>` |
| `data-sets` | `id  path=<path>` |
| `notes` | facts for reviewers, see below |

Native components print `public` and `private` instead of `data`, `computed` and `methods`, because those mirror the public bindings.

### Block tree

- Blocks form an indented tree: two spaces per depth level below the `blocks` header, no box-drawing characters.
- Siblings are sorted alphabetically, one block per line.
- A moved leaf block is exactly one removed and one added line.
  A moved subtree changes exactly its own lines.
- A block with several parents appears once under each parent.
- A block that has a different parent in the two states appears under both parents, with `[until v6.8.0]` and `[from v6.8.0]`.

### Markers

Markers follow the item after two spaces, separated from each other by one space, in this order:

1. Block facets: `[inherited]`, `[replaced]`, `[keepsParent]`, `[repeated]`, `[empty]`.
2. Block context: `[after v-if]`, then `[scope: <names>]` with the names sorted and separated by a comma and a space, see "Block context".
3. `[until v6.8.0]` or `[from v6.8.0]` for items that exist in one state.
   The version is the version of the major flag (`v6.8.0.0` gives `v6.8.0`), so the marker stays readable in old commits: `[until v6.8.0]` exists in every release before 6.8.0, `[from v6.8.0]` from 6.8.0 on.
4. `[deprecated tag:vX]`, without the message; the message is in the `.d.ts`.
5. `[experimental]`; the stable version and the feature are in the `.d.ts`.
6. `[private]`.

Every non-blank line of a private entry carries `[private]`: the first line, every header line (`extends`, `registered`, `source`, `sfc`, `template`, `visibility-source`, `entity`, `title`, `routes`) and every item line.
The only lines without it are the section header words (`methods`, `blocks` and so on), which belong to no entry.
In a `types/` file each declaration is its own entry, so the `types <path>` line never carries it.
A private member of a public entry carries `[private]` on its own line only.
A visibility change therefore changes every affected line.

### Notes

`notes` lines are facts for reviewers, never classifications:

- `flag-removal-undeprecated block <name>`: the block exists only in the current state and has no `@deprecated` tag, so its removal in the major is not announced in the source.
- `visibility-conflict`: export and registration tags disagree.
- `duplicate-snippet-key <key>`: the key is also defined in another file.
- `dynamic-block <expression>`: a native `<sw-block :name>` that cannot be enumerated.

The report never contains counts, reverse references ("used by", "extended by") or facts from other files.
Those change for reasons unrelated to the unit and would cause churn and merge conflicts.

## Machine index (D15)

`index.json` is generated from the same model, sorted, for tools that cannot load `.d.ts` files cheaply.
It replaces the four old lists (D10): `blocks-list.json`, `position-identifiers.json`, `data-sets.json` and `shopware-modules.json`.

```json
{
    "components": {
        "sw-sales-channel-detail": {
            "file": "module/sw-sales-channel/page/sw-sales-channel-detail",
            "visibility": "public",
            "extends": null,
            "blocks": ["sw_sales_channel_detail", "sw_sales_channel_detail_actions"]
        }
    },
    "mixins": { "notification": { "file": "app/mixin/notification", "visibility": "private" } },
    "modules": { "sw-sales-channel": { "file": "module/sw-sales-channel/module" } },
    "positionIdentifiers": { "sw-sales-channel-detail": ["sw-sales-channel-detail"] },
    "dynamicPositionIdentifiers": {},
```

- `virtualModules` has the shape of the old `shopware-modules.json`.
- Consumers: `build/vite-plugins/virtual-shopware-modules`, `test/_setup/setup-shopware.js`, the Jest helpers, `eslint-rules/core-rules/replace-top-level-blocks-to-extends.js` and the successor of `meta.spec.js`.

## Plugin consumption

`extension-tooling/admin-types.d.ts` gets one line in its header, directly below `/// <reference types="node" />` and before the first `import`:

```ts
/// <reference types="node" />
/// <reference path="../public-api/current.d.ts" />

import '../src/global.types';
```

TypeScript reads triple-slash directives only at the top of a file, before the first statement.
A reference after an `import` is ignored without a warning, and plugins then fail with `Cannot find namespace 'AdminApi'`.

A new `extension-tooling/admin-types.major.d.ts` is identical but references `../public-api/major.d.ts` at the same place.
A program must load exactly one of the two entry points.
Loading both is silent under `skipLibCheck`, so `admin:check-extensions` asserts it.

### Typed `Component.override` (D20)

Core types `Shopware.Component.override` through the global interface `ComponentOverrideFn` with today's loose signature.
`_base/admin-api.d.ts` merges a generic call signature into it, so a plugin that loads the snapshot calls the real function without a cast:

```ts
Shopware.Component.override('sw-sales-channel-detail', {
    inject: ['themeService'],
    methods: {
        getLoadSalesChannelCriteria() {
            const criteria = this.$super('getLoadSalesChannelCriteria');
            criteria.addAssociation('themes');
            return criteria;
        },
        async onSave() {
            this.isLoading = true;
            await this.$super('onSave');
        },
    },
});
```

`this` has the props, data, computed values, methods and injects of the component and its extends chain, the members of its mixins, the members added by core overrides, and Vue's instance API.
`$super` accepts only method and computed names of the target, with the argument count checked.
A redefined base method must stay assignable to the base signature.
Lifecycle hooks and other component options are accepted as in `ComponentOptions`.
An Options API override of a native component sees only its public bindings, props and injects, as at runtime.

The core change is small and does not touch the runtime of `override`.
In `src/global.types.ts`, inside `declare global`:

```ts
/**
 * Component names that a loaded public API snapshot types.
 * Empty in core, so the loose signatures below accept every name.
 */
interface ComponentOverrideTypedTargets {}

/**
 * Call signature of `Shopware.Component.override`.
 * The public API snapshot merges a typed signature into this interface.
 */
interface ComponentOverrideFn {
    <Name extends string>(
        componentName: Name extends keyof ComponentOverrideTypedTargets ? never : Name,
        componentConfiguration: ComponentConfig | (() => Promise<ComponentConfig>),
        overrideIndex?: number | null,
    ): () => Promise<ComponentConfig>;
}

/**
 * Call signature of `Shopware.Component.wrapOverrideConfig`, merged the same way.
 */
interface WrapOverrideConfigFn {
    <Name extends string>(
        componentName: Name extends keyof ComponentOverrideTypedTargets ? never : Name,
        componentConfiguration: ComponentConfig,
    ): ComponentConfig;
}
```

In `src/core/factory/async-component.factory.ts`:

```ts
/**
 * Types an override config that lives in its own file. Returns the config unchanged.
 * @public
 */
function wrapOverrideConfig(componentName: string, componentConfiguration: ComponentConfig): ComponentConfig {
    return componentConfiguration;
}

export default {
    register,
    extend,
    override: override as ComponentOverrideFn,
    wrapOverrideConfig: wrapOverrideConfig as WrapOverrideConfigFn,
    // ... the other members unchanged
};
```

In `src/core/shopware.ts`, `public Component` gains `wrapOverrideConfig: AsyncComponentFactory.wrapOverrideConfig`.

`componentName` is unused at runtime and only exists for the typed signature.
The Administration ESLint config keeps the default `args: 'after-used'` of `@typescript-eslint/no-unused-vars`, which does not report an unused parameter before a used one.
When the core change lands, check that the rule options still have that default, otherwise name the parameter `_componentName` and allow the prefix.

Why the loose signature excludes the typed names:
TypeScript tries overloads in order and takes the first one that accepts the call.
An error inside an override, such as a wrong `$super` name in a returned expression, makes the typed signature reject the call, and the loose signature would then accept it silently.
`_base` therefore merges `interface ComponentOverrideTypedTargets extends AdminApi.Components {}`, which turns the loose signature's name parameter into `never` for every name the snapshot knows.
Names the snapshot does not know, for example components of another plugin, keep the loose signature.
Without the snapshot loaded, `ComponentOverrideTypedTargets` is empty and nothing changes.

`_base/admin-api.d.ts` starts with `/// <reference path="../../src/global.types.ts" />`.
TypeScript puts the overloads of a later declaration first, and the reference guarantees that core is loaded before `_base`, however a plugin program lists its files.

### Outsourced override files (D21)

An override config in its own file uses `Shopware.Component.wrapOverrideConfig('<target>', {...})`, which returns the config unchanged and gives it the same types as an inline override.
SwagCommercial loads 152 of its 246 overrides lazily with `() => import()`, so this is the common case.

```ts
// sw-sales-channel-detail.override.ts
export default Shopware.Component.wrapOverrideConfig('sw-sales-channel-detail', {
    methods: {
        getLoadSalesChannelCriteria() {
            const criteria = this.$super('getLoadSalesChannelCriteria');
            criteria.addAssociation('themes');
            return criteria;
        },
    },
});

// index.ts
Shopware.Component.override('sw-sales-channel-detail', () => import('./sw-sales-channel-detail.override'));
```

The wrapped config carries its target as a type-only brand (`AdminApi.WrappedOverrideConfig`).
The lazy signature accepts only a module whose default export was wrapped for the same target, so `override('sw-a', () => import('./wrapped-for-sw-b'))` and a lazy plain object are type errors.

Limits:

- A computed override that returns `this.$super(...)` needs a return type annotation, otherwise tsc reports a circular type (TS7023).
- A typo in the target name of `override` or `wrapOverrideConfig` falls through to the loose signature.
  `admin:check-extensions` reports unknown targets from its string index.
- With `strictPublicApi: true`, private components are excluded from the typed signature but stay in `ComponentOverrideTypedTargets`, so overriding them needs a cast.
- JS members are `any`, so tsc checks names and arity, not value types.

### String names

Helper types turn the string namespaces into unions:

- `AdminApi.BlockName<'sw-sales-channel-detail'>`
- `AdminApi.SuperName<N>`, `AdminApi.Instance<N>`, `AdminApi.PreviousState<N>`
- `AdminApi.RouteName`, `AdminApi.MiddlewareRouteName`, `AdminApi.RouteParams<R>`
- `AdminApi.SnippetKey`, `AdminApi.PositionIdentifierName`, `AdminApi.DataSetId`

A plugin can add `strictPublicApi: true` to `AdminApi.Options` to hide private components and mixins from these helpers.
Plugins add their own components with `declare global { namespace AdminApi { interface Components { ... } } }`.

### `admin:check-extensions`

Most plugins are JS and Twig, which tsc does not see.
`admin:check-extensions` covers them:

1. Index every string use in the plugin with the TS AST and a Twig tokenizer: `Component.override`, `wrapOverrideConfig` and `extend` targets (also through forwarding helpers), override method and computed keys, `$super('...')` literals, `this.x` reads in overrides, top-level and nested block names in override templates, `swDefineOverride` keys and `<sw-block extends>` names in `.override.vue` files, `routeMiddleware` route names, route names in `name:` and `parentPath:`, `$t` keys, position identifiers and data set ids.
2. Write each use as a typed constant into a generated file, with the plugin location as a comment, for example `const _1: AdminApi.BlockName<'sw-sales-channel-detail'> = 'sw_sales_channel_detail_content_tab_theme'; // .../sw-sales-channel-detail.html.twig:1`.
3. Run tsc against `current.d.ts` and against `major.d.ts`, and map each error back to the plugin line.
4. Read the JSDoc tags of every resolved name and report uses of `@private` or `@deprecated` items as warnings.
5. Report an override key that is not a member of the target as a warning (`override_member_unknown`), because a rename in core turns it into a dead method.
6. Report a lazy override whose `wrapOverrideConfig` target differs from the `override` target, also in JS.
7. Check the context of every overridden block.
   The free identifiers in the override's template expressions that are neither members of the target nor its own `v-for` or slot variables must be scope variables of the block (`AdminApi.BlockScope<N, B>`).
   An override whose first element has `v-else-if` or `v-else` needs a block with `afterIf` (`AdminApi.BlockAfterIf<N, B>`).
   Both are checked against `current.d.ts` and `major.d.ts` like the names in step 3.

Against `major.d.ts`, the Storefront's override of `sw_sales_channel_detail_content_tab_theme` fails, because that block exists only with `v6.8.0.0` off.

## CI

Two checks run on every PR that touches the Administration (D7).

- Drift check: regenerate the snapshot, fail when `git diff` is not empty, then type-check `current.d.ts` and `major.d.ts` with `skipLibCheck: false`.
  The second step evaluates the consistency checks in the entry points: every entry fits its shape, every native entry fits `NativeComponentShape`, and every `extends`, mixin, route component, route parent, redirect and `parentPath` points to an existing name.
  `_base` references `src/global.types.ts`, which pulls in the whole Administration type surface.
  With `skipLibCheck: false` that program also reports diagnostics in third-party `.d.ts` files below `node_modules` and in local declaration files such as `src/entity-schema-definition.d.ts`, which the snapshot does not control.
  The step therefore runs each entry point as its own program through the TypeScript API and fails only on diagnostics whose file is below `public-api/`.
  Global diagnostics without a file also fail the step.
- Break check: run the trunk generator on base and head, compare the models per state, classify by the taxonomy, apply `accepted-breaks.json` and print the result.
  It does not read the committed snapshot, so a PR that only regenerates the snapshot still fails on a break.

### Element ids

Every finding names its element with a stable id, which is also the key in `accepted-breaks.json`:

```text
component:<name>
component:<name>/<kind>:<member>
component:<name>/block:<block>/scope:<variable>
mixin:<name>/<kind>:<member>
module:<id>
route:<name>
snippet:<key>
service:<name>/member:<member>
store:<id>/<state|getter|action>:<member>
shopware:<dotted path>
virtual-module:<specifier>/export:<name>
type:<src path>/<Name>
type:<src path>/<Name>.<member>
```

`<kind>` is `prop`, `emit`, `slot`, `mixin`, `inject`, `provide`, `data`, `computed`, `method`, `block`, `crossing`, `position-id`, `data-set` or `setup`.
Nested data keys use dots (`data:productComparison.templateName`).
A crossing is named `crossing:<element>@<opening block>><closing block>`, a `v-if` chain crossing `crossing:v-if@<block of the v-if>><block of the continuation>`.
A scope variable of a block is named `component:<name>/block:<block>/scope:<variable>`.

### Findings

| Finding | Group | Explanation | Fix hint |
|---|---|---|---|
| `<kind>_missing` | break | The element is gone, so plugins that use its name fail, for example through `$super`, `this`, a template override or `$t`. | Keep the element and mark it `@deprecated tag:vX`, or accept the break. |
| `block_missing` | break | The block is gone, so template overrides of it render nothing. | Keep the block, even empty, and mark it `{# @deprecated tag:vX #}`. |
| `block_moved_parent` | break | The block has a new parent block, so overrides of the old parent without `{% parent %}` now drop it, and overrides of the new parent drop it too. | Keep the block under its old parent. |
| `element_crosses_block` | break | An HTML element opens in one block and closes in another, so overriding either block without `{% parent %}` breaks the markup. | Open and close the element inside the same block. |
| `if_chain_crosses_block` | break | A `v-if` chain continues in another block, so overriding the block with the `v-if` without `{% parent %}` leaves the `v-else-if` or `v-else` without its partner. | Keep the whole chain inside one block. |
| `block_scope_missing` | break | A template variable from a `v-for` or slot is no longer available in the block, so plugin overrides that use it fail at render time. | Keep the block inside the loop or slot, or keep the variable name. |
| `block_if_context_lost` | break | The block no longer follows an open `v-if` chain, so plugin overrides that start with `v-else-if` or `v-else` no longer compile. | Keep the `v-if` element directly before the block. |
| `prop_now_required` | break | Existing usages that do not pass the prop now fail validation. | Keep the prop optional with a default. |
| `type_changed` | break | The declared type of the member became incompatible. | Keep the old type or widen it. |
| `method_signature_changed` | break | A parameter was added as required, removed or reordered, or the method switched between sync and `async`. | Add new parameters as optional at the end. |
| `route_parent_changed` | break | A top-level route became a child or the other way round, so `routeMiddleware` children and `parentPath` uses change. | Keep the route at its level. |
| `route_params_changed` | break | A path parameter was removed or renamed, so `$router.push` calls with it fail. | Keep the parameter. |
| `snippet_signature_changed` | break | The placeholders or the number of plural forms of the English text changed, so callers pass the wrong values. | Add a new key and deprecate the old one. |
| `setup_binding_kind_changed` | break | A native binding changed between ref, computed, reactive and function, so overrides merge differently. | Keep the binding kind. |
| `visibility_became_private` | break | A public element became `@private`, which removes it from the public API. | Deprecate first, make it private in the major. |
| `<kind>_added` | addition | A new public element that plugins can rely on from now on. | Mark it `@private` if it is not meant for plugins. |
| `deprecation_added` | info | The element now carries `@deprecated tag:vX`. | Add the upgrade note. |
| `deprecated_removal` | allowed | The element carried `@deprecated tag:vX` at base and the head version is X or later. | None. |
| any break | accepted | The finding matches an entry in `accepted-breaks.json`. | None. |
| any finding on a private element | private | Private parts are never API (D2, D13). | None. |
| `type_widened` | info | `Untyped` became a concrete type, or a type became wider. | None. |
| `method_param_renamed` | info | A parameter changed its name, not its position. | None. |
| `crossing_resolved` | info | A crossing from the baseline is gone. | None. |
| `acceptance_stale` | info | An entry added to `accepted-breaks.json` in this PR matches no finding. | Fix the finding or element id, or remove the entry. |

`<kind>` in `<kind>_missing` and `<kind>_added` is one of the element kinds above with `-` written as `_`, or `component`, `mixin`, `module`, `route`, `snippet`, `service`, `service_member`, `store`, `store_member`, `shopware_member`, `virtual_module_export`, `type` and `type_member`.
For example `block_missing`, `route_missing`, `setup_missing` or `type_member_missing`.

A removed element that comes back with another name in the same parent is reported as `<kind>_missing` plus `<kind>_added`, with a "possible rename" hint on the break.
Descendants of a moved block are not reported separately.
A break in the parent of an extend chain is reported once, on the declaring component, with the extend children listed under "also affects".

## Intended breaks (D14)

A break that a PR makes on purpose is accepted through `public-api/accepted-breaks.json`, never through a PR label.

```json
{
    "accepted": [
        {
            "finding": "block_missing",
            "element": "component:sw-mail-template-index/block:sw_mail_template_list_tabs_templates",
            "states": ["major"],
            "justification": "The legacy sw-tabs branch is replaced by mt-tabs in 6.8, see UPGRADE-6.8.md.",

        }
    ]
}
```

- One entry per finding: `finding`, `element` and a non-empty `justification` are required, `states` and `issue` are optional.
  Without `states`, the entry applies to both states.
- An entry accepts the break with the same finding id and element id.
  The finding is then reported in the `accepted` group with its justification and does not block.
- Only entries added by the PR count: the break check compares the file at base and at head.
  Entries already present at base are history and are neither applied nor reported.
- An added entry that matches no finding is reported as `acceptance_stale`.
- Entries are sorted by element id, then finding id.
  Entries are removed when the major that contains them is released.
- The file is protected by code ownership.
  Proposed entry for the root `.codeowners` file, which is not changed by this branch:

  ```text
  src/Administration/Resources/app/administration/public-api/accepted-breaks.json @shopware/product-cc-framework
  ```

## Test fixtures

The generator and the break check are tested against hand-written golden files.
All fixtures live in `scripts/generate-public-api/__fixtures__/`.
Its hand-written `.gitattributes` marks every `expected/` folder as `linguist-generated`, so the golden output stays collapsed in PR diffs like the snapshot.

### Taxonomy fixtures

Each case is a folder `scripts/generate-public-api/__fixtures__/<case>/`:

| Path | Content |
|---|---|
| `case.json` | The taxonomy row, the head version and the flag list |
| `before/` | Minimal source tree at base |
| `after/` | Minimal source tree at head |
| `expected/before/` | Snapshot files the generator writes for `before/` |
| `expected/after/` | Snapshot files the generator writes for `after/` |
| `expected/findings.txt` | Break check output for `before/` to `after/`, in the summary format |

- `before/` and `after/` mirror the Administration root, but contain only what the case needs: for example `src/module/<dir>/index.js` with the `Module.register` and the component directories.
- `expected/before/` and `expected/after/` mirror `public-api/`, including `current.d.ts`, `major.d.ts` and `index.json`.
- `case.json`:

  ```json
  {
      "row": "Block moved under a different parent block",
      "headVersion": "6.7",
      "majorFlags": ["v6.8.0.0"],
      "acceptedBreaks": null
  }
  ```

  `acceptedBreaks` is `null` or the path of an `accepted-breaks.json` inside `after/`.
- `headVersion` is the `major.minor` version the base branch releases next.
  In CI the break check gets it as `--head-version`.
  A `deprecated_removal` is allowed when the tag version is not higher than `headVersion`, or when the element is removed only in the major state and the tag names that major.
- `findings.txt` contains only the summary, without annotations, and ends with a newline.
  A case without findings expects `Public API check passed: no breaks.`

One case can cover several variants of its taxonomy row, so a case may expect several findings.

| Case | Taxonomy row | Expected findings |

## Open points

- Whether the SFC migration of a component (Options API to native) gets its own classification rule.
  The surface changes for all three consumer kinds: unlisted members move to `_private`, props leave `previousState`, and `$super` reaches only public bindings.
- The SFC migration codemod writes `@private` on every migrated component without `@public`.
  Under D1 and D13 that silently turns public components private, so the codemod has to follow D1.
- The compiled runtime ABI on `Shopware.Component` (`overrideComponentSetup`, `registerNativeExtensionTargets`, `registerOverrideComponent`, `attachOverrides`, `getExposedProps`) is tagged `@private` but called by every built plugin bundle.
  It needs a marker that keeps it out of the `private` group.
- Whether removing a trailing method parameter is always a break.
  #20959 (`onDeleteItem(item, itemIndex)` to `onDeleteItem(item)`) is classified as a break above, which makes three findings instead of the two the plan expected.
- Whether the HTML page can be attached to the PR, or has to stay a workflow artifact.

The review of the golden files left these gaps in this spec.
The fixtures fill them by convention, and the generator step has to settle them:

- Finding texts.
  The findings table gives one explanation and one fix hint per finding id, but the fixtures use kind-specific texts, for example for `prop_missing`, `computed_missing` and the sync-to-async case of `method_signature_changed`.
  The spec needs one text template per finding id and element kind.
- Order inside a summary group.
  The fixtures sort findings by element id and print no blank line between them.
- Finding ids the table does not define yet: `method_optional_param_added`, `service_member_missing`, `store_member_missing`, `setup_missing`, and a changed location of a position identifier or data set.
- The consistency checks do not verify block parents or the block names of a `crossings` entry.
  A `Block<'sw_bogus'>` compiles.
- Fixture `expected/` folders reference `./_base/admin-api.d.ts`, which only exists in `public-api/`.
  The fixture test has to copy `_base` next to them or rewrite the reference.
- Core-internal native overrides (`swDefineOverride`, `<sw-block extends>`) have no representation in `ComponentOverrides` yet (D17).
- A public extend child of a `@private` base (about 17 cases in core, including `sw-bulk-edit-*` on `sw-custom-field-set-renderer`) needs a rule for the inherited blocks (D13).
- With the snapshot loaded, a lazy `override('<known name>', () => import('./plain'))` becomes a type error until the file uses `wrapOverrideConfig` (D21).
  The upgrade notes have to say so.
