- **Resolvability gate** (DAL `PreWriteValidationEvent`): `Validation/ContentLayoutWriteValidator` (well-formedness on `content_layout` + synchronous re-check of bound layouts via tagged `Binding/LayoutBindingEnumerator`s) and `Validation/ContentLayoutAssignmentWriteValidator` (runs the binding check on entity assignments, delegating to the shared `Validation/LayoutBindingChecker`). Layout decoding runs through the shared `Validation/LayoutTreeDecoder`, injected directly into `Validation/ContentLayoutWriteValidator` and `Validation/LayoutBindingChecker` (the assignment validator does not decode itself — it delegates to `LayoutBindingChecker`). `Validation/LayoutGate` exposes the two gate predicates `wellFormedness()` / `resolvability()`, each returning a `Diagnostics/DiagnosticsReport` whose `isWellFormed()` / `isResolvable()` are the actual predicates; its `isBindingEnforced(SourceBinding)` seam (default enforces every binding) is the single override point for a future draft/versioning system. `LayoutGate::SKIP_VALIDATION_STATE` write-context flag bypasses both gates
- **Write-boundary default seeding**: `Layout/LayoutDefaultSeeder` seeds each element's type primitive defaults into stored `properties` at the single DAL write chokepoint for the `layout` field (`Layout/Field/ContentElementListFieldSerializer::normalize`), so every tree written to `content_layout` through the DAL carries its type defaults regardless of how it was built (direct DAL write, Sync API, import, fixtures, or the `Mutation/` ops). It handles both `ContentElement` and raw-array payloads, never overwrites an authored value, and shares the per-type rule (`Layout/Type/PrimitiveDefaultProvider`) with the mutations. `normalize` runs before `PreWriteValidationEvent`, so the gate decodes a seeded tree; the write validator stays a pure gate (it never rewrites). Migrations write raw SQL via `Connection` and bypass this seam
- **Delete protection**: a `content_layout` bound to any source cannot be deleted — `RestrictDelete` on the five `content_layout` OneToMany assignment associations (`Layout/Entity/ContentLayoutDefinition` for product/category/landing-page, `Storefront/.../Extension/ContentLayoutExtension` for header/footer) makes the DAL throw `RestrictDeleteViolationException` before any SQL, backed by `ON DELETE RESTRICT` on each `content_layout_id` foreign key. This is DAL-core machinery, not a content-system gate, so `SKIP_VALIDATION_STATE` does not bypass it. Sibling foreign keys (`sales_channel_id`, `domain_id`) stay `ON DELETE CASCADE` — deleting the referenced channel/domain still removes the assignment while the layout survives
- **Draft Check**: `DraftLayoutChecker` (module root) — the preview action's draft-layout check; runs the same `LayoutDiagnostics` intrinsic subset as the persistence gate
- **Resolve-and-diagnose route**: `Api/ContentDiagnoseController` (`POST /api/_action/content-system/layout/diagnose`); operates only on a draft layout tree from the request, never the persisted `content_layout` entity; source selection via `Api/SpecificationSourceLocator` (`entityType` or `section`)
- **Layout mutation**: `Mutation/MutationPipeline` (apply one structural edit to an already-decoded tree → diagnose the whole new tree → assemble a `Mutation/MutationResult`) drives eight `Mutation/Op` operations (`InsertElement`, `RemoveElement`, `MoveElement`, `ReplaceElement`, `DuplicateElement`, `WrapElements`, `UnwrapElement`, `AttachElement`), all extending `Mutation/AbstractLayoutMutation` (immutable path-copying tree surgery). Exposed by `Api/LayoutMutationController` (`POST /api/_action/content-system/layout/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element}`), which decodes the request draft via the shared `Api/DraftLayoutDecoder` before the pipeline and reuses `Api/SpecificationSourceLocator` for the optional root-context binding. Operations never silently lose content: detached subtrees come back via `orphaned()` (re-placeable with `AttachElement`), dropped wiring keys via `droppedWiring()`. `AttachElement` splices a caller-supplied subtree (e.g. those orphans, or a copy) back in, reminting every id
- **Persisted layout mutation**: `Mutation/PersistedLayoutMutator` commits one operation to a stored `content_layout` (the persisted counterpart to `MutationPipeline`). Exposed by `Api/ContentLayoutMutationController` (`POST /api/_action/content-system/layout/{layoutId}/{insert-element,…,unwrap-element,attach-element}`). It loads the layout by id (`ContentSystemException::contentLayoutNotFound`, 404), guards an optimistic-concurrency token against the row's `updatedAt` (`layoutVersionConflict`, 409, no write on a mismatch; a `null` token matches a never-updated row), applies the op, then persists the mutated tree — whose write runs the resolvability gates, so a binding-breaking edit is rejected there. Response diagnostics are derived from the layout's real bindings via the tagged `Binding/LayoutBindingEnumerator`s, not a request hint. A committed op never silently loses content: detached subtrees (`orphaned`) and dropped wiring (`droppedWiring`) are omitted from the stored tree but returned in the result, so the caller re-places them with an `attach-element` call or re-wires

## Constraints

- `RenderingSpecificationResolver`: iterates sources via `supports()` bool check, first match wins — NOT null-return
- `ContentPipeline::load()`: receives a loaded `RenderableLayout` → PreHydration events → hydration (FULL mode only) → PostHydration events
- Specification resolution and layout-entity loading happen in `ContentRoute`, NOT in `ContentPipeline`
- OpenAPI schemas: update `src/Core/Framework/Api/ApiDefinition/Generator/Schema/StoreApi/` when modifying endpoints
- Data loader type introspection: `ContentSystemDataLoaderTypeResolver` assembles the source→capability map at runtime from each loader's `producibleTypes()` (memoized per kernel runtime); `ContentSystemDataLoaderTypeCompilerPass` only validates at build time (dry-runs `AbstractContentDataLoader::extendsDescriptor()`, so loaders MUST have `@extends AbstractContentDataLoader<T>` PHPDoc); wildcard loaders (`entity`, `entity_collection`) override `producibleTypes()`/`resolveProducedType()` to enumerate the live registry (so plugin/app/custom entities appear on the next kernel boot without a container rebuild)
- Schema API endpoint: `GET /api/_info/content-system-data-loader-types.json` (registered in `InfoController`)
- `ContentSystemDataLoaderTypeMap` lookups are subtype-aware (`is_a`): `getSourcesFor($class)` returns every source whose `producedType` is the class or a subclass; `capabilityFor($source, $class)` returns that source's first matching `LoaderTypeCapability`, or `null` when the source cannot produce the class
- Entity type introspection: `ContentLayoutAssignableCompilerPass` introspects `content_system.entity_specification_source` tagged services for `AbstractContentLayoutAssignableDefinition` arguments — entity types baked into schema generator at build time
- Schema API endpoint: `GET /api/_info/content-system-entity-types.json` (registered in `InfoController`)
- Type spec `properties` = hydrated output schema, NOT storage schema; property key links type spec → data_requirements → accepts_context → setProperty()
- Primitive property satisfaction is strict: `Diagnostics/LayoutDiagnostics` reports a required primitive as `UnresolvedRequired` iff the element has no stored value for it (`ContentElement::getProperty($key) === null`); the type default is not consulted, because serving renders the stored `properties` verbatim and applies no default. A primitive's default reaches storage only via creation-time seeding (`Mutation` scaffold/replace) and the write-boundary `Layout/LayoutDefaultSeeder`, never at diagnosis. This mirrors the reference branch (satisfied iff a source will fill it at serving). Because satisfaction requires a stored value, a tree that reaches `content_layout` WITHOUT passing the write-boundary `Layout/LayoutDefaultSeeder` — a raw-SQL or migration write (both use `Connection`, not the DAL) or a row predating the seam — that carries a type whose required primitive declares a default but stores no value will be reported `UnresolvedRequired` and rejected the next time the resolvability gate re-checks it (e.g. when an assignment binds the layout, the gate re-decodes the stored tree verbatim via `Validation/LayoutBindingChecker`). A raw-SQL/migration writer must seed such a value itself; the DAL write path seeds it automatically. The draft `Api/ContentDiagnoseController` / preview path is likewise not seeded (only DAL writes seed), so `/diagnose` reports such a primitive as unresolved while a subsequent save would seed it and pass — diagnosis deliberately over-reports a missing required value rather than under-reporting it. (The shipped core type definitions currently pair `required` only with non-defaulted primitives or references, so no shipped type triggers this today; it is a property of the rule, not a known live break.)
- Client-defect classification: `ContentSystemException::isClientDefect()` (+ `CLIENT_DEFECT_CODES`, six codes) marks the error codes that signal a defect in client-supplied layout input — a typo'd entity (`UNKNOWN_LOADER_ENTITY`), undecodable/invalid config (`INVALID_FIELD_VALUE_TYPE`), an unregistered source (`DATA_LOADER_NOT_REGISTERED`, `CONFIG_SERIALIZER_NOT_REGISTERED`), or an element-definition context-wiring violation (`CONSUMER_ALIAS_WITHOUT_REDISTRIBUTE`, `PROPERTY_ALIAS_WITH_DOT_NOTATION`) — rather than an internal fault. `Diagnostics/LayoutDiagnostics` catches only these per element and maps them to a `ViolationCode::InvalidConfig` violation; every other code propagates, so an internal fault is never relabelled as the client's mistake. A status-code filter is insufficient — some HTTP 500 codes (e.g. `DATA_LOADER_NOT_REGISTERED`, `INVALID_FIELD_VALUE_TYPE`) are legitimate client defects for a client-supplied tree
