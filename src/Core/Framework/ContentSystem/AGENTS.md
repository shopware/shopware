- **Layout Value Objects**: `RenderableLayout` (reference + stored elements), `LayoutReference` (id, name, version), `ResolvedContentLayout` (layout ID + `RenderingSpecification`)
- **Store API**: `SalesChannel/ContentRoute` (single class, DI-parameterized per format + section)
- **Admin Preview API**: `Api/ContentPreviewController` — one route minting a short-lived token for an unsaved draft layout and returning a Storefront preview URL that renders it against real entity data, assignment-free. Route, mint-time admission, the absent direct render route and the payload store's contract are in [Api/AGENTS.md](Api/AGENTS.md); the wire contract in [Api/docs/preview-url.md](Api/docs/preview-url.md)
- **Resolution & Diagnostics**: `Resolution/ElementResolver` + `Resolution/AvailableContextResolver` (kernel), `Diagnostics/LayoutDiagnostics` (`analyze(tree, rootContext)` → `LayoutAnalysis`: per-element `PropertyResolution`s + a `DiagnosticsReport`), `Diagnostics/RootContextMapper` (bound source → root-ambient context). `ViolationCode` resolves a violation's scope (intrinsic/binding) + severity
- **Resolvability gate** (DAL `PreWriteValidationEvent`): two subscribers enforce served-implies-resolvable — `Validation/ContentLayoutWriteValidator`, the single ordered `content_layout` write gate, and `Validation/ContentLayoutAssignmentWriteValidator`, a tree-blind type-match on the bound layout's immutable `root_source`. `Validation/LayoutGate` holds the two predicates and the `SKIP_VALIDATION_STATE` bypass. Gate ordering, the edit-path membership re-check, every error code, and the served-implies-resolvable stationarity caveat are owned by [Validation/AGENTS.md](Validation/AGENTS.md) / [Validation/README.md](Validation/README.md)
- **Write-boundary default seeding**: `Layout/LayoutWriteBoundary` is the one admission point every layout write passes through, reached from the DAL write chokepoint for the `layout` field (`Layout/Field/StoredElementListFieldSerializer::normalize`). `normalize` runs before `PreWriteValidationEvent` and memoizes the admitted tree on the write `Context`, so the gate judges a seeded tree and the write validator stays a pure gate that never rewrites. Migrations write raw SQL via `Connection` and bypass this seam. What the three passes do — `Layout/LayoutDefaultSeeder` and its shared per-type rule included — is owned by [Layout/README.md](Layout/README.md) and [Binding/docs/write-boundary.md](Binding/docs/write-boundary.md)
- **Delete protection**: a `content_layout` bound to any source cannot be deleted — `RestrictDelete` on the five `content_layout` OneToMany assignment associations (`Layout/Entity/ContentLayoutDefinition` for product/category/landing-page, `Storefront/.../Extension/ContentLayoutExtension` for header/footer) makes the DAL throw `RestrictDeleteViolationException` before any SQL, backed by `ON DELETE RESTRICT` on each `content_layout_id` foreign key. This is DAL-core machinery, not a content-system gate, so `SKIP_VALIDATION_STATE` does not bypass it. Sibling foreign keys (`sales_channel_id`, `domain_id`) stay `ON DELETE CASCADE` — deleting the referenced channel/domain still removes the assignment while the layout survives
- **Draft Check**: `DraftLayoutChecker` (module root) — the preview action's draft-layout check; runs the same `LayoutDiagnostics` intrinsic subset as the persistence gate
- **Resolve-and-diagnose route**: `Api/ContentDiagnoseController` (`POST /api/_action/content-system/layout/diagnose`); operates only on a draft layout tree from the request, never the persisted `content_layout` entity; an optional `rootSource` in the request resolves its root-ambient context via `Adapter/RootSourceRegistry::resolveGated()` (empty/absent → intrinsic well-formedness only)
- **Layout mutation**: `Mutation/MutationPipeline` is the stateless runner over an already-decoded tree, driving nine `Mutation/Op` operations (`InsertElement`, `RemoveElement`, `MoveElement`, `ReplaceElement`, `DuplicateElement`, `WrapElements`, `UnwrapElement`, `AttachElement`, `BindElement`), all extending `Mutation/AbstractLayoutMutation` and editing through `Layout/StoredTree`'s own immutable tree surgery. `Mutation/PersistedLayoutMutator` is the persisted counterpart, committing one operation to a stored `content_layout` through the resolvability gates. No operation ever silently loses content — detached subtrees come back via `orphaned()`, dropped wiring via `droppedWiring()`, uncarryable values via `droppedProperties()`. Runner contracts, per-op rules and every error code are owned by [Mutation/AGENTS.md](Mutation/AGENTS.md) and its `Mutation/docs/`; the two controllers exposing them by [Api/AGENTS.md](Api/AGENTS.md)
- **Assignment-free resolution**: `Adapter/RenderingSpecificationResolver::resolveWithoutLayout()` selects a source via `supportsEntityType()`; `RenderingSpecificationFactory::createWithoutLayout()` assembles a `RenderingSpecification` with no layout id
- **Schema**: `Schema/ContentSystemDataLoaderMapResolver`, `Schema/ContentSystemDataLoaderMap`, `Schema/ContentSystemDataLoaderSchemaGenerator`
- **Root Source Registry**: `Adapter/RootSourceRegistry` — the single authority over the valid root-source set and their resolution. `knownRootSources()` (entity types + section keys + `none`, excludes `main`), `entityRootSources()` (entity-type subset, backs `content-system-entity-types.json`), `resolve(rootSource, Context): list<ProvidedContext>` (fail-hard on an unknown id), `sourceFor(rootSource)`. The `none` root source is `Adapter/NoneSpecificationSource`
- **Compiler Pass**: `Framework/DependencyInjection/CompilerPass/ContentSystemDataLoaderCompilerPass` — build-time validation of every `content_system.data_loader`-tagged service: its class shape, its `@extends` annotation, and a dry-run of its `configSpecification()` on an instance built without the constructor (the runtime resolver assembles the type map). Full rejection catalogue: [Hydration/DataLoader/AGENTS.md](Hydration/DataLoader/AGENTS.md)
- **Element Type Registry**: `Layout/Type/Registry/ContentSystemElementTypeRegistry`

- **Style Option Registry**: `Layout/Element/Style/Registry/ContentSystemStyleOptionRegistry` (decoration trio, `cache.system`) aggregates the `content_system.style_option_loader`-tagged loaders whose YAML directories `Framework/DependencyInjection/CompilerPass/ContentSystemStyleOptionCompilerPass` discovers. - **Element style storage**: each element's `style` inside the `content_layout.layout` JSON (no separate column) is encoded and decoded through `Layout/Codec/StoredTreeCodec`; `Layout/Codec/StoredTreeConstraints` composes the write-time constraints against the registry (the strict write rejects unknown options, mirroring the element-type system's unknown-`component` handling). Carried through every structural edit by the `Mutation/` ops, and onto the wire out of `RenderedElement::$style` by `Output/Encoder/ContentPageEncoder` (full format) and `Output/Encoder/ContentDecomposedPageEncoder` (decomposed), and through `Output/Struct/ContentSkeletonElement` for the skeleton format; omitted when empty in all three, and absent from the data format, which serves no structure

## Constraints

- `RenderingSpecificationResolver`: iterates sources via `supports()` bool check, first match wins — NOT null-return
- `ContentPipeline::load()`: receives a loaded `RenderableLayout` (stored elements) → `ContentTreePreparationEvent` → stored preparation (`Layout/Scaffolding/StoredTreePreparer::prepare()`, which takes the `SalesChannelContext`: language reduction, then placeholder resolution — both inside one FULL-mode guard, in that order — then the virtual-root wrap via `Layout/Scaffolding/VirtualRootWrapper`, then the partial prune via `Output/PartialRenderer`, all still stored, returning a `Layout/Scaffolding/TreePreparationResult`) → duplicate-element-id rejection on the result's pre-prune forest → `Rendering/WiringPlanner::plan()` (wiring validation on that same pre-prune forest, then redistribute derivation on the result's pruned tree) → the render step (`Rendering/ElementLowering::lower()`: forest-wide data resolution, the once-per-render root-ambient resolution of the specification's page-level data requirements against the virtual-root wrapper the pipeline hands it from the pre-prune forest, context-delivery resolution, rendered-tree minting; FULL does all four, SKELETON mints structure only) → the finishing steps, now on the rendered forest (`VirtualRootWrapper::unwrap()`, then `PartialRenderer::extractTarget()`, both driven by the `RenderScaffolding`) → `RenderedTreeFinalizationEvent` over the rendered forest, in both modes → duplicate-element-id rejection again, over the forest the event handed back, because a finalization listener may replace it and the pre-lowering check ran too early to see that. Both checks throw `DUPLICATE_ELEMENT_ID` (500, not a client defect) and run in either mode. It returns an `Output/RenderResult` (finished rendered forest, layout reference, optional `Output/Index/ResolvedValueIndex`), and takes both format answers from the route: the `RenderingMode` and whether the format collects a value index
- Language reduction is the first preparation pass, and its position is load-bearing. It replaces each translatable property's language map with the value of the first entry along `SalesChannelContext::getLanguageIdChain()`, verbatim; a key outside the chain is never selected, so a dangling language id cannot reach serving, and a map carrying no chain entry collapses to the null variant, which the mint skips. Placeholder resolution runs second because substitution touches string values and never descends into a map. In FULL mode, everything after it reads plain strings: the lowering, the mint, every encoder, the value index and the Twig components. SKELETON reaches the same end by a different route — reduction is skipped, so `Rendering/WiringPlanner` (which runs in both modes) receives the unreduced maps and is indifferent to them because it reads no property value, and the SKELETON mint strips properties entirely. Neither mode puts a language map on the wire. A non-map value on a translatable property at reduction throws `TRANSLATION_SHAPE_INVALID` (500, deliberately absent from `CLIENT_DEFECT_CODES` — the same internal-fault reading as `DUPLICATE_ELEMENT_ID`): every client-supplied path rejects that shape earlier, so reaching it means the write constraints were bypassed or a `ContentTreePreparationEvent` listener introduced it after a conforming read
- Wiring validation and redistribute derivation are the two halves of `Rendering/WiringPlanner::plan()`, deliberately split: validation judges the pre-prune forest (a defect in a subtree a partial render discards still fails the render), derivation runs on the surviving tree and throws nothing
- Specification resolution and layout-entity loading happen in `ContentRoute`, NOT in `ContentPipeline`
- OpenAPI schemas: update `src/Core/Framework/Api/ApiDefinition/Generator/Schema/StoreApi/` when modifying endpoints
- Data loader type introspection: `ContentSystemDataLoaderMapResolver` assembles the source→capability map at runtime from each loader's `producibleTypes()` (memoized per kernel runtime); `ContentSystemDataLoaderCompilerPass` only validates at build time (dry-runs `AbstractContentDataLoader::extendsDescriptor()`, so loaders MUST have `@extends AbstractContentDataLoader<T>` PHPDoc, plus the `configSpecification()` dry-run under **Compiler Pass** above); wildcard loaders (`entity`, `entity_collection`) override `producibleTypes()`/`resolveProducedType()` to enumerate the live registry (so plugin/app/custom entities appear on the next kernel boot without a container rebuild)
- Schema API endpoint: `GET /api/_info/content-system-data-loaders.json` (registered in `InfoController`)
- `ContentSystemDataLoaderMap` lookups are subtype-aware (`is_a`): `getSourcesFor($class)` returns every source whose `producedType` is the class or a subclass; `capabilityFor($source, $class)` returns that source's first matching `LoaderTypeCapability`, or `null` when the source cannot produce the class
- Entity type introspection: `ContentLayoutAssignableCompilerPass` introspects `content_system.entity_specification_source` tagged services for `AbstractContentLayoutAssignableDefinition` arguments — the entity-type id list is baked into `Adapter/RootSourceRegistry` at build time, and `InfoController::contentSystemEntityTypes()` returns `RootSourceRegistry::entityRootSources()`
- Schema API endpoint: `GET /api/_info/content-system-entity-types.json` (registered in `InfoController`)
- Schema API endpoint: `GET /api/_info/content-system-root-sources.json` (registered in `InfoController`)
- Type spec `properties` = hydrated output schema; the storage schema is a separate fold on the same endpoint, `storageSchema`, derived per type by `Layout/Type/StoredSchemaResolver` (stored keys, three kinds, precedence `property` > `resolvedByStorage` > `config`). The property key links type spec → dataRequirements → acceptsContext → the key `Rendering/RenderedElementFactory` writes the resolved value under on the rendered element
- Primitive property satisfaction is strict: `Diagnostics/LayoutDiagnostics` reports a required primitive as `UnresolvedRequired` iff the element has no stored value for it (`LayoutDiagnostics::hasStoredValue()`); the type default is not consulted, because serving renders the stored `properties` verbatim. For a TRANSLATABLE property the anchor rule supersedes present-and-not-null: satisfaction needs the property's language map to carry `Defaults::LANGUAGE_SYSTEM` with a string value, so a present, non-null map no longer satisfies on its own, and the same rule governs `UnfilledRequiredInput` because both violations read the one `hasStoredValue()`. A default reaches storage only through creation-time seeding (`Mutation` scaffold/replace) and the write-boundary `Layout/LayoutDefaultSeeder`, so a writer that bypasses the DAL (raw SQL, migration) must seed a required defaulted primitive itself or the next resolvability re-check rejects the row, and the unseeded draft path (`Api/ContentDiagnoseController`, preview) deliberately over-reports it. See [Diagnostics/AGENTS.md](Diagnostics/AGENTS.md)
- Client-defect classification: `ContentSystemException::isClientDefect()` (+ `CLIENT_DEFECT_CODES`, fourteen codes) marks the error codes that signal a defect in client-supplied layout input: a typo'd entity (`UNKNOWN_LOADER_ENTITY`), undecodable/invalid config (`INVALID_FIELD_VALUE_TYPE`), a field value outside its permitted range (`INVALID_FIELD_VALUE_RANGE`), an unregistered source (`DATA_LOADER_NOT_REGISTERED`, `CONFIG_SERIALIZER_NOT_REGISTERED`), an element-definition context-wiring violation (`CONSUMER_ALIAS_WITHOUT_REDISTRIBUTE`, `PROPERTY_ALIAS_WITH_DOT_NOTATION`, `PROPERTY_ALIAS_COLLISION`, `REDISTRIBUTE_DOTTED_PATH`, `REDISTRIBUTE_CONFLICT`, `ROOT_SCOPE_WITH_REDISTRIBUTE`; the last four's enforcement sites: [Layout/Element/Context/AGENTS.md](Layout/Element/Context/AGENTS.md)), a child-facing provider-key collision (`PROVIDER_DELIVERY_COLLISION`), a numeric wiring key (`INVALID_MAP_KEY`), or an element id outside the decode gate's value domain (`INVALID_ELEMENT_ID`), rather than an internal fault. `Diagnostics/LayoutDiagnostics` catches only these per element and maps them to a `ViolationCode::InvalidConfig` violation; every other code propagates, so an internal fault is never relabelled as the client's mistake. A status-code filter is insufficient: some HTTP 500 codes (e.g. `DATA_LOADER_NOT_REGISTERED`, `INVALID_FIELD_VALUE_TYPE`) are legitimate client defects for a client-supplied tree
