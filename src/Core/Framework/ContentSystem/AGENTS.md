- **Admin Preview API**: `Api/ContentPreviewController` — `POST /api/_action/content-system/preview/entity` renders an unsaved draft layout against real entity data (assignment-free); `POST /api/_action/content-system/preview/entity/url` stores the same envelope behind a short-lived token (`Api/ContentPreviewPayloadStore`, five-minute cache TTL) and returns a Storefront preview URL (`frontend.content-system.preview`). Both delegate to `Api/ContentPreviewPageBuilder`. See `ADMINISTRATION.md`
- **Resolution & Diagnostics**: `Resolution/ElementResolver` + `Resolution/AvailableContextResolver` (kernel), `Diagnostics/LayoutDiagnostics` (`analyze(tree, rootContext, context)` → `LayoutAnalysis`: per-element `PropertyResolution`s + a `DiagnosticsReport`), `Diagnostics/RootContextMapper` (bound source → root-ambient context). `ViolationCode` resolves a violation's scope (intrinsic/binding) + severity
- **Resolvability gate** (DAL `PreWriteValidationEvent`): two subscribers enforce served-implies-resolvable. `Validation/ContentLayoutWriteValidator` is the single ordered `content_layout` write gate — well-formedness → `root_source` membership in `Adapter/RootSourceRegistry` → resolvability against the declared root source (on a layout-only edit, membership of the committed `root_source` is re-checked before `resolve()`, so a de-registered source is an `unknownRootSource` 400, not a 500). `Validation/ContentLayoutAssignmentWriteValidator` is a tree-blind type-match that rejects an assignment whose layout's immutable `root_source` ≠ the assignment definition's `getContentLayoutEntityType()` (`rootSourceAssignmentMismatch`, 400). `Validation/LayoutGate` holds the two predicates `wellFormedness()` / `resolvability()` and the `SKIP_VALIDATION_STATE` bypass. Full gate ordering, the edit-path membership re-check, and the served-implies-resolvable stationarity caveat (the type-match assumes a layout's resolvability inputs stay stable after its write) are documented in `Validation/AGENTS.md` / `README.md`
- **Write-boundary default seeding**: `Layout/LayoutDefaultSeeder` seeds each element's type primitive defaults into stored `properties` at the single DAL write chokepoint for the `layout` field (`Layout/Field/ContentElementListFieldSerializer::normalize`), so every tree written to `content_layout` through the DAL carries its type defaults regardless of how it was built (direct DAL write, Sync API, import, fixtures, or the `Mutation/` ops). It handles both `ContentElement` and raw-array payloads, never overwrites an authored value, and shares the per-type rule (`Layout/Type/PrimitiveDefaultProvider`) with the mutations. `normalize` runs before `PreWriteValidationEvent`, so the gate decodes a seeded tree; the write validator stays a pure gate (it never rewrites). Migrations write raw SQL via `Connection` and bypass this seam
- **Delete protection**: a `content_layout` bound to any source cannot be deleted — `RestrictDelete` on the five `content_layout` OneToMany assignment associations (`Layout/Entity/ContentLayoutDefinition` for product/category/landing-page, `Storefront/.../Extension/ContentLayoutExtension` for header/footer) makes the DAL throw `RestrictDeleteViolationException` before any SQL, backed by `ON DELETE RESTRICT` on each `content_layout_id` foreign key. This is DAL-core machinery, not a content-system gate, so `SKIP_VALIDATION_STATE` does not bypass it. Sibling foreign keys (`sales_channel_id`, `domain_id`) stay `ON DELETE CASCADE` — deleting the referenced channel/domain still removes the assignment while the layout survives
- **Draft Check**: `DraftLayoutChecker` (module root) — the preview action's draft-layout check; runs the same `LayoutDiagnostics` intrinsic subset as the persistence gate
- **Resolve-and-diagnose route**: `Api/ContentDiagnoseController` (`POST /api/_action/content-system/layout/diagnose`); operates only on a draft layout tree from the request, never the persisted `content_layout` entity; an optional `rootSource` in the request resolves its root-ambient context via `Adapter/RootSourceRegistry::resolve()` (empty/absent → intrinsic well-formedness only). The response also carries `applicableBindings` (`Binding/ApplicableBindingsResolver::resolve()`), a per-element-type binding specification lookup independent of `rootSource`
- **Layout mutation**: `Mutation/MutationPipeline` (apply one structural edit to an already-decoded tree → diagnose the whole new tree → assemble a `Mutation/MutationResult`) drives nine `Mutation/Op` operations (`InsertElement`, `RemoveElement`, `MoveElement`, `ReplaceElement`, `DuplicateElement`, `WrapElements`, `UnwrapElement`, `AttachElement`, `BindElement`), all extending `Mutation/AbstractLayoutMutation` (immutable path-copying tree surgery). Exposed by `Api/LayoutMutationController` (`POST /api/_action/content-system/layout/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element,bind-element}`), which decodes the request draft via the shared `Api/DraftLayoutDecoder` before the pipeline and resolves the optional request `rootSource` through `Adapter/RootSourceRegistry::resolve()` for the root-context binding. Operations never silently lose content: detached subtrees come back via `orphaned()` (re-placeable with `AttachElement`), dropped wiring keys via `droppedWiring()`. `AttachElement` splices a caller-supplied subtree (e.g. those orphans, or a copy) back in, reminting every id. `BindElement` applies a registered `Binding/BindingSpecification`'s wiring onto an element — see **Binding Specification System** below
- **Persisted layout mutation**: `Mutation/PersistedLayoutMutator` commits one operation to a stored `content_layout` (the persisted counterpart to `MutationPipeline`). Exposed by `Api/ContentLayoutMutationController` (`POST /api/_action/content-system/layout/{layoutId}/{insert-element,…,attach-element,bind-element}`). It loads the layout by id (`ContentSystemException::contentLayoutNotFound`, 404), guards an optimistic-concurrency token against the row's `updatedAt` (`layoutVersionConflict`, 409, no write on a mismatch; a `null` token matches a never-updated row), applies the op, then persists the mutated tree — whose write runs the resolvability gates, so a resolvability-breaking edit is rejected there. Response diagnostics are derived from the loaded layout's single `root_source` (resolved once via `RootSourceRegistry::resolve()`), not a request hint. A committed op never silently loses content: detached subtrees (`orphaned`) and dropped wiring (`droppedWiring`) are omitted from the stored tree but returned in the result, so the caller re-places them with an `attach-element` call or re-wires. Both mutation responses additionally carry `applicableBindings`, populated the same way as the diagnose route
- **Assignment-free resolution**: `Adapter/RenderingSpecificationResolver::resolveWithoutLayout()` selects a source via `supportsEntityType()`; `RenderingSpecificationFactory::createWithoutLayout()` assembles a `RenderingSpecification` with no layout id

The `none` root source is `Adapter/NoneSpecificationSource`

- **Binding Specification System**: `Binding/BindingSpecification` — an authored declaration wiring a type's reference properties to loaders (`resolves`, keyed by property → `Binding/LoaderBinding`) and seeding its primitive properties (`inputs`, keyed by property → `Binding/BindingInput`). Loader/registry trio mirrors the style-option system: `Binding/Loader/YamlBindingSpecificationLoader` (core/bundle/plugin, plus app in dev) and `Binding/Loader/DatabaseBindingSpecificationLoader` (active app bindings in prod) are tagged `content_system.binding_specification_loader` and aggregated by `Binding/Registry/AbstractContentSystemBindingSpecificationRegistry` (`ContentSystemBindingSpecificationRegistry` leaf, `CachedContentSystemBindingSpecificationRegistry` `cache.system` decorator), discovered by `Framework/DependencyInjection/CompilerPass/ContentSystemBindingSpecificationCompilerPass`. Two class-level constraints gate a declaration: `Binding/Validation/WellFormedBindingSpecification` (structural shape only) then `Binding/Validation/TypeConsistentBindingSpecification` (semantic — the declared type is registered, every `resolves`/`inputs` key names an actual property, every loader produces an assignable type). Two admin routes (`Api/LayoutMutationController::bind()`, `Api/ContentLayoutMutationController::bind()`) and one introspection route (`GET /api/_info/content-system-binding-specifications.json`) expose it. ## Constraints

- `RenderingSpecificationResolver`: iterates sources via `supports()` bool check, first match wins — NOT null-return
- `ContentPipeline::load()`: receives a loaded `RenderableLayout` → PreHydration events → hydration (FULL mode only) → PostHydration events
- Specification resolution and layout-entity loading happen in `ContentRoute`, NOT in `ContentPipeline`
- OpenAPI schemas: update `src/Core/Framework/Api/ApiDefinition/Generator/Schema/StoreApi/` when modifying endpoints
- Data loader type introspection: `ContentSystemDataLoaderTypeResolver` assembles the source→capability map at runtime from each loader's `producibleTypes()` (memoized per kernel runtime); `ContentSystemDataLoaderTypeCompilerPass` only validates at build time (dry-runs `AbstractContentDataLoader::extendsDescriptor()`, so loaders MUST have `@extends AbstractContentDataLoader<T>` PHPDoc); wildcard loaders (`entity`, `entity_collection`) override `producibleTypes()`/`resolveProducedType()` to enumerate the live registry (so plugin/app/custom entities appear on the next kernel boot without a container rebuild)
- Schema API endpoint: `GET /api/_info/content-system-data-loader-types.json` (registered in `InfoController`)
- `ContentSystemDataLoaderTypeMap` lookups are subtype-aware (`is_a`): `getSourcesFor($class)` returns every source whose `producedType` is the class or a subclass; `capabilityFor($source, $class)` returns that source's first matching `LoaderTypeCapability`, or `null` when the source cannot produce the class
- Entity type introspection: `ContentLayoutAssignableCompilerPass` introspects `content_system.entity_specification_source` tagged services for `AbstractContentLayoutAssignableDefinition` arguments — the entity-type id list is baked into `Adapter/RootSourceRegistry` at build time, and `InfoController::contentSystemEntityTypes()` returns `RootSourceRegistry::entityRootSources()`
- Schema API endpoint: `GET /api/_info/content-system-entity-types.json` (registered in `InfoController`)
- Type spec `properties` = hydrated output schema, NOT storage schema; property key links type spec → dataRequirements → acceptsContext → setProperty()
- Primitive property satisfaction is strict: `Diagnostics/LayoutDiagnostics` reports a required primitive as `UnresolvedRequired` iff the element has no stored value for it (`ContentElement::getProperty($key) === null`); the type default is not consulted, because serving renders the stored `properties` verbatim and applies no default. A primitive's default reaches storage only via creation-time seeding (`Mutation` scaffold/replace) and the write-boundary `Layout/LayoutDefaultSeeder`, never at diagnosis. This mirrors the reference branch (satisfied iff a source will fill it at serving). Because satisfaction requires a stored value, a tree that reaches `content_layout` WITHOUT passing the write-boundary `Layout/LayoutDefaultSeeder` — a raw-SQL or migration write (both use `Connection`, not the DAL) or a row predating the seam — that carries a type whose required primitive declares a default but stores no value will be reported `UnresolvedRequired` and rejected the next time the resolvability gate re-checks it (e.g. a later `content_layout` layout edit, where `Validation/ContentLayoutWriteValidator` re-decodes the written tree and re-resolves it against the committed `root_source` read through `Validation/LayoutRootSourceReader`). A raw-SQL/migration writer must seed such a value itself; the DAL write path seeds it automatically. The draft `Api/ContentDiagnoseController` / preview path is likewise not seeded (only DAL writes seed), so `/diagnose` reports such a primitive as unresolved while a subsequent save would seed it and pass — diagnosis deliberately over-reports a missing required value rather than under-reporting it. (The shipped core type definitions currently pair `required` only with non-defaulted primitives or references, so no shipped type triggers this today; it is a property of the rule, not a known live break.)
- Client-defect classification: `ContentSystemException::isClientDefect()` (+ `CLIENT_DEFECT_CODES`, six codes) marks the error codes that signal a defect in client-supplied layout input — a typo'd entity (`UNKNOWN_LOADER_ENTITY`), undecodable/invalid config (`INVALID_FIELD_VALUE_TYPE`), an unregistered source (`DATA_LOADER_NOT_REGISTERED`, `CONFIG_SERIALIZER_NOT_REGISTERED`), or an element-definition context-wiring violation (`CONSUMER_ALIAS_WITHOUT_REDISTRIBUTE`, `PROPERTY_ALIAS_WITH_DOT_NOTATION`) — rather than an internal fault. `Diagnostics/LayoutDiagnostics` catches only these per element and maps them to a `ViolationCode::InvalidConfig` violation; every other code propagates, so an internal fault is never relabelled as the client's mistake. A status-code filter is insufficient — some HTTP 500 codes (e.g. `DATA_LOADER_NOT_REGISTERED`, `INVALID_FIELD_VALUE_TYPE`) are legitimate client defects for a client-supplied tree
