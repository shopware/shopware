## Source Code References

- **Entity Specification Sources**: `Content/Product/Aggregate/ProductContentLayout/ProductSpecificationSource`, `Content/Category/Aggregate/CategoryContentLayout/CategorySpecificationSource`, `Content/LandingPage/Aggregate/LandingPageContentLayout/LandingPageSpecificationSource`
- **Header/Footer Sources**: `Storefront/ContentSystem/HeaderContentLayout/HeaderSpecificationSource`, `Storefront/ContentSystem/FooterContentLayout/FooterSpecificationSource`
- **Resolver**: `Adapter/RenderingSpecificationResolver` (3 instances: main, header, footer — see DI config)
- **Events**: `Event/ContentTreePreparationEvent`, `Event/RenderedTreeFinalizationEvent`
- **Pipeline**: `ContentPipeline` (steps 3-5), `RenderingMode` (FULL vs SKELETON)
- **Layout Value Objects**: `RenderableLayout` (reference + stored elements), `LayoutReference` (id, name, version), `ResolvedContentLayout` (layout ID + `RenderingSpecification`)
- **Store API**: `SalesChannel/ContentRoute` (single class, DI-parameterized per format + section)
- **Admin Preview API**: `Api/ContentPreviewController` — one route, `POST /api/_action/content-system/preview/entity/url`, which stores an unsaved draft layout envelope behind a short-lived token (`Api/ContentPreviewPayloadStore`) and returns a Storefront preview URL (`frontend.content-system.preview`) that renders it against real entity data (assignment-free). Mint-time admission, the absent direct render route, and the payload store's contract are in [Api/AGENTS.md](Api/AGENTS.md); the wire contract in [Api/docs/preview-url.md](Api/docs/preview-url.md)
- **Resolution & Diagnostics**: `Resolution/ElementResolver` + `Resolution/AvailableContextResolver` (kernel), `Diagnostics/LayoutDiagnostics` (`analyze(tree, rootContext)` → `LayoutAnalysis`: per-element `PropertyResolution`s + a `DiagnosticsReport`), `Diagnostics/RootContextMapper` (bound source → root-ambient context). `ViolationCode` resolves a violation's scope (intrinsic/binding) + severity
- **Resolvability gate** (DAL `PreWriteValidationEvent`): two subscribers enforce served-implies-resolvable. `Validation/ContentLayoutWriteValidator` is the single ordered `content_layout` write gate — well-formedness → `root_source` membership in `Adapter/RootSourceRegistry` → resolvability against the declared root source (on a layout-only edit, membership of the committed `root_source` is re-checked before `resolve()`, so a de-registered source is an `unknownRootSource` 400, not a 500). `Validation/ContentLayoutAssignmentWriteValidator` is a tree-blind type-match that rejects an assignment whose layout's immutable `root_source` ≠ the assignment definition's `getContentLayoutEntityType()` (`rootSourceAssignmentMismatch`, 400). `Validation/LayoutGate` holds the two predicates `wellFormedness()` / `resolvability()` and the `SKIP_VALIDATION_STATE` bypass. Full gate ordering, the edit-path membership re-check, and the served-implies-resolvable stationarity caveat (the type-match assumes a layout's resolvability inputs stay stable after its write) are documented in [Validation/AGENTS.md](Validation/AGENTS.md) / [Validation/README.md](Validation/README.md)
- **Write-boundary default seeding**: `Layout/LayoutWriteBoundary`, the one admission point every layout write passes through, is reached from the DAL write chokepoint for the `layout` field (`Layout/Field/StoredElementListFieldSerializer::normalize`); its first pass `Layout/LayoutDefaultSeeder` seeds each element's type primitive defaults into stored `properties`, so every tree written to `content_layout` through the DAL carries its type defaults regardless of how it was built (direct DAL write, Sync API, import, fixtures, or the `Mutation/` ops). It never overwrites an authored value, and shares the per-type rule (`Layout/Type/PrimitiveDefaultProvider`) with the mutations. `normalize` runs before `PreWriteValidationEvent` and memoizes the admitted tree on the write `Context`, so the gate judges a seeded tree; the write validator stays a pure gate (it never rewrites). Migrations write raw SQL via `Connection` and bypass this seam
- **Delete protection**: a `content_layout` bound to any source cannot be deleted — `RestrictDelete` on the five `content_layout` OneToMany assignment associations (`Layout/Entity/ContentLayoutDefinition` for product/category/landing-page, `Storefront/.../Extension/ContentLayoutExtension` for header/footer) makes the DAL throw `RestrictDeleteViolationException` before any SQL, backed by `ON DELETE RESTRICT` on each `content_layout_id` foreign key. This is DAL-core machinery, not a content-system gate, so `SKIP_VALIDATION_STATE` does not bypass it. Sibling foreign keys (`sales_channel_id`, `domain_id`) stay `ON DELETE CASCADE` — deleting the referenced channel/domain still removes the assignment while the layout survives
- **Draft Check**: `DraftLayoutChecker` (module root) — the preview action's draft-layout check; runs the same `LayoutDiagnostics` intrinsic subset as the persistence gate
- **Resolve-and-diagnose route**: `Api/ContentDiagnoseController` (`POST /api/_action/content-system/layout/diagnose`); operates only on a draft layout tree from the request, never the persisted `content_layout` entity; an optional `rootSource` in the request resolves its root-ambient context via `Adapter/RootSourceRegistry::resolveGated()` (empty/absent → intrinsic well-formedness only)
- **Layout mutation**: `Mutation/MutationPipeline` (apply one structural edit to an already-decoded tree → diagnose the whole new tree → assemble a `Mutation/MutationResult`) drives nine `Mutation/Op` operations (`InsertElement`, `RemoveElement`, `MoveElement`, `ReplaceElement`, `DuplicateElement`, `WrapElements`, `UnwrapElement`, `AttachElement`, `BindElement`), all extending `Mutation/AbstractLayoutMutation` and editing through `Layout/StoredTree`'s own immutable tree surgery. Exposed by `Api/LayoutMutationController` (`POST /api/_action/content-system/layout/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element,bind-element}`), which decodes the request draft via the shared `Api/DraftLayoutDecoder` before the pipeline and resolves the optional request `rootSource` through `Adapter/RootSourceRegistry::resolveGated()` for the root-context binding. Operations never silently lose content: detached subtrees come back via `orphaned()` (re-placeable with `AttachElement`), dropped wiring keys via `droppedWiring()`. `AttachElement` splices a caller-supplied subtree (e.g. those orphans, or a copy) back in, reminting every id. `BindElement` applies a registered `Binding/Specification/BindingSpecification`'s wiring onto an element — see **Binding Specification System** below
- **Persisted layout mutation**: `Mutation/PersistedLayoutMutator` commits one operation to a stored `content_layout` (the persisted counterpart to `MutationPipeline`). Exposed by `Api/ContentLayoutMutationController` (`POST /api/_action/content-system/layout/{layoutId}/{insert-element,…,attach-element,bind-element}`). It loads the layout by id (`ContentSystemException::contentLayoutNotFound`, 404), guards an optimistic-concurrency token against the row's `updatedAt` (`layoutVersionConflict`, 409, no write on a mismatch; a `null` token matches a never-updated row), applies the op, then persists the mutated tree — whose write runs the resolvability gates, so a resolvability-breaking edit is rejected there. Response diagnostics are derived from the loaded layout's single `root_source` (resolved once via `RootSourceRegistry::resolve()`), not a request hint. A committed op never silently loses content: detached subtrees (`orphaned`) and dropped wiring (`droppedWiring`) are omitted from the stored tree but returned in the result, so the caller re-places them with an `attach-element` call or re-wires
- **Assignment-free resolution**: `Adapter/RenderingSpecificationResolver::resolveWithoutLayout()` selects a source via `supportsEntityType()`; `RenderingSpecificationFactory::createWithoutLayout()` assembles a `RenderingSpecification` with no layout id
- **Schema**: `Schema/ContentSystemDataLoaderMapResolver`, `Schema/ContentSystemDataLoaderMap`, `Schema/ContentSystemDataLoaderSchemaGenerator`
- **Root Source Registry**: `Adapter/RootSourceRegistry` — the single authority over the valid root-source set and their resolution. `knownRootSources()` (entity types + section keys + `none`, excludes `main`), `entityRootSources()` (entity-type subset, backs `content-system-entity-types.json`), `resolve(rootSource, Context): list<ProvidedContext>` (fail-hard on an unknown id), `sourceFor(rootSource)`. The `none` root source is `Adapter/NoneSpecificationSource`
- **Compiler Pass**: `Framework/DependencyInjection/CompilerPass/ContentSystemDataLoaderCompilerPass` — build-time validation of every `content_system.data_loader`-tagged service: its class shape, its `@extends` annotation, and a dry-run of its `configSpecification()` on an instance built without the constructor (the runtime resolver assembles the type map). Full rejection catalogue: [Hydration/DataLoader/AGENTS.md](Hydration/DataLoader/AGENTS.md)
- **Element Type Registry**: `Layout/Type/Registry/ContentSystemElementTypeRegistry`
- **Element Type API**: `GET /api/_info/content-system-element-types.json` (registered in `InfoController`); each type entry folds in its `bindingSpecifications` and its `storageSchema` (`Layout/Type/StoredSchemaResolver`), and the response carries one top-level `styleOptions` catalog
- **Style Option Registry**: `Layout/Element/Style/Registry/ContentSystemStyleOptionRegistry` (decoration trio, `cache.system`) aggregates the `content_system.style_option_loader`-tagged loaders whose YAML directories `Framework/DependencyInjection/CompilerPass/ContentSystemStyleOptionCompilerPass` discovers. Universal per-breakpoint presentation options (alignment, span, spacing, display) settable on every element; one registry feeds both validation and introspection. App options persist to `app_content_system_style_option` via `App/Lifecycle/Persister/ContentSystemStyleOptionPersister`. See [Layout/Element/Style/AGENTS.md](Layout/Element/Style/AGENTS.md)
- **Style Option API**: `GET /api/_info/content-system-style-options.json` (`InfoController::getContentSystemStyleOptions()`), plus a folded `styleOptions` key on `content-system-element-types.json`. Wire schema: `style` on the StoreApi `ContentElement` (omitted when empty)
- **Element style storage**: each element's `style` inside the `content_layout.layout` JSON (no separate column) is encoded and decoded through `Layout/Codec/StoredTreeCodec`; `Layout/Codec/StoredTreeConstraints` composes the write-time constraints against the registry (the strict write rejects unknown options, mirroring the element-type system's unknown-`component` handling). Carried through every structural edit by the `Mutation/` ops, and onto the wire out of `RenderedElement::$style` by `Output/Encoder/ContentPageEncoder` (full format) and `Output/Encoder/ContentDecomposedPageEncoder` (decomposed), and through `Output/Struct/ContentSkeletonElement` for the skeleton format; omitted when empty in all three, and absent from the data format, which serves no structure
- **Binding Specification System**: `Binding/Specification/BindingSpecification` — a declaration wiring a type's reference properties to loaders (`resolves`, keyed by property → `Binding/Specification/LoaderBinding`) and seeding its primitive properties (`inputs`, keyed by property → `Binding/Specification/BindingInput`), either authored inline in the optional top-level `bindings:` map of an element-type YAML file, or synthesized automatically (`Binding/DefaultBindingSpecificationSynthesizer`) from a type's `resolvedBy` reference properties — the resolvedBy shorthand needing no `bindings:` section at all. Loader/registry trio mirrors the style-option system: `Binding/Loader/YamlBindingSpecificationLoader` (core/bundle/plugin, plus app in dev) and `Binding/Loader/DatabaseBindingSpecificationLoader` (active app bindings in prod) are tagged `content_system.binding_specification_loader` and aggregated by `Binding/Registry/AbstractContentSystemBindingSpecificationRegistry` (`ContentSystemBindingSpecificationRegistry` leaf, `CachedContentSystemBindingSpecificationRegistry` `cache.system` decorator), discovered by `Framework/DependencyInjection/CompilerPass/ContentSystemElementTypeCompilerPass` (the single pass that injects the discovered element-type directories into both the type loader and the binding loader). Two class-level constraints gate a declaration: `Binding/Validation/WellFormedBindingSpecification` (structural shape only) then `Binding/Validation/TypeConsistentBindingSpecification` (semantic — the declared type is registered, every `resolves`/`inputs` key names an actual property or an undeclared `resolvedBy` storage key, every loader produces an assignable type). App bindings persist to `app_content_system_binding_specification` (`UNIQUE (app_id, name)`, migration `V6_7/Migration1782423128...`) via `App/Lifecycle/Persister/ContentSystemBindingSpecificationPersister`, validated at manifest time by `App/Validation/ContentSystemBindingSpecificationAppValidator`. `BindingSpecification::isDefault()` derives `id === type` (computed, never stored) — at most one default per type; `Mutation/Op/InsertElement` and `Mutation/Op/ReplaceElement` fill-apply a type's default onto every freshly scaffolded/replaced element (`Binding/BindingApplicator::applyFillOnly()`, wiring only absent keys, attributing only wired keys; zero defaults is a no-op, more than one throws), so a `resolvedBy` element needs no client-side binding step at all. `Mutation/Op/BindElement` applies a specification's wiring onto an element explicitly (`BindingApplicator::apply()`, merged into existing data requirements overwriting the same keys; an input default seeds only an unset key); `Binding/AttributionReconciler` re-derives each element's `attributedSpecifications` at the `content_layout` write boundary, dropping (never throwing on) any attribution whose wiring has since diverged. Four mutation route actions additionally let a client apply a specification explicitly (`bind()` and `insert()` on both `Api/LayoutMutationController` and `Api/ContentLayoutMutationController` — `insert()` applies an optional `bindingSpecificationId` onto the freshly scaffolded element via `BindingApplicator::apply()`, layered on top of the auto-applied default, the extracted merge `Mutation/Op/BindElement` shares), plus one introspection surface: the `bindingSpecifications` fold on each type entry of `content-system-element-types.json`, each entry's `default: bool` marking the type's synthesized default — a client derives the specifications applicable to an element from `bindingSpecifications[element.component]`. See [Binding/AGENTS.md](Binding/AGENTS.md)
- **Type-Loader Bridge**: `Schema/ContentSystemDataLoaderMap`, `Schema/ContentSystemDataLoaderMapResolver`

## Constraints

- `RenderingSpecificationResolver`: iterates sources via `supports()` bool check, first match wins — NOT null-return
- `ContentPipeline::load()`: receives a loaded `RenderableLayout` (stored elements) → `ContentTreePreparationEvent` → stored preparation (`Layout/Scaffolding/StoredTreePreparer`: placeholder resolution, then the virtual-root wrap via `Layout/Scaffolding/VirtualRootWrapper`, then the partial prune via `Output/PartialRenderer`, all still stored, returning a `Layout/Scaffolding/TreePreparationResult`) → duplicate-element-id rejection on the result's pre-prune forest → `Rendering/WiringPlanner::plan()` (wiring validation on that same pre-prune forest, then redistribute derivation on the result's pruned tree) → the render step (`Rendering/ElementLowering::lower()`: forest-wide data resolution, context-delivery resolution, rendered-tree minting; FULL does all three, SKELETON mints structure only) → the finishing steps, now on the rendered forest (`VirtualRootWrapper::unwrap()`, then `PartialRenderer::extractTarget()`, both driven by the `RenderScaffolding`) → `RenderedTreeFinalizationEvent` over the rendered forest, in both modes → duplicate-element-id rejection again, over the forest the event handed back, because a finalization listener may replace it and the pre-lowering check ran too early to see that. Both checks throw `DUPLICATE_ELEMENT_ID` (500, not a client defect) and run in either mode. It returns an `Output/RenderResult` (finished rendered forest, layout reference, optional `Output/Index/ResolvedValueIndex`), and takes both format answers from the route: the `RenderingMode` and whether the format collects a value index
- Wiring validation and redistribute derivation are the two halves of `Rendering/WiringPlanner::plan()`, deliberately split: validation judges the pre-prune forest (a defect in a subtree a partial render discards still fails the render), derivation runs on the surviving tree and throws nothing
- Specification resolution and layout-entity loading happen in `ContentRoute`, NOT in `ContentPipeline`
- OpenAPI schemas: update `src/Core/Framework/Api/ApiDefinition/Generator/Schema/StoreApi/` when modifying endpoints
- Data loader type introspection: `ContentSystemDataLoaderMapResolver` assembles the source→capability map at runtime from each loader's `producibleTypes()` (memoized per kernel runtime); `ContentSystemDataLoaderCompilerPass` only validates at build time (dry-runs `AbstractContentDataLoader::extendsDescriptor()`, so loaders MUST have `@extends AbstractContentDataLoader<T>` PHPDoc, plus the `configSpecification()` dry-run under **Compiler Pass** above); wildcard loaders (`entity`, `entity_collection`) override `producibleTypes()`/`resolveProducedType()` to enumerate the live registry (so plugin/app/custom entities appear on the next kernel boot without a container rebuild)
- Schema API endpoint: `GET /api/_info/content-system-data-loaders.json` (registered in `InfoController`)
- `ContentSystemDataLoaderMap` lookups are subtype-aware (`is_a`): `getSourcesFor($class)` returns every source whose `producedType` is the class or a subclass; `capabilityFor($source, $class)` returns that source's first matching `LoaderTypeCapability`, or `null` when the source cannot produce the class
- Entity type introspection: `ContentLayoutAssignableCompilerPass` introspects `content_system.entity_specification_source` tagged services for `AbstractContentLayoutAssignableDefinition` arguments — the entity-type id list is baked into `Adapter/RootSourceRegistry` at build time, and `InfoController::contentSystemEntityTypes()` returns `RootSourceRegistry::entityRootSources()`
- Schema API endpoint: `GET /api/_info/content-system-entity-types.json` (registered in `InfoController`)
- Type spec `properties` = hydrated output schema; the storage schema is a separate fold on the same endpoint, `storageSchema`, derived per type by `Layout/Type/StoredSchemaResolver` (stored keys, three kinds, precedence `property` > `resolvedByStorage` > `config`). The property key links type spec → dataRequirements → acceptsContext → the key `Rendering/RenderedElementFactory` writes the resolved value under on the rendered element
- Primitive property satisfaction is strict: `Diagnostics/LayoutDiagnostics` reports a required primitive as `UnresolvedRequired` iff the element has no stored value for it (`LayoutDiagnostics::hasStoredValue()`); the type default is not consulted, because serving renders the stored `properties` verbatim. A default reaches storage only through creation-time seeding (`Mutation` scaffold/replace) and the write-boundary `Layout/LayoutDefaultSeeder`, so a writer that bypasses the DAL (raw SQL, migration) must seed a required defaulted primitive itself or the next resolvability re-check rejects the row, and the unseeded draft path (`Api/ContentDiagnoseController`, preview) deliberately over-reports it. See [Diagnostics/AGENTS.md](Diagnostics/AGENTS.md)
- Client-defect classification: `ContentSystemException::isClientDefect()` (+ `CLIENT_DEFECT_CODES`, ten codes) marks the error codes that signal a defect in client-supplied layout input — a typo'd entity (`UNKNOWN_LOADER_ENTITY`), undecodable/invalid config (`INVALID_FIELD_VALUE_TYPE`), a field value outside its permitted range (`INVALID_FIELD_VALUE_RANGE`), an unregistered source (`DATA_LOADER_NOT_REGISTERED`, `CONFIG_SERIALIZER_NOT_REGISTERED`), an element-definition context-wiring violation (`CONSUMER_ALIAS_WITHOUT_REDISTRIBUTE`, `PROPERTY_ALIAS_WITH_DOT_NOTATION`), a child-facing provider-key collision (`PROVIDER_DELIVERY_COLLISION`), a numeric wiring key (`INVALID_MAP_KEY`), or an element id outside the decode gate's value domain (`INVALID_ELEMENT_ID`) — rather than an internal fault. `Diagnostics/LayoutDiagnostics` catches only these per element and maps them to a `ViolationCode::InvalidConfig` violation; every other code propagates, so an internal fault is never relabelled as the client's mistake. A status-code filter is insufficient — some HTTP 500 codes (e.g. `DATA_LOADER_NOT_REGISTERED`, `INVALID_FIELD_VALUE_TYPE`) are legitimate client defects for a client-supplied tree
