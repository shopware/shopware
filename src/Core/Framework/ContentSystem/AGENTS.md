- **Element style storage**: each element's `style` inside the `content_layout.layout` JSON (no separate column) is encoded and decoded through `Layout/Codec/StoredTreeCodec`; `Layout/Codec/StoredTreeConstraints` composes the write-time constraints against the registry (the strict write rejects unknown options, mirroring the element-type system's unknown-`component` handling). Carried through every structural edit by the `Mutation/` ops, and onto the wire out of `RenderedElement::$style` by `Output/Encoder/ContentPageEncoder` (full format) and `Output/Encoder/ContentDecomposedPageEncoder` (decomposed), and through `Output/Struct/ContentSkeletonElement` for the skeleton format; omitted when empty in all three, and absent from the data format, which serves no structure
- **Binding Specification System**: `Binding/Specification/BindingSpecification` — a declaration wiring a type's reference properties to loaders (`resolves`, keyed by property → `Binding/Specification/LoaderBinding`) and seeding its primitive properties (`inputs`, keyed by property → `Binding/Specification/BindingInput`), either authored inline in the optional top-level `bindings:` map of an element-type YAML file, or synthesized automatically (`Binding/DefaultBindingSpecificationSynthesizer`) from a type's `resolvedBy` reference properties — the resolvedBy shorthand needing no `bindings:` section at all. Loader/registry trio mirrors the style-option system: `Binding/Loader/YamlBindingSpecificationLoader` (core/bundle/plugin, plus app in dev) and `Binding/Loader/DatabaseBindingSpecificationLoader` (active app bindings in prod) are tagged `content_system.binding_specification_loader` and aggregated by `Binding/Registry/AbstractContentSystemBindingSpecificationRegistry` (`ContentSystemBindingSpecificationRegistry` leaf, `CachedContentSystemBindingSpecificationRegistry` `cache.system` decorator), discovered by `Framework/DependencyInjection/CompilerPass/ContentSystemCompilerPass` (the single pass that injects the discovered element-type directories into both the type loader and the binding loader). Two class-level constraints gate a declaration: `Binding/Validation/WellFormedBindingSpecification` (structural shape only) then `Binding/Validation/TypeConsistentBindingSpecification` (semantic — the declared type is registered, every `resolves`/`inputs` key names an actual property or an undeclared `resolvedBy` storage key, every loader produces an assignable type). App bindings persist to `app_content_system_binding_specification` (`UNIQUE (app_id, name)`, migration `V6_7/Migration1782423128...`) via `App/Lifecycle/Persister/ContentSystemBindingSpecificationPersister`, validated at manifest time by `App/Validation/ContentSystemBindingSpecificationAppValidator`. `BindingSpecification::isDefault()` derives `id === type` (computed, never stored) — at most one default per type; `Mutation/Op/InsertElement` and `Mutation/Op/ReplaceElement` fill-apply a type's default onto every freshly scaffolded/replaced element (`Binding/BindingApplicator::applyFillOnly()`, wiring only absent keys, attributing only wired keys; zero defaults is a no-op, more than one throws), so a `resolvedBy` element needs no client-side binding step at all. `Mutation/Op/BindElement` applies a specification's wiring onto an element explicitly (`BindingApplicator::apply()`, merged into existing data requirements overwriting the same keys; an input default seeds only an unset key); `Binding/AttributionReconciler` re-derives each element's `attributedSpecifications` at the `content_layout` write boundary, dropping (never throwing on) any attribution whose wiring has since diverged. Four mutation route actions additionally let a client apply a specification explicitly (`bind()` and `insert()` on both `Api/LayoutMutationController` and `Api/ContentLayoutMutationController` — `insert()` applies an optional `bindingSpecificationId` onto the freshly scaffolded element via `BindingApplicator::apply()`, layered on top of the auto-applied default, the extracted merge `Mutation/Op/BindElement` shares), plus one introspection surface: the `bindingSpecifications` fold on each type entry of `content-system-element-types.json`, each entry's `default: bool` marking the type's synthesized default — a client derives the specifications applicable to an element from `bindingSpecifications[element.component]`. See [Binding/AGENTS.md](Binding/AGENTS.md)
- **Data Mapping**: an author points a property declared `mappable: true` at the layout's root entity, stored as a root-scoped `acceptsContext` consumer keyed by the destination property and carrying a typed `source` reference (`text` → `{type: root, id: category, path: name}`). Whole values omit `path`; explicit `source` tells mappings apart from wiring `Mutation/ContextConsumerMirror` writes. `Mapping/MappingConsumers` owns that test for its three readers (`Mapping/StoredMappingInspector`, `Diagnostics/LayoutDiagnostics`, `Resolution/ElementResolver`). The offer set is curated, never derived: `Mapping/Provider/AbstractMappingCandidateProvider` implementations (tag `content_system.mapping_candidate_provider`; entity-specific providers live with their entity, while cross-cutting providers may support many roots) are aggregated by `Mapping/Registry/ContentSystemMappingCandidateRegistry`, which backs both `GET /api/_info/content-system-mapping-candidates.json` and the admissibility rules. Those rules are `Mapping/StoredMappingInspector`'s — a mapping is admitted only when the property opted in, the source reference matches a catalogued candidate, the projection matches the candidate's, and the candidate type and cardinality fit the declared property — and TWO surfaces report them from that one place: `Validation/StoredMappingValidator` refuses the `content_layout` write with a specific `CONTENT_SYSTEM__*` code per rule, and `Diagnostics/LayoutDiagnostics` reports an `invalid_mapping` violation on the diagnose and mutation routes so the Experience Studio can mark the control before save. Both are keyed on the mapped property rather than the path. The rules need the root SOURCE (a catalogue lookup), not the resolved root context, which is why `analyze()` takes it as a separate argument and a caller without one leaves mappings unjudged. Dedicated `map-property`/`unmap-property` draft and persisted mutations derive context type and projection server-side. Delivery is `Rendering/ContextDeliveryResolver`'s root overlay — see [Rendering/AGENTS.md](Rendering/AGENTS.md) for missing-source omission and projection rules
- **Property Projections**: `Mapping/Projection/AbstractContentPropertyProjection` (tag `content_system.property_projection`, aggregated by `ContentSystemPropertyProjectionRegistry`) — a named, pure reshaping applied between a mapped path and the property it fills, for data a dotted path can reach but not restructure (`product.media` is a `ProductMediaCollection` of assignment records; the gallery wants a `MediaCollection` of pictures). A candidate advertises the EFFECTIVE type and keeps its projection to itself, so the authoring UI never chooses one. Core projections live with their domain: `Content/Product/ContentSystem/Mapping/{ProductMediaToMediaProjection,ProductMediaCollectionToMediaCollectionProjection}`
- **Type-Loader Bridge**: `Schema/ContentSystemDataLoaderMap`, `Schema/ContentSystemDataLoaderMapResolver`
- **Compiler Pass**: `Framework/DependencyInjection/CompilerPass/ContentLayoutAssignableCompilerPass` — collects the assignable entity-type id list at build time and bakes it into `Adapter/RootSourceRegistry` (`$entityTypes` argument)
- **Compiler Pass**: `Framework/DependencyInjection/CompilerPass/ContentSystemPropertyProjectionCompilerPass` — build-time validation of every `content_system.property_projection`-tagged service: it extends the base class, its `name()` is unique across the container, and its `inputType()`/`outputType()` each name an existing class or a `PropertyType::PRIMITIVE_TYPES` member. Both checks guard something with no second line of defence — a duplicate name changes what stored layouts render by service order, and an unresolvable type makes the render path's input gate vacuous

## Constraints

- Specification resolution and layout-entity loading happen in `ContentRoute`, NOT in `ContentPipeline`
- `RenderingSpecificationResolver` iterates sources via a `supports()` bool check, first match wins — NOT a null-return
- Type spec `properties` is the hydrated output schema; the storage schema is the separate `storageSchema` fold derived by `Layout/Type/StoredSchemaResolver`. The property key links type spec → dataRequirements → acceptsContext → the key `Rendering/RenderedElementFactory` writes the resolved value under
- Primitive property satisfaction is strict: a required primitive with no stored value is `UnresolvedRequired`, and the type default is not consulted — serving renders stored `properties` verbatim. See [Diagnostics/AGENTS.md](Diagnostics/AGENTS.md)
- A writer that bypasses the DAL (raw SQL, migration) seeds a required defaulted primitive itself, or the next resolvability re-check rejects the row
- `ContentSystemDataLoaderMap` lookups are subtype-aware (`is_a`): `getSourcesFor($class)` returns every source whose produced type is the class or a subclass
- Introspection endpoints (`InfoController`): `content-system-{element-types,data-loaders,entity-types,root-sources,style-options}.json`
- OpenAPI schemas: update `src/Core/Framework/Api/ApiDefinition/Generator/Schema/StoreApi/` when modifying endpoints
