## Source Code References

- `ContentPreviewController` - Two routes, scope `ApiRouteScope`, both binding `ContentPreviewRequest` and delegating orchestration to `ContentPreviewPageBuilder`: `POST /api/_action/content-system/preview/entity` (name `api.action.content_system.preview.entity`) renders an unsaved draft against real entity data and returns a full-format `ContentPage`; `POST /api/_action/content-system/preview/entity/url` (name `api.action.content_system.preview.entity.url`) stores the same envelope behind a short-lived token via `ContentPreviewPayloadStore` and returns a Storefront preview URL (`frontend.content-system.preview`)
- `ContentDiagnoseController` - Route `POST /api/_action/content-system/layout/diagnose` (name `api.action.content_system.layout.diagnose`), scope `ApiRouteScope`; decodes the request draft via `DraftLayoutDecoder::decodeLintable()` (config defects become `invalid_config` diagnostics) and operates only on that draft tree — it never reads or writes the stored `content_layout` entity — returning a `DiagnoseResponse` (`{ resolutions, diagnostics, applicableBindings }`) without persisting. An optional `rootSource` enables the resolvability branch via `RootSourceRegistry::resolve()` (empty/absent → intrinsic well-formedness only). `applicableBindings` comes from `Binding/ApplicableBindingsResolver::resolve()` over the decoded tree, independent of `rootSource`
- `LayoutMutationController` - Nine routes `POST /api/_action/content-system/layout/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element,bind-element}` (names `api.action.content_system.layout.{insert,remove,move,replace,duplicate}_element`, `..._elements`, `..._element`, `attach_element`, `bind_element`), scope `ApiRouteScope`. Each action builds one `Mutation/Op` and calls private `respond()`, which decodes the draft layout via `DraftLayoutDecoder::decode()`, runs `Mutation/MutationPipeline::run()` on the decoded tree, and returns the eight-key `MutationResponse` shape without persisting. `attach` additionally decodes the supplied `element` via `DraftLayoutDecoder::decodeOne()`. `bind` builds a `Mutation/Op/BindElement` from the injected `Binding/Registry/AbstractContentSystemBindingSpecificationRegistry` and `Hydration/DataLoader/DataLoaderConfigSerializerProvider`. `resolveRootContext()` resolves the optional `rootSource` through `RootSourceRegistry::resolve()` to seed binding-scope resolvability; empty/absent → only well-formedness is evaluated
- `ContentLayoutMutationController` - The persisted counterpart to `LayoutMutationController`: nine routes `POST /api/_action/content-system/layout/{layoutId}/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element,bind-element}` (names `api.action.content_system.layout.persisted_{insert,remove,move,replace,duplicate}_element`, `..._elements`, `..._element`, `persisted_attach_element`, `persisted_bind_element`), scope `ApiRouteScope`. Each action takes the `{layoutId}` path argument plus its DTO, builds one `Mutation/Op`, and calls private `respond()`, which delegates to `Mutation/PersistedLayoutMutator::mutate()` (load by id, version-guard, apply, commit through the gates) and serializes the `MutationResult` into a `MutationResponse` like the draft routes. `attach` decodes the supplied `element` via the injected `DraftLayoutDecoder::decodeOne()`; `bind` builds the same `Mutation/Op/BindElement` as the draft route. No request source field: the response's binding-scope diagnostics are derived from the loaded layout's single `root_source` inside the mutator
- `ContentPreviewRequest` / `ContentDiagnoseRequest` / the nine draft mutation request DTOs (`InsertElementRequest`, `RemoveElementRequest`, `MoveElementRequest`, `ReplaceElementRequest`, `DuplicateElementRequest`, `WrapElementsRequest`, `UnwrapElementRequest`, `AttachElementRequest`, `BindElementRequest`) / the nine persisted mutation request DTOs (`ContentLayoutInsertRequest`, `ContentLayoutRemoveRequest`, `ContentLayoutMoveRequest`, `ContentLayoutReplaceRequest`, `ContentLayoutDuplicateRequest`, `ContentLayoutWrapElementsRequest`, `ContentLayoutUnwrapRequest`, `ContentLayoutAttachRequest`, `ContentLayoutBindRequest`) - envelope DTOs; each controller action binds its DTO via `#[MapRequestPayload(validationFailedStatusCode: Response::HTTP_BAD_REQUEST)]` on the **action parameter** (the attribute is on the parameter, not on the DTO class). `WrapElementsRequest`/`ContentLayoutWrapElementsRequest` `$elementIds` carries `#[Assert\Type('array')]` + `#[Assert\All([new Assert\Type('string'), new Assert\NotBlank()])]` + `#[Assert\Unique]`. The attach DTOs carry a raw `element` (the subtree to splice in, decoded via `DraftLayoutDecoder::decodeOne()`). `BindElementRequest`/`ContentLayoutBindRequest` carry `elementId` plus `bindingSpecificationId` (the source-qualified id, `source:id`) in place of the other DTOs' op-specific fields. The draft DTOs carry the op params, the raw `layout`, and an optional `rootSource`. The persisted DTOs carry the op params plus a required-but-nullable `expectedVersion` (the layout's `updatedAt`, `null` for a never-updated layout); they have no `layout` (the tree is loaded from storage) and no `rootSource` (the source comes from the loaded layout). `layoutId` is the route path argument, not a DTO field
- `DraftLayoutDecoder` - Shared request draft-layout decode (structural pre-decode gate + per-element `ContentElementFieldSerializer::decodeElement()`), injected into the preview, diagnose, and both mutation controllers. `decode()` is strict (malformed or config-defective element → 400 `invalidLayoutStructure`); `decodeOne()` runs the same gate on one element (the attach subtree) and returns it; `decodeLintable()` returns `[tree, list<Violation>]`, collecting client config defects as `invalid_config` violations for the diagnose route. Storage-side decode of the persisted `content_layout` column stays separate in `Validation/LayoutTreeDecoder`
- `LayoutDiagnosticsResultNormalizer` - Zero-dependency (`new`-able) normalizer for the resolutions map (`normalizeResolutions()`) and the diagnostics report (`normalizeReport()`). Instantiated inside the `MutationResponse::fromResult()` and `DiagnoseResponse::fromReport()` factories (not by the controllers) so the diagnostics half of every admin content response shares one wire shape
- `MutationResponse` - `\JsonSerializable` (`@final`, `#[Package('framework')]`) owning the mutation response wire shape for all eighteen draft + persisted routes. Private constructor plus a `fromResult(MutationResult, ContentElementFieldSerializer)` factory; the overridden `jsonSerialize()` is the single definition of the eight keys (`layout`, `resolutions`, `diagnostics`, `affectedElementIds`, `orphaned`, `droppedWiring`, `droppedProperties`, `applicableBindings`) and of which are JSON maps (`resolutions`/`droppedProperties`/`applicableBindings`, `(object)`-cast to `{}` when empty) versus lists (`[]` when empty); `applicableBindings` is itself a map whose values are `list<string>`, each `[]` when empty. Built per request by both mutation controllers' `respond()`; not a service. Output-only: serialized to the HTTP response and discarded, never cached, stored in a `SerializedField`, or `StructNormalizer::denormalize()`d
- `DiagnoseResponse` - Sibling `\JsonSerializable` for the resolve-and-diagnose route, owning its three-key shape (`resolutions`, `diagnostics`, `applicableBindings`). `fromReport(array $resolutions, DiagnosticsReport $report, array $applicableBindings)` normalizes the raw resolutions plus the already-merged report via `LayoutDiagnosticsResultNormalizer`; `jsonSerialize()` casts `resolutions` and `applicableBindings` to `{}`-when-empty. Same output-only discipline as `MutationResponse`
- Preview resolution entry: `Adapter/RenderingSpecificationResolver::resolveWithoutLayout(entityType, entityId, request, context)` — assignment-free, selects source by `supportsEntityType()`
- Root-context selection (diagnose + draft mutation routes): the request `rootSource` is resolved through `Adapter/RootSourceRegistry::resolve($rootSource, $context)`, which routes to the matching source (`sourceFor()`: entity type, section key, or `none`) and returns its `providedRootContext()`. An empty/absent `rootSource` means intrinsic well-formedness only. It does NOT use `resolveWithoutLayout()` (that is the preview path)
- Check: `DraftLayoutChecker` (module root) — preview-action draft check (intrinsic-subset diagnostics)
- Introspection endpoints the admin UI pairs with this action: `Framework/Api/Controller/InfoController` (`content-system-element-types`, `content-system-data-loader-types`, `content-system-entity-types`, `content-system-style-options`, `content-system-binding-specifications`)

## Constraints

- Draft-route failures are 400 (`ContentSystemException`): `unknownEntityType` (preview, unmatched `entityType`), `invalidLayoutStructure`, `elementTypesInvalid` (preview), the mutation structural codes `mutationTargetNotFound` / `mutationCycle` / `mutationSlotRequired` / `mutationInvalidWrapTargets` / `mutationUnknownType`, the bind-element codes `bindingSpecificationNotFound` / `bindingTypeMismatch`, plus hydration and sales-channel-context exceptions (preview). The diagnose and draft-mutation routes gate `rootSource` membership against `RootSourceRegistry::knownRootSources()` and reject an unknown non-empty `rootSource` with `unknownRootSource` (400) — the same gate as the write validator, so `RootSourceRegistry::resolve()` never sees an unregistered id. The persisted routes add two non-400 failures: `contentLayoutNotFound` (404, unknown `layoutId`) and `layoutVersionConflict` (409, stale `expectedVersion`, no write); a resolvability-breaking edit is rejected by the `content_layout` write gate (`WriteException`, 400)
- Mutation responses (draft and persisted) are the eight-key `MutationResponse` shape `{ layout, resolutions, diagnostics, affectedElementIds, orphaned, droppedWiring, droppedProperties, applicableBindings }` (HTTP 200); the draft routes never persist, the persisted routes commit the mutated tree. `layout` and `orphaned` are serialized via `ContentElementFieldSerializer::serializeContentElement()`, `resolutions` and `diagnostics` via `LayoutDiagnosticsResultNormalizer`, `applicableBindings` via `Binding/ApplicableBindingsResolver::resolve()` over the resulting tree, all inside `MutationResponse::fromResult()`. `resolutions`, `droppedProperties`, and `applicableBindings` are cast to `(object)` in `MutationResponse::jsonSerialize()` so an empty map encodes as `{}`, not `[]` (same discipline as the diagnose route's `DiagnoseResponse`); a listed element's own `applicableBindings` list stays a plain array, `[]` when its type has no applicable specification. A persisted op that detaches content (a `replace` dropping a slot's children) commits the tree without them and returns them in `orphaned`, never silently lost — the caller re-places them with an `attach-element` call
- Diagnose reports per-element client config defects as `invalid_config` violations in the response body (HTTP 200), not as errors; only non-client-defect faults propagate — see `ContentSystemException::isClientDefect()`
- `layout` is decoded via the shared `Api/DraftLayoutDecoder` (which delegates to `ContentElementFieldSerializer::decodeElement()` per element) — do NOT re-model `ContentElement` in the DTO
- Preview: no persistence, no caching — empty `RenderingCacheContext`, `RenderingMode::FULL`. Diagnose: no persistence, no rendering — it resolves and reports against the draft tree only
- `applicableBindings` is a per-element-type lookup against the binding specification registry (`Binding/ApplicableBindingsResolver`), not a resolution against an element's actual wiring or ancestry — a specification declared for a type is listed for every element of that type regardless of position. It is a response-assembly-layer concern only: never consulted by `Diagnostics/LayoutDiagnostics::analyze()` or the `content_layout` write gate
- OpenAPI: every content-system route carries an `AdminApi/paths/` entry: the introspection GET routes (`content-system-{element,data-loader,entity}-types.json`, `content-system-style-options.json`, `content-system-binding-specifications.json`) plus the preview, diagnose, draft-mutation, and persisted-mutation POST `_action` routes (`content-system-preview.json`, `content-system-diagnose.json`, `content-system-layout-mutation.json`, `content-system-layout-persisted-mutation.json`). The path files carry the request/response schemas; the full human contract (error model, examples) lives in `../ADMINISTRATION.md`
