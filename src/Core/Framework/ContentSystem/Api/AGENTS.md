## Source Code References

- `ContentPreviewController` - One route, scope `ApiRouteScope`, binding `ContentPreviewRequest` and delegating orchestration to `ContentPreviewPageBuilder`: `POST /api/_action/content-system/preview/entity/url` (name `api.action.content_system.preview.entity.url`) stores an unsaved draft envelope behind a short-lived token via `ContentPreviewPayloadStore` and returns a Storefront preview URL (`frontend.content-system.preview`). It admits the draft through `ContentPreviewPageBuilder::build()` — the same build the Storefront render route runs on redemption — and discards the page, so a draft it refuses never becomes a token, at one full build per mint. The gate is the write's own decoder (`Layout/Codec/StoredElementCodec` via `DraftLayoutDecoder`), so a non-array nested container is refused here exactly as it is on write. There is no direct render route: checking a draft's well-formedness and resolvability, without minting a token, is done through the diagnose route
- `ContentPreviewPayloadStore` - Both directions of the token-addressed preview envelope: `store(ContentPreviewRequest): string` serializes and caches for five minutes, `load(string $token): ?ContentPreviewRequest` reads back. `load()` returns `null` only for a token with no cache entry (the Storefront route's 404); a hit that is not exactly what `ContentPreviewRequest` declares — its field set, read off the constructor by reflection, and its constraint attributes, validated against the rebuilt DTO — is a `previewPayloadInvalid` 500 (`CONTENT_SYSTEM__PREVIEW_PAYLOAD_INVALID`), because the store writes only validated envelopes and the mint request rejects a non-string `queryParameters` key, so a malformed hit is server-side state
- `ContentDiagnoseController` - Route `POST /api/_action/content-system/layout/diagnose` (name `api.action.content_system.layout.diagnose`), scope `ApiRouteScope`; decodes the request draft via `DraftLayoutDecoder::decodeLintable()` (config defects become `invalid_config` diagnostics) and operates only on that draft tree — it never reads or writes the stored `content_layout` entity — returning a `DiagnoseResponse` (`{ resolutions, diagnostics }`) without persisting. An optional `rootSource` enables the resolvability branch via `RootSourceRegistry::resolveGated()` (empty/absent → intrinsic well-formedness only)
- `LayoutMutationController` - Nine routes `POST /api/_action/content-system/layout/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element,bind-element}` (names `api.action.content_system.layout.{insert,remove,move,replace,duplicate}_element`, `..._elements`, `..._element`, `attach_element`, `bind_element`), scope `ApiRouteScope`. Each action builds one `Mutation/Op` and calls private `respond()`, which decodes the draft layout via `DraftLayoutDecoder::decode()`, runs `Mutation/MutationPipeline::run()` on the decoded tree, and returns the seven-key `MutationResponse` shape without persisting. `attach` additionally decodes the supplied `element` via `DraftLayoutDecoder::decodeOne()`. `bind` builds a `Mutation/Op/BindElement`, and `insert` passes the optional `bindingSpecificationId` into `Mutation/Op/InsertElement`, both from the injected `Binding/Registry/AbstractContentSystemBindingSpecificationRegistry` and `Binding/BindingApplicator` (the controller injects the applicator, not the config serializer provider). `respond()` also resolves the optional `rootSource` via `RootSourceRegistry::resolveGated()`, membership-gated: absent/empty → `null` (only well-formedness is evaluated); a value not in `knownRootSources()` → `unknownRootSource` (400); a member value → its root-ambient context, seeding binding-scope resolvability
- `ContentLayoutMutationController` - The persisted counterpart to `LayoutMutationController`: nine routes `POST /api/_action/content-system/layout/{layoutId}/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element,bind-element}` (names `api.action.content_system.layout.persisted_{insert,remove,move,replace,duplicate}_element`, `..._elements`, `..._element`, `persisted_attach_element`, `persisted_bind_element`), scope `ApiRouteScope`. Each action takes the `{layoutId}` path argument plus its DTO, builds one `Mutation/Op`, and calls private `respond()`, which delegates to `Mutation/PersistedLayoutMutator::mutate()` (load by id, version-guard, apply, commit through the gates) and serializes the `MutationResult` into a `MutationResponse` like the draft routes. `attach` decodes the supplied `element` via the injected `DraftLayoutDecoder::decodeOne()`; `bind` builds the same `Mutation/Op/BindElement` and `insert` the same optionally-bound `Mutation/Op/InsertElement` as the draft route, both from the injected `Binding/Registry/AbstractContentSystemBindingSpecificationRegistry` and `Binding/BindingApplicator`. No request source field: the response's binding-scope diagnostics are derived from the loaded layout's single `root_source` inside the mutator
- `ContentPreviewRequest` / `ContentDiagnoseRequest` / the nine draft mutation request DTOs (`InsertElementRequest`, `RemoveElementRequest`, `MoveElementRequest`, `ReplaceElementRequest`, `DuplicateElementRequest`, `WrapElementsRequest`, `UnwrapElementRequest`, `AttachElementRequest`, `BindElementRequest`) / the nine persisted mutation request DTOs (`ContentLayoutInsertRequest`, `ContentLayoutRemoveRequest`, `ContentLayoutMoveRequest`, `ContentLayoutReplaceRequest`, `ContentLayoutDuplicateRequest`, `ContentLayoutWrapElementsRequest`, `ContentLayoutUnwrapRequest`, `ContentLayoutAttachRequest`, `ContentLayoutBindRequest`) - envelope DTOs; each controller action binds its DTO via `#[MapRequestPayload(validationFailedStatusCode: Response::HTTP_BAD_REQUEST)]` on the **action parameter** (the attribute is on the parameter, not on the DTO class). `WrapElementsRequest`/`ContentLayoutWrapElementsRequest` `$elementIds` carries `#[Assert\Type('array')]` + `#[Assert\All([new Assert\Type('string'), new Assert\NotBlank()])]` + `#[Assert\Unique]`. The attach DTOs carry a raw `element` (the subtree to splice in, decoded via `DraftLayoutDecoder::decodeOne()`). `BindElementRequest`/`ContentLayoutBindRequest` carry `elementId` plus `bindingSpecificationId` (the source-qualified id, `source:id`) in place of the other DTOs' op-specific fields. `InsertElementRequest`/`ContentLayoutInsertRequest` additionally carry an optional trailing `bindingSpecificationId` (the source-qualified id to apply onto the inserted element atomically; both DTOs stay `ALLOW_EXTRA_ATTRIBUTES => false`). The draft DTOs carry the op params, the raw `layout`, and an optional `rootSource`. The persisted DTOs carry the op params plus a required-but-nullable `expectedVersion` (the layout's `updatedAt`, `null` for a never-updated layout); they have no `layout` (the tree is loaded from storage) and no `rootSource` (the source comes from the loaded layout). `layoutId` is the route path argument, not a DTO field
- `DraftLayoutDecoder` - Shared request draft-layout decode (structural pre-decode gate + per-element `Layout/Codec/StoredElementCodec::decode()` + the write boundary's style canonicalisation), injected into the preview, diagnose, and both mutation controllers. Every decoded element's `style` is normalized through the same `Layout/StoredTreeStyleNormalizer` service `Layout/LayoutWriteBoundary` runs, on the strict and the lenient path alike, so a draft previews and diagnoses with the style shape its saved layout will carry. Style only: the boundary's default seeding and attribution reconciliation stay write-only by design, so a draft still shows unreconciled attribution and still over-reports an unseeded required default. `decode()` is strict (malformed or config-defective element → 400 `invalidLayoutStructure`); `decodeOne()` runs the same gate on one element (the attach subtree) and returns it; `decodeLintable()` returns `[tree, list<Violation>]`, collecting client config defects as `invalid_config` violations for the diagnose route. Storage-side decode of the persisted `content_layout` column stays separate, in `Layout/Field/StoredElementListFieldSerializer` via `Layout/Codec/StoredTreeCodec`; the write gate decodes nothing itself and reads the tree that serializer memoized
- `LayoutDiagnosticsResultNormalizer` - Zero-dependency (`new`-able) normalizer for the resolutions map (`normalizeResolutions()`) and the diagnostics report (`normalizeReport()`). Instantiated inside the `MutationResponse::fromResult()` and `DiagnoseResponse::fromReport()` factories (not by the controllers) so the diagnostics half of every admin content response shares one wire shape
- `MutationResponse` - `\JsonSerializable` (`@final`, `#[Package('framework')]`) owning the mutation response wire shape for all eighteen draft + persisted routes. Private constructor plus a `fromResult(MutationResult, StoredElementCodec)` factory; the overridden `jsonSerialize()` is the single definition of the seven keys (`layout`, `resolutions`, `diagnostics`, `affectedElementIds`, `orphaned`, `droppedWiring`, `droppedProperties`) and of which are JSON maps (`resolutions`/`droppedProperties`, `(object)`-cast to `{}` when empty) versus lists (`[]` when empty). Built per request by both mutation controllers' `respond()`; not a service. Output-only: serialized to the HTTP response and discarded, never cached, stored in a `SerializedField`, or `StructNormalizer::denormalize()`d
- `DiagnoseResponse` - Sibling `\JsonSerializable` for the resolve-and-diagnose route, owning its two-key shape (`resolutions`, `diagnostics`). `fromReport(array $resolutions, DiagnosticsReport $report)` normalizes the raw resolutions plus the already-merged report via `LayoutDiagnosticsResultNormalizer`; `jsonSerialize()` casts `resolutions` to `{}`-when-empty. Same output-only discipline as `MutationResponse`
- Preview resolution entry: `Adapter/RenderingSpecificationResolver::resolveWithoutLayout(entityType, entityId, request, context)` — assignment-free, selects source by `supportsEntityType()`
- Root-context selection (diagnose + draft mutation routes): the request `rootSource` is resolved through `Adapter/RootSourceRegistry::resolveGated($rootSource, $context)`, which routes to the matching source (`sourceFor()`: entity type, section key, or `none`) and returns its `providedRootContext()`. An empty/absent `rootSource` means intrinsic well-formedness only. It does NOT use `resolveWithoutLayout()` (that is the preview path)
- Check: `DraftLayoutChecker` (module root) — preview-action draft check (intrinsic-subset diagnostics)
- Introspection endpoints the admin UI pairs with this action: `Framework/Api/Controller/InfoController` (`content-system-element-types`, `content-system-data-loaders`, `content-system-entity-types`, `content-system-style-options`, `content-system-root-sources`)

## Constraints

- Draft-route failures are 400 (`ContentSystemException`): `unknownEntityType` (preview, unmatched `entityType`), `invalidLayoutStructure`, `elementTypesInvalid` (preview), the mutation structural codes `mutationTargetNotFound` / `mutationCycle` / `mutationSlotRequired` / `mutationInvalidWrapTargets` / `mutationUnknownType`, the bind-element codes `bindingSpecificationNotFound` / `bindingTypeMismatch`, plus hydration and sales-channel-context exceptions (preview). The diagnose and draft-mutation routes gate `rootSource` membership against `RootSourceRegistry::knownRootSources()` and reject an unknown non-empty `rootSource` with `unknownRootSource` (400) — the same gate as the write validator, so `RootSourceRegistry::resolve()` never sees an unregistered id. The persisted routes add two non-400 failures: `contentLayoutNotFound` (404, unknown `layoutId`) and `layoutVersionConflict` (409, stale `expectedVersion`, no write); a resolvability-breaking edit is rejected by the `content_layout` write gate (`WriteException`, 400)
- Mutation responses (draft and persisted) are the seven-key `MutationResponse` shape `{ layout, resolutions, diagnostics, affectedElementIds, orphaned, droppedWiring, droppedProperties }` (HTTP 200); the draft routes never persist, the persisted routes commit the mutated tree. `layout` and `orphaned` are serialized via `Layout/Codec/StoredElementCodec::encode()`, `resolutions` and `diagnostics` via `LayoutDiagnosticsResultNormalizer`, all inside `MutationResponse::fromResult()`. `resolutions` and `droppedProperties` are cast to `(object)` in `MutationResponse::jsonSerialize()` so an empty map encodes as `{}`, not `[]` (same discipline as the diagnose route's `DiagnoseResponse`). A persisted op that detaches content (a `replace` dropping a slot's children) commits the tree without them and returns them in `orphaned`, never silently lost — the caller re-places them with an `attach-element` call
- Diagnose reports per-element client config defects as `invalid_config` violations in the response body (HTTP 200), not as errors; only non-client-defect faults propagate — see `ContentSystemException::isClientDefect()`
- The three element-local wiring codes `PROPERTY_ALIAS_COLLISION`/`REDISTRIBUTE_DOTTED_PATH`/`REDISTRIBUTE_CONFLICT` are client defects. They are raised by `Layout/Codec/StoredElementCodec::decode()`. `DraftLayoutDecoder::decode()` aggregates them into the 400 `invalidLayoutStructure`. `decodeLintable()` collects each as `invalid_config`, attributed to the root element id from the pre-decode gate. The root is dropped from the returned tree
- `layout` is decoded via the shared `Api/DraftLayoutDecoder` (which delegates to `Layout/Codec/StoredElementCodec::decode()` per element) — do NOT re-model the element in the DTO
- Preview: no persistence, no caching — empty `RenderingCacheContext`, `RenderingMode::FULL`. Diagnose: no persistence, no rendering — it resolves and reports against the draft tree only
- A client derives the specifications applicable to an element from the `bindingSpecifications` map on that element's type entry in `content-system-element-types.json` (`bindingSpecifications[element.component]`) — a per-element-type catalog lookup, not a resolution against an element's actual wiring or ancestry
- OpenAPI: every content-system route carries an `AdminApi/paths/` entry: the introspection GET routes (`content-system-{element,data-loader,entity}-types.json`, `content-system-style-options.json`, `content-system-root-sources.json`) plus the preview, diagnose, draft-mutation, and persisted-mutation POST `_action` routes (`content-system-preview.json`, `content-system-diagnose.json`, `content-system-layout-mutation.json`, `content-system-layout-persisted-mutation.json`). The path files carry the request/response schemas; the full human contract (error model, examples) is indexed in [README.md](README.md#endpoint-reference)
