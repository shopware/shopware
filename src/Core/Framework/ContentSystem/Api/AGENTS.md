## Source Code References

- `ContentPreviewController` - Two routes, scope `ApiRouteScope`, both binding `ContentPreviewRequest` and delegating orchestration to `ContentPreviewPageBuilder`: `POST /api/_action/content-system/preview/entity` (name `api.action.content_system.preview.entity`) renders an unsaved draft against real entity data and returns a full-format `ContentPage`; `POST /api/_action/content-system/preview/entity/url` (name `api.action.content_system.preview.entity.url`) stores the same envelope behind a short-lived token via `ContentPreviewPayloadStore` and returns a Storefront preview URL (`frontend.content-system.preview`)
- `ContentDiagnoseController` - Route `POST /api/_action/content-system/layout/diagnose` (name `api.action.content_system.layout.diagnose`), scope `ApiRouteScope`; decodes the request draft via `DraftLayoutDecoder::decodeLintable()` (config defects become `invalid_config` diagnostics) and operates only on that draft tree — it never reads or writes the stored `content_layout` entity — returning a `DiagnoseResponse` (`{ resolutions, diagnostics }`) without persisting. Optional `entityType`/`section` enable the binding-resolvability branch via `SpecificationSourceLocator`
- `LayoutMutationController` - Eight routes `POST /api/_action/content-system/layout/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element}` (names `api.action.content_system.layout.{insert,remove,move,replace,duplicate}_element`, `..._elements`, `..._element`, `attach_element`), scope `ApiRouteScope`. Each action builds one `Mutation/Op` and calls private `respond()`, which decodes the draft layout via `DraftLayoutDecoder::decode()`, runs `Mutation/MutationPipeline::run()` on the decoded tree, and returns the seven-key `MutationResponse` shape without persisting. `attach` additionally decodes the supplied `element` via `DraftLayoutDecoder::decodeOne()`. `resolveRootContext()` resolves the optional `entityType` (then `section`) through `SpecificationSourceLocator` to seed binding-scope resolvability; with neither, only well-formedness is evaluated
- `ContentLayoutMutationController` - The persisted counterpart to `LayoutMutationController`: eight routes `POST /api/_action/content-system/layout/{layoutId}/{insert-element,remove-element,move-element,replace-element,duplicate-element,wrap-elements,unwrap-element,attach-element}` (names `api.action.content_system.layout.persisted_{insert,remove,move,replace,duplicate}_element`, `..._elements`, `..._element`, `persisted_attach_element`), scope `ApiRouteScope`. Each action takes the `{layoutId}` path argument plus its DTO, builds one `Mutation/Op`, and calls private `respond()`, which delegates to `Mutation/PersistedLayoutMutator::mutate()` (load by id, version-guard, apply, commit through the gates) and serializes the `MutationResult` into a `MutationResponse` like the draft routes. `attach` decodes the supplied `element` via the injected `DraftLayoutDecoder::decodeOne()`. No request `entityType`/`section`: the response's binding-scope diagnostics are derived from the layout's real bindings inside the mutator
- `ContentPreviewRequest` / `ContentDiagnoseRequest` / the eight draft mutation request DTOs (`InsertElementRequest`, `RemoveElementRequest`, `MoveElementRequest`, `ReplaceElementRequest`, `DuplicateElementRequest`, `WrapElementsRequest`, `UnwrapElementRequest`, `AttachElementRequest`) / the eight persisted mutation request DTOs (`ContentLayoutInsertRequest`, `ContentLayoutRemoveRequest`, `ContentLayoutMoveRequest`, `ContentLayoutReplaceRequest`, `ContentLayoutDuplicateRequest`, `ContentLayoutWrapElementsRequest`, `ContentLayoutUnwrapRequest`, `ContentLayoutAttachRequest`) - envelope DTOs; each controller action binds its DTO via `#[MapRequestPayload(validationFailedStatusCode: Response::HTTP_BAD_REQUEST)]` on the **action parameter** (the attribute is on the parameter, not on the DTO class). `WrapElementsRequest`/`ContentLayoutWrapElementsRequest` `$elementIds` carries `#[Assert\Type('array')]` + `#[Assert\All([new Assert\Type('string'), new Assert\NotBlank()])]` + `#[Assert\Unique]`. The attach DTOs carry a raw `element` (the subtree to splice in, decoded via `DraftLayoutDecoder::decodeOne()`). The persisted DTOs carry the op params plus a required-but-nullable `expectedVersion` (the layout's `updatedAt`, `null` for a never-updated layout); they have no `layout` (the tree is loaded from storage) and no `entityType`/`section`. `layoutId` is the route path argument, not a DTO field
- `DraftLayoutDecoder` - Shared request draft-layout decode (structural pre-decode gate + per-element `ContentElementFieldSerializer::decodeElement()`), injected into the preview, diagnose, and both mutation controllers. `decode()` is strict (malformed or config-defective element → 400 `invalidLayoutStructure`); `decodeOne()` runs the same gate on one element (the attach subtree) and returns it; `decodeLintable()` returns `[tree, list<Violation>]`, collecting client config defects as `invalid_config` violations for the diagnose route. Storage-side decode of the persisted `content_layout` column stays separate in `Validation/LayoutTreeDecoder`
- `LayoutDiagnosticsResultNormalizer` - Zero-dependency (`new`-able) normalizer for the resolutions map (`normalizeResolutions()`) and the diagnostics report (`normalizeReport()`). Instantiated inside the `MutationResponse::fromResult()` and `DiagnoseResponse::fromReport()` factories (not by the controllers) so the diagnostics half of every admin content response shares one wire shape
- `MutationResponse` - `\JsonSerializable` (`@final`, `#[Package('framework')]`) owning the mutation response wire shape for all sixteen draft + persisted routes. Private constructor plus a `fromResult(MutationResult, ContentElementFieldSerializer)` factory; the overridden `jsonSerialize()` is the single definition of the seven keys (`layout`, `resolutions`, `diagnostics`, `affectedElementIds`, `orphaned`, `droppedWiring`, `droppedProperties`) and of which are JSON maps (`resolutions`/`droppedProperties`, `(object)`-cast to `{}` when empty) versus lists (`[]` when empty). Built per request by both mutation controllers' `respond()`; not a service. Output-only: serialized to the HTTP response and discarded, never cached, stored in a `SerializedField`, or `StructNormalizer::denormalize()`d
- `DiagnoseResponse` - Sibling `\JsonSerializable` for the resolve-and-diagnose route, owning its two-key shape (`resolutions`, `diagnostics`). `fromReport(array $resolutions, DiagnosticsReport $report)` normalizes the raw resolutions plus the already-merged report via `LayoutDiagnosticsResultNormalizer`; `jsonSerialize()` casts `resolutions` to `{}`-when-empty. Same output-only discipline as `MutationResponse`
- Preview resolution entry: `Adapter/RenderingSpecificationResolver::resolveWithoutLayout(entityType, entityId, request, context)` — assignment-free, selects source by `supportsEntityType()`
- Diagnose source selection: `SpecificationSourceLocator::resolveByEntityType(entityType)` (first match over the tagged entity sources via `supportsEntityType()`) or `resolveBySection(ContentSection)` (a `ContentSection`-keyed `ServiceLocator` populated by the `content_system.specification_source` tag, `index-by="section"`); the controller then calls `->providedRootContext($context)` on the selected source to seed binding-scope resolvability. It does NOT use `resolveWithoutLayout()`
- Check: `DraftLayoutChecker` (module root) — preview-action draft check (intrinsic-subset diagnostics)
- Introspection endpoints the admin UI pairs with this action: `Framework/Api/Controller/InfoController` (`content-system-element-types`, `content-system-data-loader-types`, `content-system-entity-types`)

## Constraints

- Draft-route failures are 400 (`ContentSystemException`): `unknownEntityType`, `noSourceForSection` (diagnose/mutation `section` branch), `invalidLayoutStructure`, `elementTypesInvalid` (preview), the mutation structural codes `mutationTargetNotFound` / `mutationCycle` / `mutationSlotRequired` / `mutationInvalidWrapTargets` / `mutationUnknownType`, plus hydration and sales-channel-context exceptions (preview). The persisted routes add two non-400 failures: `contentLayoutNotFound` (404, unknown `layoutId`) and `layoutVersionConflict` (409, stale `expectedVersion`, no write); a binding-breaking edit is rejected by the `content_layout` write gate (`WriteException`, 400)
- Mutation responses (draft and persisted) are the seven-key `MutationResponse` shape `{ layout, resolutions, diagnostics, affectedElementIds, orphaned, droppedWiring, droppedProperties }` (HTTP 200); the draft routes never persist, the persisted routes commit the mutated tree. `layout` and `orphaned` are serialized via `ContentElementFieldSerializer::serializeContentElement()`, `resolutions` and `diagnostics` via `LayoutDiagnosticsResultNormalizer`, all inside `MutationResponse::fromResult()`. `resolutions` and `droppedProperties` are cast to `(object)` in `MutationResponse::jsonSerialize()` so an empty map encodes as `{}`, not `[]` (same discipline as the diagnose route's `DiagnoseResponse`). A persisted op that detaches content (a `replace` dropping a slot's children) commits the tree without them and returns them in `orphaned`, never silently lost — the caller re-places them with an `attach-element` call
- Diagnose reports per-element client config defects as `invalid_config` violations in the response body (HTTP 200), not as errors; only non-client-defect faults propagate — see `ContentSystemException::isClientDefect()`
- `layout` is decoded via the shared `Api/DraftLayoutDecoder` (which delegates to `ContentElementFieldSerializer::decodeElement()` per element) — do NOT re-model `ContentElement` in the DTO
- Preview: no persistence, no caching — empty `RenderingCacheContext`, `RenderingMode::FULL`. Diagnose: no persistence, no rendering — it resolves and reports against the draft tree only
- OpenAPI: every content-system route carries an `AdminApi/paths/` entry: the introspection GET routes (`content-system-{element,data-loader,entity}-types.json`) plus the preview, diagnose, draft-mutation, and persisted-mutation POST `_action` routes (`content-system-preview.json`, `content-system-diagnose.json`, `content-system-layout-mutation.json`, `content-system-layout-persisted-mutation.json`). The path files carry the request/response schemas; the full human contract (error model, examples) lives in `../ADMINISTRATION.md`
- Full request/response contract: `../ADMINISTRATION.md`
