# Api

Admin API controllers for the content system. Store API rendering lives in `SalesChannel/`; this directory holds Admin-scoped (`ApiRouteScope`) endpoints: layout preview, resolve-and-diagnose, the stateless draft mutation actions, and the persisted mutation actions that commit one edit to a stored layout.

## Key Classes

- `ContentPreviewController` - One action, binding `ContentPreviewRequest` via `#[MapRequestPayload]` and delegating the orchestration to `ContentPreviewPageBuilder`. Mints a short-lived, openable preview URL for an unsaved draft layout, admitting it through the same build the URL's render redeems — a draft the build gate refuses never becomes a token. The action persists nothing; the draft envelope lives only in the token store below. Route, mint mechanics, and the decode gate: [docs/preview-url.md](docs/preview-url.md).
- `ContentPreviewPageBuilder` - The shared orchestration behind both preview paths (admin `ContentPreviewController` and the Storefront `frontend.content-system.preview` render route). `build(ContentPreviewRequest, Context)` synthesizes the sales-channel context, resolves the assignment-free `RenderingSpecification`, decodes and checks the draft layout, runs `ContentPipeline` in `RenderingMode::FULL` without value-index collection, and returns `['result' => RenderResult, 'salesChannelContext' => SalesChannelContext]`.
- `ContentPreviewPayloadStore` - Holds a serialized `ContentPreviewRequest` envelope under a 32-character token in the application cache for five minutes (`expiresAfter(300)`), never in the database. `store()` mints the token (or throws `ContentSystemException::previewPayloadStoreFailed`, 500, if the cache write is rejected); `load()` returns the payload, `null` once the token addresses no entry, or throws `previewPayloadInvalid` (500) on a hit that is not exactly what `ContentPreviewRequest` declares (field set and constraints alike) — a server fault rather than a client one, because the store writes only validated envelopes and the mint action rejects everything the envelope cannot carry.
- `ContentPreviewRequest` - envelope DTO bound via `#[MapRequestPayload]` on the controller action parameter: required `layout` (raw array), `entityType`, `entityId`, `salesChannelId`; optional `languageId`, `currencyId`, `domainId`, `customerId`, `queryParameters`. The `layout` stays raw so `DraftLayoutDecoder` remains the single decode path.
- `ContentDiagnoseController` - Single `POST /api/_action/content-system/layout/diagnose` action. Decodes the draft layout from the request via `DraftLayoutDecoder` (lenient mode — element config defects surface as `invalid_config` diagnostics rather than failing the request); it never reads or writes the stored `content_layout` entity — optionally binds the request `rootSource`'s root context (via `Adapter/RootSourceRegistry::resolveGated()`), runs `Diagnostics/LayoutDiagnostics`, and returns a `DiagnoseResponse` (`{ resolutions, diagnostics }`) — per-element property resolutions and a well-formedness/resolvability report. No persistence, no rendering.
- `ContentDiagnoseRequest` - envelope DTO bound via `#[MapRequestPayload]` on the controller action parameter: optional `layout` (raw array, defaults to an empty tree), optional `rootSource`. Without `rootSource`, only intrinsic well-formedness is evaluated.
- `DraftLayoutDecoder` - Shared draft-layout decode (structural pre-decode gate plus `Layout/Codec/StoredElementCodec::decode()`) used by the preview, diagnose, and mutation routes. `decode()` is strict (a malformed or config-defective element is a 400 `invalidLayoutStructure`); `decodeLintable()` is lenient (config defects become `invalid_config` violations, the rest of the tree survives) for the diagnose route.
- `LayoutMutationController` - The stateless draft mutation actions, one per `Mutation/Op` operation. Each binds its request DTO, decodes the draft layout via `DraftLayoutDecoder`, builds one `Mutation/` operation, and runs it through `Mutation/MutationPipeline`, returning a `MutationResponse` without persisting. Routes, request contract, and error model: [docs/mutation.md](docs/mutation.md).
- `ContentLayoutMutationController` - The persisted counterpart: loads the stored layout by id, guards the `expectedVersion` token, applies the operation via `Mutation/PersistedLayoutMutator`, and commits through the resolvability gates. Routes, request contract, and error model: [docs/persisted-mutation.md](docs/persisted-mutation.md).
- Draft mutation request DTOs - One per action, each bound via `#[MapRequestPayload]`, carrying the raw `layout`, the operation's parameters, and an optional `rootSource`. Class names and field-by-field shape: [docs/mutation.md](docs/mutation.md#request).
- Persisted mutation request DTOs - One per action, each bound via `#[MapRequestPayload]`, carrying the operation's parameters plus a required-but-nullable `expectedVersion`; no `layout` field (loaded from storage) and no `rootSource` field. Class names and field-by-field shape: [docs/persisted-mutation.md](docs/persisted-mutation.md#request).
- `LayoutDiagnosticsResultNormalizer` - Zero-dependency normalizer for the diagnostics half of an admin content response (the resolutions map and the diagnostics report). Invoked inside the `MutationResponse` and `DiagnoseResponse` factories so the diagnostics half of every admin content response shares one wire shape.
- `MutationResponse` - `\JsonSerializable` owning the seven-key mutation response wire shape for every draft and persisted mutation route. Class shape and field-by-field encoding: [docs/mutation-response.md](docs/mutation-response.md).
- `DiagnoseResponse` - Sibling `\JsonSerializable` owning the resolve-and-diagnose two-key wire shape (`resolutions`, `diagnostics`). Class shape and encoding: [docs/diagnose-response.md](docs/diagnose-response.md).
