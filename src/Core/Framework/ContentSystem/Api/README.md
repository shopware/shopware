# Api

Admin API controllers for the content system. Store API rendering lives in `SalesChannel/`; this directory holds Admin-scoped (`ApiRouteScope`) endpoints: layout preview, resolve-and-diagnose, the nine stateless draft mutation actions, and the nine persisted mutation actions that commit one edit to a stored layout.

## Key Classes

- `ContentPreviewController` - Two actions, each binding `ContentPreviewRequest` via `#[MapRequestPayload]` and delegating the orchestration (synthesize a `SalesChannelContext`, resolve the entity context by entity type **without** requiring a layout assignment, decode the draft layout via `DraftLayoutDecoder`, validate it, run `ContentPipeline`) to `ContentPreviewPageBuilder`. `POST /api/_action/content-system/preview/entity` returns the full-format `ContentPage`; `POST /api/_action/content-system/preview/entity/url` instead stores the envelope via `ContentPreviewPayloadStore` and returns a Storefront preview URL. No persistence, no caching.
- `ContentPreviewPageBuilder` - The shared orchestration behind both preview paths (admin `ContentPreviewController` and the Storefront `frontend.content-system.preview` render route). `build(ContentPreviewRequest, Context)` synthesizes the sales-channel context, resolves the assignment-free `RenderingSpecification`, decodes and checks the draft layout, runs `ContentPipeline` in `RenderingMode::FULL`, and returns `['contentPage' => ContentPage, 'salesChannelContext' => SalesChannelContext]`.
- `ContentPreviewPayloadStore` - Holds a serialized `ContentPreviewRequest` envelope under a 32-character token in the application cache for five minutes (`expiresAfter(300)`), never in the database. `store()` mints the token (or throws `ContentSystemException::previewPayloadStoreFailed`, 500, if the cache write is rejected); `load()` returns the payload or `null` once it has expired. Backs the preview-URL round-trip.
- `ContentPreviewRequest` - envelope DTO bound via `#[MapRequestPayload]` on the controller action parameter: required `layout` (raw array), `entityType`, `entityId`, `salesChannelId`; optional `languageId`, `currencyId`, `domainId`, `customerId`, `queryParameters`. The `layout` stays raw so `DraftLayoutDecoder` remains the single decode path.
- `ContentDiagnoseController` - Single `POST /api/_action/content-system/layout/diagnose` action. Decodes the draft layout from the request via `DraftLayoutDecoder` (lenient mode — element config defects surface as `invalid_config` diagnostics rather than failing the request); it never reads or writes the stored `content_layout` entity — optionally binds the request `rootSource`'s root context (via `Adapter/RootSourceRegistry::resolveGated()`), runs `Diagnostics/LayoutDiagnostics`, and returns a `DiagnoseResponse` (`{ resolutions, diagnostics, applicableBindings }`) — per-element property resolutions, a well-formedness/resolvability report, and the per-element applicable binding specification ids (`Binding/ApplicableBindingsResolver`, independent of `rootSource`). No persistence, no rendering.
- `ContentDiagnoseRequest` - envelope DTO bound via `#[MapRequestPayload]` on the controller action parameter: optional `layout` (raw array, defaults to an empty tree), optional `rootSource`. Without `rootSource`, only intrinsic well-formedness is evaluated.
- `DraftLayoutDecoder` - Shared draft-layout decode (structural pre-decode gate plus `ContentElementFieldSerializer::decodeElement()`) used by the preview, diagnose, and mutation routes. `decode()` is strict (a malformed or config-defective element is a 400 `invalidLayoutStructure`); `decodeLintable()` is lenient (config defects become `invalid_config` violations, the rest of the tree survives) for the diagnose route.
- `LayoutMutationController` - Nine `POST /api/_action/content-system/layout/{insert,remove,move,replace,duplicate}-element`, `.../wrap-elements`, `.../unwrap-element`, `.../attach-element`, `.../bind-element` actions. Each binds its request DTO, decodes the draft layout via `DraftLayoutDecoder`, builds one `Mutation/` operation, and runs it through `Mutation/MutationPipeline`, returning the re-resolved layout plus a diagnostics report as a `MutationResponse`. No persistence. The optional `rootSource` binds its root context (via `Adapter/RootSourceRegistry::resolveGated()`) for binding-scope resolvability. `bind-element` applies a registered `Binding/Specification/BindingSpecification`'s wiring onto an element, sourced from the injected `Binding/Registry/AbstractContentSystemBindingSpecificationRegistry`.
- `ContentLayoutMutationController` - The persisted counterpart: nine `POST /api/_action/content-system/layout/{layoutId}/{insert,remove,move,replace,duplicate}-element`, `.../wrap-elements`, `.../unwrap-element`, `.../attach-element`, `.../bind-element` actions. Each binds its request DTO, builds one `Mutation/` operation, and runs it through `Mutation/PersistedLayoutMutator`, which loads the stored layout by id, guards the `expectedVersion` token, applies the operation, and commits the mutated tree through the resolvability gates. The response binding-scope diagnostics come from the loaded layout's single `root_source`, not a request hint.
- Draft mutation request DTOs - One per action (`InsertElementRequest`, `RemoveElementRequest`, `MoveElementRequest`, `ReplaceElementRequest`, `DuplicateElementRequest`, `WrapElementsRequest`, `UnwrapElementRequest`, `AttachElementRequest`, `BindElementRequest`), each bound via `#[MapRequestPayload]` on the controller action parameter. Each carries the raw `layout` (decoded through `DraftLayoutDecoder`) plus the operation's parameters and the optional `rootSource`. `AttachElementRequest` also carries the raw `element` subtree to splice in; `BindElementRequest` carries `elementId` plus the source-qualified `bindingSpecificationId` to apply.
- Persisted mutation request DTOs - One per action (`ContentLayoutInsertRequest`, `ContentLayoutRemoveRequest`, `ContentLayoutMoveRequest`, `ContentLayoutReplaceRequest`, `ContentLayoutDuplicateRequest`, `ContentLayoutWrapElementsRequest`, `ContentLayoutUnwrapRequest`, `ContentLayoutAttachRequest`, `ContentLayoutBindRequest`), each bound via `#[MapRequestPayload]`. Each carries the operation's parameters plus a required-but-nullable `expectedVersion` (the layout's `updatedAt`); the tree is loaded from storage, so there is no `layout` field, and `layoutId` is the route path argument.
- `LayoutDiagnosticsResultNormalizer` - Zero-dependency normalizer for the diagnostics half of an admin content response (the resolutions map and the diagnostics report). Invoked inside the `MutationResponse` and `DiagnoseResponse` factories so the diagnostics half of every admin content response shares one wire shape.
- `MutationResponse` - `\JsonSerializable` owning the mutation response wire shape (the eight keys `{ layout, resolutions, diagnostics, affectedElementIds, orphaned, droppedWiring, droppedProperties, applicableBindings }`) for all eighteen draft + persisted mutation routes. Private constructor plus a `fromResult(MutationResult, ContentElementFieldSerializer)` factory; its overridden `jsonSerialize()` is the single definition of which fields are JSON maps (`resolutions`/`droppedProperties`/`applicableBindings`, `{}` when empty) versus lists (`[]` when empty). `applicableBindings` maps element id to its applicable binding specification ids (`Binding/ApplicableBindingsResolver`), a per-type lookup independent of the element's actual wiring. Output-only: serialized to the HTTP response and discarded, never cached or denormalized.
- `DiagnoseResponse` - Sibling `\JsonSerializable` owning the resolve-and-diagnose wire shape (`{ resolutions, diagnostics, applicableBindings }`). `fromReport(array $resolutions, DiagnosticsReport, array $applicableBindings)` normalizes via `LayoutDiagnosticsResultNormalizer`, and `jsonSerialize()` casts the `resolutions` and `applicableBindings` maps to `{}`-when-empty, the same discipline as `MutationResponse`.
