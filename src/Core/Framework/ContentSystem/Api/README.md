# Api

Admin API controllers for the content system. Store API rendering lives in `SalesChannel/`; this directory holds Admin-scoped (`ApiRouteScope`) endpoints: layout preview, resolve-and-diagnose, the eight stateless draft mutation actions, and the eight persisted mutation actions that commit one edit to a stored layout.

## Key Classes

- `ContentPreviewController` - Single `POST /api/_action/content-system/preview/entity` action. Synthesizes a `SalesChannelContext`, resolves the entity context by entity type **without** requiring a layout assignment, decodes the draft layout via `DraftLayoutDecoder`, validates it, runs `ContentPipeline`, and returns a full-format `ContentPage`. No persistence, no caching.
- `ContentPreviewRequest` - envelope DTO bound via `#[MapRequestPayload]` on the controller action parameter: required `layout` (raw array), `entityType`, `entityId`, `salesChannelId`; optional `languageId`, `currencyId`, `domainId`, `customerId`, `queryParameters`. The `layout` stays raw so `DraftLayoutDecoder` remains the single decode path.
- `ContentDiagnoseController` - Single `POST /api/_action/content-system/layout/diagnose` action. Decodes the draft layout from the request via `DraftLayoutDecoder` (lenient mode — element config defects surface as `invalid_config` diagnostics rather than failing the request); it never reads or writes the stored `content_layout` entity — optionally binds a source's root context (via `SpecificationSourceLocator`), runs `Diagnostics/LayoutDiagnostics`, and returns `{ resolutions, diagnostics }` — per-element property resolutions plus a well-formedness/resolvability report. No persistence, no rendering.
- `ContentDiagnoseRequest` - envelope DTO bound via `#[MapRequestPayload]` on the controller action parameter: optional `layout` (raw array, defaults to an empty tree), optional `entityType`, optional `section`. With neither source field, only intrinsic well-formedness is evaluated.
- `DraftLayoutDecoder` - Shared draft-layout decode (structural pre-decode gate plus `ContentElementFieldSerializer::decodeElement()`) used by the preview, diagnose, and mutation routes. `decode()` is strict (a malformed or config-defective element is a 400 `invalidLayoutStructure`); `decodeLintable()` is lenient (config defects become `invalid_config` violations, the rest of the tree survives) for the diagnose route.
- `SpecificationSourceLocator` - Request-time source selection shared by the diagnose and mutation routes: `resolveByEntityType()` first-matches the tagged entity sources via `supportsEntityType()`; `resolveBySection()` reads a `ContentSection`-keyed `ServiceLocator`. The route calls `providedRootContext()` on the returned source.
- `LayoutMutationController` - Eight `POST /api/_action/content-system/layout/{insert,remove,move,replace,duplicate}-element`, `.../wrap-elements`, `.../unwrap-element`, `.../attach-element` actions. Each binds its request DTO, decodes the draft layout via `DraftLayoutDecoder`, builds one `Mutation/` operation, and runs it through `Mutation/MutationPipeline`, returning the re-resolved layout plus a diagnostics report. No persistence. The optional `entityType`/`section` binds a source's root context (via `SpecificationSourceLocator`) for binding-scope resolvability.
- `ContentLayoutMutationController` - The persisted counterpart: eight `POST /api/_action/content-system/layout/{layoutId}/{insert,remove,move,replace,duplicate}-element`, `.../wrap-elements`, `.../unwrap-element`, `.../attach-element` actions. Each binds its request DTO, builds one `Mutation/` operation, and runs it through `Mutation/PersistedLayoutMutator`, which loads the stored layout by id, guards the `expectedVersion` token, applies the operation, and commits the mutated tree through the resolvability gates. The response binding-scope diagnostics come from the layout's real bindings, not a request hint.
- Draft mutation request DTOs - One per action (`InsertElementRequest`, `RemoveElementRequest`, `MoveElementRequest`, `ReplaceElementRequest`, `DuplicateElementRequest`, `WrapElementsRequest`, `UnwrapElementRequest`, `AttachElementRequest`), each bound via `#[MapRequestPayload]` on the controller action parameter. Each carries the raw `layout` (decoded through `DraftLayoutDecoder`) plus the operation's parameters and the optional `entityType`/`section`. `AttachElementRequest` also carries the raw `element` subtree to splice in.
- Persisted mutation request DTOs - One per action (`ContentLayoutInsertRequest`, `ContentLayoutRemoveRequest`, `ContentLayoutMoveRequest`, `ContentLayoutReplaceRequest`, `ContentLayoutDuplicateRequest`, `ContentLayoutWrapRequest`, `ContentLayoutUnwrapRequest`, `ContentLayoutAttachRequest`), each bound via `#[MapRequestPayload]`. Each carries the operation's parameters plus a required-but-nullable `expectedVersion` (the layout's `updatedAt`); the tree is loaded from storage, so there is no `layout` field, and `layoutId` is the route path argument.
- `LayoutDiagnosticsResultNormalizer` - Zero-dependency normalizer for the diagnostics half of an admin content response (the resolutions map and the diagnostics report). Shared by the diagnose, draft-mutation, and persisted-mutation controllers so they emit the same wire shape.
