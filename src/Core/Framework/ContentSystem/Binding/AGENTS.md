## Source Code References

- **Value objects** (`Specification/`): `BindingSpecification` (`id`, `type`, `label`, `resolves (array<string, LoaderBinding>)`, `inputs (array<string, BindingInput>)`, `source`; `qualifiedId()` — the source-qualified `source:id` registry key and wire identifier, `isDefault()` — derived (`id === type`), never stored, `toSchema()` for introspection — always emits `default: bool`), `LoaderBinding` (`source`, `config`), `BindingInput` (`hasDefault (bool)`, `default (mixed)` — presence-gated, not null-gated, `required (bool)` — derived by the canonicalizer)
- **resolvedBy loader branch**: `ResolvedByLoaderBranch` (module root; `@internal` enum, cases `Entity`/`EntityCollection`) — the closed tier-A classification a `resolvedBy` bare property-reference string resolves against: `fromReferenceFqcn(fqcn)` maps an `Entity`/`EntityCollection` subclass to its branch (`null` for neither); `loaderSource()` returns the built-in loader's `SOURCE` constant (`EntityLoader::SOURCE` / `EntityCollectionLoader::SOURCE`, never a bare string literal); `fromLoaderSource(source)` is the inverse, used by `ReplaceElement` to recognize a carryable storage key; `matchesStoredValueShape(value)` is the per-branch stored-value shape check (a string for `Entity`, a list of strings for `EntityCollection`), deliberately stricter than the tolerant list-filtering the `entity_collection` loader applies at serve time
- **Default synthesizer**: `DefaultBindingSpecificationSynthesizer` (module root; `@internal`) — injected into `YamlBindingSpecificationLoader`, invoked once per type file regardless of whether the file also carries a `bindings:` key. `synthesize(data, type, path): ?array` scans the file's raw parsed `properties` map (before any type-pipeline validation) for `resolvedBy` keys; returns `null` when none are present, otherwise a raw specification-data array (`type`, `label` — `meta.label` falling back to the type name —, `resolves` — one entry per `resolvedBy` property, fed through the standard load path — and no `inputs`) fed through the same denormalize/canonicalize/validate path as an authored entry. Enforces its own `MAX_ID_LENGTH = 255` on the minted id (the type name) and the storage-key collision rules (a storage key colliding with a declared property key, or two `resolvedBy` properties of one type naming the same storage key) as hard load errors naming the file
- **Registry**: `Registry/AbstractContentSystemBindingSpecificationRegistry` (abstract, decoration pattern; `all(): array<string, BindingSpecification>` keyed by source-qualified id `"source:id"`, `byType(type): list<BindingSpecification>`, `get(qualifiedId): ?BindingSpecification`, `invalidate()`), `Registry/ContentSystemBindingSpecificationRegistry` (stateless aggregator over loaders tagged `content_system.binding_specification_loader`; `all()` merges every loader's specifications keyed by source-qualified id, throwing `bindingSpecificationDuplicate` on a collision — see Constraints), `Registry/CachedContentSystemBindingSpecificationRegistry` (`cache.system` pool decorator, single cache key `content_system.binding_specifications`)
- **Compiler Pass**: `Framework/DependencyInjection/CompilerPass/ContentSystemElementTypeCompilerPass` — the single pass that discovers the element-type directories and injects them into both `Layout/Type/Loader/YamlTypeLoader` and `YamlBindingSpecificationLoader`; the binding loader scans those same directories' files for their inline `bindings:` sections. The directory set is core `Layout/Type/Definitions` (prefix `Sw`), each non-plugin bundle's `Resources/content-system/types` (prefix `Sw`), each active plugin's `Plugin::getContentTypeDirectory()` (prefix = plugin name), and dev-only each active app's `Resources/content-system/types` (prefix = app name). Each loader receives its own `ElementTypeSourceDirectory` definition instances. Any new throw uses `DependencyInjectionException` (the namespace must not throw `ContentSystemException`)

- **Serializer**: `Serialization/BindingSpecificationSerializer` (`denormalize` array → DTO; `normalize` DTO → array, used to hash/persist an app binding's schema)
- **Canonicalizer**: `Serialization/BindingSpecificationCanonicalizer` — load-time expansion of sugared `resolves` entries into canonical `{loader, config}` form (tier A bare string / tier B single-key loader form / tier C canonical). Tier B and tier C are driven entirely by the loaders' `Hydration/DataLoader/LoaderConfigSpecification` kinds, so no rule names a loader source; tier A is the exception — a closed classification (`ResolvedByLoaderBranch`) that resolves a bare string directly to the `entity` or `entity_collection` loader by the reference property's declared FQCN (`Entity` vs. `EntityCollection` subclass), never a registry search. - **Specification DTO**: `Specification/Dto/BindingSpecificationDto` (`#[WellFormedBindingSpecification]` only; the id is not carried here — it is the `bindings:` map key, supplied to `toBindingSpecification(id, source)` by the loader), `Specification/Dto/BindingSpecificationDtoCollection` (`#[TypeConsistentBindingSpecification]` at the class level, plus a `typeOverlay` field the semantic validator reads — a per-load overlay cannot ride the DI `ValidatorInterface`, so it is carried on the validated object)

- **Applicator**: `BindingApplicator` (final instance service, injects `Hydration/DataLoader/DataLoaderConfigSerializerProvider`) — the apply-side of a binding decision, extracted so `Mutation/Op/BindElement`, `Mutation/Op/InsertElement`, and `Mutation/Op/ReplaceElement` share it (naming rationale in `../NAMING.md`). ## Constraints

- Uniqueness is by source-qualified id (`"source:id"`), not by bare id: `ContentSystemBindingSpecificationRegistry::all()` keys on `BindingSpecification::qualifiedId()`, so two different sources (e.g. two apps, or core and a plugin) may legitimately declare the same bare id — only a duplicate **within** one source/directory throws `bindingSpecificationDuplicate`. This is intentionally looser than the style-option system's flat global namespace: a binding is scoped to the element type it declares, not a Store-API wire key
- The two validators sit at different levels: `WellFormedBindingSpecification` (shape) is class-level on `BindingSpecificationDto` and runs per dto via the collection's `#[Assert\Valid]` cascade; `TypeConsistentBindingSpecification` (live registries) is class-level on `BindingSpecificationDtoCollection` and iterates the collection's dtos itself. Both still run; `TypeConsistent` re-checks `resolves`/`inputs` array-shapes internally, so a shape violation on an entry does not also produce a confusing semantic violation on the same entry. `TypeConsistent` resolves each dto's declared type overlay-first (the collection's `typeOverlay`) then registry — DB-sourced rows validate with an empty overlay (registry only, app active at that point), exactly as before
- **App type overlay:** an app inline binding's implicit type is always one of the app's own types — the persister and validator scan only the app's own `Resources/content-system/types` with the app's own name as prefix, so the overlay built from those same type files always covers it and an app binding can never target another app's type. The registry half of overlay-then-registry serves the non-app paths instead: `YamlBindingSpecificationLoader::load()` (the compiler-pass scan) and `DatabaseBindingSpecificationLoader` rows both pass an empty overlay, so the registry is their only resolution. A malformed app type file makes the app validator's `buildTypeOverlay` fall back to an empty overlay, so the binding surfaces as `bindingSpecificationUnknownType` (reported as a schema error, never an exception); on the persister path the same malformed file fails the install (wrapped `AppException`) before the binding load runs
- **Default uniqueness** is at most one default specification per element type — `BindingSpecification::isDefault()` derives `id === type` (computed, never stored), so the guarantee rests on four mechanisms rather than a runtime check: type names are globally unique across sources; a synthesized specification's type is always its own containing file's type, so only the owning source can synthesize it; the app persister and validator resolve app types through the app's own overlay only; the dev/prod loader split means an app's specifications come from exactly one loader per environment. An authored `bindings:` entry can never claim the reserved id (`bindingSpecificationReservedId`, 409, at load). At *application* time (not load time) the default set for a type (`byType(type)` filtered by `isDefault()`, `AbstractLayoutMutation::resolveDefaultSpecification()`) is read as zero/one/more: zero is a no-op, one is fill-applied, more than one throws `bindingSpecificationDefaultAmbiguous` (409) — the one case the four mechanisms do not prevent is an out-of-lifecycle database row that fakes `id === type` for a foreign type, which collides into that 409 only when a legitimate default coexists; for a type with no legitimate default the lone fake is read as the sole default and silently fill-applied
- `TypeConsistentBindingSpecification` decodes each `resolves` entry's loader config and resolves its produced type via the same `Diagnostics/RootContextMapper::resolveType()` the diagnostics kernel uses, so a specification that would fail at diagnosis time is rejected at load time instead — a client-defect exception becomes a validation violation, any other exception propagates
- `BindingApplicator::apply()` (overwrite; shared by `Mutation/Op/BindElement` and the explicit path of `Mutation/Op/InsertElement`) merge order is caller-overwrites-nothing at the wiring/attribution level but element-overwrites-loser at the property-default level: `resolves`/attribution entries from the applied specification win over the element's prior entries for the same key (re-binding replaces), while `inputs` defaults are the merge **base** (existing properties spread on top), so an authored value — including an explicit `null` — always wins over a seeded default. `applyFillOnly()` (fill-only; the auto-applied-default path of `Mutation/Op/InsertElement` and `Mutation/Op/ReplaceElement`) inverts the wiring/attribution rule to caller-existing-wins entirely: a `resolves` entry is wired and attributed only into a key the element carries no data requirement for yet; `inputs` seeding is unchanged (`hasProperty()` gate)
- `AttributionReconciler` is a drop-not-throw seam by design: attribution is bookkeeping over the element's real wiring, not a constraint the write should fail over. A user who hand-edits a key's wiring away from its attributed specification simply loses that key's attribution on the next write; every other key's attribution is evaluated independently
- Registered as `content_system.binding_specification_loader` (loader tag, parallel to `content_system.style_option_loader`); `ContentSystemElementTypeCompilerPass` — the single element-type discovery pass — injects the discovered element-type directories into this loader as well as the type loader (see the Compiler Pass bullet above). Core ships no dedicated binding-specification directory and no authored inline `bindings:` entry: core's only binding specification, `core:Sw:Media:Image`, is `DefaultBindingSpecificationSynthesizer`'s synthesized default for the Image type's `resolvedBy` property (`Layout/Type/Definitions/media/image.yaml`), wiring `media` from its own `mediaId` storage key via the `entity` loader
- `DatabaseBindingSpecificationLoader` returns empty in dev (apps load from the filesystem via the compiler pass in dev), mirroring `DatabaseStyleOptionLoader`. Each row is validated independently (identified by `source:id`, so no bare-id collision); a row whose schema fails to decode or validate is skipped and logged at `warning` level rather than failing the whole load — unlike `YamlBindingSpecificationLoader`, which fails hard on an authored file.
- This subsystem does not share implementation with `Layout/Element/Style/` beyond following the same shape (loader trio, decorated registry, compiler pass, app tier); see README "Design Note: Deliberate Duplication"
