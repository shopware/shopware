## Constraints

- Uniqueness is by source-qualified id (`"source:id"`), not by bare id: `ContentSystemBindingSpecificationRegistry::all()` keys on `BindingSpecification::qualifiedId()`, so two different sources (e.g. two apps, or core and a plugin) may legitimately declare the same bare id — only a duplicate **within** one source/directory throws `bindingSpecificationDuplicate`. This is intentionally looser than the style-option system's flat global namespace: a binding is scoped to the element type it declares, not a Store-API wire key
- The two validators sit at different levels: `WellFormedBindingSpecification` (shape) is class-level on `BindingSpecificationDto` and runs per dto via the collection's `#[Assert\Valid]` cascade; `TypeConsistentBindingSpecification` (live registries) is class-level on `BindingSpecificationDtoCollection` and iterates the collection's dtos itself. Both still run; `TypeConsistent` re-checks `resolves`/`inputs` array-shapes internally, so a shape violation on an entry does not also produce a confusing semantic violation on the same entry. `TypeConsistent` resolves each dto's declared type overlay-first (the collection's `typeOverlay`) then registry — DB-sourced rows validate with an empty overlay (registry only, app active at that point), exactly as before
- **App type overlay:** an app inline binding's implicit type is always one of the app's own types — the persister and validator scan only the app's own `Resources/content-system/types` with the app's own name as prefix, so the overlay built from those same type files always covers it and an app binding can never target another app's type. The registry half of overlay-then-registry serves the non-app paths instead: `YamlBindingSpecificationLoader::load()` (the compiler-pass scan) and `DatabaseBindingSpecificationLoader` rows both pass an empty overlay, so the registry is their only resolution. A malformed app type file makes the app validator's `buildTypeOverlay` fall back to an empty overlay, so the binding surfaces as `bindingSpecificationUnknownType` (reported as a schema error, never an exception); on the persister path the same malformed file fails the install (wrapped `AppException`) before the binding load runs
- **Promoted uniqueness** is at most one promoted specification per element type, enforced at two points: **hard** in `YamlBindingSpecificationLoader::load()` (`bindingSpecificationPromotedDuplicate`, 409, across all its directories/sources) and **soft** in the app validator (a schema error when the app promotes one type twice across its own specifications — an own-set check, independent of the aggregated registry). `promoted` is pure catalog metadata — no server behavior (scaffold, gate, `bind-element`) reads it
- `TypeConsistentBindingSpecification` decodes each `resolves` entry's loader config and resolves its produced type via the same `Diagnostics/RootContextMapper::resolveType()` the diagnostics kernel uses, so a specification that would fail at diagnosis time is rejected at load time instead — a client-defect exception becomes a validation violation, any other exception propagates
- `BindingApplicator::apply()` merge order (shared by `Mutation/Op/BindElement` and `Mutation/Op/InsertElement`) is caller-overwrites-nothing at the wiring/attribution level but element-overwrites-loser at the property-default level: `resolves`/attribution entries from the applied specification win over the element's prior entries for the same key (re-binding replaces), while `inputs` defaults are the merge **base** (existing properties spread on top), so an authored value — including an explicit `null` — always wins over a seeded default
- `AttributionReconciler` is a drop-not-throw seam by design: attribution is bookkeeping over the element's real wiring, not a constraint the write should fail over. A user who hand-edits a key's wiring away from its attributed specification simply loses that key's attribution on the next write; every other key's attribution is evaluated independently
- Registered as `content_system.binding_specification_loader` (loader tag, parallel to `content_system.style_option_loader`); `ContentSystemElementTypeCompilerPass` — the single element-type discovery pass — injects the discovered element-type directories into this loader as well as the type loader (see the Compiler Pass bullet above). Core ships no dedicated binding-specification directory: `core:from-media-library`, wiring the Image element's `media` reference from its own `mediaId` via the `entity` loader, is authored inline in `Layout/Type/Definitions/media/image.yaml`'s `bindings:` section
- `DatabaseBindingSpecificationLoader` returns empty in dev (apps load from the filesystem via the compiler pass in dev), mirroring `DatabaseStyleOptionLoader`. Each row is validated independently (identified by `source:id`, so no bare-id collision); a row whose schema fails to decode or validate is skipped and logged at `warning` level rather than failing the whole load — unlike `YamlBindingSpecificationLoader`, which fails hard on an authored file.
- This subsystem does not share implementation with `Layout/Element/Style/` beyond following the same shape (loader trio, decorated registry, compiler pass, app tier); see README "Design Note: Deliberate Duplication"
