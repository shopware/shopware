## Constraints

- Uniqueness is by source-qualified id (`"source:id"`), not by bare id: `ContentSystemBindingSpecificationRegistry::all()` keys on `source() . ':' . id()`, so two different sources (e.g. two apps, or core and a plugin) may legitimately declare the same bare id — only a duplicate **within** one source/directory throws `bindingSpecificationDuplicate`. This is intentionally looser than the style-option system's flat global namespace: a binding is scoped to the element type it declares, not a Store-API wire key
- The two validators run in a fixed order via the class-level constraint stack on `BindingSpecificationDto`: `WellFormedBindingSpecification` (shape) always runs; `TypeConsistentBindingSpecification` (live registries) inspects `resolves`/`inputs` entries only when they are already array-shaped, so a shape violation on an entry does not also produce a confusing semantic violation on the same entry
- `TypeConsistentBindingSpecification` decodes each `resolves` entry's loader config and resolves its produced type via the same `Diagnostics/RootContextMapper::resolveType()` the diagnostics kernel uses, so a specification that would fail at diagnosis time is rejected at load time instead — a client-defect exception becomes a validation violation, any other exception propagates
- `BindElement::apply()` merge order is caller-overwrites-nothing at the wiring/attribution level but element-overwrites-loser at the property-default level: `resolves`/attribution entries from the applied specification win over the element's prior entries for the same key (re-binding replaces), while `inputs` defaults are the merge **base** (existing properties spread on top), so an authored value — including an explicit `null` — always wins over a seeded default
- `AttributionReconciler` is a drop-not-throw seam by design: attribution is bookkeeping over the element's real wiring, not a constraint the write should fail over. A user who hand-edits a key's wiring away from its attributed specification simply loses that key's attribution on the next write; every other key's attribution is evaluated independently
- Registered as `content_system.binding_specification_loader` (loader tag, parallel to `content_system.style_option_loader`); the compiler pass mirrors `ContentSystemStyleOptionCompilerPass` except the discovered directory is `Resources/content-system/binding-specifications` and the core source directory is `Binding/Definitions` (ships `media/image/from-media-library.yaml`, which wires the Image element's `media` reference from its own `mediaId` via the `entity` loader)
- `DatabaseBindingSpecificationLoader` returns empty in dev (apps load from the filesystem via the compiler pass in dev), mirroring `DatabaseStyleOptionLoader`. Each row is validated independently (identified by `source:id`, so no bare-id collision); a row whose schema fails to decode or validate is skipped and logged at `warning` level rather than failing the whole load — unlike `YamlBindingSpecificationLoader`, which fails hard on an authored file.
- `ApplicableBindingsResolver::resolve()` is a per-`component` lookup, not a resolution against an element's actual wiring or ancestry: a specification declared for a type is listed for every element of that type regardless of position or existing bindings
- This subsystem does not share implementation with `Layout/Element/Style/` beyond following the same shape (loader trio, decorated registry, compiler pass, app tier); see README "Design Note: Deliberate Duplication"
