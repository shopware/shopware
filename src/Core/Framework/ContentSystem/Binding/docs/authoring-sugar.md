# Authoring Sugar and Canonicalization

The three shapes a `resolves` entry may be authored in, and the load-time expansion that reduces them to one.

An author can write a `resolves` entry in one of three shapes; `Serialization/BindingSpecificationCanonicalizer` expands the first two into the third at load time, between `Serialization/BindingSpecificationSerializer::denormalize()` and constraint validation, so the two validators only ever see canonical `{loader, config}` entries. Tier B and tier C name no loader source — both key off the loaders' declared config specifications (`Hydration/DataLoader/LoaderConfigSpecification`), so an extension loader that declares the same `ConfigKeyKind`s participates identically. Tier A is the one exception: it resolves directly to one of the two built-in resolvedBy loaders (`ResolvedByLoaderBranch`), a closed rule no loader-registry search can change.

- **Tier A — a bare property-reference string** (`media: mediaId`): closed to two branches by the reference property's declared FQCN — a subclass of `Entity` resolves to the built-in `entity` loader, a subclass of `EntityCollection` to the built-in `entity_collection` loader (the string fills each loader's `property` key); anything else is a hard load error naming the tier B/C fix. No loader search runs, and installing an extension loader can neither expand nor break tier A. The FQCN-to-entity-name derivation for the loader's `entity` key (the branch-parameterized `deriveEntityName()`) still ranges over the open entity registry — see [entity-name-derivation.md](entity-name-derivation.md).
- **Tier B — the single-key loader form** (`media: { entity: { property: mediaId } }`): the one key names the loader source, its value is the flat config; every required `entityName`-kind key absent from that config is derived from the reference property's FQCN. A config key the loader does not declare is a load-time error.
- **Tier C — the canonical form** (`media: { loader: entity, config: { entity: media, property: mediaId } }`): passed through unchanged; the only shape for unusual configs.

The canonicalizer injects `AbstractContentSystemElementTypeRegistry` (declared FQCNs, registered-type gate), `AbstractContentSystemDataLoaderMapResolver` (loader config specifications only, via `resolve()->configSpecificationFor()`/`sourceToConfigSpecifications` — tier B/C key resolution and the mixed-source guard; tier A never reads the map, it resolves directly against `ResolvedByLoaderBranch`), and `DefinitionInstanceRegistry`/`SalesChannelDefinitionInstanceRegistry` (FQCN → entity-name derivation, still open-registry for both tier A's automatic `entity` key and an unauthored tier-B `entityName` key).

Every specification the canonicalizer processes — sugared or already canonical — must declare a registered element type; an unknown type is a hard load error (`ContentSystemException::bindingSpecificationUnknownType`, 400). Any sugar that cannot expand deterministically (an unrecognized entry shape, a `loader` key mixed with a loader-source key, a tier-A reference FQCN that is neither an `Entity` nor an `EntityCollection` subclass, zero or several entities producing the FQCN, an unknown tier-B config key) is a hard load error (`ContentSystemException::bindingSpecificationCanonicalizationFailed`, 400) whose message carries the mechanical fix. Sugar never resolves by precedence and never degrades to a best guess. `DatabaseBindingSpecificationLoader` never canonicalizes: app rows are persisted canonical by construction.
