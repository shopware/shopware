# Two Validators, Two Concerns

The two class-level constraints every binding declaration passes at load time, and why they sit at different levels.

Every declaration passes two constraints, at two levels:

- **`Validation/WellFormedBindingSpecification`** — class-level on `BindingSpecificationDto`, structural shape only: `type`/`label` non-blank, `resolves`/`inputs` (if present) are arrays of arrays, each `resolves` entry declares a non-blank `loader`, each `inputs` entry's `default` (if present) is a scalar or `null`. No registry lookups. Runs per dto via the collection's `#[Assert\Valid]` cascade.
- **`Validation/TypeConsistentBindingSpecification`** — class-level on `BindingSpecificationDtoCollection` (not the dto), semantic consistency against live registries: it iterates the collection's dtos and, for each, resolves the declared `type` **overlay-first then registry** (the collection carries a per-load `typeOverlay`, empty on every non-app path); every `resolves` key names a reference property the type actually has, and the configured loader's produced type is assignable to that property's declared FQCN; every `propertyReference` config key of any loader names either a declared primitive property or an undeclared key (a `resolvedBy` storage key — a typo and an intentional storage key are indistinguishable by construction, so this is accepted and fails safe downstream); a declared *non-primitive* property is still a violation. Every `inputs` key names a primitive property, and a present `default` matches that property's declared type. Violation paths are keyed on the binding id (`bindings[<id>].…`).

The validator injects `AbstractContentSystemElementTypeRegistry`, `DataLoaderConfigSerializerProvider`, `Diagnostics/RootContextMapper`, and `AbstractContentSystemDataLoaderMapResolver`: it decodes each `resolves` entry's loader config and resolves its produced type via the same `Diagnostics/RootContextMapper::resolveType()` the diagnostics kernel uses, so a specification that would fail at diagnosis time is rejected at load time instead — a client-defect exception becomes a validation violation, any other exception propagates. Both constraints still run; `TypeConsistentBindingSpecification` re-checks `resolves`/`inputs` array-shapes internally, so a shape violation on an entry does not also produce a confusing semantic violation on the same entry.

The constraint lives on the collection because a per-load type overlay cannot ride through the dependency-injected `ValidatorInterface`, but it can be a field on the validated object that the validator reads. Splitting shape (dto) from semantics (collection) still mirrors the element-type and style-option systems' "shape first, then live-registry consistency" load-time gate, so a malformed declaration and a declaration that targets a real but wrong property fail with distinctly diagnosable violations.
