# Two Validators, Two Concerns

Every declaration passes its constraints at two levels:

- **`Validation/WellFormedBindingSpecification`**: class-level on `BindingSpecificationDto`, structural shape only: `type`/`label` non-blank, `resolves`/`inputs` (if present) are arrays of arrays. Each `resolves` entry declares a non-blank `loader`. Each `inputs` entry's `default` (if present) is a scalar or `null`. No registry lookups. Runs per dto via the collection's `#[Assert\Valid]` cascade.
- **`Validation/TypeConsistentBindingSpecification`**: class-level on `BindingSpecificationDtoCollection` (not the dto), semantic consistency against live registries. It iterates the collection's dtos and, for each, resolves the declared `type` **overlay-first then registry** (the collection carries a per-load `typeOverlay`, empty on every non-app path). Every `resolves` key names a reference property the type actually has, and the configured loader's produced type is assignable to that property's declared FQCN. Every `propertyReference` config key of any loader names either a declared primitive property or an undeclared key (a `resolvedBy` storage key). A typo and an intentional storage key are indistinguishable by construction, so this is accepted and fails safe downstream. A declared *non-primitive* property is still a violation. So is a declared primitive that cannot hold a value the key's `referencedType` admits, decided by `Hydration/DataLoader/ConfigKeySpecification::admitsDeclaredPrimitive()`. Only a `string` declaration, translatable or not, qualifies for a `string` key, and no primitive qualifies for a `list<string>` key. Every `inputs` key names a primitive property, and a present `default` matches that property's declared type. A translatable property passes the `isPrimitive()` gate and stays a valid `inputs` target. A `null` default on one is a violation, because `null` is no valid language-map entry and could never seed. A `!scoped` config value ([resolved-by.md](resolved-by.md)) must be the direct value of a Literal config key of the loader and map registered root sources to strings. A scoped map nested inside another config value is a violation at `bindings[<id>].resolves[<key>].config.<configKey>`. Every scoped value of one `resolves` entry's config must name the same root-source set, because applying the binding collapses the whole config for one root source. A differing set is a violation at `bindings[<id>].resolves[<key>].config`. The loader config is then decoded and its produced type resolved once per root source of that set. Violation paths are keyed on the binding id (`bindings[<id>].…`).

The validator injects `AbstractContentSystemElementTypeRegistry`, `DataLoaderConfigSerializerProvider`, `Diagnostics/RootContextMapper`, and `AbstractContentSystemDataLoaderMapResolver`. It decodes each `resolves` entry's loader config and resolves its produced type via the same `Diagnostics/RootContextMapper::resolveType()` the diagnostics kernel uses. A specification that would fail at diagnosis time is therefore rejected at load time instead. A client-defect exception becomes a validation violation. Any other exception propagates. Both constraints still run; `TypeConsistentBindingSpecification` re-checks `resolves`/`inputs` array-shapes internally, so a shape violation on an entry does not also produce a confusing semantic violation on the same entry.

The constraint lives on the collection because a per-load type overlay cannot be passed to the dependency-injected `ValidatorInterface`. The overlay can be a field on the validated object that the validator reads. Splitting shape (dto) from semantics (collection) still mirrors the element-type and style-option systems' "shape first, then live-registry consistency" load-time gate. A malformed declaration and a declaration that targets a real but wrong property therefore fail with distinctly diagnosable violations.
