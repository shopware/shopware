## Constraints

- Loaders MUST return `ContentDataLoaderResult` on every path — a loader throws nothing itself; the only exceptions that leave `load()` are a collaborator's classes outside the `ShopwareHttpException` boundary (two bullets down), passing through by design
- A loader that dereferences a `PropertyReference` value as an entity id MUST guard it with `Uuid::isValid()`, degrading to `notFound()` on failure. The stored map can hold anything, including an unsubstituted placeholder token such as `{{categoryId}}` that passes `LoaderInputResolver::dereference()`'s string type check untouched. The guard runs AFTER any normalization the loader applies to the value (e.g. a `u()->lower()` call): `Uuid::VALID_PATTERN` is lowercase-only, so guarding the raw value rejects a legitimate uppercase id
- A loader that calls any collaborator inside `load()` that can throw, whether a Store API route, a service such as `NavigationLoaderInterface`, a repository or an HTTP client, MUST wrap that call in `try`/`catch (ShopwareHttpException)` and degrade to `notFound()` on catch. The catch is deliberately broad rather than an enumerated union, for two reasons. The reachable set is open: `ProductListingRoute` and `ProductCrossSellingRoute` both throw `EntityNotFoundException` and `NoFilterException` out of `ProductStreamBuilder` (`src/Core/Content/ProductStream/Service/ProductStreamBuilder.php:66,85`), a collaborator that never appears as a `throw` in either route's own file. And a decorator can rewrap a class the clause names into one it does not: `AppScriptProductPriceCalculator` (registered as a `ProductPriceCalculator` decorator at `src/Core/Content/DependencyInjection/product.php:490`) calls `ScriptExecutor::execute()`, which catches every `\Throwable` an app script raises and rethrows it as `ScriptExecutionFailedException` (`src/Core/Framework/Script/Execution/ScriptExecutor.php:69`), so an enumeration cannot be made complete by tracing harder. `ShopwareHttpException` is the common ancestor of the Shopware exception classes these chains are known to reach, and `HttpException` extends it (`src/Core/Framework/HttpException.php:8`), so both roots are one inheritance line; it is a deliberate boundary, not a proof that every reachable class descends from it — `ExtensionDispatcher::publish()` rethrows whatever a listener throws (`src/Core/Framework/Extensions/ExtensionDispatcher.php:69`), and a listener is third-party code outside this catalogue. Classes outside the boundary propagate by design: `\JsonException` (`src/Core/Content/Product/SalesChannel/Listing/ProductListingLoader.php:220,252`), `\AssertionError` (`src/Core/Content/Product/SalesChannel/CrossSelling/ProductCrossSellingRoute.php:147`), and Doctrine DBAL exceptions (`src/Core/Framework/DataAbstractionLayer/Dbal/EntitySearcher.php:99`) all surface as errors: degrading those hides a defect in the loader instead of reporting a missing entity
- `load(LoaderInputs $inputs, DataRequirement $requirement, …)` — read every config/property input off `$inputs`; a loader never touches `$requirement->config` nor the `StoredElement`. `$requirement` stays in the signature as the extension-point affordance for a third-party loader keying off `source`
- `LoaderInputResolver` (called by `ElementDataResolver`) dereferences each `PropertyReference` key against the element's stored properties and type-checks it; an absent or wrongly typed stored value resolves to null. Presence and type guards belong there, NOT in the loader — but a domain emptiness fallback (e.g. an empty-string activeId) stays in the loader, because an empty string is a resolved value
- A key's *static* fallback lives in its `ConfigKeySpecification` default, never as a `??` in `load()` — an in-body fallback drifts from the introspection schema. A *context-derived* fallback, one whose value comes from the request, the sales channel or the context, is the exception: it is declared `hasDefault: false` and applied in `load()`, because the specification is dry-run at build time and cannot reach any of those. No drift arises, because `hasDefault: false` publishes exactly what the config contract holds — no default (`navigation`'s `depth`, falling back to the sales channel's `navigationCategoryDepth`)
- DI tag: `content_system.data_loader`, indexed by `getRequirementType()` static method
- Each loader needs a config class + serializer pair (config serializer tag: `content_system.config_serializer`) — `ContentSystemDataLoaderCompilerPass` fails the build on a source with no registered serializer (`dataLoaderSourceWithoutConfigSerializer`)
- The same pass rejects two class-level shapes before it reads any specification: a service carrying the `content_system.data_loader` tag that does not extend `AbstractContentDataLoader` (`taggedServiceHasWrongType`), and a tagged class that is abstract (`dataLoaderClassIsAbstract`)
- Domain loaders registered in their owning module's DI, not in `content-system.php`
- Use `$context->getContext()` for entity repository queries
- Built-in sources: `entity`, `entity_collection`, `product_listing`, `navigation`, `service_menu`, `cross_selling`, `product_review`, `product_search`, `product_suggest`, `breadcrumb`, `language`, `currency`, `payment_method`, `shipping_method`
- `@extends AbstractContentDataLoader<T>` PHPDoc annotation required — the base `producibleTypes()`/`resolveProducedType()` derive the produced type from it, and `ContentSystemDataLoaderCompilerPass` dry-runs `extendsDescriptor()` at build time; missing or unresolvable annotation fails the build
- Wildcard loaders (`entity`, `entity_collection`) override `producibleTypes()` and `resolveProducedType()` — enumerate the live `DefinitionInstanceRegistry`, declaring the sales-channel class where a sales-channel definition exists, otherwise the base class
- `configSpecification()` MUST be constructor-independent — `ContentSystemDataLoaderCompilerPass` dry-runs it at build time on an instance built without the constructor (declare it from literals/constants, never from injected state); it fails the build on duplicate keys, value types outside `ConfigKeySpecification::TYPES`, non-string `propertyReference`/`entityName` keys, incoherent defaults (including a default on a required key), a `referencedType` outside `ConfigKeySpecification::REFERENCED_TYPES` or a non-default one (any value but `string`) set on a non-`propertyReference` key, an invalid `mergesInto` (non-`propertyReference` key, a merger not referencing `list<string>`, self-merge, a target that is absent or not a `list<string>` literal, or a target a second merger key already claims — at most one merger per target), the reserved names `loader`/`config` (as source name or config key), and two loaders declaring the same source
