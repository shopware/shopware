## Key Relationship

One declaration, two consumers that cannot drift:
- `StyleOptionConstraintDeriver` turns a `StyleOptionValueType` into the Symfony constraints the write boundary enforces.
- `StyleOptionSpecification::toSchema()` turns the same declaration into the introspection schema.
- Both read the one `AbstractContentSystemStyleOptionRegistry`, so an option that is introspected is enforced and vice versa.

## Constraints

- Option names are flat global wire keys (`col-span`), **not** source-prefixed like element type names. The name is the kebab-case filename (leading letter required so a name can never coerce to an int array key on read). Uniqueness is enforced across all sources by `StyleOptionCollisionDetector` and the `app_content_system_style_option.name` `UNIQUE KEY`. The write and install paths fail hard on a cross-loader duplicate (`all()` throws `styleOptionDuplicate` with source labels `core` / `bundle:Name` / `plugin:Name` / `app:Name`); the introspection endpoints use the lenient `allResolved()`, which resolves a duplicate silently by source precedence (core, bundle, plugin, database/app; first-registered wins within a tier) — `all()` is the loud surface, so a collision is never logged from inside the cached read view. The content decode/serve path is registry-free, so a collision never reaches it.
- One option per YAML file. The file is a **flat** declaration with **no** `meta:` wrapper, unlike element-type YAML. `breakpointAware` defaults to `true`; an option opts out with `breakpointAware: false`. No shipped core option declares it — the flag is forward-looking, and every shipped core option stays breakpoint-aware. `kind` is the option's write-time canonicalisation discriminator: its only defined value is `StyleOptionSpecification::KIND_BOX_SPACING` (`box-spacing`), which makes `ElementStyleNormalizer` canonicalise the value into explicit four-part CSS; any other value fails the declaration's `Assert\Choice`, so a bad `kind` fails hard at `YamlStyleOptionLoader` and is skipped-with-a-warning at `DatabaseStyleOptionLoader`. No shipped core option declares it either.
- `Breakpoint` is a fixed framework primitive; it is not plugin- or app-extensible. `Breakpoint::values()` is the allowed key set; per-breakpoint values are individually optional.
- Value types are limited to the canonical primitives (`string`, `integer`, `number`, `boolean`). No FQCN, no nested object, no regex. A string or number with no declared `maxLength` is bounded by `DEFAULT_STRING_MAX_LENGTH = 255` (surfaced by `maxLength()` and the introspection schema) so a client cannot store an unbounded value (including a long numeric string) in the JSON column.
- `default` is an authoring hint (introspection/Admin pre-fill), so `style` stays omitted-when-empty — an option whose every value equals its default drops as unset. It reaches stored JSON only through `ElementStyleNormalizer` (run at the write boundary by `Layout/LayoutWriteBoundary`), which fills the *missing* breakpoints of a partially specified map from the default. Storage already held such values, expanded Admin-side before sending; only the seeding site moved to the server.
- Write is strict over what `ElementStyleNormalizer` leaves, since it runs first: a breakpoint-aware option sent as a bare scalar is broadcast into the full breakpoint map instead of rejected. An unknown breakpoint key never reaches the normalizer at all: `StoredElementCodec::decodeStyle()` runs first on every request and column payload and rejects it, so the normalizer's own key-dropping in `expandBreakpointMap()` applies only to an `ElementStyle` built in-process. The canonical form that survives is then judged per flag — unknown option, unknown breakpoint, constraint-violating value and a flat option sent as a breakpoint map are all rejected. Read (`StoredElementCodec::decodeStyle()`) is registry-free and structural: a malformed style shape (reachable only by a raw-SQL or migration write, or by a DAL write predating the codec) throws on read. Re-saving a layout whose `style` still references a removed option is rejected until it is cleared. `Diagnostics/ViolationCode::UnknownStyleOption` (intrinsic, error) names one where the write only rejects: the diagnose and draft mutation routes carry the code in their 200 diagnostics; the preview route 400s with the message, not the code; the DAL write — hence the persisted mutation routes, which commit before diagnosing — rejects at this serializer's `encode()` constraint, before the diagnostics gate runs.
- The constraint `Collection` is derived fresh per write and reused across every element within that write, not memoized across writes.
- Registry uses the Shopware decoration pattern (abstract → leaf → `cache.system` decorator, above). Consumers type-hint the abstract; `invalidate()` throws `DecorationPatternException` except on the cached decorator.
- `DatabaseStyleOptionLoader` returns empty in dev, where apps load from the filesystem via the compiler pass. It joins `app` and filters `WHERE app.active = 1`, so a deactivated app's options drop from that query with no extra write, and the lifecycle handler's invalidations (above) make the cached set reflect an activation change immediately rather than lagging until the next install/update; `StyleOptionCollisionDetector` also considers inactive app options to prevent cross-app name collisions.
- The `Plugin` base class is untouched: bundles and plugins share the fixed `Resources/content-system/style-options` convention directory (an optional `Plugin::getStyleOptionDirectory()` hook was deliberately deferred).
- `ElementStyle` immutability is load-bearing: the mutation subsystem aliases an untouched element's `ElementStyle` by reference into rebuilt and cloned nodes, which is only safe because it cannot be changed in place.
