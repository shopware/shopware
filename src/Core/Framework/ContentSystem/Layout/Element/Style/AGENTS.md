## Key Relationship

One declaration, two consumers that cannot drift:
- `StyleOptionConstraintDeriver` turns a `StyleOptionValueType` into the Symfony constraints the write boundary enforces.
- `StyleOptionSpecification::toSchema()` turns the same declaration into the introspection schema.
- Both read the one `AbstractContentSystemStyleOptionRegistry`, so an option that is introspected is enforced and vice versa.

## Constraints

- Option names are flat global wire keys (`col-span`), **not** source-prefixed like element type names. The name is the kebab-case filename (`YamlStyleOptionLoader::NAME_PATTERN` = `[a-z][a-z0-9]*(-[a-z0-9]+)*`, leading letter required so a name can never coerce to an int array key on read); there is no prefix. Uniqueness is enforced across all sources by `StyleOptionCollisionDetector` and the `app_content_system_style_option.name` `UNIQUE KEY`. The write and install paths fail hard on a cross-loader duplicate (the strict `all()`, throwing `styleOptionDuplicate` with source labels `core` / `bundle:Name` / `plugin:Name` / `app:Name`); the introspection endpoints use the lenient `allResolved()`, which resolves a duplicate silently by source precedence (core, then bundle, then plugin, then database/app; first-registered wins within a tier) — the strict `all()` is the loud surface, so a collision is never logged from inside the cached read view. The content decode/serve path is registry-free, so a collision never reaches it.
- One option per YAML file. The file is a **flat** declaration (`type`, optional `enum` / `range` / `maxLength` / `default`, optional `adminUI`) — there is **no** `meta:` wrapper, unlike element-type YAML.
- `Breakpoint` is a fixed framework primitive (`xs, sm, md, lg, xl, xxl`); it is not plugin- or app-extensible. `Breakpoint::values()` is the allowed key set; per-breakpoint values are individually optional.
- Value types are limited to the canonical primitives (`string`, `integer`, `number`, `boolean`). No FQCN, no nested object, no regex. A string or number with no declared `maxLength` is bounded by `DEFAULT_STRING_MAX_LENGTH = 255` (surfaced by `maxLength()` and the introspection schema) so a client cannot store an unbounded value (including a long numeric string) in the JSON column.
- `default` is advisory only — an introspection/Admin pre-fill hint. It is never seeded into stored element JSON and never applied at serve time, so `style` stays omitted-when-empty.
- Write is strict (unknown option / unknown breakpoint / constraint-violating value rejected); read (`deserialize`) is registry-free (unknown options ride through verbatim so an old layout still renders). Re-saving a layout whose `style` still references a removed option is rejected until it is cleared, so a normal edit round-trip no longer auto-clears it — the same posture the element type system has for an unknown `component`.
- The constraint `Collection` is derived fresh per write and reused across every element within that write, not memoized across writes.
- Registry uses the Shopware decoration pattern: `AbstractContentSystemStyleOptionRegistry` → `ContentSystemStyleOptionRegistry` (leaf) → `CachedContentSystemStyleOptionRegistry` (decorator, `cache.system`). Consumers type-hint the abstract; `invalidate()` throws `DecorationPatternException` except on the cached decorator.
- `DatabaseStyleOptionLoader` returns empty in dev (apps load from the filesystem via the compiler pass in dev). It joins `app` and filters `WHERE app.active = 1`, so a deactivated app's options drop from that query with no extra write, and `ContentSystemStyleOptionLifecycleHandler` invalidates the cached registry on activate, deactivate, uninstall, and local delete (as well as the persister on install/update), so the cached set reflects an activation change immediately rather than lagging until the next install/update; `StyleOptionCollisionDetector` also considers inactive app options to prevent cross-app name collisions.
- The `Plugin` base class is untouched: bundles and plugins share the fixed `Resources/content-system/style-options` convention directory (an optional `Plugin::getStyleOptionDirectory()` hook was deliberately deferred).
- `ElementStyle` immutability is load-bearing: the mutation subsystem aliases an untouched element's `ElementStyle` by reference into rebuilt and cloned nodes, which is only safe because it cannot be changed in place.
