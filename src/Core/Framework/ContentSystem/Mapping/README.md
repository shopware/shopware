# Content System Data Mapping

A field mapping binds one declared `mappable: true` element property to a typed source reference. The same registered providers supply the Administration candidate catalogue, the server-side write validator, and the runtime resolver. `StoredMappingInspector` owns property opt-in, source identity, type, and cardinality admission for map mutations, default seeding, and persisted writes. A client cannot create a mapping by inventing a source or member path.

## Source providers

Register an `AbstractMappingCandidateProvider` service with the `content_system.mapping_candidate_provider` tag. `supports($rootSource)` and `provide($rootSource)` describe the candidates available for a layout root source. Declare stable display names in `registeredCandidateKeys()` so the container build can reject collisions before requests use the catalogue. Providers whose candidates come from persisted/runtime data return an empty declaration. The registry checks runtime collisions across all providers. Return only values safe to expose to layout authors, with explicit effective value type, cardinality, label, and description. Do not derive member lists by reflecting over entities, loader results, requests, or contexts.

The Admin candidate catalogue requires `content_layout:read`. Layout readers can see labels and help text for active, Store-API-visible custom fields assigned to the root entity without needing general custom-field read access.

Providers may attach internal metadata cache tags to a candidate; the registry adds them when resolving that candidate. A provider can also return metadata dependencies from `cacheTagsForMapping($rootSource, $path)` for an attempted mapping, including a currently unavailable candidate. This hook receives an unadmitted display name and must not read source values or trust supplied configuration. It declares dependencies only; admission and exact source/configuration matching remain unchanged. Registry decorators inherit forwarding of this hook to the inner registry. Candidate cache tags are not part of the API schema.

The custom-field provider adds `content-system-custom-field-mapping-metadata` only when the render attempts a mapping under the supported root's `customFields` path, including unavailable fields. Whole-field and inline mappings use the same policy. Custom-field definition, set, and relation writes/deletes invalidate this tag, including relation deletions with only an ID in their payload. This deliberately invalidates cached pages using any custom-field mapping when mapping metadata changes. Layouts using only core mappings such as `product.name` receive no such tag and are not invalidated by this policy. Literal mapping-looking text outside supported positions does not create a dependency.

The provider's separate catalogue cache retains its `custom_field_mapping_candidates` tag, and available candidates retain their precise field/set tags. These caches and rendered-page dependencies are invalidated through their respective existing paths. Metadata invalidation follows the normal cache invalidator's immediate/delayed purge policy.

Root candidates use `MappingSourceReference::root($contextKey, $path)`. Non-root providers may use another stable source type and id, an optional validated config, and an optional member path. Candidate identity and runtime identity must match exactly: `MappingCandidate::$path` must equal the source's `displayName()`, and each `type:id.path` must be unique for a root source. Stable declared-key collisions fail the container build. A collision discovered while building the runtime catalogue excludes every candidate and provider owner for that display name, logs one warning per name and catalogue build, and leaves unrelated candidates available. A third provider cannot restore an ambiguous name. Source configurations with the same display name also conflict. Excluded mappings follow the existing unavailable-source write and rendering rules; provider order never selects a winner. Other provider errors still propagate through normal error handling.

The registry dispatches both whole-field mappings and inline tokens to the provider that offered the exact candidate for the layout's root source. Its single resolution entry point is `resolveSource(string $rootSource, MappingSourceReference $source, MappingSourceResolutionContext $context)`; decorators forward all three arguments. A render without a bound root source handles omission before calling the registry. For root sources, override `resolveRootSource()` when a candidate needs a storefront-facing accessor, translation fallback, or inheritance handling; the inherited reader preserves existing `Struct` path providers. For non-root sources, override `supportsSource()` and `resolveSource()`; a broad `supportsSource()` match alone does not claim another provider's candidate. `MappingSourceResolution` and `MappingSourceResolutionContext` are public provider API types. The runtime context contains the current element, its already-resolved loader values keyed by requirement key, root values, and the rendering cache context. Context-dependent data must go through data loaders; the provider context exposes neither the sales-channel context nor the HTTP request. Return only values declared safe by the provider's catalogue, including scalar and array values that do not pass through entity field protection. When deriving cacheable external data, add its cache tags to the supplied cache context. Return `MappingSourceResolution::resolved($value)` for a value, including a present `null`; return `noValue()` for missing source data. Provider errors propagate to normal error handling and abort rendering; missing source data remains an ordinary `noValue()` outcome. Whole-field rendering delivers only resolved results, and a present `null` remains present; inline rendering removes only an unavailable or non-text-convertible token while preserving surrounding authored text. Authored tokens in eligible text positions are expanded or removed. Valid tokens inside HTML markup, including attributes, stay literal and remain subject to normal template sanitization.

A loader-backed provider can offer a source whose stable config identifies a loader or requirement. It must validate that config at the mutation/write boundary, declare each exposed result member in its candidates, and resolve from a validated loader result. It must not trust a client-supplied loader name or path, invoke arbitrary loaders, or expose unlisted result members. Plugin providers are supported; app-based provider registration is not part of the current contract.

The product provider returns `MediaEntity` for `product.cover` and a position-sorted `MediaCollection` for `product.media` directly. Providers reshape intermediate data before returning it; the candidate's `valueType` describes that delivered value.

## Plugin sources and explicit overrides

For a new plugin-owned source, use the bundle name as the source `type` and a bundle-local source name as `id`:

```php
$source = new MappingSourceReference('AcmePlugin', 'recommendations', path: 'title');
```

This reference has the display name `AcmePlugin:recommendations.title` and the inline token `{{map:AcmePlugin:recommendations.title}}`. Another bundle can offer its own `recommendations.title` without a collision. Use the same reference in the candidate, `supportsSource()`, and `resolveSource()`, and declare the same display name in `registeredCandidateKeys()` when it is stable. The bundle name must fit the inline token identifier grammar to offer inline tokens. Keep names stable because layouts persist them. Names are supplied explicitly; existing references and root paths such as `product.name` are not automatically rewritten or prefixed. Labels remain independent of source identifiers.

To change an existing core mapping intentionally, decorate the public `AbstractContentSystemMappingCandidateRegistry` service. Do not register another provider with the same name. Concrete core provider classes remain internal. Forward `forRootSource()` to preserve the catalogue when only changing a value; if changing metadata or its effective type, keep admission and runtime resolution consistent for both whole-field and inline mappings. Preserve exact source identity checks, including configuration, before returning a replacement, and forward unrelated sources. Add any new data dependencies to the supplied rendering cache context.

For example, a decorator resolving `product.name` can first delegate to the inner registry, then transform a resolved string only when the root source is `product` and the reference exactly matches `MappingSourceReference::root('product', 'name')`. Missing data, explicit null, rejected references, and provider errors retain their normal handling. Its `getDecorated()` returns the inner registry. The inherited `reset()` forwards to that registry; a decorator with its own request-local cache must clear it and forward the reset too.

Register the decorator using Symfony service decoration, with its `.inner` service injected as `AbstractContentSystemMappingCandidateRegistry`:

```xml
<service id="AcmePlugin\Mapping\ProductNameRegistry"
         decorates="Shopware\Core\Framework\ContentSystem\Mapping\Registry\AbstractContentSystemMappingCandidateRegistry">
    <argument type="service" id="AcmePlugin\Mapping\ProductNameRegistry.inner"/>
</service>
```

Multiple intentional decorators follow Symfony's explicit decoration ordering. Duplicate provider registrations remain conflicts rather than an override mechanism.

## Built-in sources

Built-in candidates come from products, categories, landing pages, and their active, Store-API-visible custom fields. Storefront context values such as currency, language, and tax state are not offered.

## Stored mappings and rendering

`MappingRuntimeResolver` coordinates admission through `StoredMappingInspector`, provider dispatch through the registry, and runtime type checks for both mapping forms. It returns the provider's resolved or missing-data result, or an internal `MappingRejection` for an unavailable source or incompatible value. Whole-field delivery owns authored/loader fallback and omission; inline interpolation owns stringification, escaping, and token removal. Provider errors propagate through normal error handling.

A property's optional `defaultMapping` declaration names a typed source reference. Fresh insertion, preset attachment, and replacement scaffolds seed it only if the layout's root source offers a compatible candidate; other layouts leave it unset. Each mutation explicitly reports freshly scaffolded ids for seeding and consumer mirroring. The root source for these decisions comes from `StoredTree::$rootSource`; it is preserved across subsequent edits and normalization. Existing wiring wins, and duplication preserves the copied mapping or deliberate unmapping. Clearing the seeded mapping exposes the property's authored/resolved-by control so the author can choose a specific entity.

Direct DAL, Admin CRUD API, and Sync API creation does not seed `defaultMapping`; callers must supply the mapping consumer explicitly or use the layout mutation actions. This differs from primitive and nested stored property defaults, which are filled at the DAL write boundary. Saving an existing element never restores a deliberately removed mapping.

A mapping is stored as a root-scoped context consumer keyed by its destination property. The consumer carries a `source` object (`type`, `id`, optional `config`, optional `path`). Both root and other typed references resolve through their registered provider. For whole-field mappings, a `resolved(null)` value is delivered as null and overrides authored content. A missing source (`noValue()`) or an empty string or countable collection falls back to the field's authored or loader-resolved value. An invalid mapping remains omitted and does not fall back. Provider errors abort rendering through normal error handling. Inline token behavior is separate: unavailable tokens are removed while surrounding authored text remains.

Inline text mapping uses `{{map:...}}` tokens in opted-in top-level string properties. Root and typed non-root tokens use the same root-source candidate catalogue. Mapping-looking text outside those properties and valid tokens inside HTML markup, including attributes, stay literal. Normal template sanitization still applies. Preparation only parses opted-in properties, so the mapping parser's input limit does not apply to ordinary or undeclared properties. Ordinary placeholders such as `{{productId}}` still resolve there, but placeholder names beginning with `map:` (after leading whitespace) are reserved and cannot be supplied through query parameters to replace mapping syntax, including in literal loader configuration. Preview remains read-only; authors edit the stored text through the property controls.

Each opted-in property is limited to 256 KiB of authored text. Token scanning is linear in that bounded input size; the parser does not impose a separate token-count cap.

Inline expansion is additionally limited to 1 MiB per property and 4 MiB across one render, including surrounding literal text and escaped replacements. Exceeding either allowance aborts the render through normal error handling with HTTP 500 and `CONTENT_SYSTEM__INLINE_MAPPING_EXPANSION_TOO_LARGE`; the error message and parameters identify the byte limit and its property/render scope. No successful result with partial or blanked content is returned, and later properties are not resolved. Stored authoring content stays unchanged. Preview propagates the same error; it is not an `invalid_mapping` finding. A fresh render starts with a fresh allowance. These limits apply to inline expansion, not to whole-field mappings or ordinary properties without inline tokens. The authored-input cap remains a separate HTTP 400 validation error.

Internal rendering calls require their mapping inputs explicitly: lowering receives the parsed `InlineMappingMetadata` captured during preparation, and delivery/expansion callers provide root source, cache context, and loader values. An explicit null root source or cache context remains valid for callers without one. `InlineMappingExpander` creates one expansion budget for its complete forest and passes that same instance to every property's interpolator and token replacement, including descendants; neither lower-level method can omit or replace it with a fallback budget. A new expansion call starts a fresh budget. `ReplaceElement` likewise requires its `StoredMappingInspector`; only an intentionally unbound tree skips source-specific inspection. These contracts prevent missing wiring from silently bypassing mapping checks, metadata, or output limits.

## Rich-text rendering

Mapped inline values follow the text component's existing rich-text contract. Interpolation HTML-escapes a replacement before inserting it into authored content. For example, a source value of `<b>Special offer</b>` becomes `&lt;b&gt;Special offer&lt;/b&gt;` in the expanded property returned through the Store API.

The Storefront `Sw:Content:Text` component passes that property through `sw_sanitize` before rendering, including in preview. When enabled, the configured sanitizer decodes HTML entities before filtering the resulting markup. Allowed formatting from a mapped value can therefore become formatting in the rendered rich text; the example can display as bold text. Disallowed markup is filtered according to the sanitizer configuration, alongside authored HTML. Inline escaping does not guarantee that mapped markup remains literal text after this step. Other Store API clients determine their own rendering and sanitization behavior.

This behavior is intentional and is retained for data mapping. A requirement to keep mapped values strictly plain text inside authored rich text needs a separate rendering design; the shared sanitizer's entity-decoding behavior is unchanged. Providers remain responsible for exposing Storefront-safe values.
