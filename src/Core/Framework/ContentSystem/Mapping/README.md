# Content System Data Mapping

A field mapping binds one declared `mappable: true` element property to a typed source reference. The same registered providers supply the Administration candidate catalogue, the server-side write validator, and the runtime resolver. `StoredMappingInspector` owns property opt-in, source identity, type, and cardinality admission for map mutations, default seeding, and persisted writes. A client cannot create a mapping by inventing a source or member path.

## Source providers

Register an `AbstractMappingCandidateProvider` service with the `content_system.mapping_candidate_provider` tag. `supports($rootSource)` and `provide($rootSource)` describe the candidates available for a layout root source. Declare stable display names in `registeredCandidateKeys()` so the container build can reject collisions before requests use the catalogue. Providers whose candidates come from persisted/runtime data return an empty declaration and must handle collisions in that dynamic data themselves. Return only values safe to expose to layout authors, with explicit effective value type, cardinality, label, and description. Do not derive member lists by reflecting over entities, loader results, requests, or contexts.

The Admin candidate catalogue requires `content_layout:read`. Layout readers can see labels and help text for active, Store-API-visible custom fields assigned to the root entity without needing general custom-field read access.

Providers may attach internal metadata cache tags to a candidate. The registry adds those tags to the rendering cache context only when that candidate is consulted, so a core-only mapping does not inherit custom-field invalidation. The custom-field provider caches its candidate metadata under the `custom_field_mapping_candidates` cache tag; writes to custom fields, sets, and set relations invalidate that catalogue cache and the relevant rendered field/set tags. Candidate cache tags are not part of the API schema.

Root candidates use `MappingSourceReference::root($contextKey, $path)`. Non-root providers may use another stable source type and id, an optional validated config, and an optional member path. Candidate identity and runtime identity must match exactly: `MappingCandidate::$path` must equal the source's `displayName()`, and each `type:id.path` must be unique for a root source. Duplicate candidate keys throw during catalogue construction; providers must coordinate keys rather than relying on registration order.

The registry dispatches both whole-field mappings and inline tokens to the provider that offered the exact candidate for the layout's root source. Its single resolution entry point is `resolveSource(string $rootSource, MappingSourceReference $source, MappingSourceResolutionContext $context)`; decorators forward all three arguments. A render without a bound root source handles omission before calling the registry. For root sources, override `resolveRootSource()` when a candidate needs a storefront-facing accessor, translation fallback, or inheritance handling; the inherited reader preserves existing `Struct` path providers. For non-root sources, override `supportsSource()` and `resolveSource()`; a broad `supportsSource()` match alone does not claim another provider's candidate. `MappingSourceResolution` and `MappingSourceResolutionContext` are public provider API types. The runtime context contains the current element, its already-resolved loader values keyed by requirement key, root values, and the rendering cache context. Context-dependent data must go through data loaders; the provider context exposes neither the sales-channel context nor the HTTP request. Return only values declared safe by the provider's catalogue, including scalar and array values that do not pass through entity field protection. When deriving cacheable external data, add its cache tags to the supplied cache context. Return `MappingSourceResolution::resolved($value)` for a value, including a present `null`; return `noValue()` for missing source data. Provider errors propagate to normal error handling and abort rendering; missing source data remains an ordinary `noValue()` outcome. Whole-field rendering delivers only resolved results, and a present `null` remains present; inline rendering removes only an unavailable or non-text-convertible token while preserving surrounding authored text. Mapping token syntax from supported inline-mappable properties never reaches Storefront output.

A loader-backed provider can offer a source whose stable config identifies a loader or requirement. It must validate that config at the mutation/write boundary, declare each exposed result member in its candidates, and resolve from a validated loader result. It must not trust a client-supplied loader name or path, invoke arbitrary loaders, or expose unlisted result members. Plugin providers are supported; app-based provider registration is not part of the current contract.

The product provider returns `MediaEntity` for `product.cover` and a position-sorted `MediaCollection` for `product.media` directly. Providers reshape intermediate data before returning it; the candidate's `valueType` describes that delivered value.

## Built-in sources

Built-in candidates come from products, categories, landing pages, and their active, Store-API-visible custom fields. Storefront context values such as currency, language, and tax state are not offered.

## Stored mappings and rendering

`MappingRuntimeResolver` coordinates admission through `StoredMappingInspector`, provider dispatch through the registry, and runtime type checks for both mapping forms. It returns the provider's resolved or missing-data result, or an internal `MappingRejection` for an unavailable source or incompatible value. Whole-field delivery owns authored/loader fallback and omission; inline interpolation owns stringification, escaping, and token removal. Provider errors propagate through normal error handling.

A property's optional `defaultMapping` declaration names a typed source reference. Fresh insertion, preset attachment, and replacement scaffolds seed it only if the layout's root source offers a compatible candidate; other layouts leave it unset. Each mutation explicitly reports freshly scaffolded ids for seeding and consumer mirroring. Existing wiring wins, and duplication preserves the copied mapping or deliberate unmapping. Clearing the seeded mapping exposes the property's authored/resolved-by control so the author can choose a specific entity.

Direct DAL, Admin CRUD API, and Sync API creation does not seed `defaultMapping`; callers must supply the mapping consumer explicitly or use the layout mutation actions. This differs from primitive and nested stored property defaults, which are filled at the DAL write boundary. Saving an existing element never restores a deliberately removed mapping.

A mapping is stored as a root-scoped context consumer keyed by its destination property. The consumer carries a `source` object (`type`, `id`, optional `config`, optional `path`). Both root and other typed references resolve through their registered provider. For whole-field mappings, a `resolved(null)` value is delivered as null and overrides authored content. A missing source (`noValue()`) or an empty string or countable collection falls back to the field's authored or loader-resolved value. An invalid mapping remains omitted and does not fall back. Provider errors abort rendering through normal error handling. Inline token behavior is separate: unavailable tokens are removed while surrounding authored text remains.

Inline text mapping uses `{{map:...}}` tokens in opted-in top-level string properties. Root and typed non-root tokens use the same root-source candidate catalogue. Mapping-looking text outside those properties or in HTML attributes stays literal. Preparation only parses opted-in properties, so the mapping parser's input limit does not apply to ordinary or undeclared properties. Ordinary placeholders such as `{{productId}}` still resolve there, but placeholder names beginning with `map:` (after leading whitespace) are reserved and cannot be supplied through query parameters to replace mapping syntax, including in literal loader configuration. Preview remains read-only; authors edit the stored text through the property controls.

Each opted-in property is limited to 256 KiB of authored text. Token scanning is linear in that bounded input size; the parser does not impose a separate token-count cap.

Inline expansion is additionally limited to 1 MiB per property and 4 MiB across one render, including surrounding literal text and escaped replacements. Exceeding either allowance aborts the render through normal error handling with HTTP 500 and `CONTENT_SYSTEM__INLINE_MAPPING_EXPANSION_TOO_LARGE`; the error message and parameters identify the byte limit and its property/render scope. No successful result with partial or blanked content is returned, and later properties are not resolved. Stored authoring content stays unchanged. Preview propagates the same error; it is not an `invalid_mapping` finding. A fresh render starts with a fresh allowance. These limits apply to inline expansion, not to whole-field mappings or ordinary properties without inline tokens. The authored-input cap remains a separate HTTP 400 validation error.
