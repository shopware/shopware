# Content System Data Mapping

A field mapping binds one declared `mappable: true` element property to a typed source reference. Registered providers supply the Administration catalogue and the runtime resolver. `StoredMappingInspector` owns property opt-in, exact source identity, effective type, and cardinality admission. `Validation/StoredMappingValidator` rejects writes with specific error codes; `Diagnostics/LayoutDiagnostics` reports the same rules as property-specific `invalid_mapping` findings.

Admission needs the layout's source ID for a catalogue lookup; it cannot infer it from resolved entity data. Without that ID, whole-field mappings remain unjudged. Diagnostics additionally reports explicit inline tokens as requiring a bound source when the root context is also null. A supplied root context without a source ID runs no mapping checks. The write gate supplies its known source for static provider backing while leaving mapping errors to the dedicated validator. A client cannot invent a source or member path to bypass admission.

Design rules and rationale: [data-mapping principles](../docs/principles/data-mapping.md).

## Built-in sources

Built-in candidates come from products, categories, landing pages, and their active, Store-API-visible custom fields. Storefront context values such as currency, language, and tax state are not offered.

## Stored mappings and rendering

`MappingRuntimeResolver` coordinates admission through `StoredMappingInspector`, provider dispatch through the registry, and runtime type checks for both mapping forms. It returns the provider's resolved or missing-data result, or an internal `MappingRejection` for an unavailable source or incompatible value. Whole-field delivery owns authored/loader fallback and omission; inline interpolation owns stringification, escaping, and token removal.

A property's optional `defaultMapping` declaration names a typed source reference. Fresh insertion, preset attachment, wrapping containers, and replacement scaffolds seed it only if the layout's root source offers a compatible candidate; other layouts leave it unset. Each mutation explicitly reports freshly scaffolded ids for seeding and consumer mirroring. The root source for these decisions comes from `StoredTree::$rootSource`; it is preserved across subsequent edits and normalization. Existing wiring wins, and duplication and reattachment preserve the copied mapping or deliberate unmapping. Clearing the seeded mapping exposes the property's authored/resolved-by control so the author can choose a specific entity.

Direct DAL, Admin CRUD API, and Sync API creation does not seed `defaultMapping`; callers must supply the mapping consumer explicitly or use the layout mutation actions. This differs from primitive and nested stored property defaults, which are filled at the DAL write boundary. Saving an existing element never restores a deliberately removed mapping.

`Sw:Product:VariantSelection` keeps the default page-product mapping and the custom product picker. Its configurator options follow the product that actually wins mapping and fallback delivery. The product-domain `ProductVariantSelectionSubscriber` loads those options during rendered-tree finalization using the existing configurator service, before the optional value index is built. It replaces unrelated page options, clears them when no product is available, and shares results only for the same product within one render. The selected product and its parent contribute cache tags to the caller's render context. Skeletons load no options and gain no properties. Page-level configurator data remains available to other consumers; no general loader/mapping phase is reordered.

Default seeding and explicit mapping use the decoder's consumer destination rule: take `propertyAlias` when present, otherwise the consumer key, then compare the first dotted segment through `ConsumerBaseKeyResolver`. Defaults skip occupied destinations and existing consumer keys. Explicit mapping rejects conflicts with ordinary wiring using `propertyAliasCollision`; replacing the existing typed mapping at that same property remains allowed. A dotted consumer aliased to a different destination does not reserve its original base key.

A mapping is stored as a root-scoped context consumer keyed by its destination property. The consumer carries a `source` object (`type`, `id`, optional `config`, optional `path`). Both root and other typed references resolve through their registered provider. For whole-field mappings, a `resolved(null)` value is delivered as null and overrides authored content. A missing source (`noValue()`) or an empty string, empty array, or empty `Countable` value falls back to the field's authored or loader-resolved value. An invalid mapping remains omitted and does not fall back. Its destination is also excluded from the working values passed to child providers and from distribution-referenced output, including a keyed provider's `keyProperty`; no property provenance is recorded for an omitted destination. These checks reuse the existing delivery/fallback outcome without resolving the source again. Inline token behavior is separate: an empty string replaces the token with empty text; unavailable or non-text-convertible values remove only the token. Surrounding authored text remains, with no whole-field fallback.

Inline text mapping uses `{{map:...}}` tokens in opted-in top-level string properties. Root and typed non-root tokens use the same root-source candidate catalogue. Mapping-looking text outside those properties and valid tokens inside HTML markup, including attributes, stay literal. Normal template sanitization still applies. Preparation only parses opted-in properties, so the mapping parser's input limit does not apply to ordinary or undeclared properties. Ordinary placeholders such as `{{productId}}` still resolve there, but placeholder names beginning with `map:` (after leading whitespace) are reserved and cannot be supplied through query parameters to replace mapping syntax, including in literal loader configuration. Preview remains read-only; authors edit the stored text through the property controls.

Ordinary placeholders match keys exactly, including whitespace and colons; keys are not trimmed. After substitution, a lone unresolved ordinary placeholder becomes null (or removes a literal loader-config key), while an embedded unresolved placeholder stays literal. For example, `{{external:id}}` without a value and `{{ productId }}` with only an unpadded `productId` key become null. `InlineMappingTokenParser` owns the reserved-name check used by preparation; it does not parse literal properties or apply mapping input limits there. Mapping-looking text inserted by an ordinary placeholder remains literal and never becomes an authored mapping token.

The inline editor preserves an authored token-only paragraph such as `<p>{{map:product.name}}</p>`. When loading text without block structure, it records whether it added a paragraph for the editor. Only a known editor-added wrapper around a single unformatted token is removed when saving; unknown ownership preserves the paragraph. This temporary flag survives the field's own value echoes and background token parsing, and resets when an external document is loaded. It is never stored in the layout. Additional text, formatting, and multiple paragraphs are retained; deleting all content still clears the value. Loading a field alone does not rewrite its stored text.

Chip labels follow the reactive catalogue, including when labels arrive after editing has started; unavailable entries display their technical path. Label changes update only the visible chip text, preserving the editor, document, caret, and stored tokens. Removing a chip stops its label watcher.

Each opted-in property is limited to 256 KiB of authored text. Token scanning is linear in that bounded input size; the parser does not impose a separate token-count cap.

If the regular-expression engine fails during token scanning or path validation, the parser throws `CONTENT_SYSTEM__INLINE_MAPPING_PARSING_FAILED` (HTTP 500). It never returns an incomplete scan or classifies an engine failure as a malformed path. The error identifies the operation and engine reason without including authored content. Parsing, diagnosis, and validation requests propagate this fault instead of returning successful token lists or mapping findings; rendering follows the request boundaries below. Ordinary no-match results and malformed paths remain separate outcomes.

Inline expansion is additionally limited to 1 MiB per property and 4 MiB across one render, including surrounding literal text and escaped replacements. Exceeding either allowance aborts the content pipeline with `CONTENT_SYSTEM__INLINE_MAPPING_EXPANSION_TOO_LARGE` (an HTTP 500 exception); the error message and parameters identify the byte limit and its property/render scope. The pipeline returns no successful partial or blanked content result, and later properties are not resolved. Stored authoring content stays unchanged. This is not an `invalid_mapping` finding. Store API and preview propagate the exception as HTTP 500; the Storefront can catch it and continue without the content page, as described under [runtime error handling](#runtime-error-handling). A fresh render starts with a fresh allowance. These limits apply to inline expansion, not to whole-field mappings or ordinary properties without inline tokens. The authored-input cap remains a separate HTTP 400 validation error.

Rendering carries authored token spans through admission, dependency collection, and expansion. Every mapping uses the caller's non-null `RenderingCacheContext`, including uncached renders; providers add dependencies to that same instance. One expansion call shares one output budget across every property and descendant; a new call starts fresh. Required internal inputs cannot silently bypass these checks. An intentionally unbound `ReplaceElement` drops source-bearing consumers and reports their keys in `droppedWiring`; a bound replacement retains only mappings admitted for the new type. Inline tokens remain authored property text.

The concrete mapping registry requires an explicit logger for catalogue warnings. `RenderedElementFactory::create()` requires the delivery's calculated mapping-fallback keys explicitly, including an empty list when no field permits fallback; `RenderedTreeFactory` forwards those keys from each element's delivery.

For a mapping in fallback mode, a null loader result does not replace an authored value, either on the rendered element or in the working values supplied to child providers. A non-null loader result keeps its precedence. This exception does not apply to ordinary unmapped properties or a null value resolved by the mapping itself.

Static diagnostics recognize an admitted reference mapping as backing for context provided to children. They use the candidate's effective output type and validate its stored cardinality, without reading source values. The known layout source is supplied explicitly, including at the write gate, which leaves mapping error codes to `StoredMappingValidator`. This checks capability rather than whether a particular preview entity has a value.

If the editor's latest diagnosis request fails, it clears outdated findings and shows a localized error notification indicating that diagnostic results are unavailable. A successful empty report stays quiet. Older responses and failures cannot replace current findings or issue stale error notifications. This applies to static layout checks, including the follow-up after a refused save; runtime rendering and missing-value rules are unchanged.

Diagnostic resolutions report an applied mapping for both primitive and reference properties as the selected `root` source, with the typed source display name in `contextKey`. Here `root` describes mapping delivery scope, including non-root plugin providers. For references this selection wins over saved picker wiring and suggested sources; admission errors remain separate `invalid_mapping` findings. It does not inspect values or change the required-primitive rule.

## Runtime error handling

Provider faults, inline parser failures, and inline-output exhaustion abort the content pipeline rather than becoming missing values or successful partial content results. The outer request handling differs:

- Store API content requests propagate the failure through normal error handling. Inline-output exhaustion returns HTTP 500 with `CONTENT_SYSTEM__INLINE_MAPPING_EXPANSION_TOO_LARGE`, and parser failures return HTTP 500 with `CONTENT_SYSTEM__INLINE_MAPPING_PARSING_FAILED`; provider faults retain their normal error status and code.
- Preview URL creation and preview rendering propagate the same failures. A failed build during URL creation stores no preview token.
- Storefront content loading through `StorefrontController::loadContentPage()` catches `\Exception` from the content route and returns a null content page. Callers such as `NavigationController::content()` can then render a successful HTTP response without the content page. This catch includes parser failures, the output-limit exception, and provider exceptions, but does not catch PHP `Error` or `TypeError`.

The rendering rules are shared across these paths, while their outer HTTP handling differs. Missing source data continues to use the whole-field fallback and inline-token omission rules above.

## Rich-text rendering

Mapped inline values follow the text component's existing rich-text contract. Interpolation HTML-escapes a replacement before inserting it into authored content. For example, a source value of `<b>Special offer</b>` becomes `&lt;b&gt;Special offer&lt;/b&gt;` in the expanded property returned through the Store API.

The Storefront `Sw:Content:Text` component passes that property through `sw_sanitize` before rendering, including in preview. When enabled, the configured sanitizer decodes HTML entities before filtering the resulting markup. Allowed formatting from a mapped value can therefore become formatting in the rendered rich text; the example can display as bold text. Disallowed markup is filtered according to the sanitizer configuration, alongside authored HTML. Inline escaping does not guarantee that mapped markup remains literal text after this step. Other Store API clients determine their own rendering and sanitization behavior.

This behavior is intentional and is retained for data mapping. A requirement to keep mapped values strictly plain text inside authored rich text needs a separate rendering design; the shared sanitizer's entity-decoding behavior is unchanged. Providers remain responsible for exposing Storefront-safe values.
