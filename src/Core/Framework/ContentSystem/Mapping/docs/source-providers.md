# Source providers

Register an `AbstractMappingCandidateProvider` service with the `content_system.mapping_candidate_provider` tag. `supports($rootSource)` and `provide($rootSource)` describe the candidates available for a layout root source. Declare stable display names in `registeredCandidateKeys()` so the container build can reject collisions before requests use the catalogue. Providers whose candidates come from persisted/runtime data return an empty declaration. The registry checks runtime collisions across all providers. Return only values safe to expose to layout authors, with explicit effective value type, cardinality, label, and description. Do not derive member lists by reflecting over entities, loader results, requests, or contexts.

The catalogue is an exposure allowlist. Entity definitions do not establish which translated, inherited, or reshaped value a Storefront component needs. `StructEncoder` applies entity field protection to `Struct` values. Scalar leaves and plain arrays cannot rely on that protection. Providers must therefore explicitly vouch for each offered value, using entity accessors where needed.

Provider service classes may reference container parameters, such as `%plugin.provider.class%`. Compilation resolves these parameters before checking the provider type and stable declarations. Missing parameters, invalid provider classes, and declared-key collisions still fail the build through their normal error handling.

The Admin candidate catalogue requires `content_layout:read`. Layout readers can see labels and help text for active, Store-API-visible custom fields assigned to the root entity without needing general custom-field read access.

Catalogue requests reject malformed catalogue-map or per-root-list structures instead of treating them as empty results. A failed load or refresh clears selectable candidates and the successful-load flag, using the existing error banner and Retry action. Valid empty maps and lists remain successful results. Existing stored mappings, server-recognized chips, and authored text are preserved; text remains editable while new mapping insertion is unavailable. A successful retry restores available choices and labels.

Providers may attach internal metadata cache tags to a candidate; the registry adds them when resolving that candidate. A provider can also return metadata dependencies from `cacheTagsForMapping($rootSource, $path)` for an attempted mapping, including a currently unavailable candidate. This hook receives an unadmitted display name and must not read source values or trust supplied configuration. It declares dependencies only; admission and exact source/configuration matching remain unchanged. Registry decorators inherit forwarding of this hook to the inner registry. Candidate cache tags are not part of the API schema.

Custom-field mappings add a metadata dependency only to renders that attempt them; see [cache invalidation](../../Cache/README.md#invalidation).

Root candidates use `MappingSourceReference::root($contextKey, $path)`. Non-root providers may use another stable source type and id, an optional validated config, and an optional member path. `MappingCandidate::$path` must equal the source's `displayName()`. Each display name must be unique within a root source's catalogue, including across different source configurations.

Stable declared-key collisions fail the container build. A collision discovered during a runtime catalogue build excludes every candidate and provider owner for that display name. It logs one warning per name and catalogue build; unrelated candidates remain available. A third provider cannot restore an ambiguous name. Provider order never selects a winner. Excluded mappings follow the [unavailable-source admission and rendering rules](../README.md#stored-mappings-and-rendering).

Source identity compares `type`, `id`, and `path` exactly. Configuration uses `StoredValue` equality: map key order is irrelevant at every nesting level, while scalar types, list order, and the distinction between lists and maps remain significant. An omitted configuration and an empty configuration are equivalent. This comparison does not rewrite the stored configuration or use loader-config canonicalization, which also sorts lists.

## Dispatch and resolution

The registry dispatches whole-field mappings and inline tokens to the provider that offered the exact candidate for the layout's root source. Its final entry point is `resolveSource(string $rootSource, MappingSourceReference $source, MappingSourceResolutionContext $context)`. It checks exact source identity and configuration against the effective catalogue and collects metadata dependencies before calling the protected `resolveAdmittedSource()` hook. These checks apply to decorators and direct callers. Intentional overrides use the [plugin decoration contract](plugin-sources.md). Readers may rely on receiving an admitted source. A render without a bound source handles omission before registry dispatch.

For root sources, override `resolveRootSource()` when a candidate needs a Storefront-facing entity accessor, translation fallback, inheritance handling, or reshaping. The inherited reader supports `Struct` paths and a terminal lookup into array-backed `customFields`. For non-root sources, offer candidates through `provide()` and implement `resolveSource()`. Catalogue ownership determines dispatch without a second support declaration. Keep checks for missing or unsuitable loaded data in the reader.

`MappingSourceResolution` and `MappingSourceResolutionContext` are public provider API types. The runtime context contains the current element, its already-resolved loader values keyed by requirement key, root values, and the caller's rendering cache context. It exposes neither the sales-channel context nor the HTTP request. Context-dependent data must go through data loaders. Add external cache dependencies to the supplied cache context.

Return `MappingSourceResolution::resolved($value)` for a value, including a present `null`, and `noValue()` for missing source data. See [stored mappings and rendering](../README.md#stored-mappings-and-rendering) for whole-field fallback and inline substitution, and [runtime error handling](../README.md#runtime-error-handling) for provider faults.

A loader-backed provider controls write-time configuration admission through the exact source references it offers in `provide()`. The inspector compares the stored reference, including config, with that catalogue; there is no provider validation callback receiving stored config at write time. Offer only validated, stable configs and declared result members. Resolve from validated loader results without trusting client-supplied loader names or paths, invoking arbitrary loaders, or exposing unlisted members. Plugin providers are supported; app-based registration is outside the current contract.

The product provider returns `MediaEntity` for `product.cover` and a position-sorted `MediaCollection` for `product.media` directly. Providers reshape intermediate data before returning it; the candidate's `valueType` describes that delivered value.
