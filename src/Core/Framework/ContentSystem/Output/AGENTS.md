## Constraints

- Runs AFTER the render step — MUST NOT load data, query database, or modify element properties. The one exception is the partial prune (`ElementTreePruner`, `PartialRenderer::pruneToTarget()`), which runs before the render step on `StoredElement`s; the same no-loading rule holds there
- `PartialRenderer` straddles the render step: `pruneToTarget()` takes and returns `list<StoredElement>` before it, `extractTarget()` takes `list<RenderedElement>` and returns a `RenderedElement` after it. `SubTreeExtractor` is rendered-side too, and returns the found instance rather than a copy — `RenderedElement` is `final readonly`, so nothing can mutate what the rest of the tree still points at
- `ElementTreePruner::pruneToPathAndDescendants()` returns `null` for a root that does not hold the target — not an error, because the caller has other roots to try; `extractTarget()` raises `elementNotFound` once the forest is exhausted
- The pruner rebuilds kept ancestors through `StoredElement::withSlots()`, never through the constructor — the same idiom `Layout/StoredTree`'s surgery uses
- Multi-root partial: searches sequentially, returns first match only
- The decomposed format is about response format (structure/data separation), NOT partial rendering (`?elementId`)
- `RenderingMode` determines whether data and context are resolved inside the render step, which runs either way: FULL resolves both, SKELETON mints structure only
- The full format's wire shape is owned by `Encoder/ContentPageEncoder`, not by `StructEncoder`: it writes the page keys (`id`, `name`, `version`, `elements`), every element's keys (`id`, `component`, `properties`, `slots` and `style` omitted when empty, `apiAlias` last), and the `apiAlias` on every node at every depth. `Struct`-valued property leaves are delegated to `StructEncoder::encode()` — that delegation is the only thing applying the framework's protection gate (ApiAware, `isProtected`, customFields blocklist) to an entity payload, so a leaf that bypasses it publishes every field
- `Encoder/ContentResponseEncodingListener` (`kernel.response`, priority 10500 — strictly between `StoreApiSeoResolver` at 11000 and `StoreApiResponseListener` at 10000, both of which set their own priority in `getSubscribedEvents()`) selects by `SalesChannel/AbstractContentRouteResponse` and replaces three of the four format responses — full, decomposed and data, each through its own encoder, selected by an explicit `match` over the three concrete response classes rather than through a common encoder interface — with a `Struct/EncodedContentPage` carrier. The listener touches no parameter bag: `includes`/`excludes` never reach a content response at all, because `SalesChannel/ContentRoute::load()` rejects either parameter with a 400 (`ContentSystemException::fieldSelectionNotSupported`) at request admission, and `Api/ContentPreviewController::previewUrl()` makes the same refusal. The skeleton response is deliberately not among the three and keeps its struct; the listener's private `encode()` answering `null` for it is what leaves it to the framework encoder
- The decomposed and data formats read `Index/ResolvedValueIndex` through the shared `Encoder/ResolvedValueIndexEncoder`, which produces both wire maps (`data`: ref → value; `assignments`: element id → property key → ref) and runs every `Struct` leaf through `StructEncoder::encode()` — the same load-bearing protection gate the full format's encoder applies per leaf. A render result with no index is a broken wiring invariant rather than a state to serve around, so the encoder throws `resolvedValueIndexMissing`: an empty `data` map cannot be told apart from a page whose elements resolved nothing
- `Encoder/ContentDecomposedPageEncoder` reads both halves of the render result — the rendered forest for its skeletons, the index for the two maps — and derives neither from the other; `Encoder/ContentDataPageEncoder` builds no structure at all, not even to discard it
- The skeleton stays a plain `Struct` through `StructEncoder` — safe because it is homogeneous and carries no entity payloads — so `Struct/ContentSkeletonPage`'s property names ARE its response keys, and they carry no `layout` prefix. `Struct/ContentSkeletonElement` is minted only through `fromRendered()` and serves the skeleton format alone: the decomposed format's encoder projects the same node shape itself and repeats the `content_skeleton_element` alias as its own constant rather than building the struct to ask it
- The carrier is built at the HTTP boundary only. In-process consumers take a `Struct/ContentPage` ahead of it, by different paths, all through `ContentPage::fromRenderResult()`. Either way, nothing pays for encoding a body it will not send
