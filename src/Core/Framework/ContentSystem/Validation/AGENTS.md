## Source Code References

- `LayoutGate` — the layout gate; exposes the two gate predicates `wellFormedness(list<ContentElement> $tree, Context)` / `resolvability(list<ContentElement> $tree, list<ProvidedContext> $providedRootContext, Context)` — only `resolvability()` takes the bound source's `list<ProvidedContext>` root context the serving gate checks (each runs `LayoutDiagnostics::analyze()`, which returns a `Diagnostics/LayoutAnalysis`, and returns its `->report` half — a `Diagnostics/DiagnosticsReport`, whose `isWellFormed()` / `isResolvable()` are the actual predicates — they live on the report, not here) plus the `isBindingEnforced()` binding-enforcement seam; it never throws — it returns a `DiagnosticsReport`. `const SKIP_VALIDATION_STATE = 'content-system-skip-layout-validation'` bypasses both gates when set via `Context::addState`; `@internal` constructor
- `ContentLayoutWriteValidator` — `kernel.event_subscriber` on `PreWriteValidationEvent`; enforces the well-formedness gate on `content_layout` writes (via `LayoutGate`); skips any command whose entity is not `content_layout` or that does not carry the `layout` field; + synchronous re-check of already-bound layouts via tagged `Binding/LayoutBindingEnumerator`s
- `ContentLayoutAssignmentWriteValidator` — `kernel.event_subscriber` on `PreWriteValidationEvent`; the serving-gate validator for entity-assignment writes (it runs the binding check and rejects the write by adding a `WriteConstraintViolationException` to the event); skips any command whose entity is not an `Adapter/Entity/AbstractContentLayoutAssignableDefinition` or that does not carry the `content_layout_id` field, and skips the check for any derived binding that `LayoutGate::isBindingEnforced()` exempts; delegates load-and-check to `LayoutBindingChecker`
- `LayoutBindingChecker` — shared binding-check core that applies the resolvability gate to a layout referenced by id (it asks `LayoutGate` for resolvability; it does not define a gate); `bindingViolations(mixed $contentLayoutId, list<ProvidedContext> $providedRootContext, list<WriteCommand> $commands, Context): ConstraintViolationList`; resolves the tree from the in-flight write batch first (`treeFromCommands()`), falling back to the committed store (`loadTreeFromDb()`), and returns an empty list when neither yields a tree; an in-batch decode raising a non-client-defect `ContentSystemException` propagates out of `bindingViolations()` (client-defect decodes are swallowed so the committed-store fallback decides — see `LayoutTreeDecoder`); consumed by both `ContentLayoutAssignmentWriteValidator` and Storefront's `HeaderFooterAssignmentWriteValidator`, which each pass the `PreWriteValidationEvent` commands through
- `LayoutTreeDecoder` — single decode path (`content_layout` `layout` storage value → `list<ContentElement>`) shared by `ContentLayoutWriteValidator` and `LayoutBindingChecker`; throws `ContentSystemException` on a decode defect; each caller keeps its own catch policy — `ContentLayoutWriteValidator` maps a client-defect decode (`ContentSystemException::isClientDefect()`) to a `ViolationCode::InvalidConfig` violation and rethrows any non-client-defect, while `LayoutBindingChecker` swallows the client-defect and falls back to the committed store
- `ViolationConstraintMapper` — maps `list<Violation>` to `ConstraintViolationList`; property-path format `/{elementId}` or `/{elementId}/{key}`; places `Violation::$code->value` (a `Diagnostics/ViolationCode` string) in the Symfony constraint `code` field, which `WriteConstraintViolationException::getErrors()` surfaces as the `code` key of each write-error object

## Constraints

- `SKIP_VALIDATION_STATE` suppresses **both** write validators' checks (`ContentLayoutWriteValidator` and `ContentLayoutAssignmentWriteValidator` each early-return on the flag) when added to the write `Context` via `Context::addState`; intended for trusted bulk importers that have pre-validated their layouts — no in-repo path sets it (migrations bypass the DAL, writing raw SQL through `Connection`), and it is absent on all normal write paths including the Sync API
- Gate predicates (`isWellFormed()`, `isResolvable()`) live on `Diagnostics/DiagnosticsReport`; `LayoutGate` calls `LayoutDiagnostics::analyze()` (which returns a `LayoutAnalysis`) and returns its `->report` (`DiagnosticsReport`) — it does not own the predicates
- `LayoutGate::isBindingEnforced(SourceBinding): bool` defaults to `true`; the single overridable seam for a future draft/versioning system to exempt non-live bindings
- Atomic create-and-bind — a layout and its binding written in one batch (Admin or Sync) — runs the binding check via `LayoutBindingChecker` rather than being skipped
- Both `ContentLayoutWriteValidator` and `ContentLayoutAssignmentWriteValidator` are registered as `kernel.event_subscriber` in `content-system.xml`; Storefront registers its own `HeaderFooterAssignmentWriteValidator` using the same `LayoutBindingChecker`
- `ViolationConstraintMapper` accumulates all violations into one list; a batch write reports every violation rather than short-circuiting on the first
