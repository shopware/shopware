## Source Code References

- `LayoutGate` — the layout gate; exposes the two gate predicates `wellFormedness(list<StoredElement> $tree)` / `resolvability(list<StoredElement> $tree, list<ProvidedContext> $providedRootContext)` — only `resolvability()` takes the declared root source's `list<ProvidedContext>` root context the serving gate checks; both hand the stored tree straight to `LayoutDiagnostics`, which speaks that model itself, so the gate lowers nothing (each runs `LayoutDiagnostics::analyze()`, which returns a `Diagnostics/LayoutAnalysis`, and returns its `->report` half — a `Diagnostics/DiagnosticsReport`, whose `isWellFormed()` / `isResolvable()` are the actual predicates — they live on the report, not here); it never throws — it returns a `DiagnosticsReport`. `const SKIP_VALIDATION_STATE = 'content-system-skip-layout-validation'` bypasses both gates when set via `Context::addState`; `@internal` constructor
- `ContentLayoutWriteValidator` — `kernel.event_subscriber` on `PreWriteValidationEvent`; the single ordered `content_layout` write gate. It never decodes the column: `Layout/Field/StoredElementListFieldSerializer` decoded the payload, admitted it through `Layout/LayoutWriteBoundary` and left the result on the write `Context` as a `Layout/LayoutWriteContext` memo, so the gate judges the very tree about to be stored. Reading the memo consumes it, on the skip path as well, and a missing entry is a broken write path (`ContentSystemException::layoutWriteMemoMissing`), not an input to rule on. Per command it runs: (1) well-formedness on the memoized tree (only when the write touches the `layout` column); (2) membership of the written `root_source` in `Adapter/RootSourceRegistry::knownRootSources()` — an unknown value adds an `unknownRootSource` 400 violation and returns early, so `RootSourceRegistry::resolve()` is never handed an unregistered id; (3) resolvability of the tree against the declared root source's context (the create payload's `root_source`, else the committed row's, read via `LayoutRootSourceReader`), resolved through `RootSourceRegistry::resolve()`. On a layout-only edit step 3 re-checks membership of the committed `root_source` first (it could have been de-registered after the write, or be a stray non-member value) and surfaces a non-member as the same `unknownRootSource` 400 instead of letting `resolve()` fail-hard — so `resolve()` is never handed an unregistered id on either path. Skips a command whose entity is not `content_layout` or that touches neither the `layout` nor the `root_source` field
- `ContentLayoutAssignmentWriteValidator` — `kernel.event_subscriber` on `PreWriteValidationEvent`; a tree-blind type-match for entity-assignment writes. It reads the bound layout's immutable `root_source` via `LayoutRootSourceReader` (in-flight write batch first, then committed) and rejects the write — `ContentSystemException::rootSourceAssignmentMismatch()` (400), added as a `WriteConstraintViolationException` — when it does not equal the assignment definition's `getContentLayoutEntityType()`. It never decodes or resolves the tree: the tree was proven resolvable at the `content_layout` write and both the tree and `root_source` are immutable, so a pure type-match suffices. This served-implies-resolvable guarantee holds only while the resolvability inputs the layout was validated against stay stable after that write — the bound definition's `getPageDataRequirements()` (its `providedRootContext`) and the live element-type registry; neither passes through this gate, and drift in them is a serve-time or registry-change concern, not the assignment gate's to enforce. A `null` root source (layout not loadable) is left to the FK constraint. Skips a command whose entity is not an `Adapter/Entity/AbstractContentLayoutAssignableDefinition` or that does not carry the `content_layout_id` field
- `LayoutRootSourceReader` — the shared read of a layout's immutable `root_source` at write time, resolving it from the in-flight write batch first (so an atomic create-and-bind sees the layout's INSERT payload — only an INSERT sets `root_source`, since the field is immutable), falling back to the committed row. The single read path used by `ContentLayoutWriteValidator` (edit path), `ContentLayoutAssignmentWriteValidator`, and Storefront's `HeaderFooterAssignmentWriteValidator`, so the "in-flight first, then committed" rule lives in one place across modules
- `ViolationConstraintMapper` — maps `list<Violation>` to `ConstraintViolationList`; property-path format `/{elementId}` or `/{elementId}/{key}`; places `Violation::$code->value` (a `Diagnostics/ViolationCode` string) in the Symfony constraint `code` field, which `WriteConstraintViolationException::getErrors()` surfaces as the `code` key of each write-error object

## Constraints

- `SKIP_VALIDATION_STATE` suppresses **both** write validators' checks (`ContentLayoutWriteValidator` and `ContentLayoutAssignmentWriteValidator` each early-return on the flag) when added to the write `Context` via `Context::addState`; intended for trusted bulk importers that have pre-validated their layouts — no in-repo path sets it (migrations bypass the DAL, writing raw SQL through `Connection`), and it is absent on all normal write paths including the Sync API
- `SKIP_VALIDATION_STATE` is not the only way the gate goes unrun: a write carrying any constraint-level defect never reaches it. Field-serializer constraints are enforced inside `encode()` → `validateIfNeeded()`, and `DataAbstractionLayer/Write/EntityWriter::upsert()` calls `tryToThrow()` before `gateway->execute()` raises `PreWriteValidationEvent` in `EntityWriteGateway::executeCommands()`, so a payload that trips e.g. the `Layout/Codec/StoredTreeConstraints` descriptor's unknown-option constraint fails with that constraint error alone and no diagnostics violations beside it. Pre-existing DAL ordering, not something this module can reorder
- Gate predicates (`isWellFormed()`, `isResolvable()`) live on `Diagnostics/DiagnosticsReport`; `LayoutGate` calls `LayoutDiagnostics::analyze()` (which returns a `LayoutAnalysis`) and returns its `->report` (`DiagnosticsReport`) — it does not own the predicates
- `ContentLayoutWriteValidator` orders membership before resolvability with an early return because `PreWriteValidationEvent` listeners do not short-circuit: an unknown `root_source` must surface as the intended `unknownRootSource` 400, never reach `RootSourceRegistry::resolve()` (which fail-hards 500 on an unknown id). `root_source` is immutable, so a write either creates the row (membership + resolvability against the new source) or edits the layout (membership + resolvability against the committed source); there is no source-flip case. The edit path re-checks membership because a committed source can stop being a member after the write (de-registered by a plugin/app uninstall, or a stray non-member value), and that must surface as the `unknownRootSource` 400, not a 500
- Atomic create-and-bind — a layout and its assignment written in one batch (Admin or Sync) — is matched, not skipped: `LayoutRootSourceReader` reads the layout's in-flight INSERT `root_source` so the assignment type-match runs
- Both `ContentLayoutWriteValidator` and `ContentLayoutAssignmentWriteValidator` are registered as `kernel.event_subscriber` in `content-system.php`; Storefront registers its own `HeaderFooterAssignmentWriteValidator` using the same `LayoutRootSourceReader`
- `ViolationConstraintMapper` accumulates all violations into one list; a batch write reports every violation rather than short-circuiting on the first
