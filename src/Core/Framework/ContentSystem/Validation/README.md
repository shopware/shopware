# Validation

DAL `PreWriteValidationEvent` gate for content layouts. Two subscribers enforce that a served layout is resolvable, and a third guards the product and category default layouts held in system config. `ContentLayoutWriteValidator` is the single ordered `content_layout` write gate (well-formedness → root-source membership → resolvability against the declared root source → exact mapping admission). `ContentLayoutAssignmentWriteValidator` is a tree-blind type-match that rejects an assignment whose layout's immutable `root_source` does not match the assignment's entity type.

The assignment type-match guarantees that a served layout is resolvable only while the resolvability inputs a layout was validated against stay stable after its write: the bound definition's `getPageDataRequirements()` (its `providedRootContext`) and the live element-type registry, as [context-wiring.md](../docs/principles/context-wiring.md#the-write-gate-computes-each-delivery-rule-it-checks-exactly-as-serving-computes-it) states.

## Writes that skip the gate

`LayoutGate::SKIP_VALIDATION_STATE`, added to the write `Context` via `Context::addState`, makes `ContentLayoutWriteValidator` and `ContentLayoutAssignmentWriteValidator` return early. It is meant for a trusted bulk import that has pre-validated its layouts. No in-repo path sets it: migrations write raw SQL through `Connection`, and the Sync API does not set it.

A write with a constraint-level defect never reaches the gate. `EntityWriter::upsert()` throws field-serializer constraint errors before `PreWriteValidationEvent` is raised. A payload that trips a `Layout/Codec/StoredTreeConstraints` constraint (for example an unknown option) therefore fails with that constraint error alone and no diagnostics violations. This DAL ordering is outside the module.

## Key Classes

- `LayoutGate` — the layout gate: a persistence gate and a serving gate, each returning a `Diagnostics/DiagnosticsReport` whose `isWellFormed()` / `isResolvable()` are the actual predicates; never throws; holds the `SKIP_VALIDATION_STATE` constant
- `ContentLayoutWriteValidator`: the single ordered `content_layout` write gate, run once per layout record on its state after the batch as the DAL `WriteOutcome` reports it.
  The gated tree is the one the layout field serializer left on the write `Context` (`Layout/LayoutWriteContext`) under the write's `WriteContext` for the layout value the batch writes for the record, so an intermediate tree the batch overwrites is not gated.
  The gate checks well-formedness on that tree, then membership of the resulting `root_source` in `Adapter/RootSourceRegistry` (early return on a miss), then resolvability against that root source's context, then exact mapping admission of the tree's stored mappings against that root source through `StoredMappingValidator`.
  On a layout-only edit the resulting `root_source` is the stored one, so a source removed from the registry after the write is an `unknownRootSource` 400 on the next edit instead of an unrepairable 500
- `StoredMappingValidator`: validates whole-field and inline mappings through `Mapping/StoredMappingInspector` and returns specific `CONTENT_SYSTEM__*` errors on property paths. The resolvability gate receives the known source for mapped provider backing with generic mapping reporting disabled. See [mapping checks](../Diagnostics/README.md#mapping-checks).
- `ContentLayoutAssignmentWriteValidator`: a tree-blind type-match on entity-assignment writes. For each assignment record that is new or writes `content_layout_id`, it checks the layout the record is assigned after the batch, reading that layout's immutable `root_source` (via `LayoutRootSourceReader`) and rejects the write (`ContentSystemException::rootSourceAssignmentMismatch`, 400) when it does not equal the assignment definition's entity type
- `ContentLayoutDefaultValidator`: on a system config change and on a `content_layout` delete. A product or category default layout value must name an existing layout (`contentLayoutNotFound`, 404) whose `root_source` matches the key's entity type (`rootSourceAssignmentMismatch`, 400). Deleting a layout that is a default throws `defaultContentLayoutDeletion` (400). `SKIP_VALIDATION_STATE` does not bypass it
- `LayoutRootSourceReader`: shared read of the immutable `root_source` of many layouts at once at write time: a layout the batch writes from its state after the batch (DAL `WriteOutcome`), every other layout from its stored row, all of those in one query. The Core assignment and default validators use it. It leaves out a layout that is not loadable or that does not exist after the batch: `ContentLayoutAssignmentWriteValidator` leaves that id to the FK constraint, and `ContentLayoutDefaultValidator` rejects it with `contentLayoutNotFound` (404)
- `ViolationConstraintMapper`: converts `Diagnostics/Violation`s to Symfony `ConstraintViolation`s with property paths in `/{elementId}` or `/{elementId}/{key}` format (the key segment is omitted for element-level violations). The `ViolationCode` string value is the constraint `code` field and the write-error API payload's `code` key. It accumulates all violations into one list, so a batch write reports every one
