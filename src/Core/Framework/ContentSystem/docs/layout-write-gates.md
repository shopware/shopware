# Layout Write Gates

- **Resolvability gate** (DAL `PreWriteValidationEvent`): two subscribers ensure a layout resolves: `Validation/ContentLayoutWriteValidator`, the single ordered `content_layout` write gate, and `Validation/ContentLayoutAssignmentWriteValidator`, a tree-blind type-match on the bound layout's immutable `root_source`. `Validation/LayoutGate` holds the two predicates and the `SKIP_VALIDATION_STATE` bypass. Gate ordering, the edit-path membership re-check, every error code, and the caveat on that guarantee are owned by [Validation/AGENTS.md](../Validation/AGENTS.md) / [Validation/README.md](../Validation/README.md)
- **Write-boundary default seeding**: `Layout/LayoutWriteBoundary` admits [every layout write](principles/write-admission.md#every-layout-write-passes-through-the-write-boundary-a-single-choke-point), reached from the DAL write chokepoint for the `layout` field (`Layout/Field/StoredElementListFieldSerializer::normalize`), which memoizes the admitted tree on the write `Context`. See [Diagnostics report, gates check, and neither rewrites](principles/drafts-and-gates.md#diagnostics-report-gates-check-and-neither-rewrites). What the three passes do, `Layout/LayoutDefaultSeeder` and its shared per-type rule included, is owned by [Layout/README.md](../Layout/README.md) and [Binding/docs/write-boundary.md](../Binding/docs/write-boundary.md)
- **Delete protection**: a `content_layout` bound to any source cannot be deleted. `RestrictDelete` on the `content_layout` OneToMany assignment associations (`Layout/Entity/ContentLayoutDefinition` for product/category/landing-page, `Storefront/.../Extension/ContentLayoutExtension` for header/footer) makes the DAL throw `RestrictDeleteViolationException` before any SQL. `ON DELETE RESTRICT` on each `content_layout_id` foreign key backs it. This is DAL-core machinery, not a content-system gate, so `SKIP_VALIDATION_STATE` does not bypass it. Sibling foreign keys (`sales_channel_id`, `domain_id`) stay `ON DELETE CASCADE`: deleting the referenced channel/domain still removes the assignment while the layout survives
- **Default layout**: `Validation/ContentLayoutDefaultValidator` checks the product and category default layout held in system config and refuses to delete a layout that is a default. Its checks are owned by [Validation/README.md](../Validation/README.md#key-classes)
- Primitive property satisfaction is strict: `Diagnostics/LayoutDiagnostics` reports a required primitive as `UnresolvedRequired` iff the element has no non-null stored value for it; the type default is not consulted. A default reaches storage only through creation-time seeding (`Mutation` scaffold/replace), the input defaults that `Binding/BindingApplicator` writes, and the write-boundary `Layout/LayoutDefaultSeeder`. A style option default reaches storage only as a missing breakpoint that `Layout/Element/Style/ElementStyleNormalizer` fills into a present style map. The unseeded draft path (`Api/ContentDiagnoseController`, preview) deliberately over-reports a required primitive. See [Diagnostics/AGENTS.md](../Diagnostics/AGENTS.md)

- **Mapping admission**: after source-aware resolvability, `Validation/StoredMappingValidator` uses the shared inspector for exact catalogue identity/configuration, effective type, cardinality, and property opt-in. It reports specific mapping errors independently of generic binding diagnostics. [Mapping principles](principles/data-mapping.md) explain static provider backing and required-primitive behavior.
