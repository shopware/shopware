# Pipeline Steps

The diagram is in [data-flow.md](data-flow.md).

- `ContentPipeline::load()`: receives the loaded stored forest → `ContentTreePreparationEvent` → stored preparation (`Layout/Scaffolding/StoredTreePreparer::prepare()`: placeholder resolution in FULL mode only, then the virtual-root wrap via `Layout/Scaffolding/VirtualRootWrapper`, then the partial prune via `Output/PartialRenderer`, all still stored) → duplicate-element-id rejection on the result's pre-prune forest → `Rendering/WiringPlanner::plan()` (wiring validation on that same pre-prune forest, then redistribute derivation on the result's pruned tree) → the render step (`Rendering/ElementLowering::lower()`: forest-wide data resolution, the once-per-render root-ambient resolution of the specification's page-level data requirements against the virtual-root wrapper the pipeline hands it from the pre-prune forest, context-delivery resolution, rendered-tree minting; FULL does all four, SKELETON mints structure only) → the finishing steps, on the rendered forest (`VirtualRootWrapper::unwrap()`, then `PartialRenderer::extractTarget()`, both driven by the `RenderScaffolding`) → `RenderedTreeFinalizationEvent` over the rendered forest, in both modes → duplicate-element-id rejection again, over the forest the event handed back, because a finalization listener may replace it and the pre-lowering check ran too early to see that. Both checks throw `DUPLICATE_ELEMENT_ID` (500, not a client defect) and run in either mode. The pipeline takes both format answers from the route: the `RenderingMode` and whether the format collects a value index
- Wiring validation and redistribute derivation are deliberately split inside `Rendering/WiringPlanner::plan()`: validation judges the pre-prune forest (a defect in a subtree a partial render discards still fails the render), derivation runs on the surviving tree and throws nothing
- Specification resolution and layout-entity loading happen in `ContentRoute`, NOT in `ContentPipeline`
